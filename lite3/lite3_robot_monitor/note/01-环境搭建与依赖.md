## 1.1 `python3 -m venv` 报 `ensurepip is not available`

**现象**
执行 `python3 -m venv .venv` 失败，提示 ensurepip 不可用，venv 目录建了一半。

**原因分析**
Ubuntu/Debian 把 `ensurepip` 拆到了独立包 `python3.8-venv` 里。
`python3 -m venv` 这个**入口存在**，但底层依赖的 ensurepip 没装 —— 所以
"能不能 import venv" 不能作为判据，必须检测 **ensurepip**。
`install.sh` 的注释里明确写了这一点：

```bash
# Ubuntu 20.04 常见坑：`python3 -m venv` 存在，但 ensurepip 位于独立的
# `python3.8-venv` 包里，未安装时报 “ensurepip is not available”。
# 因此这里检测的必须是 ensurepip，而不是 venv。
```

**解决方案**

```bash
sudo apt-get -o Acquire::ForceIPv4=true install -y python3.8-venv python3-pip
python3 -c "import ensurepip; print('ensurepip OK')"   # 验证
```

脚本里的等价写法（`install.sh` 已内置，仅作对照）：

```bash
if ! "$PY_BIN" -c "import ensurepip" >/dev/null 2>&1; then
    ... 安装 python${PY_VER}-venv ...
fi
```

**规避建议**
写自建环境脚本时，**检测 ensurepip 而不是 venv**；不要假设"有 venv 模块就能建环境"。

## 1.2 apt 卡住几十秒后失败，看起来"没有外网"

**现象**
`apt-get update` 长时间无输出，最后超时失败；但 `ping` 网关是通的。

**原因分析**
apt 默认 **IPv6 优先**。内网机器常无可用 IPv6 路由，于是 apt 先走 IPv6 静默等待超时，
再退回 IPv4 —— 表现为"看起来完全不通网"。`install.sh` 注释：

```bash
# 常见坑：apt 默认 IPv6 优先，IPv6 不通时会静默超时数十秒再失败。
# 强制 IPv4 可让 apt 在很多"看似不通外网的"内网机器上恢复可用。
APT_OPTS=(-o Acquire::ForceIPv4=true)
```

**解决方案**
所有 apt 调用加 `-o Acquire::ForceIPv4=true`：

```bash
sudo apt-get -o Acquire::ForceIPv4=true update -qq
sudo apt-get -o Acquire::ForceIPv4=true install -y python3.8-venv python3-pip
```

**规避建议**
把这条写进部署脚本的默认参数，别等到超时才想起来。pip 同理，走内网源更快：

```bash
PIP_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple sudo -E bash deploy/install.sh /home/test/monitor
```

## 1.3 虚拟环境创建失败后留下残缺目录

**现象**
上一次安装失败后，再次运行 `install.sh` 报一些奇怪的路径错误。

**原因分析**
失败时 `.venv` 目录可能已建好但 **`bin/python` 不可执行**（半成品）。
后续脚本若直接复用它，会在一个不可用的解释器上装依赖。

**解决方案**
`install.sh` 已内置清理逻辑（无需手动执行，这里说明其行为）：

```bash
if [[ -d "$VENV_DIR" ]] && [[ ! -x "$VENV_DIR/bin/python" ]]; then
    warn "发现残缺的 .venv，删除后重建"
    rm -rf "$VENV_DIR"
fi
```

手工排查时直接删掉重建最省事：

```bash
rm -rf /home/test/monitor/.venv
```

**规避建议**
判断"虚拟环境是否可用"要用 **`bin/python` 是否可执行**，而不是"目录是否存在"。

## 1.4 装不上 venv 时的三层降级

**现象**
内网机器既装不了 `python3.x-venv`，也连不上 PyPI 装 virtualenv。

**原因分析**
不同机器的可用工具链不一致，单点依赖任何一个都会卡死安装流程。

**解决方案**
`install.sh` 采用三层降级，最终兜底到系统 Python：

| 层级 | 方式 | 说明 |
| --- | --- | --- |
| 1 | `python3 -m venv` | 首选，需 ensurepip |
| 2 | `python3 -m virtualenv` | PyPI 在线安装；**用 `-m` 模块方式调用**，避免 `~/.local/bin` 不在 sudo PATH 中 |
| 3 | 系统 Python | 依赖写入系统 site-packages，卸载需 `pip3 uninstall` |

> 兜底到系统 Python 时脚本会打印告警，这是**可接受但不推荐**的状态。

**规避建议**
保留降级链而不是硬失败。注意第 2 层的调用姿势：

```bash
python3 -m virtualenv .venv     # ✅ 推荐
virtualenv .venv                # ❌ 可能因 PATH 找不到
```

## 1.5 aarch64 上装 `uvicorn[standard]` 编译失败

**现象**
在 Jetson（aarch64）上 `pip install uvicorn[standard]` 卡在编译 httptools / uvloop，或直接失败。

**原因分析**
`uvicorn[standard]` 依赖的 `httptools`、`uvloop` 在 aarch64 上**常常没有预编译 wheel**，
只能现场编译，既慢又容易因缺少编译工具链失败。`backend/requirements.txt` 注释：

```
# 说明：aarch64 上 `uvicorn[standard]` 依赖的 httptools / uvloop 常常没有预编译 wheel，
#       现场编译既慢又容易失败，所以这里只依赖纯 Python 版 uvicorn。
```

**解决方案**
项目依赖刻意只写纯 Python 版：

```
fastapi>=0.110
uvicorn>=0.27
websockets>=12.0
pydantic>=2.6
```

**规避建议**
保持 `requirements.txt` 现状，**不要擅自加 `[standard]`**。
若确认 103 上能顺利编译且确实需要性能，再手动加装：

```bash
/home/test/monitor/.venv/bin/pip install "uvicorn[standard]"
```

## 1.6 新增代码用了 3.9/3.10 语法，103 上启动失败

**现象**
本地（Python 3.10+）开发一切正常，同步到 103 后服务起不来，报 `TypeError` 或语法错误。

**原因分析**
103 是 Python 3.8。以下写法在 3.8 上不可用（`README.md` 注意事项第 4 条）：

| 不可用 | 说明 | 替代写法 |
| --- | --- | --- |
| `list[str]` / `dict[str, int]` | 3.9+ 内置泛型 | `from typing import List, Dict` |
| `str \| None` | 3.10+ 联合类型 | `Optional[str]` |
| `match` 语句 | 3.10+ | if/elif |

**解决方案**
按 3.8 兼容改写；模块顶部加 `from __future__ import annotations` 可缓解**注解**层面的问题
（本项目 `main.py` 已这么做），但**运行时求值的表达式**仍会报错。

**规避建议**
- 开发机上用 Python 3.8 建 venv 做本地验证；或至少在提交前跑一次语法检查。
- 新增文件统一遵循现有风格：`from __future__ import annotations` + `typing` 里的 `Optional/List/Dict`。

## 1.7 依赖版本下限与 pydantic v2

**现象**
`pip install` 装到旧版 pydantic（v1）后，启动报大量模型校验错误。

**原因分析**
项目代码按 **pydantic v2** 编写（`BaseModel`、`Field` 的用法与 v1 有差异），
`requirements.txt` 里 `pydantic>=2.6` 是硬下限。

**解决方案**

```bash
/home/test/monitor/.venv/bin/python -c "import pydantic, fastapi, uvicorn; print(pydantic.VERSION, fastapi.__version__)"
```

确认 pydantic 主版本 ≥ 2。若不是：

```bash
/home/test/monitor/.venv/bin/pip install -U "pydantic>=2.6"
```

**规避建议**
不要把 `requirements.txt` 里的下限改小；新增依赖时同样按 **Python 3.8 有 wheel** 来选版本。

## 1.8 本机（Windows）与 103 的环境差异

**现象**
在 Windows 开发机上运行后端，抓包模式不可用或报平台错误。

**原因分析**
`AF_PACKET` 旁路抓包是 **Linux 专有**能力，Windows 上没有。
`LITE3_UDP_MODE=auto` 在 Windows 上会自动退回 `bind`。

**解决方案**
Windows 上用于开发/看接口即可，数据联调用内置模拟器（见 `03` 与 `README` 第八章）：

```bash
cd /home/test/monitor
/home/test/monitor/.venv/bin/python tools/mock_sender.py     # 默认 127.0.0.1:43897，10Hz
```

**规避建议**
把"抓包"相关的验证全部放到 103 上做；Windows 只负责编码与前端构建。

## 1.9 写远程脚本时的换行符问题

**现象**
在 Windows 上编辑好 `.sh` 脚本传到 103，执行时报 `/usr/bin/env: 'bash\r'` 之类的错误。

**原因分析**
Windows 文本模式会把 `\n` 写成 `\r\n`，Linux 内核把 `bash\r` 当成解释器名。

**解决方案**

```bash
sed -i 's/\r$//' your_script.sh    # 去掉 CR
bash -n your_script.sh             # 语法自检
```

**规避建议**
- 上传前统一转换；或用编辑器的 "LF" 换行模式保存。
- 该项目 `deploy/*.sh` 均已按 LF 提交，**不要**用 Windows 记事本改它们。
