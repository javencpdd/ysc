## 3.1 直接在 103 上 bind 43897 → Nav2 丢失里程计（头号大坑）

**现象**
Monitor 能收到数据，但 103 上的 ROS/Nav2 开始报错，`/imu/data`、`/leg_odom2` 断流。

**原因分析**
103 的 UDP **43897 已被 `transfer_ros2` 独占**。
UDP 单播端口被两个进程同时 bind 时，Linux **不会**给两份拷贝 —— **后 bind 的会把报文抢走**：

```
Monitor 抢走 43897 → transfer_ros2 收不到状态
                   → leg_odom2 / /imu/data 断流
                   → Nav2 失去本体里程计
```

**解决方案**
103 上一律用 **sniff**：`AF_PACKET` 从链路层读取流经网卡的报文，**不 bind 任何端口**，
与 `transfer_ros2` 完全共存。

```ini
# /etc/systemd/system/lite3-monitor.service
Environment=LITE3_UDP_MODE=sniff
```

**规避建议**
- `LITE3_UDP_MODE=auto`（默认）会优先 sniff、失败才退回 bind —— 103 上建议**显式写 sniff**，
  避免"悄悄降级成 bind 却不自知"。
- 需要 bind 前先确认端口空闲：`sudo ss -lunp | grep 43897`。
- 用 `/api/status` 的 `udp_mode` 字段确认当前到底是 sniff 还是 bind。

## 3.2 抓包报 `PermissionError` / 降级成 bind

**现象**
日志出现 `PermissionError`，或 `/api/status` 里 `udp_mode` 是 `bind` 而不是 `sniff`。

**原因分析**
`AF_PACKET` 需要 `CAP_NET_RAW` 能力。服务以普通用户（`ysc`）运行时默认没有。

**解决方案**
在 unit 里用 **AmbientCapabilities** 授予（最小权限，不必跑 root）：

```ini
[Service]
User=ysc
Group=ysc
AmbientCapabilities=CAP_NET_RAW
CapabilityBoundingSet=CAP_NET_RAW
```

改完必须：

```bash
sudo systemctl daemon-reload && sudo systemctl restart lite3-monitor
```

若 systemd/内核不支持该写法，退而求其次把 `User=` 改成 `root`（**不推荐**，权限过大）。

**规避建议**
- 手动前台调试时抓包也要 `sudo`：
  ```bash
  cd /home/test/monitor/backend
  sudo LITE3_UDP_MODE=sniff ../.venv/bin/python -m uvicorn main:app --host 0.0.0.0 --port 8000
  ```
- 排查第一步：`journalctl -u lite3-monitor -n 50`。

## 3.3 抓到大量无关流量 / 抓错网卡

**现象**
`packets_received` 涨得飞快但 `packets_parsed` 很少；或 `connected` 一直 false。

**原因分析**
`AF_PACKET` 抓的是网卡上**所有**报文。103 上还跑着 RTSP 视频流拉取等大流量业务，
会把无关流量一并抓进来；另外状态流走的是**业务网**那张网卡，抓错网卡就收不到。

**解决方案**
指定业务网网卡（连 `192.168.1.120` 的那张）：

```ini
Environment=LITE3_UDP_IFACE=eth0      # 换成 103 上实际的网卡名
```

网卡名用 `ip addr` 确认。

**规避建议**
部署时就填上 `LITE3_UDP_IFACE`，别留空（留空 = 抓所有网卡）。

## 3.4 AF_PACKET 丢包率高

**现象**
`/api/status` 里 `packets_dropped` 相对 `packets_received` 占比很高
（**实测约 56%**），但面板显示正常、`connected=true`。

**原因分析**
AF_PACKET 先在内核环形缓冲收下**全部**流量，再由 Python 逐个筛 43897；
高遥测频率（本体 IMU 约 200Hz）叠加视频流时，缓冲来不及取走就被覆盖。

**解决方案（当前状态：不影响监控实时性，可选优化）**
- 已缓解手段：设 `LITE3_UDP_IFACE` 减少无关流量（见 3.3）。
- 【待验证】进一步可加 BPF 过滤，只让 43897 的报文进入应用层；
  或调大 AF_PACKET 环形缓冲。这两项在本项目中**尚未实测**，改动前请先评估。

**规避建议**
- 做**实时监看**不受影响（面板是 10Hz 推送）。
- 若要用抓包数据做**离线分析/统计**，注意样本有缺失，别直接当全量数据用。

## 3.5 ROS1 / ROS2 切换导致 43897 归属变化

**现象**
在 103 上切换 ROS1 与 ROS2 链路后，监控的数据表现变化；
ROS2 的桥接数据源变成 `none`，实际退回 sniff。

**原因分析**
两套 transfer **抢同一个 UDP 端口 43897**：

| 链路 | 进程 | 端口 |
| --- | --- | --- |
| ROS2 | `jetson2motion`（+`jetson2app`） | 收 43897 |
| ROS1 | `qnx2ros`（+`ros2qnx`/`nx2app`） | 收 43897 |

同时 `lite3-ros-bridge.service`（把 ROS topic 转发到本机 43900）是 **ROS2 节点**，
切到 ROS1 后没有对应的桥接，ROS 数据源自然失效、回退 sniff。

**解决方案**
- **监控本身不受影响**：sniff 与 ROS 版本无关，两套下都能工作。
- 需要按版本切换行为时，用项目里的 ROS 版本识别能力（`backend/ros_env.py`、`ros_profiles.py`、
  `ros_switch.py`），它会按版本选择数据源策略（ROS2→ros，ROS1→sniff）并给出 `/api/ros`。
- 核对当前是谁占着端口：
  ```bash
  sudo ss -lunp | grep 43897
  ```

**规避建议**
- ROS1 与 ROS2 的 transfer **不要同时启用**。
- 切回 ROS2 时注意 `transfer_ros2.service` 若是 `enabled`，**103 重启后会自启并抢回 43897**，
  想长期跑 ROS1 需要 `sudo systemctl disable transfer_ros2.service`（详见 `05-部署运维.md`）。

## 3.6 协议解析：两套数值编码千万别混

**现象**
自己解析报文时数值完全对不上，或负数看起来"很怪"。

**原因分析**
Lite3 协议里**并存两套编码**，适用对象不同：

| 指令类型 | 报文 | 值所在字段 | 类型 | 负数如何表示 |
| --- | --- | --- | --- | --- |
| 速度指令（`0x0140/0x0145/0x0141`） | 复杂指令 20B，type=1 | `data`（8B） | **double** | IEEE 754 **符号位**（最高位 0→1，其余位不变） |
| 轴指令等简单指令 | 简单指令 12B，type=0 | 指令值字段（4B） | **int32** | **补码**（取反加一） |

例：
```
+0.35 → 666666666666D63F
-0.35 → 666666666666D6BF     ← 只有最高字节 3F→BF（符号位置 1），其余字节完全相同
-500(int32) → 0xFFFFFE0C     ← 补码：取反加一
```

**解决方案**
按指令类型选解码方式，不要统一按整数或统一按浮点处理：

```python
import struct
struct.unpack('<d', pkt[12:20])[0]     # 复杂指令：小端 double
struct.unpack('<i', pkt[4:8])[0]       # 简单指令：小端 int32
```

**规避建议**
- 判断依据看第 9–12 字节的 `type` 字段：`1` = 复杂指令（值在 data，double），`0` = 简单指令。
- 已知小坑：对 0.0 做"取反"运算会产生 **`-0.0`**（位模式 `0000000000000080`），
  数值上等于 0（`−0.0 == 0.0` 为真）但字节不是全零，排查报文时容易被误判为异常值。
  项目已在速度取反处做了 `+ 0.0` 归一化。

## 3.7 ROS 数据源 `data_source: none`

**现象**
`/api/status` 里 `data_source` 是 `none`，或 ROS 桥接始终没数据。

**原因分析**（`docs/ros_troubleshooting.md`）
常见三类：
1. 桥接服务没起来（ROS 环境没 source / `rclpy` 不可用）
2. 桥接订阅的 topic 名与 `transfer_ros2` 实际发布的不一致
3. 端口对不上（第二套实例是 `43900 + TAG`）

**解决方案**

```bash
# ① 桥接在不在跑
systemctl status lite3-ros-bridge
# ② 43900 有没有包
sudo tcpdump -i any -nn udp dst port 43900 -c 5
# ③ ROS 侧 topic 是否真的在发布
ros2 topic list | grep -E "imu|leg_odom|joint"
```

topic 名不一致就改 unit 的 ExecStart 参数 `--imu/--odom/--joints`。

**规避建议**
保持 `LITE3_DATA_SOURCE=auto`：ROS 断流超过 `LITE3_ROS_STALE_TIMEOUT`（10s）会自动回退 sniff，
ROS 恢复后再切回（**双向自愈**）。显式写 `ros` 则不做自动降级。

## 3.8 机器人没上电时怎么联调

**现象**
现场没开机，但需要验证解析链路。

**原因分析**
数据链路依赖机器人实际发报文；没上电就完全没有数据源。

**解决方案**
用内置模拟器向本机 43897 发符合协议的数据：

```bash
cd /home/test/monitor
/home/test/monitor/.venv/bin/python tools/mock_sender.py     # 默认 127.0.0.1:43897，10Hz
```

另两个工具：`tools/smoke_test.py`（冒烟）、`tools/inspect_control_packets.py`（控制报文审计）。

**规避建议**
新环境首次部署时，先用模拟器跑通，再去连真机 —— 能把"解析问题"和"链路问题"分开。
