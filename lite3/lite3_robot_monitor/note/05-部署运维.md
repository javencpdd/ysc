## 5.1 systemd unit 的关键配置项

**现象**
服务起不来、抓包降级、或多实例互相打架。

**原因分析**
unit 里几行配置直接决定了功能是否可用，改错一个就出怪问题。

**解决方案**（`deploy/lite3-monitor.service` 要点）

```ini
[Service]
User=ysc
Group=ysc
# 用 AmbientCapabilities 而不是直接跑 root，遵循最小权限原则
AmbientCapabilities=CAP_NET_RAW
CapabilityBoundingSet=CAP_NET_RAW
Environment=PYTHONUNBUFFERED=1
Environment=PYTHONPATH=/home/test/monitor/backend
Environment=LITE3_UDP_MODE=sniff
Environment=LITE3_UDP_PORT=43897
Environment=LITE3_UDP_IFACE=          # 建议填业务网网卡
Environment=LITE3_HTTP_HOST=0.0.0.0
Environment=LITE3_HTTP_PORT=8000
Environment=LITE3_ROS_BRIDGE_PORT=43900
Environment=LITE3_PUSH_HZ=10
Environment=LITE3_LINK_TIMEOUT=3.0
ExecStart=/home/test/monitor/.venv/bin/python -m uvicorn main:app --host 0.0.0.0 --port 8000
```

**规避建议**
- 改完 unit 必须 `daemon-reload` 再 `restart`，否则改的不生效。
- 不要为了省事把 `User=` 改成 `root`，用 `AmbientCapabilities` 才是正确姿势。

## 5.2 多实例并行（TAG）的端口与命名映射

**现象**
装第二套做验证时，两个实例互相顶掉，或端口冲突。

**原因分析**
多实例靠 **TAG** 区分，服务名、HTTP 端口、桥接端口、ROS 节点名都要跟着变。

**解决方案**（`install.sh` 逻辑）

| 项 | 单实例（无 TAG） | TAG=2 |
| --- | --- | --- |
| 安装目录 | `/home/test/monitor` | `/home/test/monitor2` |
| 服务名 | `lite3-monitor` | `lite3-monitor2` |
| HTTP 端口 | 8000 | 8002 |
| ROS 桥接端口 | 43900 | 43902 |
| ROS 节点名 | `lite3_ros_bridge` | `lite3_ros_bridge2` |

```bash
sudo bash deploy/install.sh /home/test/monitor2 2
```

**规避建议**
- monitor 与 ros-bridge **必须用同一个 TAG**。
- 内嵌订阅模式下还要保证 `LITE3_ROS_NODE_NAME` 不同，或用 `ROS_DOMAIN_ID` 隔离。
- TAG 是第二个位置参数（历史版本曾把它当 pip 源，详见 `02` 的 2.7）。

## 5.3 `install.sh` 到底做了什么（以及不做什么）

**现象**
不敢跑安装脚本，怕破坏现有环境。

**原因分析**
不清楚脚本边界就不敢用。脚本注释与 `deploy/README.md` 已明确它的动作范围。

**解决方案**
脚本只做「安装与注册」：

1. 建虚拟环境（venv → virtualenv → 系统 Python 三层降级）
2. 安装 `requirements.txt` 依赖
3. 拷贝后端与 `frontend/dist`
4. **抓包自检**
5. 注册 systemd 并启动

**它不改动**：`transfer_ros2`、`jy_exe` 以及任何现有配置。

**规避建议**
日常更新**不要**重复跑它（会重建 venv、重装依赖，且可能删掉前端），改代码走 `02` 的增量更新。

## 5.4 日志查不到历史（103 的 journald 是易失的）

**现象**
服务重启后，`journalctl` 看不到重启前的日志；`journalctl --list-boots` 报权限不足。

**原因分析**
103 上 `/var/log/journal` 目录不存在，journald 默认 `auto` 会退化成**内存盘**，
**重启即全部清空**。历史日志只能靠 rsyslog 落盘的 `/var/log/syslog*`、`kern.log*`。
另外 `ysc` 不在 `adm` 组，而 `/var/log/syslog` 是 `640 root:adm`，直接 `cat`/`grep` 会被拒绝。

**解决方案**

```bash
journalctl -u lite3-monitor -n 50      # 只能看本次开机以来
journalctl -u lite3-monitor -f         # 实时跟随
printf "\047\n" | sudo -S grep lite3 /var/log/syslog    # 历史：必须 sudo
```

需要跨重启保留日志就先开持久化：

```bash
sudo mkdir -p /var/log/journal
sudo systemctl restart systemd-journald
```

**规避建议**
遇到"重启就好了"的故障，**先开持久化再等复现** —— 否则重启这个动作本身会删掉证据。

## 5.5 远端跑长任务输出为空

**现象**
在 103 上跑耗时长的前端构建/大文件同步，命令返回后什么输出都没有。

**原因分析**
前台 SSH 长命令可能被掐断；且 `/tmp` 下的日志会被清理。

**解决方案**
脱离会话运行，并把日志写到工程目录内：

```bash
setsid nohup <cmd> > /home/test/monitor/logs/xxx.log 2>&1 < /dev/null &
```

之后分批轮询该日志。

**规避建议**
不要用 `/tmp` 存需要复看的日志。

## 5.6 ROS2 CLI 输出被缓冲导致"看起来没输出"

**现象**
`ros2 topic list > file` 后文件是空的，或命令被中断后丢失输出。

**原因分析**
ROS2 CLI 输出有缓冲，被 `timeout`/SIGTERM 杀掉时缓冲区内容丢失。

**解决方案**
用无缓冲方式调用：

```bash
python3 -u /opt/ros/foxy/bin/ros2 topic list
# 或
stdbuf -oL ros2 topic list
```

**规避建议**
另外注意 Foxy 的 `ros2 topic hz` **没有 `--qos-*` 参数**、固定 RELIABLE 订阅，
对 BEST_EFFORT 发布端的话题会"可见但收不到"，别误判为话题不存在。

## 5.7 `transfer_ros2` 开机自启抢回 43897

**现象**
为了跑 ROS1 手动停了 `transfer_ros2`，103 重启后发现它又活了，43897 被抢回。

**原因分析**
`systemctl stop` 只是**当前停止**，服务若是 `enabled`，**开机仍会自启**。
实测中这个坑已经发生过一次。

**解决方案**

```bash
systemctl is-enabled transfer_ros2.service    # 先看状态
sudo systemctl stop transfer_ros2.service     # 当前停止
sudo systemctl disable transfer_ros2.service  # 关键：禁止开机自启
```

**规避建议**
- 判断"服务会不会开机自启"要看 `is-enabled`，不是 `is-active`。
- 长期跑 ROS1 一定要 `disable`；恢复 ROS2 时再 `enable` + `start`
  （且要先停 ROS1 的 transfer，否则 43897 冲突）。

## 5.8 回滚

**现象**
需要把 103 恢复到部署 Monitor 之前的状态。

**原因分析**
Monitor 是纯增量安装（只加了 `/home/test/monitor` 和一个 systemd unit），
所以回滚很干净。

**解决方案**

```bash
sudo systemctl stop lite3-monitor
sudo systemctl disable lite3-monitor
sudo rm /etc/systemd/system/lite3-monitor.service
sudo systemctl daemon-reload
sudo rm -rf /home/test/monitor
```

现有 ROS 服务、120 侧配置**全程未被修改**，回滚后系统回到部署前状态。

**规避建议**
多实例场景下回滚要带上 TAG 后缀的服务名与目录，避免误删正在运行的实例。

## 5.9 日常运维命令速查

```bash
systemctl status lite3-monitor          # 状态
journalctl -u lite3-monitor -f          # 实时日志
journalctl -u lite3-monitor -n 50       # 最近 50 行
systemctl restart lite3-monitor         # 重启（改配置后必做）
curl -s http://127.0.0.1:8000/api/status | python3 -m json.tool   # 健康与模式
sudo tcpdump -i any -nn udp dst port 43897 -c 5                   # 数据到没到
sudo ss -lunp | grep 43897                                        # 端口归属
```

`/api/status` 关键字段判读：

| 字段 | 期望 | 含义 |
| --- | --- | --- |
| `udp_mode` | `sniff` | 旁路抓包生效，未占用 43897 |
| `connected` | `true` | 已收到机器人状态 |
| `packets_parsed` | 持续增长 | 解析链路正常 |
| `ros_version` | `ros1` / `ros2` | 当前识别到的 ROS 版本（新增能力） |
| `ros_degraded` | `false` | 为 true 表示方案切换失败并走了回退 |
