# 02 编译构建与打包

> 依据：`README.md` 第 5.3 / 5.6 节、`deploy/pack.sh`、`deploy/install.sh`、`deploy/deploy_103.sh`。

这一章最重要的结论：**日常改代码不要用 `install.sh` 更新**。理由见 2.3。

---

## 2.1 在 Jetson 上跑 `npm run build` 极慢

**现象**
在 103 上执行前端构建，耗时远超笔记本，甚至跑不完。

**原因分析**
Jetson Xavier NX 的 CPU 性能与存储 IO 远弱于开发机，而 Vite 构建是 CPU 密集任务。
README 里直接给了结论：「Jetson 上 npm build 很慢，建议本地构建后传产物」。

**解决方案**
在**笔记本**上构建，只传产物：

```bash
# 笔记本
cd frontend && npm run build          # 产出 frontend/dist
bash deploy/pack.sh                   # 自动剔除 node_modules，几百 MB → 几十 KB
scp lite3-monitor-deploy.tar.gz ysc@192.168.1.103:/home/test/   # 落在本机工作区
```

```bash
# 103
cd /tmp && tar xzf lite3-monitor-deploy.tar.gz
sudo bash lite3_robot_monitor/deploy/install.sh /home/test/monitor
```

**规避建议**
把 `node_modules` 永远留在笔记本上，`pack.sh` 已自动排除它。
**不要**把 `frontend/node_modules` 拷到 103。

> **关于上传落地点**：README 早期版本两处写法不一致（4.1 用 `/home/test/`、5.3 用 `/tmp/`），
> 现已统一为 **`/home/test/`**。原因：解压后得到的 `/home/test/lite3_robot_monitor`
> 是**本机源码树**，后续增量更新（rsync 到 `/home/test/monitor`）依赖它；
> 而 `/tmp` 会被系统清理，源码树放那儿下次更新还得重传。
>
> ⚠️ 反过来，**`install.sh` 的安装目录绝不能写成 `/tmp`** —— 会被清理，
> 服务跑几次就没了。运行目录请用 `/home/test/monitor` 这类持久路径。

## 2.2 打包时没有 `frontend/dist`，装完页面打不开

**现象**
部署后 `http://192.168.1.103:8000` 打不开页面，或只有 API 能用。

**原因分析**
`pack.sh` 只在检测到 `frontend/dist` 时才打包前端产物，否则打警告：

```bash
echo "[pack] 警告：未发现 frontend/dist（103 上将只提供 API）"
```

`install.sh` 同样会 warn：「未发现 frontend/dist，将只提供 API」。

**解决方案**
先构建再打包，顺序不能反：

```bash
cd frontend && npm run build && cd .. && bash deploy/pack.sh
```

**规避建议**
把 `npm run build` 和 `pack.sh` 串成一条命令执行，避免漏步。
可用 `LITE3_SERVE_FRONTEND=false` 显式关闭静态资源挂载（纯 API 部署场景）。

## 2.3 日常改后端用 `install.sh` 更新 → 前端被删坏

**现象**
只改了一行后端代码，重跑 `install.sh` 后页面白屏 / 404。

**原因分析**
`install.sh` 里有这一行：

```bash
if [[ -d "$SRC_DIR/frontend/dist" ]]; then
    rm -rf "$TARGET/frontend"        # ← 先删再拷
    mkdir -p "$TARGET/frontend"
    cp -r "$SRC_DIR/frontend/dist" "$TARGET/frontend/"
```

**只有当源目录带着新的 `dist` 时才会拷贝**；如果这次打包没带 `dist`，
旧的前端就被 `rm -rf` 删掉且没有新内容补上。此外它还会重建 venv、重装依赖。
README 5.6 明确写了：「日常改后端**不需要**重跑 install.sh」。

**解决方案**
改用增量更新（103 本机，源目录与运行目录都在本地时）：

```bash
# 1) 同步后端（排除缓存）
sudo rsync -av --exclude '__pycache__' --exclude '*.pyc' \
  /home/test/lite3_robot_monitor/backend/ /home/test/monitor/backend/

# 2) 清旧字节码，避免用到过期 .pyc
sudo find /home/test/monitor/backend -name '__pycache__' -type d -exec rm -rf {} + 2>/dev/null

# 3) 重启（config 是 frozen dataclass，import 时固化，不重启不生效）
sudo systemctl restart lite3-monitor
```

从笔记本同步则用 `deploy/deploy_103.sh`（rsync + 重启，按 TAG 只动对应实例）。

**规避建议**
记住 **只有这 4 种情况才重跑 `install.sh`**：
1. 改了 `requirements.txt`
2. 改了 `deploy/*.service`
3. 要部署新构建的 `frontend/dist`
4. 首次安装 / 更换安装目录

## 2.4 改了代码但行为没变（用了过期 `.pyc`）

**现象**
同步了新代码、也重启了，但跑的还是旧逻辑。

**原因分析**
Python 的 `__pycache__/*.pyc` 在源文件 mtime/size 未变时会被复用；
rsync 跨机同步时若时间戳处理不当，可能留下与新源码不匹配的字节码。

**解决方案**
同步后**显式清掉** `__pycache__`（见 2.3 第 2 步），再重启。

**规避建议**
把 `rsync --exclude '__pycache__'` 与 `find ... -exec rm -rf {} +` 固化成一条更新脚本，
不要只 rsync 就重启。

## 2.5 改了环境变量 / 配置但没生效

**现象**
改了 unit 里的 `Environment=...` 或 `LITE3_*`，重启后行为依旧。

**原因分析**
`backend/config.py` 的配置对象是 **frozen dataclass**，在 **import 时**读取环境变量并固化；
运行期不会重新读取。

**解决方案**
必须**重启服务**（不是 reload）：

```bash
sudo systemctl restart lite3-monitor
```

若用 drop-in 改的，还需先 `daemon-reload`：

```bash
sudo systemctl edit lite3-monitor      # 写 [Service] Environment=...
sudo systemctl daemon-reload
sudo systemctl restart lite3-monitor
```

**规避建议**
把「改配置 → 重启」当成一个不可分割的动作。可以用 `/api/status` 的字段反查是否生效
（如 `udp_mode`、`ros_version`）。

## 2.6 前端改动怎么正确上线

**现象**
改了 Vue 组件，只 rsync 了 `frontend/src`，页面没变化。

**原因分析**
浏览器加载的是**构建产物** `frontend/dist`，不是 `src`。

**解决方案**

```bash
# 笔记本：构建
cd frontend && npm run build

# 同步 dist 到 103
rsync -av /path/to/lite3_robot_monitor/frontend/dist/ \
  ysc@192.168.1.103:/home/test/monitor/frontend/dist/
```

**规避建议**
不要 rsync `src`；也不要手动去改 103 上的 `dist` 文件（下次构建会被整体覆盖）。

## 2.7 并行部署第二套实例时把旧实例覆盖了

**现象**
想装一份新版本做验证，结果正在运行的旧实例被换掉了。

**原因分析**
`install.sh` 用 **TAG** 区分实例（服务名加后缀、HTTP 端口 `8000+N`、桥接端口 `43900+N`）。
**TAG 是第二个位置参数**。脚本注释里记了历史坑：

```
TAG             非负整数；留空=单实例，填 N 则服务名加后缀 N、HTTP=8000+N、桥接=43900+N
                注意：TAG 是第二个位置参数。历史版本把第二个参数当成 pip 源，
                导致 `install.sh <dir> 2` 被解析成 `-i 2` 且 TAG 为空，请勿再那样传
```

漏传 TAG 就等价于装到默认目录，会动到正在运行的旧实例。

**解决方案**
显式传 TAG，或用等价的 `--tag`：

```bash
sudo bash deploy/install.sh /home/test/monitor2 2      # ✅ TAG=2
sudo bash deploy/install.sh /home/test/monitor2 --tag 2 # ✅ 等价
```

脚本内置了安全护栏：检测到 TAG 漏传/传错会**提前中止**并提示，避免白建 venv。

**规避建议**
- 永远显式写 TAG，不要依赖位置记忆。
- 装完核对三处：服务名 `lite3-monitor2`、HTTP 端口 `8002`、桥接端口 `43902`。
- 两边（monitor 与 ros-bridge）必须用**同一个 TAG**。
