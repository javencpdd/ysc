# 多机器人协同巡检仿真验证方案 v0.1
### 空—地异构编队：Lite3 机器狗 × UGV 无人车 × 无人机巢

> 编写时间：2026-09-30　版本：v0.1（待评审）
> 上游文档：[Lite3 火灾巡检系统 v1.0 — 工程实施计划](Lite3%20火灾巡检系统%20v1.0%20工程实施计划.md)（单机版，Phase 0–4）
> 本方案定位：把「**巡检队形 + 路径规划 + 无人车 + 无人机**」融合进**同一个场景**，
> 先在**仿真**里验证，再上真机。**不改动 103 现有真机栈**。

---

## 0. 一句话结论（先行）

**先在仿真里把"狗 + 车 + 机"的接口、队形、任务分配、异常复核闭环跑通，再上真机。**

三条定调：

| # | 结论 | 理由 |
|---|---|---|
| 1 | **仿真一律跑在本机工作站（ROS 2 Humble + Gazebo Ignition），不占 103 资源** | 103 只有 6 核 / 6.7 GiB，真机栈（雷达+SLAM+规划+YOLO）已经吃满；再加仿真必崩 |
| 2 | **用「一个场景四个阶段」把四类能力串成闭环**，而不是各做各的 demo | 队形/规划/UGV/无人机只有在同一任务里才有协同语义 |
| 3 | **分层验证 L0→L3，每层有硬判据，不过关不进下一层** | 避免"看起来能跑"但接口没对齐，上真机后返工 |

## 1. 场景定义：一个场景装下四类能力

**场景名：园区周界巡检 + 火情复核处置**（沿用上游火灾巡检业务，扩展为多机协同）

```text
┌─ 阶段 A 常态巡检 ────────────────────────────────┐
│  Lite3（前方/复杂地形） + UGV（后方/载荷与中继）    │
│  按编队路线沿周界行进：队形保持 + 协同路径规划      │
└──────────────────────┬──────────────────────────┘
                       │ YOLO 检出异常（火情/入侵/设备）
┌──────────────────────▼──────────────────────────┐
│  阶段 B 空中复核：无人机巢收到告警 → 起飞 →        │
│  高空广域扫描 → 回传确认/否证                      │
└──────────────────────┬──────────────────────────┘
                       │ 确认为真
┌──────────────────────▼──────────────────────────┐
│  阶段 C 协同处置：UGV 携物资到场 → Lite3 近距细查   │
│  （可选：无人机持续俯瞰，提供全局视角）             │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│  阶段 D 归位：无人机回巢充电 → 狗/车返回充电桩      │
└─────────────────────────────────────────────────┘
```

**你要的四类能力 → 场景中的落点**：

| 能力 | 承担平台 | 出现在阶段 | 验证层级 |
|---|---|---|---|
| 巡检队形 | Lite3 + UGV | A | L1 |
| 路径规划 | Lite3（SCAN-Planner）/ UGV（Nav2）/ 无人机（航点） | A、B、C | L0、L2 |
| 无人车 | UGV | A（编队）、C（物资） | L1、L2 |
| 无人机（巢） | Drone + Dock | B（复核）、D（归位） | L2、L3 |

## 2. 技术选型（对比表 + 选型理由）

| 层 | 候选 | 选型 | 理由 |
|---|---|---|---|
| **仿真器** | Gazebo Ignition Fortress / Gazebo classic 11 / Webots | **Ignition Fortress** | ROS 2 原生；PX4 SITL 官方支持最好；SITL+Gazebo 是无人机仿真的事实组合 |
| **中间件（仿真侧）** | ROS 2 Humble / ROS 2 Foxy | **Humble**（本机工作站新装） | Ignition Fortress 与 Humble 配套；Foxy 已 EOL 且 Ignition 支持弱 |
| **中间件（真机侧）** | ROS 1 Noetic（103 现状） | **保持 ROS 1 不动** | Lite3 的雷达/FAST-LIO/SCAN-Planner/本体链路已全部跑通在 Noetic，改造代价极高 |
| **跨栈桥接** | ros1_bridge / MQTT 网关 / 各自双栈 | **ros1_bridge（只桥必要话题）** | 已有安装经验（0.9.7-1focal）；原则同避坑第 4 章：**只桥控制与状态，绝不桥点云** |
| **狗的规划器** | SCAN-Planner（ROS1）/ Nav2（经桥接） | **SCAN-Planner**（沿用真机） | 已在真机验证；仿真里可直接跑同一份代码，保真度最高 |
| **UGV 导航** | Nav2 | **Nav2** | 地面轮式标准方案，生态成熟 |
| **无人机** | PX4 SITL + Gazebo / 纯航点插件 | **PX4 SITL** | 与真机飞控同构，仿真→真机可迁移；无人机巢先建模为"起飞/降落点 + 状态机" |
| **队形控制** | 虚拟结构法 / leader-follower | **leader-follower（UGV 跟狗）** | 实现最简单、对通信依赖低；狗做 leader 天然匹配其"前方探路"角色 |
| **任务分配** | 行为树 BT.CPP / 拍卖算法 / 静态脚本 | **L2 用静态脚本，L3 再上行为树** | 先保证接口跑通（MoSCoW：BT 是 Should，不是 Must） |

## 3. 分层验证计划（L0 → L3，逐层放行）

| 层级 | 目标 | 场景内容 | **通过判据（硬指标）** |
|---|---|---|---|
| **L0 单机基线** | 每个平台各自能完成基本导航 | 狗：SCAN-Planner 走到目标点；UGV：Nav2 走固定路线；无人机：航点起降 | 狗：到达误差 ≤ 0.6 m（注意真机有 0.6 m 固定超调，仿真应更小）；UGV：≤ 0.3 m；无人机：航点误差 ≤ 1.5 m |
| **L1 队形保持** | 狗+车编队沿路线行进 | 周界路线，UGV 保持队形跟狗 | 队形间距误差 ≤ 0.5 m（稳态）；跟随时纵向滞后 ≤ 1.5 m；无相互穿越/碰撞 |
| **L2 协同任务闭环** | 异常 → 无人机复核 → 处置 | 注入火情 → 狗告警 → 无人机出巢复核 → UGV 到场 | 端到端时延 ≤ 60 s（告警→无人机到位）；任务状态机无死锁；告警消息零丢失 |
| **L3 容错降级** | 断链/单机失效仍能收敛 | 注入：无人机通信中断 30 s / UGV 故障 / 狗被阻挡 | 降级策略被正确触发（如无人机返巢、UGV 退出队形）；系统不崩溃、能回到安全态 |

> **放行规则**：每层跑 5 次，5 次全部满足判据才进下一层；任一关键项不满足 → 回本层修，不允许"带病升级"。

## 4. 仿真环境搭建（可执行）

### 4.1 前置条件

| 项 | 要求 | 备注 |
|---|---|---|
| 仿真工作站 | Ubuntu 22.04 + ROS 2 Humble + Ignition Fortress | **不要用 103**（资源不足），本机 PC 或另备 x86 主机 |
| 模型资产 | Lite3 URDF（**已有**：`lite3_description`，真机那份可直接复用） | UGV/无人机模型需新建或用开源模型 |
| 场景地图 | 园区 .world（可先用 Gazebo 自带 warehouse.sdf 改造） | 周界路线 ≥ 50 m，含 1 处窄道、1 处坡道/台阶（发挥狗的优势） |
| 网络 | 仿真机与 103 同网段（如需 ros1_bridge 联调） | 纯仿真阶段不需要 103 |

### 4.2 目录建议

```text
~/multi_robot_sim/
├── worlds/          # 园区 world + 周界路线
├── models/          # lite3(复用) / ugv / drone / dock
├── src/
│   ├── formation_controller/     # 队形（leader-follower）
│   ├── mission_manager/          # 任务状态机 + 分配
│   ├── dock_simulator/           # 无人机巢（起降/充电状态机）
│   └── sim_bridge/               # ROS1↔ROS2 话题白名单（联调真机时才用）
└── launch/
    ├── l0_single.launch.py
    ├── l1_formation.launch.py
    └── l2_mission.launch.py
```

### 4.3 启动顺序（示例）

```bash
# 1) 起仿真世界（含三个机器人 + 巢）
ros2 launch sim_bringup world.launch.py world:=campus_perimeter

# 2) L0：单机能力各自验证
ros2 launch sim_bringup l0_single.launch.py robot:=lite3   # 狗：SCAN-Planner（ROS1 侧）
ros2 launch sim_bringup l0_single.launch.py robot:=ugv     # 车：Nav2
ros2 launch sim_bringup l0_single.launch.py robot:=drone   # 机：PX4 SITL + 航点

# 3) L1：编队
ros2 launch sim_bringup l1_formation.launch.py leader:=lite3 follower:=ugv formation:=column

# 4) L2：任务闭环（含异常注入）
ros2 launch sim_bringup l2_mission.launch.py inject_alert:=true
```

> ⚠️ **狗的 SCAN-Planner 是 ROS 1**：仿真里让它跑需要一条桥，或者**先做纯 ROS 2 的等效替代**
> （用 Nav2 + 相同队形逻辑跑 L1），把 SCAN-Planner 的差异留到真机联调阶段。
> 这是 v0.1 的**关键取舍**：L1/L2 用"行为等价"验证协同逻辑，L3 之后再做真机闭环。

## 5. 接口与消息契约（先定契约，再写代码）

| 话题 / 服务 | 类型（建议） | 方向 | 说明 |
|---|---|---|---|
| `/formation/order` | `FormationOrder`（自定义：leader_id, offsets[], shape） | 任务层 → 队形层 | 下发队形参数 |
| `/formation/state` | `FormationState`（errors, follower_id） | 队形层 → 监控 | L1 队形误差判据的数据源 |
| `/mission/task` | `TaskAssignment`（robot_id, task_type, target_pose, priority） | 任务层 → 各平台 | 任务分配结果 |
| `/mission/status` | `MissionStatus`（phase, robot_states[]） | 各平台 → 任务层 | 阶段 A/B/C/D 状态机 |
| `/alert` | `Alert`（type, pose, confidence, source_robot, stamp） | 狗（YOLO）→ 任务层 | **衔接上游 `/fire_alert`**，建议升级为带位姿的结构化告警 |
| `/dock/cmd` | `DockCmd`（takeoff / land / charge / status） | 任务层 → 巢 | 无人机出巢/回巢 |
| `/robotX/cmd_vel` | `geometry_msgs/Twist` | 规划 → 平台执行 | 各平台独立，最后一层才下发 |

**统一坐标系约定**：

- 全局统一帧 `map`（仿真）/ `world`（SCAN-Planner 侧），两者用**静态 TF 对齐**（真机上已这么做：`world ≡ camera_init`）。
- 所有位姿消息必须带 `frame_id` 与 **统一时间源**（仿真用 `/clock`，真机用主机时钟 + 已验证的时间同步）。

## 6. 评价指标（KPI）

| 类别 | 指标 | 目标值 | 采集方式 |
|---|---|---|---|
| 队形 | 间距误差 RMS | ≤ 0.5 m | `/formation/state` |
| 队形 | 跟随时纵向滞后 | ≤ 1.5 m | 两机里程计差分 |

| 资源 | 仿真机 CPU / 内存 | < 80% / < 70% | top |

## 7. 进度计划（MoSCoW）

| 优先级 | 内容 | 说明 |
|---|---|---|
| **Must** | L0 单机基线、L1 队形保持 | 没这两个，协同无从谈起 |
| **Must** | 场景 world + 三个模型 + 周界路线 | 验证载体 |
| **Must** | 消息契约（第 5 节）落地 | 接口对齐是仿真的核心产出 |
| **Should** | L2 任务闭环（异常注入→无人机复核） | 体现"多机"价值的关键 |
| **Should** | 无人机巢状态机（起飞/降落/充电） | 可与 dock 真机行为对齐 |
| **Could** | L3 容错降级 | 工程化阶段再做 |
| **Could** | 行为树任务分配（替代静态脚本） | 静态脚本跑通后再升级 |
| **Won't（v0.1）** | 真机联调、多狗、视觉 SLAM 融合 | 留出边界 |

**建议节奏**：S1 环境搭建 → S2 L0 → S3 L1 → S4 L2 → S5 复盘与真机衔接设计。

## 8. 风险登记

| # | 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|---|
| R1 | **ROS 1 / ROS 2 混栈**（狗是 Noetic，仿真是 Humble） | 联调复杂度高 | 高 | v0.1 仿真内用"行为等价"替代，真机联调另立阶段；桥接严格白名单，不桥点云 |
| R2 | **仿真→真机差异**（真机有 0.6 m 固定超调、LIO 会漂） | 仿真通过≠真机能用 | 高 | 仿真判据留余量；真机阶段重新标定；**仿真不代替真机验证** |
| R3 | 仿真机资源不足（三机器人 + PX4 SITL） | 仿真卡顿/失真 | 中 | 分阶段启动（L0 单机分别跑）；必要时降频/降分辨率 |
| R4 | 无人机与巢的模型/协议未知 | 场景 B 无法建模 | 中 | 先用状态机抽象（起飞/降落/充电），协议待真机资料补齐 |
| R5 | UGV 型号与接口未确认 | L1 队形无法对接 | 中 | 先用通用差速模型；接口按 `/cmd_vel` + 里程计抽象 |
| R6 | 时间同步与 `use_sim_time` 混乱 | 协同判据失真 | 中 | 统一 `/clock`；真机联调时明确时间源 |

## 9. 与真机的衔接（Gap 分析）

**103 真机现状（2026-09-30 已验证）**：

- ✅ 雷达（Mid360）→ FAST-LIO → SCAN-Planner → `/scan_planner/cmd_vel` → 本体，**整链已打通，狗能按指令行走**
- ✅ 自主模式 + 心跳、起立门禁、状态探针、预检脚本均已脚本化
- ⚠️ 已知偏差：固定超调 ≈ 0.6 m；搬动狗会导致 LIO 发散；目标距离需 ≥ 1 m（或降速到 0.4）

**仿真通过后的上真机 checklist**：

1. 队形参数按真机超调重新标定（仿真里的间距在真机会放大）
2. 桥接白名单落地：只桥 `/mission/*`、`/formation/*`、`/alert`、**绝不桥点云与 `/tf`**
3. 狗的真机安全层保留最终否决权（VOA / 急停），上游方案 F7 已要求
4. 无人机巢与 UGV 的真机协议补齐后，替换仿真里的状态机桩
