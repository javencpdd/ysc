## 1. 网络与软件源

### 1.1 ⚠️ 103 的联网状态随时间波动，必须实时复测

103 的上联是 **120 主机**（默认路由 `via 192.168.1.120`），因此"103 能不能出网"取决于 120 当时的状态。

- 实测记录：`01:24` DNS 全断 → 半小时后 `01:47` 自动恢复。
- **教训**：曾据此得出"103 没有外网"的结论，写入方案并据此设计了离线依赖方案，属于**错误结论**。
- **对策**：任何需要联网的步骤前先跑一次连通性测试，把结果**当场**记进日志，不要引用历史结论。

```bash
ping -c 2 223.5.5.5 && getent hosts github.com && echo "OK"
```

### 1.2 ⚠️ GitHub 直连不通（TCP 443 超时），走代理

直连 `20.205.243.166:443` 超时。可用通道按优先级：

| 通道 | 实测 | 备注 |
|---|---|---|
| 代理 `http://192.168.2.47:7897` | ✅ ping 1.8ms，`git clone --depth 1` 约 **4m29s**，成功拉到 122M 仓库 | 推荐，SOCKS5 也可用但更慢 |
| `https://gh-proxy.com/https://github.com/...` | `ls-remote` 通，完整 clone 比代理慢 | 兜底 |
| `gitclone.com` | ❌ 502 | 不要用 |

```bash
export http_proxy=http://192.168.2.47:7897
export https_proxy=http://192.168.2.47:7897
# apt 另需写 /etc/apt/apt.conf.d/01proxy
```

### 1.3 ⚠️ 清华 `ubuntu-ports` 镜像返回 403

`https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports/` 会让 `apt-get update` 退出码非 0（100）。
**注意**：这是源本身的问题，与代理无关，不要浪费时间排查代理链路。

**对策**：备份后整体替换为官方源（已固化到机器上）：

```bash
cp /etc/apt/sources.list /etc/apt/sources.list.bak.20260921
sed -i 's|https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports/|http://ports.ubuntu.com/ubuntu-ports/|g' /etc/apt/sources.list
```

可用的源：`packages.ros.org`（ROS1 + ROS2）、`repo.download.nvidia.com`、`ports.ubuntu.com`。

### 1.4 103 只有 IPv4

无全局 IPv6 地址、无 IPv6 默认路由。任何依赖 IPv6 的拉取方式都会失败。DNS 用 `223.5.5.5` / `119.29.29.29` 正常。

## 2. ROS1 / ROS2 共存环境

### 2.1 ⚠️ `~/.bashrc` 默认 source foxy

103 同时装了 `/opt/ros/noetic`（347 个包）和 `/opt/ros/foxy`。
`~/.bashrc` 第 139 行是 `source /opt/ros/foxy/setup.bash` —— **默认进入的是 ROS2 环境**。

不隔离直接跑 catkin 会出现难以定位的链接/ Python 路径错误。

### 2.2 必须做 ROS1 环境隔离（`scripts/env.sh`）

`scripts/env.sh` 做三件事，缺一不可：

1. `unset`：`AMENT_PREFIX_PATH`、`COLCON_PREFIX_PATH`、`ROS_VERSION`、`ROS_PYTHON_VERSION`、`ROS_DISTRO`
2. 从 `PYTHONPATH` 里**剔除** foxy 与 `lite_cog_ros2` 相关路径
3. 再 `source /opt/ros/noetic/setup.bash` → `source devel/setup.bash`
4. 设定 `ROS_MASTER_URI=http://127.0.0.1:11311`、`ROS_IP=192.168.1.103`

正确标志（每次进遥控器先确认）：

```
[env] ROS_DISTRO=noetic  AMENT=[]
```

### 2.3 常驻服务不要随手停

| 服务 | 说明 | 能否停 |
|---|---|---|
| `transfer_ros2.service` | 机器人实时链路 | ❌ 不要停 |
| `lite3-monitor.service` | 监控 | ⚠️ 可临时停以腾 CPU |

### 2.4 ⚠️ `roslaunch: command not found`

**现象**：新开终端直接敲 `roslaunch scan_planner lio_relay.launch` → `bash: roslaunch: command not found`。

**根因**：`~/.bashrc` 第 139 行 `source /opt/ros/foxy/setup.bash`，而 **foxy 里根本没有 `roslaunch`**
（ROS2 是 `ros2 launch`）。`roslaunch` 只存在于 ROS1：

```bash
ls -l /opt/ros/noetic/bin/roslaunch   # 存在
ls -l /opt/ros/foxy/bin/roslaunch     # No such file or directory
```

**对策**（二选一）：

```bash
# A. 先建环境，再敲命令
source /home/test/scan_planner/scripts/env.sh
roslaunch scan_planner lio_relay.launch

# B. 用封装脚本（内部自带 source，推荐）
bash /home/test/scan_planner/scripts/start_lio_relay.sh
bash /home/test/scan_planner/scripts/start_scan_real.sh
```

### 2.5 ⚠️ `ROS_MASTER_URI` 两边必须一致，否则各连各的 master

`.bashrc` 第 124 行是 `export ROS_MASTER_URI=http://192.168.1.103:11311`，
而 ROS1 的 `setup.bash` 一 source 就会把它重置成 `http://localhost:11311`。

**坑中坑**：如果在 source 之后才写 `export ROS_MASTER_URI=${ROS_MASTER_URI:-默认值}`，
读到的是被 setup.bash 改过的值，等于没设。必须在 source **之前**把原值存档。

`env.sh` 已处理（source 前存档 → source → 再写回）。正确标志：

```
[env] ROS_DISTRO=noetic  AMENT=[empty]
[env] ROS_MASTER_URI=http://192.168.1.103:11311  ROS_HOSTNAME=192.168.1.103
```

若两边 master 不同，表现为"找不到话题"或 `Unable to contact my own server`。

### 2.6 临时环境的备份与复原

`env.sh` 在改动**任何**环境变量之前，先把原值快照下来：

```bash
source scripts/env.sh          # 建环境，同时生成 logs/env_backup_<时间戳>_<pid>.sh
source scripts/env_restore.sh  # 关环境，精确复原（含"原本未设置"的变量）
```

覆盖的变量：`PATH`、`PYTHONPATH`、`LD_LIBRARY_PATH`、`PKG_CONFIG_PATH`、`CMAKE_PREFIX_PATH`、
`ROS_MASTER_URI`、`ROS_HOSTNAME`、`ROS_IP`、`ROS_DISTRO`、`ROS_VERSION`、`ROS_PYTHON_VERSION`、
`ROS_ROOT`、`ROS_ETC_DIR`、`ROS_PACKAGE_PATH`、`AMENT_PREFIX_PATH`、`COLCON_PREFIX_PATH`、
`ROS_DOMAIN_ID`、`RMW_IMPLEMENTATION`。

设计要点（都是踩过的）：

1. 原本没设的变量写 `unset`，不是写成空串，复原后才不会留下空壳变量；
2. 用 `printf %q` 转义，路径里有空格也不会坏；
3. **同一 shell 内重复 source 不会覆盖快照** —— 否则第二次会把 noetic 的值当成"原值"存下来，复原就失效了
   （靠 `SCAN_PLANNER_ENV_BACKUP` 标记判断）；
4. 未列入的变量（如 ROS2 的 `ROS_DOMAIN_ID` 之外那些）本来就没动，照原样。

实测往返：

```
建立后: ROS_DISTRO=noetic  ROS_DOMAIN_ID=7
恢复后: ROS_DISTRO=unset   ROS_DOMAIN_ID=7  RMW=rmw_cyclonedds_cpp
PATH: 已精确复原
```

查看历史快照：`ls -lt logs/env_backup_*.sh`；指定某一份复原：
`source scripts/env_restore.sh logs/env_backup_0923_023000_1234.sh`

## 3. 拉取与编译

### 3.1 ⚠️ 仓库根目录就是 workspace 根

SCAN-Planner 根目录**没有**顶层 `CMakeLists.txt`，`src/` 下直接就是各 ROS 包。
不要在外面再套一层 `src/`，否则 `catkin_make` 报找不到工作空间。

### 3.2 ⚠️ 分支选错：`ros2-community` 不能用

- `main` 分支：catkin + **ROS1 Noetic** ✅
- `ros2-community` 分支：Ubuntu 22.04 + Humble + C++17 ❌

103 是 Ubuntu 20.04 + Foxy，**不匹配**。实测采用 `main`，commit `348e8a5`。

### 3.3 ⚠️ 编译固定 `-j2`

6 核 / ~6.7 GiB 内存 + 3 GiB swap，PCL、OpenCV 头文件内存占用大。
实测 `-j2` 全量编译约 **14 分钟**，0 错误，内存未打满。**不要用 `-j6`**。

```bash
bash scripts/build.sh     # catkin_make -j2 -DCMAKE_BUILD_TYPE=Release，日志落 logs/
```

### 3.4 编译产物清单（用于确认是否编译完整）

`scan_planner/{scan_planner_node, closed_loop_controller, open_loop_controller, go2_kinematic_sim, go2_gait_publisher}`、
`local_sensing_node/pcl_render_node`、`mockamap/mockamap_node`、`map_generator/map_pub`、`odom_visualization/odom_visualization`。

自定义消息验证：`rosmsg show scan_planner/Bspline`、`rosmsg show scan_planner/DataDisp`。

## 4. 桥接：这是最容易被过度设计的一环

### 4.1 ⚠️ 不需要全量桥接

曾一度认为需要把点云、里程计全部从 ROS1 桥到 ROS2。实际调查结果是：

| 数据源 | 所在栈 | 是否需要桥 |
|---|---|---|
| 雷达驱动 `/home/ysc/lite_cog/drivers/mid360_ws` | **ROS1** | ❌ 否 |
| FAST-LIO `/home/ysc/lite_cog/slam/src/faster-lio` | **ROS1** | ❌ 否 |
| SCAN-Planner | **ROS1** | — |
| 机器人执行链（`transfer_ros2.service` 消费 `/cmd_vel`） | **ROS2** | ✅ 是 |

**真正跨域的只有一个话题**：规划器输出的 `/cmd_vel`（`geometry_msgs/Twist`）。

### 4.2 正确做法：静态单话题桥

ROS1 侧先把输出 remap 到 `/scan_planner/cmd_vel`（避免与 ROS2 侧已有 `/cmd_vel` 撞名），然后：

```bash
ros2 run ros1_bridge parameter_bridge /scan_planner/cmd_vel@geometry_msgs/msg/Twist@geometry_msgs/Twist
```

**不要用 `dynamic_bridge`** —— 它会把两侧所有话题都拉起来，带来大量无用桥接与调试噪音。

### 4.3 ros1_bridge 可直接 apt 安装

不需要离线折腾依赖或源码编译：

```bash
apt install ros-foxy-ros1-bridge      # 实测候选 0.9.7-1focal arm64
```

## 5. 远程 Shell 操作（这两个坑各浪费过一次完整排查）

### 5.1 ⚠️ `pkill -f <pattern>` 会杀掉自己的 SSH 会话

**现象**：命令返回空 stdout、退出码 255 / SIGTERM，看不出任何错误信息。
**原因**：`ssh host '... pkill -f rosmaster ...'` 里，外层 shell 的命令行本身就包含 "rosmaster" 这个字符串，
`pkill -f` 匹配整个命令行 → 把自己的 shell 也杀了，**命令执行结果随之丢失**。

**对策**（二选一）：

```bash
pkill -9 -f 'rosmas[t]er'      # 方括号技巧：正则 rosmaster 不匹配字面 rosmas[t]er
```

或者把清理逻辑**写进脚本文件**再调用（脚本自身命令行不含模式串）。
`scripts/ab_test.sh` 用的就是后者。

⚠️ **`pgrep -f` 同样中招**：`for p in $(pgrep -f "scan_planner/devel/lib"); do kill -9 $p; done`
会把外层 shell 自己列进去并杀掉（表现为命令无输出、退出码 1）。同样用方括号：
`pgrep -f "scan_planner/devel/li[b]"`。

### 5.2 ⚠️ `cd dir && cmd &` 的后台化范围陷阱

```bash
cd /home/test/scan_planner && setsid nohup bash scripts/run_sim.sh > logs/x.log &   # 错
tail -5 logs/x.log      # → No such file or directory
```

`&` 作用于**整条 `A && B`**，于是 `cd` 发生在后台子 shell，前台仍停在原目录。
**对策**：把 `cd` 放进被调用脚本内部（`run_sim.sh` 已经这么做），或前台用 `( cd dir; cmd )` 显式子 shell。

### 5.3 ⚠️ `start_slam.sh` 依赖 gnome-terminal，且 `rviz` 默认开着——无 DISPLAY 必失败

**现象**：在 SSH 终端里 `bash start_slam.sh`，刷三遍：

```
# Option “-x” is deprecated and might be removed in a later version of gnome-terminal.
Unable to init server: Could not connect: Connection refused
# Failed to parse arguments: Cannot open display:
```

**根因（两层，缺一不可）**：

1. `start_slam.sh` 内容就是三条 `gnome-terminal -x bash -c "..."`，没有 X server 就打不开窗口；
2. 即使绕过它，`mapping_c16.launch` 里 `<arg name="rviz" default="true" />` 会拉 rviz，
   headless 下同样起不来。

注意：103 上**确实存在桌面会话**（`who` 能看到 `ysc :0`），但 **SSH 进来的 shell 里 `DISPLAY` 是空的**，
所以"机器有桌面"不代表你的终端能开窗口。

**对策**：用封装脚本 `scripts/start_slam_headless.sh`（内部 source env.sh + slam devel，自动补 `rviz:=false`）：

```bash
cd /home/test/scan_planner && source scripts/env.sh
bash scripts/start_slam_headless.sh
```

等价手动版（两件事都要做）：

```bash
source /home/ysc/lite_cog/slam/devel/setup.bash
roslaunch faster_lio mapping_c16.launch rviz:=false
```

**顺带**：`start_slam.sh` 的另外两个窗口（`gridmap.sh` / `save_map.sh`，交互输入 1 / 2）
是给 nav2 建/存栅格地图用的，**SCAN-Planner 不需要**——它自己维护 occupancy grid。

### 5.4 Windows 侧校验 XML 的路径坑

沙箱 Python 对 `/tmp` 的解析与 Linux 不同，`python3 -c "... '/tmp/xxx.xml'"` 报 `FileNotFoundError`。
**对策**：用完整 Windows 路径：

```bash
python -c "import xml.dom.minidom as m; m.parse(r'C:/Users/19046/AppData/Local/Temp/xxx.xml'); print('XML OK')"
```

## 6. 仿真测试与日志判读 ⭐ 本章最贵的教训

### 6.1 ⚠️⚠️ 伪故障：测量本身会把被测系统测坏

**这是整个过程里代价最高的一次误判。**

第三轮手工测试（同样参数、同样地图）出现了严重劣化：

```
a star error            1139
drone is in obstacle     987
Replan failed 1000         1
日志行数               16374
```

据此一度判定"Lite3 参数是坏的"，准备回退。但改用**无人值守脚本**把完全相同的参数复跑两次：

```
V3a：a star error 0，drone is in obstacle 0，1000-fail 0，616 行  → 干净通过
V3b：a star error 20，drone is in obstacle 0，1000-fail 0，712 行 → 干净通过
```

**真相**：第三轮测试过程中，我在同一窗口里反复执行 `rostopic hz`、`rostopic echo`、`rosparam get` 进行探测。
Jetson 只有 6 核，`pcl_render_node` 的射线投射本来就吃满 CPU，被额外抢占后会拖慢感知闭环，
机器人偏离既定轨迹 → 撞进"刚发现"的障碍 → 触发 `drone is in obstacle` 连锁反应。

**对策（写进流程）**：
1. 度量窗口内**禁止**并行执行任何 `rostopic hz / echo / rosparam get`；
2. 回归判定一律交给无人值守脚本（`scripts/ab_test.sh`）；
3. 任何疑似劣化，**至少复跑两次**再下结论。

### 6.2 地图是确定性的，可以做真正可重复的 A/B

`mockamap` 在 `launch/simulator.xml` 里有固定配置，这让 A/B 对比成立：

| 项 | 值 |
|---|---|
| 随机种子 `seed` | **127**（固定） |
| 起点（navi_mode=1） | `(-19.0, 1.0, 0.25)` |
| 地图尺寸 | 40 × 40 × 5 m |
| 障碍 | type=2 随机盒子，`obstacle_number=500`，`height_min/max=2.0` |

所以**同一用例每次跑出来的地图完全一致**，参数才是唯一变量。

### 6.3 日志里的错误要分级，不要看到 ERROR 就判失败

| 日志 | 位置 | 含义 | 是否算失败 |
|---|---|---|---|
| `a star error` | `dyn_a_star` | 密集地图下 A\* 寻路重试 | ❌ 不算，算法有 `fail_safe` 自愈 |
| `ERROR! the drone is in obstacle. This should not happen.` | `bspline_optimizer.cpp:757` | 从被占点往前回溯，连第 0 个控制点都被占用 → **轨迹起点就在膨胀障碍里** | ✅ 严重信号 |
| `WARN! terminal point ... is in obstacle, skip this planning.` | 同上 `:773` | 终点不可达 | ⚠️ 关注 |
| `Suddenly discovered obstacles. emergency stop!` | FSM | 新发现障碍触发急停 | ⚠️ 关注频次 |
| `Replan failed 1000 times. Emergency stop and wait for a new target.` | FSM | 达到 `max_replan_fail_count` 上限 | ✅ 判定失败 |

**判定口径**：不要只看"有没有 ERROR"，要看 **终态 Pose + 是否出现 1000-fail / EMERGENCY_EXIT**。

### 6.4 ⚠️ `rosparam get` 报 "not set" 多半是名字写错

launch 里的 `<arg name="max_vel">` 到了运行时是**节点私有空间下的多个副本**，直接按 arg 名取会失败：

```bash
rosparam get /scan_planner_node/max_vel            # → ERROR: Parameter is not set
rosparam get /scan_planner_node/manager/max_vel          # → 0.75
rosparam get /scan_planner_node/optimization/max_vel     # → 0.75
```

不确定名字就先列：`rosparam list | grep max_vel`。

### 6.5 地图外 = 占用

`grid_map.h` 的 `getInflateOccupancyFromBuffer()` 在点位**不在地图边界内**时返回 `-1`，
而 `-1` 在 C++ 里是**真值**。所以"出地图边界"会被等价于"被占用"。
排查占用类问题时，别忘了先确认点位是否还在滑动地图范围内（10×10×5 m）。

### 7.7 真机安全网：绝不直接发裸 `/cmd_vel`

**已修**（`run.launch`）：真机模式强制改道：

```xml
<node pkg="scan_planner" name="closed_loop_controller" type="closed_loop_controller" output="screen">

</node>
```

实测验证：真机模式下 `/scan_planner/cmd_vel` 存在、裸 `/cmd_vel` 数量为 **0**。

### 7.8 ⚠️ XML 注释里不能出现连续两个短横

写 launch 注释时用 `-------` 做分隔线会直接让 `roslaunch` 解析失败

**用 `====` 做分隔线。** 本机改 `lio_relay.launch` 时踩过一次。

### 7.9 ⚠️ 步态发布器只能仿真用

真机上不能启动它，已加保护：

```xml

## 10. FAST-LIO 话题适配（本机已实测）

### 10.1 问题现象

`mapping_c16.launch` **不做任何 remap**，节点用的是源码里的默认话题名，
而 SCAN-Planner 真机模式只认 `/LIO/*`。两者对不上：

| SCAN-Planner 期望 | FAST-LIO 实际发布 | 类型 / frame |
|---|---|---|
| `/LIO/odom_vehicle` | `/Odometry` | `nav_msgs/Odometry`，`frame_id=camera_init`，`child_frame_id=body` |
| `/LIO/odom_imu` | ——（无独立 IMU 话题） | 复用 `/Odometry` |
| `/LIO/clouds_lidar` | `/cloud_registered_body` | `PointCloud2`，`frame_id="body"`，**未降采样，更密** |

源码出处（`src/laser_mapping.cc`）：

```
262  pub_laser_cloud_world_  -> /cloud_registered           (frame camera_init, dense_publish_en=false 时是降采样)
263  pub_laser_cloud_body_   -> /cloud_registered_body      (frame body, 来自 scan_undistort_, 完整点数)
265  pub_odom_aft_mapped_    -> /Odometry
266  pub_path_               -> /path                        (c16.yaml 里 path_publish_en=false)
```

选 `/cloud_registered_body` 而不是 `/cloud_registered` 的理由：
`PublishFrameBody()` 发的是 `scan_undistort_` 全量点，而世界系那份在 `dense_publish_en=false`
时走的是 `scan_down_world_`（降采样），局部建图用前者更密。

### 10.2 解决方案：`lio_relay.launch`

新增 `src/planner/plan_manage/launch/lio_relay.launch`，用 `topic_tools relay` 纯转发：

```xml

<node pkg="topic_tools" type="relay" name="lio_odom_imu_relay"     args="/Odometry /LIO/odom_imu"/>
<node pkg="topic_tools" type="relay" name="lio_cloud_relay"        args="/cloud_registered_body /LIO/clouds_lidar"/>
```

好处：**不改动 ysc 的 slam 仓库**，`gridmap.sh` / `save_map.sh` / rviz 照常工作；
relay 直接转发收到的消息对象（不深拷贝），开销可忽略；SLAM 先起来之后再启它也行。

备选：想用世界系点云就 `roslaunch scan_planner lio_relay.launch cloud_in:=/cloud_registered`，
同时 SCAN-Planner 侧要 `cloud_is_world:=true`（`grid_map.cpp` 里 `cloud_is_world=true` 分支
直接把点当世界坐标用，不做旋转平移）。

### 10.3 真机模式下的坐标系约定（重要）

## 11. 雷达驱动选型：这台机器狗装的是 Livox Mid360，不是镭神 C16（已定性）

> 本章是一次**翻案**。此前我依据 FAST-LIO 的 `config/c16.yaml`（`lidar_type: 4`、
> `lid_topic: /rslidar_points`）判定硬件是镭神 C16，进而让用户跑 `start_lslidar.sh`，

### 11.1 现象

[INFO] [lslidar_driver_node-2]: lidar: c16

## 12. ROS1 / ROS2 两套 transfer 抢同一个 UDP 端口（SLAM 不出里程计的真凶）

|---|---|---|

| ROS2 | `lite_cog_ros2/transfer/src/transfer/src/Jetson2Motion.cpp` → `local_port` | **43897** |

而源码里只 `perror("bind error:")` **不退出**：

```cpp
if (bind(socket_fd_, (struct sockaddr *)&listen_addr_, sizeof(listen_addr_)) < 0)
    perror("bind error:");           // ← 打印完继续跑, 节点还活着
```

于是出现最迷惑的状态：**`rosnode list` 里 `/qnx2ros` 在、`/imu/data` 话题在、
但 Publishers 是 None、数据一条没有**。终端往上翻能看到 `bind error: Address already in use`。

### 12.3 对策：二选一

**A. 让 ROS1 接管（推荐，本次联调用，全程不需要 bridge）**

```bash

**B. 保留 ROS2 常驻服务，把 IMU 桥进 ROS1**

```bash
source /opt/ros/noetic/setup.bash && source /opt/ros/foxy/setup.bash

（代价是两条桥 + ros1_bridge 未实测。）

### 12.4 判据：一眼看出是"抢端口"而不是"雷达/FAST-LIO 坏了"

```bash

## 13. 为什么"全走 ROS2"并不会更省事（结论：不要）

有人会想：既然 ROS2 侧已有 livox 驱动 + faster_lio（`lite_cog_ros2` 里都编译好了），
何不干脆全用 ROS2？**不要。** 三条理由：

1. **SCAN-Planner 本体跑不了 ROS2。** `main` 分支是 catkin/ROS1；
   `ros2-community` 分支要求 **Ubuntu 22.04 + Humble + C++17**，103 是 20.04 + Foxy，用不了。
   所以**无论 SLAM 用哪套，规划器永远在 ROS1 侧**。

2. **这决定了桥上要过什么数据**，而这正是关键：

   | 方案 | 需要跨 ros1_bridge 的数据 |
   |---|---|
   | **ROS1 原生**（现状） | 只有一条 `/cmd_vel` Twist（几字节/帧） |
   | **ROS2 SLAM** | 10 Hz × 19968 点 × 26 B ≈ **5 MB/s 的点云 + 里程计** |

   把最重的数据丢到**唯一还没在 103 上实测过的环节**（ros1_bridge）上，是反向优化。

3. **ROS1 链路其实只差一口气。** 已实测：
   - ROS1 livox 驱动 10.04 Hz、19968 点/帧，正常；
   - `pointcloud_preprocess.cc` 的 `C16Handler` 用 `pcl::PointCloud<leishen_ros::Point>`
     只读 **x / y / z / intensity**，`tag`、`line`、`timestamp` 会被 `fromROSMsg` 忽略
     → **字段兼容，一行代码都不用改**；
   - 断的唯一一环就是 `/imu/data`，且原因是端口抢占（第 12 章），不是 ROS1 栈本身的缺陷。

> 真要"全 ROS2"，前提是 SCAN-Planner 有 Foxy/Humble 可用的移植，或 103 升到 22.04 + Humble。
> 现在不是可选项。

## 14. `qnx2ros` 刷 "udp pack length not fit into any" 是良性的（2026-09-30 实测）

### 14.1 现象

`start_transfer.sh` 后终端疯狂刷：

```
[ WARN] [...]: udp pack length not fit into any, 380 220
[ WARN] [...]: udp pack length not fit into any, 16 220
```

**结论：不用管。** 数据链路正常（`/imu/data` 200 Hz、`imu_isalive=True`）。

### 14.2 根因

`qnx2ros.cpp` 按**报文字节长度**分发解析：

```cpp
switch (recv_num_) {
  case sizeof(RobotStateReceived):  ...   // 220
  case sizeof(JointStateReceived):  ...
  case sizeof(HandleStateReceived): ...
  case sizeof(ImuDataReceived):     ...
  default:
    ROS_WARN("udp pack length not fit into any, %d %d",
             recv_num_, sizeof(QNX2ROSProtocol::RobotStateReceived));  // 打印 "380 220"
}
```

机器人新固件会发 380 字节和 16 字节的遥测包，这份老解析器不认识 → 进 `default` 刷 WARN。
**能刷 WARN 恰恰说明机器人在往 103 发流**；IMU 等已知类型照常解析（长度匹配的 case 是静默的）。

副作用：WARN 刷屏会让 `qnx2ros` 占 ~50% 单核。介意的话可以改源码把 default 的 WARN
改成节流（`ROS_WARN_THROTTLE(5.0, ...)`），但那是 ysc 的仓库，**默认不动**。

## 15. 🔴 master 归属：谁拉的 roscore，Ctrl+C 就把谁带走

### 15.1 事故现场（2026-09-30 00:37）

用 `roslaunch rosbridge_server rosbridge_websocket.launch` 起 rosbridge 时，
**master（roscore）是它的子进程**。之后在那个终端 Ctrl+C，日志里依次出现：

```
[roslaunch.pmon] ProcessMonitor exit: killing rosbridge_websocket-2
[roslaunch.pmon] ProcessMonitor exit: killing rosout-1
[roslaunch.pmon] ProcessMonitor exit: killing master          ← master 陪葬
[rosmaster.main] keyboard interrupt, will exit
```

**灾难形态**：`message_transformer` 的 4 个节点（qnx2ros/ros2qnx/nx2app/sensor_checker）
是**孤儿**——进程活着、qnx2ros 还占着 43897 还在收包刷 WARN，但没有 master，
任何话题都注册不上，`rostopic` 全部报 `Unable to communicate with master!`。
表面上"WARN 还在刷"，实际上整条链路是死的，极具迷惑性。

### 15.2 规则

1. **master 必须是独立进程**：先 `roscore`（或由封装脚本用 `setsid nohup` 拉），再起别的。
2. `start-ros1-rosbridge.sh`（2026-09-30 已修复）就是按这个规则写的：
   先探 master，没有就用 `setsid nohup roscore` 独立拉起，再 `roslaunch` rosbridge。
   这样 Ctrl+C 只杀 rosbridge 自身，master 无恙。
3. 直接用 `rosrun rosbridge_server rosbridge_websocket` 也不行——**缺 rosapi 节点**，
   Foxglove 拉话题列表会持续报
   `InvalidServiceException: /rosapi/topics_and_raw_types does not exist`。
   必须用 **launch 版**（自带 rosapi），前提同样是 master 独立。
4. 孤儿清理：`pkill -f "message_transforme[r]"`（方括号防自杀），或
   `ss -tlnp "sport = :43897"` 取 PID 再 kill。

### 15.3 顺带：脱离 ROS1 环境跑 roscore 会直接起不来

```
ModuleNotFoundError: No module named 'rosmaster'
```

SSH shell 的 PYTHONPATH 被 foxy 污染时，`/opt/ros/noetic/bin/roscore` 找不到 noetic 的模块。
起 roscore 也要先 `source scripts/env.sh`。。

## 18. 发目标点后卡在 `EXEC_TRAJ` 不动 —— 闭环控制器在等"航向对准"（2026-09-30）

### 18.1 现象

`bash scripts/goal.sh 1.0 0.0 0.3` 之后，规划器日志显示规划成功：

```
final_plan_success=1
[FSM]: from GEN_NEW_TRAJ to EXEC_TRAJ
[closed_loop_controller] received bspline traj_id=1 duration=4.480
[FSM]: state: EXEC_TRAJ      ← 一直停在这里, 机器人不动
```

### 18.2 根因：**这是设计行为，不是故障**

`closed_loop_controller.cpp` 的主循环里有一段**航向对准**逻辑：

```cpp
const double yaw_err = normalizeAngle(yaw_des - odom_yaw);
const double vyaw_cmd = clamp(kp_yaw * yaw_err, -max_vyaw, max_vyaw);

if (std::abs(yaw_err) > heading_error_threshold)   // 默认 0.8 rad ≈ 46°
{
  publishExecutionFrozen(true);      // /planning/go2_execution_frozen = True
  publishStop(vyaw_cmd);             // 原地转向: linear.x=0, angular.z=vyaw
  last_update_time = now;            // 冻结 exec_time, 不推进轨迹
  return;
}
```

同时 FSM 侧 `updateLocalTrajTimeFreeze()` 会把 `start_time_` 往后推，
于是 `t_cur > duration` 永远不成立 —— **卡在 EXEC_TRAJ 是"等待转到位"的等待态**。

实测参数（`/closed_loop_controller`）：

```
heading_error_threshold: 0.8     # ≈46°, 超过就先原地转
kp_yaw: 1.5      max_vyaw: 1.0      max_vx: 0.75      finish_dist: 0.15
```

**判据**：看 `/scan_planner/cmd_vel`，如果是

```
linear:  {x: 0.0, z: 0.0}
angular: {x: 0.0, z: 1.0}      ← angular.z 为 ±1.0(满舵), linear.x=0
```

就说明控制器正在"请你原地转向"，规划器一切正常。

### 18.3 为什么一直不收敛

因为**最后那条 relay 没开**，机器人收不到 `angular.z`，朝向永远不变 → 误差永远 > 0.8 rad。

### 18.4 处置

| 目的 | 做法 |
|---|---|
| 让狗真的动 | 四腿离地 → `rosrun topic_tools relay /scan_planner/cmd_vel /cmd_vel` → 狗会先原地转向对准，然后前进 |
| **不接机器人**也要验证 | 先**手动把狗转到目标方向**（使 yaw 误差 < 46°），再发目标点；此时 `cmd_vel` 会变成 `linear.x > 0` |
| 目标点方向 | `goal.sh 1.0 0.0 0.3` 是**世界系 +X 方向 1 米**，不是"狗的正前方"。狗若不是朝 +X，必然先转向 |

> 不建议把 `heading_error_threshold` 调大来"跳过"转向——那样会斜着平移，失去航向控制。

### 18.5 顺带

日志里 `Joint state with name: "LB_Joint" was received but not found in URDF`
是 robot_state_publisher 的告警：Lite3 的 `/joint_states` 里有我们这份 DeepRobotics URDF
不存在的关节名。**只影响机器狗模型显示，不影响规划与控制**，可忽略。

## 19. 🔴🔴 狗不动的真正根因：机器人必须在「自主模式 + 心跳」下才吃 `/cmd_vel`（2026-09-30 源码级定位）

> 这一章推翻了上一版对"没反应"的解释。
> 第 18 章说的"航向对准"只是**表象**，即便把狗摆正、把 relay 打开，狗仍然可能一动不动——
> 因为**机器人本体默认处于手柄模式，会直接忽略上位机发来的速度包**。

### 19.1 现象

- `bash scripts/goal.sh 1.0 0.0 0.3` → 规划成功（`final_plan_success=1`），FSM 进 `EXEC_TRAJ`
- `/scan_planner/cmd_vel` 有数据（`linear.x=0` / `angular.z=1.0`）
- 但狗纹丝不动

### 19.2 根因：少了「模式 + 心跳」两个前置条件

看 `ros2qnx` 的转发实现（`lite_cog/transfer/src/message_transformer/src/ros2qnx.cpp`）：

```cpp
void CmdVelCallback(geometry_msgs::TwistConstPtr msg){
  ComplexCMD complexcmd;
  complexcmd.cmd_code = 320; complexcmd.cmd_value = 8; complexcmd.type = 1;
  complexcmd.data = msg->linear.x;      // 线速度 x
  sendto(fd_, &complexcmd, ...);        // -> 192.168.1.120:43893

  complexcmd.cmd_code = 325; complexcmd.data = msg->linear.y;   // 线速度 y
  sendto(...);
  complexcmd.cmd_code = 321; complexcmd.data = -msg->angular.z; // 角速度 z（注意取负）
  sendto(...);
}
```

**103 侧不检查任何模式**，收到 `/cmd_vel` 就发。但这些 UDP 包要生效，机器人本体还必须满足：

1. **处于自主模式**（不是出厂默认的**手柄模式**）
2. **上位机持续发心跳**，否则本体超时后自行退回手柄模式

证据在 Lite3 自带的常量表 `lite_cog/pipeline/src/pipeline_tracking/scripts/constants.py`：

```python
kHeartBeat          = 0x21040001
kSetAutoMode        = 0x21010C03     # 切自主模式
kSetHandleMode      = 0x21010C02     # 切回手柄模式
kSoftEmergencyStop  = 0x21010C0E
kStandLie           = 0x21010202
kContinuousMotionGait = 0x21010C06
kSimpleCMDType      = 0x00
```

以及 `RobotCommander.py` 里心跳线程的实际频率：

```python
def KeepAliveThreadFunc(self):
    while not rospy.is_shutdown() and self.keep_alive:
        self.SendSimpleCommand(constants.kHeartBeat)
        rospy.sleep(rospy.Duration(0.25))        # = 4 Hz，这个频率要照抄
```

### 19.3 完整链路（三个环节缺一不可）

```
/scan_planner/cmd_vel
   └─[① relay]──→ /cmd_vel ──[② ros2qnx]──→ UDP 192.168.1.120:43893
                                                    └─[③ 本体：自主模式 + 心跳]──→ 电机
```

| 环节 | 谁负责 | 检查方法 |
|---|---|---|
| ① relay | `scripts/body_link.sh start` | `bash scripts/body_link.sh status` → relay PID 非空 |
| ② ros2qnx | `start_transfer.sh`（常驻） | `pgrep -x ros2qnx`；`rostopic info /cmd_vel` 的 Subscribers 有它 |
| ③ 模式+心跳 | `scripts/auto_mode.sh auto`（**必须常挂在后台**） | 进程在跑；本体表现为可接受速度指令 |

### 19.4 处置（首次联调推荐"架空"）

```bash

cd /home/test/scan_planner && bash scripts/auto_mode.sh auto

# 终端 B
bash scripts/body_link.sh status     # 先确认 ros2qnx 在跑
bash scripts/body_link.sh start      # 接通速度（脚本内有 3 秒安全确认）

# 终端 C
bash scripts/goal.sh 1.0 0.0 0.0     # 注意 z 用 0，见 19.6
```

紧急处置：

| 目的 | 命令 |
|---|---|
| 让狗立刻停住 | `bash scripts/auto_mode.sh zero`（发 320/325/321 = 0） |
| 交还手柄 | `bash scripts/auto_mode.sh handle` |
| 软急停 | `bash scripts/auto_mode.sh stop` |
| 断开速度链路 | `bash scripts/body_link.sh stop` |

### 19.5 脚本设计要点（踩过的坑都写进注释了）

- **不能 `set -u` 之后再去 `source` ROS 的 setup.bash**：会因为未绑定变量直接终止 shell，
  症状是"脚本跑了但一个字都不输出、exit 1"（与 2.4 同源）。必须 `set +u` → source → `set -u`。
- **判 relay 是否在跑不能只 `pgrep -x relay`**：`lio_relay.launch` 也会起 3 个 `topic_tools/relay`
  （`/Odometry → /LIO/*`），光看进程名会误判成"本体链路已接通"。
  正确做法是先用 `-x` 取 PID，再逐个读 `/proc/<pid>/cmdline` 过滤话题名
  （**绝不能** `pgrep -f "<完整命令行>"`，见 5.1）。
- `auto_mode.py` 走 `/simple_cmd`、`/complex_cmd` 两个 ROS 话题，
  由已经在跑的 `ros2qnx` 转发，**不另开 UDP 端口**，避免和 `RobotCommander.py` 直连 43893 冲突。
- `message_transformer` 的消息不在 scan_planner 的 env 里，包装脚本额外 source 了
  `/home/ysc/lite_cog/transfer/devel/setup.bash`。

### 19.6 顺带：目标点的 z 应该用 0

`/Odometry` 的 body 原点 z ≈ 0（FAST-LIO 的 `camera_init` 就是首帧雷达位置）。
发 `goal.sh 1.0 0.0 0.3` 等于让规划器把终点放在**离地 0.3 m**，对地面机器人没有意义。
**建议发 `1.0 0.0 0.0`**，或与你当前 `/Odometry` 的 z 对齐。

## 20. 规划狂刷 `a star error` / `GEN_NEW_TRAJ → GEN_NEW_TRAJ`（2026-09-30）

### 20.1 现象

日志尾部连续几百次（实测已到 457 次）：

```
[rebo replan]: -------------------------------------457
start:  0.984  -3.21 0.0236, 0 0 0
goal:  0.529  -1.02 0.0138, 0 0 0
[ERROR] a star error
first_optimize_step_success=0
final_plan_success=0
[FSM]: from GEN_NEW_TRAJ to GEN_NEW_TRAJ
```

同时 `/scan_planner/cmd_vel` 全 0 —— 因为**没有一条可用轨迹**，闭环控制器自然不输出。

### 20.2 根因：不是主路径搜索，而是 B 样条 rebound 阶段的绕行 A* 失败

`a star error` 的出处是 `bspline_optimizer.cpp:814`，在优化器发现控制点压在障碍物里、
调用 `AstarSearch` 找绕行路径时打的：

```cpp
ASTAR_RET ret = a_star_->AstarSearch(grid_map_->getResolution(), in, out);
if (ret == ASTAR_RET::SUCCESS) { ... }
else if (ret == ASTAR_RET::SEARCH_ERR && i + 1 < segment_ids.size()) { ... 合并到下一段 ... }
else { ROS_ERROR("a star error"); ... }
```

而 `dyn_a_star.cpp` 的 `ConvertToIndexAndAdjustStartEndPoints` 在**起点压在障碍里**时，
会沿"远离终点"的方向逐步回退；一旦退到地图外就直接返回 false：

```cpp
int occ = checkOccupancy(Index2Coord(start_idx), path_yaw);
if (occ) {
  do {
    start_pt -= start_to_end * step_size_;
    if (!Coord2Index(start_pt, start_idx)) return false;
    occ = checkOccupancy(Index2Coord(start_idx), path_yaw);
    if (occ == -1) { ROS_WARN("[Astar] Start point outside the map region."); return false; }
  } while (occ);
}
```

也就是说：**机器人当前所在的位置，在膨胀地图里被判成了障碍**（或紧邻障碍无处可退）。
注意这个 A* 是**朝向感知**的，用的是我们给 Lite3 设的双圆柱包络
（`double_cylinder_radius=0.18` / `offset=0.12` → 包络 0.60 m × 0.36 m），比无人机大得多，
在贴近障碍时更容易"无处可去"。

### 20.3 诱因：里程计漂到了不该在的地方

本次实测 `/Odometry`：

```
position: {x: 0.984, y: -3.207, z: 0.024}   twist 全 0（狗是静止的）
```

即机器人在**完全没动**的情况下，位姿已经漂到 3.2 米外并稳定在那里（见第 17 章，这是第三次）。
漂过去之后，这个位置在真实地图里可能是墙边/桌下，于是起点被判占据 → A* 全线失败。

### 20.4 处置与判据

```bash
# 判据：三行一起看
timeout 8 rostopic echo -n1 /Odometry | sed -n '6,13p'   # 位置是否合理、twist 是否≈0
tail -c 3000 logs/scan.log | grep -a "rebo replan" -A2   # start/goal 是否落在奇怪坐标
bash scripts/body_link.sh status                          # 顺带确认链路
```

| 情况 | 处置 |
|---|---|
| 位置明显不合理（漂移） | **重启 SLAM + 规划器**（规划器必须一起重启，否则脏地图残留）：`bash scripts/stop_all.sh` → `bash scripts/start_all.sh` |
| 位置合理但周围确实有障碍 | 把狗挪到空旷处，或减小 `double_cylinder_radius/offset` 再试 |
| 目标点本身在障碍里 | 日志会写 `terminal point ... is in obstacle`，换目标点即可 |

> 排查顺序建议：**先看里程计，再看地图，最后才怀疑参数**。
> 位置错了，后面全都白查。

## 23. 🔴 站立是行走的硬性前提，且「有没有走」必须用 `/leg_odom` 判定（2026-09-30 00:0x）

### 23.1 硬前提：只有「力控状态」才吃速度指令

协议文档给的**典型使用顺序**（`lite3_robot_monitor/README.md` §12.7）：

```text
1) 启用控制通道
2) 起立/趴下（0x21010202）→ 让机器人起立
3) 切「自主模式」（0x21010C03）← 关键：否则速度指令无效
4) 开启心跳（250ms 周期，0x21040001）
5) 发送速度指令（320 / 325 / 321）
6) 停止移动 → 停止心跳 → 停用控制通道
```

本机**对照实验**证实了这一条（同一条 `linear.x=0.4` 指令）：

| 狗的姿态 | `/cmd_vel` 是否发出 | `/leg_odom` 位移 | 结论 |
|---|---|---|---|
| 趴着 | ✅ 峰值 0.400 | **0.0000 m** | 本体完全不执行 |
| 起立后 | ✅ 峰值 0.400 | **1.6104 m** | 立刻执行 |

所以流程上必须是：**先确认站立 → 再接通速度**。

### 23.2 按需探针：怎么读本体状态（`scripts/robot_state_probe.py`）

ROS 侧看不到姿态：**`qnx2ros` 解析了 `RobotState` 但只转发 imu/leg_odom/joint_states/ultrasound，
`robot_basic_state` / `robot_gait_state` / `battery_level` 全都没转发**。
所以用一个**一次性探针**：跑几秒、打印、退出，**不常驻、不占端口**。

```bash
printf "\047\n" | sudo -S python3 scripts/robot_state_probe.py eth0 5
# 基本状态 : 3  力控状态（站立就绪，可运动）
# 电量     : 83.0 %
# 世界位置 : x=1.582  y=-0.768  z=0.334
# 姿态 rpy : roll=0.0  pitch=0.2  yaw=-15.2 (度)
```

实现要点（都是踩出来的）：

- **不能 bind 43897**：那个口被 `qnx2ros` 占着；`SO_REUSEPORT` 需要**所有** socket 都设置才生效，
  单方面设置没用。改用 `AF_PACKET` 旁路抓包（复用 `/home/test/monitor/backend/udp_sniffer.py`），
  代价是要 sudo。
- **只认 `code=2305(0x0901)`、长度 220 的包**：同端口还有 `0x0902/0x0903`(108B)、`0x0904`(16B)、
  `0x010901`(52B)，以及**偶发的 `0x0906`(380B)** —— 那个 380 字节的包**不是** RobotState，
  拿它解析会得到一屏垃圾值（也是 `qnx2ros` 刷 `udp pack length not fit into any, 380 220` 的来源）。
- **字段偏移由编译器给出**，别手算：

  ```bash
  g++ -w -o /tmp/off /tmp/off.cpp && /tmp/off   # 用 offsetof(RobotStateReceived, ...)
  # basic_state=12  gait=16  policy=20  rpy=28  pos_world=100
  # motion_state=184  battery=188  ultrasound=204
  ```

`robot_basic_state` 取值（厂商协议表，从 0 起编号）：

| 值 | 含义 | 能否行走 |
|---|---|---|
| 0 | 趴下 | ❌ |
| 1 | 准备起立 | ❌ |
| 2 | 正在起立 | ❌ |

## 24. 🔴 狗「横着走」+ 规划器 `bad_alloc` 崩溃：两个根因（2026-09-30 00:2x 定位）

### 24.1 横走：`max_vy` 允许了四足不该有的横向速度

现象：目标在正前方 1 米，狗却**横着往左走**，落点 `(1.582, -0.768)`（横向偏 0.77 m）。

抓取那段时间规划器实际下发的 `/cmd_vel`（每秒约 100 条）后真相大白：

| 采样点 | linear.x | **linear.y** | angular.z |
|---|---|---|---|
| 起点 | 0.000 | 0.000 | 1.000（原地转向对准） |
| 中段 | 0.089~0.130 | **0.483~0.495** | 0.02~0.09 |
| 后段 | 0.400 | 0.286→0.127 | −0.21→−0.53 |

**`linear.y` 长期顶在 0.49（上限 `closed_loop_controller/max_vy = 0.5`）** —— 规划器一直在要求
"横向移动 0.5 m/s"，狗当然横着走。**不是本体故障，是我们给了它不该有的横向速度指令。**

修复（`advanced_param.xml:117`）：

```xml
<param name="closed_loop_controller/max_vy" value="0.05" type="double"/>   <!-- 原 0.50 -->
```

四足机器人的运动学是「前进 + 转向」，不该有 0.5 m/s 的横向平移。
改后实测 **`linear.y` 从 0.49 降到 −0.022（≈0）**，走的方向立刻正常。

> ⚠️ 别设成 `0.0`：本机在 `max_vy=0` 时连续崩过（见 24.2，后来证实主因是 LIO 发散，
> 但 `0` 这个值仍未经过干净验证）。**用 0.05 这类极小非零值**最稳妥。

## 25. Foxglove 里点云"只有坐标轴 + 一堆散点"——三个原因按序排查

现象：`/cloud_pcd` 有数据、订阅上了，但 3D 面板里只看见三根坐标轴显眼，
其余全是零散小点，看不出墙、桌、门等任何轮廓。

### 25.1 原因一（本次真凶）：PCD 读取错位 255 字节

`view_pcd.sh` 里原来是：

```python
off = f.tell()                                  # 读完头部后的位置 = 数据起点
arr = np.fromfile(f, dtype=dt, count=n, offset=off)   # ❌ 又往后跳了 255 字节
```

**`np.fromfile` 的 `offset` 是"相对当前位置"的**，而 `f` 读完头部后**已经在数据起点**，
再传 `offset=off` 等于整体后移一个头部长度（本机 255 B）→ 每个点的字段全部串位。

- 表现为：俯视图退化成**一条竖线**（所有点挤在几乎同一列），3D 里就是均匀散点，毫无结构。
- **为什么之前没发现**：抽查用的是 `f.seek(off + i*32)` —— **绝对定位**，所以抽样看起来"正确"，
  把 bug 掩盖住了。
- 修复：

  ```python
  arr = np.fromfile(f, dtype=dt, count=n)   # ✅ 不传 offset
  ```

修复前后对比（同一份 `lite3.pcd`）：

| | 修复前 | 修复后 |
|---|---|---|
| 俯视图 | 一条竖线 | 有墙体/空区/成片结构 |
| 有效点 | 统计被脏点拉爆（3.4e38） | 22 502 125 点 |
| 范围 | 贴着阈值 | `x −9.5~12 / y −7.2~12 / z −3.2~6.9` |

> **通用教训**：解析 PCD 时不要在"已 seek 到数据区"的文件对象上再传 `offset`。
> 想跳就用 `f.seek()`，二者别混用。

### 25.2 原因二：显示设置（数据没问题，但你画得太细）

150 万个点撒在 20 m × 20 m × 5 m 的空间里，默认 1~2 px 的点径看过去就是"灰尘"。

Foxglove 3D 面板里改三处：

| 设置 | 默认 | 改成 |
|---|---|---|
| **Point size** | 1~2 | **3~5** |
| **Color by** | 单一颜色 | **`z`** 或 `intensity`（立刻有层次） |
| **Fixed frame** | — | `camera_init` 或 `map`（已补恒等静态 TF，两者等价） |
