## 0. 一句话结论：远程查看要用 **ROS1 的 rosbridge**，不是 ROS2 的

```bash
# ❌ 不要用这个（ROS2 版，只暴露 ROS2 话题）
ros2 launch rosbridge_server rosbridge_websocket_launch.xml

# ✅ 用这个（数据在 ROS1 域里）
cd /home/test/scan_planner && source scripts/env.sh
roslaunch rosbridge_server rosbridge_websocket.launch port:=9090
# 或者用现成封装（默认 9090, PORT=9091 可换）:
bash /home/test/foxglove/start-ros1-rosbridge.sh
```

**为什么**：走方案 A（ROS1 接管本体链路）之后，点云、里程计、栅格地图、轨迹**全在 ROS1**。
  
ROS2 的 rosbridge 只暴露 ROS2 话题，Foxglove 连上去**看不到任何 SCAN-Planner 的东西**。
  
（103 上两套都装了：noetic 0.11.17 与 foxy 1.3.1，别选错。）

Foxglove Studio 连接设置：

```
打开连接 → Rosbridge → 指定 ROS 1（选错会解析失败）→ ws://192.168.1.103:9090
```

**两种连接方式怎么选**（Foxglove 的 "ROS 1" vs "Rosbridge"）：

| 维度                      | 原生 ROS 1（11311）✅ 优先     | Rosbridge（9090）备选         |
| ----------------------- | ----------------------- | ------------------------- |
| 数据编码                    | TCPROS 二进制直传            | JSON + base64 文本          |
| 点云开销（19968 点/帧 × 10 Hz） | ≈ 原始大小                  | JSON 膨胀数倍                 |
| 103 的 CPU 负担            | 低                       | 高（编解码在 Jetson 上跑，可能拖慢规划器） |
| 网络要求                    | 能直连 master **和每个节点的端口** | 只需一个 9090 端口              |

原生连接的两个必踩点：

1. **ROS_HOSTNAME 不是填 103 的用户名**！它是"你电脑对外声明的地址"（103 的节点要回连它）。
     
   填你电脑的 WLAN IP（如 `192.168.2.47`，`ipconfig` 查），填错订阅会没数据。
2. Windows 防火墙首次弹窗时要**放行 Foxglove**，否则 103 回连不进来。

结论：同网段能通就用**原生 11311**；防火墙/跨网段连不通再退回 9090。

🔴 **master 归属规则**（2026-09-30 踩过）：

- 不要在 master 也由它拉起的情况下用裸 `roslaunch` 起 rosbridge —— 那个终端 Ctrl+C 会把 **master 陪葬**，

| 规划轨迹     | `/planning/bspline`、`/planning/data_display` |
| 速度指令     | `/scan_planner/cmd_vel`                      |

**3D 面板参考系怎么选**（2026-09-30 实测定稿）：

本链路有三个坐标系，TF 关系是 `world ==(恒等)== camera_init → body → base_link → rslidar`
（`world→camera_init`、`body→base_link` 两个恒等静态 TF 已固化进 `lio_relay.launch`，
`camera_init→body` 由 faster_lio 每帧广播，`base_link→rslidar` 是 livox launch 的静态 TF）：

| 设置 | 选什么 | 为什么 |
|---|---|---|
| 固定参考系 | **`world`** | `/grid_map/*`、`/planning/bspline`、goal 的 frame_id 都是 `world`（SCAN-Planner 的世界系）；它数值上就是 faster_lio 的 `camera_init` |
| 显示参考系 / 跟随目标 | **`body`** | 机体系，有实时 TF；配合"跟踪模式=位姿/位置"就是跟车视角 |
| 跟踪模式 | 位姿 或 位置 | 位姿=镜头贴着机体朝向；位置=只跟随平移 |

> 之前建议"固定参考系选 camera_init"是**错的**——漏了 SCAN-Planner 的消息 frame_id 叫 `world`，
> 而 `world` 原本是孤立帧（TF 树里没有），这正是 Foxglove 报
> "缺少从参考系 \<world\> 到参考系 \<body\> 的变换"的原因。已用恒等静态 TF 修复。

变换列表里带红 ❗ 的 `/base_link`、`/rslidar`（带斜杠前缀）是 livox 静态 TF 的遗留写法，无害，忽略。

**TF 里帧很多是正常的** —— TF 是"所有坐标系及它们之间关系"的总账本，每个节点都会往里注册。
本链路的完整帧来源（2026-09-30 源码核对）：

| 来源 | 帧 | 性质 |
|---|---|---|
| faster_lio（SLAM） | `camera_init → body` | 动态 ~100 Hz，里程计位姿 |
| `lio_relay.launch`（我们补的桥） | `world → camera_init`、`body → base_link` | 恒等静态，把 SCAN-Planner 的 world 和 URDF 接进同一棵树 |
| livox 驱动 | `base_link → rslidar`（遗留斜杠名） | 静态，雷达安装位 |
| robot_state_publisher + Lite3 URDF + `/joint_states` | `base_link → {FL/FR/HL/HR}_{HIP/THIGH/SHANK/FOOT}`、TORSO 等 | 四腿运动学，随关节角实时变 |
| **odom_visualization**（SCAN-Planner 自带可视化节点） | `world → base`；`base → laser / vision / height`（45°/90° 斜下） | **给仿真里的"无人机模型"画的传感器视锥装饰帧**（`odom_visualization.cpp:388-391`），真机没用，可忽略 |
| grid_map | `world → sliding_map` | grid_map 自己广播的**动态 TF**（`grid_map.cpp:1015`），表示滑动地图窗口中心 |

（更正：之前写"sliding_map 是包围盒的 frame"是推断错了——按源码 bbox Marker 的 frame 也是 `mp_.frame_id_`=world，sliding_map 是单独广播的一个动态 TF。）

**参考系已经"统一"过了** —— 不是改名，而是用 TF 声明等价：
`world == camera_init`（恒等静态）、`body == base_link`（恒等静态），
所以 TF 树是一条链：`world == camera_init → body == base_link → rslidar`。
`world` 与 `camera_init`、`body` 与 `base_link` 是**两对同义异名**（前者来自 SCAN-Planner，
后者来自 faster_lio / Lite3 URDF），数值等价。Foxglove 固定参考系选 `world` 就能同时看到
SLAM 点云、栅格地图和机器狗模型，不需要再统一。

**点云话题速查**（2026-09-30 实测 frame_id）：

| 话题 | 谁发的 | frame | 内容 | 什么时候看 |
|---|---|---|---|---|
| `/cloud_registered` | faster_lio | `camera_init` | 世界系点云，`dense_publish_en=false` 时**降采样** | 看全局地图全貌（稀疏） |
| `/cloud_registered_body` | faster_lio | `body` | 机体系点云，**未降采样更密** | 看当前帧细节 |
| `/LIO/clouds_lidar` | relay | `body` | 就是 `/cloud_registered_body` 的转发（内容不变） | SCAN-Planner 建局部栅格吃的就是它 |
| `/cloud_registered_effect_world` | faster_lio | `camera_init` | 只含**参与配准的有效点**（`scan_effect_pub_en` 才发） | 空/很少 → 特征不足、SLAM 在退化 |
| `/grid_map/occupancy` | SCAN-Planner | `world` | 占用栅格（体素中心当点云发） | 看"墙在哪" |
| `/grid_map/occupancy_inflate` | SCAN-Planner | `world` | **膨胀后**的占用（按 0.18 m 包络膨胀） | 规划器实际避障用的就是这个 |
| `/grid_map/depth_cloud` | SCAN-Planner | `world` | 当前帧深度点云 | 看传感器此刻看到什么 |
| `/grid_map/unknown` | SCAN-Planner | `world` | 未观测区域 | 通常没内容，可忽略 |
| `/grid_map/sliding_map_bbox` | SCAN-Planner | `world`（Marker 线框） | 滑动窗口包围盒 | 调试用 |

你真正会用的只有 4 个：**`world`（固定参考系）、`body`（跟随）、`camera_init`（=world 数值等价）、`base_link`（本体原点）**。
其余的放着不管即可；嫌乱可以把 run.launch 里的 odom_visualization 节点注释掉。

**若下拉里没有 `world` / `camera_init` / `body`**（2026-09-30 踩过）：主机侧 TF 是好的
（`/tf` ~105Hz + `/tf_static` 4 个发布者，`rostopic echo -n1 /tf` 能看到 camera_init→body），
是 **Foxglove 客户端没收到**。处理顺序：
1. Foxglove 完全断开重连（必要时重启 Foxglove）—— 旧连接可能停在重启前的状态；
2. Windows 防火墙放行 Foxglove（专用+公用都放）：103 的节点要**主动回连**你电脑
   `192.168.2.47` 的随机端口，被拦就表现为"连得上但没数据/帧不全"；
3. 自检：加一个 Raw Messages 面板订阅 `/tf`，能看到 `camera_init→body` 流说明链路通；
4. 重连后固定参考系下拉才会出现 `world`，选它。

### T7 下发导航点

**Foxglove 里发**：Publish 面板 → topic `/move_base_simple/goal`
  
→ type `geometry_msgs/PoseStamped` → **frame_id 填 `world`** → 填 xyz。

**或命令行**（等价）：

```bash
cd /home/test/scan_planner && source scripts/env.sh
bash scripts/goal.sh 2.5 0.0 0.0      # z 用 0；距离 >= 1.5 m
```

> `navi_mode=1` 订阅的就是 `/move_base_simple/goal`（`scan_replan_fsm.cpp:104`），两种方式等价。

⚠️ **两个硬性约束（踩过才知道）**：

| 约束 | 说明 |
|---|---|
| **z 用 0** | `/Odometry` 的 body 原点 z ≈ 0，发 `x y 0.3` 等于让终点离地 0.3 m |
| **距离 ≥ 1.5 m** | 目标太近会触发 `Need to reallocate time` → 加速度超限 → 规划反复失败；累计 1000 次后 FSM 会自己进 `EMERGENCY_STOP` 再退回 `WAIT_TARGET`，**此时重新发一个更远的目标点即可**（详见避坑第 21 章） |

> 若日志出现 `Replan failed 1000 times / Emergency stop and wait for a new target`，
> 不是崩溃，是重规划失败计数触顶（ `fsm/max_replan_fail_count=1000`）。

⚠️ **发完目标点后如果一直刷 `[FSM]: state: EXEC_TRAJ` 而机器人不动 —— 先看 `/scan_planner/cmd_vel`**：

```bash
rostopic echo -n1 /scan_planner/cmd_vel
```

若是 `linear.x: 0.0` + `angular.z: ±1.0`，说明**规划已成功**，闭环控制器在等"航向对准"
（误差 > `heading_error_threshold` 默认 0.8 rad ≈ 46° 时先原地转向，同时冻结轨迹时间）。
因为没接机器人，它永远转不到位。**这是设计行为，不是卡死**（详见避坑第 18 章）。

想验证但不想接机器人：**先把狗手动转到目标方向**（让 yaw 误差 < 46°）再发目标点，
此时 `cmd_vel` 会变成 `linear.x > 0`。注意 `goal.sh 1.0 0.0 0.3` 是**世界系 +X 方向 1 米**，
不是"狗的正前方"。

⚠️ **注意目标点的 z**：`/Odometry` 的 body 原点 z ≈ 0，`goal.sh x y 0.3` 等于让终点离地 0.3 m。
**建议 `bash scripts/goal.sh 1.0 0.0 0.0`**。

## 3·5 T6·5 —— 让狗站起来（🔴 行走的硬性前提，别跳过）

**只有 `robot_basic_state = 3（力控/站立就绪）` 时，速度指令才会被执行。**
本机对照实验：同一条 `linear.x=0.4`——趴着时 `/leg_odom` 位移 **0.0000 m**，起立后 **1.61 m**。

```bash
bash scripts/standup.sh          # 带门禁：先探状态，只有确认「趴下(0)」才发起立
bash scripts/standup.sh --check  # 只读取状态，不发起立指令
```

`robot_basic_state` 速查：`0 趴下 / 1 准备起立 / 2 正在起立 / **3 力控（可走）** / 4 正在趴下 / 5 失控保护 / 6 姿态调整 / 8 AI状态 / 9 回零`。

⚠️ **起立指令 `0x21010202` 是「起立/趴下」toggle**：狗站着时发它会**直接趴下**。
所以**千万不要盲发** —— 要么用 `standup.sh`（自带门禁），要么先目视/探针确认是趴着。
脚本遇到 `1/2` 会等待、`6/5` 等非预期状态会拒绝并提示改用**手柄起立**。

## 4. 最后一步：把速度指令接给机器人（两个动作，缺一不可）

### T8-a 让机器人进入「自主模式 + 心跳」🔴

```bash
cd /home/test/scan_planner
bash scripts/auto_mode.sh auto        # 另开一个终端，一直挂着；Ctrl+C 时自动零速度 + 退回手柄
```

**不开这个，后面 relay 接上了狗也不会动**——机器人默认在手柄模式，直接忽略上位机速度包；
且自主模式期间必须以 4 Hz 持续发心跳，否则本体会自行退回手柄模式（详见避坑第 19 章）。

### T8-b 接通速度链路

```bash
bash scripts/body_link.sh status      # 确认 ros2qnx 在跑
bash scripts/body_link.sh start       # /scan_planner/cmd_vel -> /cmd_vel（脚本内有 3 秒安全确认）
bash scripts/body_link.sh stop        # 断开
```

链路全貌（三个环节）：

```
/scan_planner/cmd_vel --[relay]--> /cmd_vel --[ros2qnx]--> UDP 192.168.1.120:43893 --[本体自主模式+心跳]--> 电机
```

⚠️ **四腿离地**再开；确认速度数值合理（≤ 0.75 m/s）再落地。
走方案 A 时命令通路是纯 ROS1（ROS1 `ros2qnx` 订阅 `/cmd_vel` → 120:43893 → 机器人），
**不需要 ros1_bridge**。

任何时候要狗立刻停住：`bash scripts/auto_mode.sh zero`；交还手柄：`bash scripts/auto_mode.sh handle`。

## 5. 收尾

按**反序**关：T8 → T7 → T5 → T4 → T3 → T2 → T1（T1 握着 roscore，最后关）。

```bash
bash scripts/body_link.sh stop                       # 先断速度链路
bash scripts/auto_mode.sh zero                       # 发一次零速度
bash scripts/auto_mode.sh handle                     # 交还手柄
bash scripts/stop_all.sh --all                       # 停掉规划/雷达/SLAM/relay/roscore（省电）
sudo systemctl enable --now transfer_ros2.service    # 恢复常驻服务
```

> 🔋 **电量不足要收工时**：103 是狗载 Jetson，跑着的 ROS 节点全在吃狗的电。
> 除了上面这套，还建议把狗**趴下并关机充电**；下次开工再从第 1 节重跑一遍预检
> （`bash scripts/preflight.sh`），因为重启后 `transfer_ros2.service` 会自己回来抢 43897。

## 6. 排障速查

| 现象                                                                | 原因                                 | 处置                                                                            |
| ----------------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------------------------------- |
| 重启后 `/imu/data` 又没了                                               | `transfer_ros2.service` 自启抢了 43897 | 第 1 节：`sudo systemctl stop transfer_ros2.service`                             |
| `roslaunch: command not found`                                    | 终端默认 foxy                          | `source scripts/env.sh`                                                       |
| `incomplete lslidar packet read: 60 bytes`                        | 起错驱动                               | 换 `start_livox.sh`                                                            |
| `start_slam.sh` 报 Cannot open display                             | gnome-terminal + headless          | 用 `start_slam_headless.sh`                                                    |
| `start_transfer.sh` 刷 `udp pack length not fit into any, 380 220` | **良性**：新固件的 380/16 字节遥测包老解析器不认识    | 不用管，链路是通的                                                                     |
| `Unable to communicate with master!` 但 WARN 还在刷                   | master 被某个 roslaunch 的 Ctrl+C 带走了  | 杀孤儿 `pkill -f "message_transforme[r]"` → 独立 `roscore` → 重起 transfer（避坑第 15 章） |
| roscore 报 `No module named 'rosmaster'`                           | 起它时没 source ROS1 环境                | 先 `source scripts/env.sh`                                                     |
| Foxglove 连上但看不到 `/grid_map/*`                                     | 连成了 ROS2 的 rosbridge               | 改连 ROS1 的 9090                                                                |
| Foxglove 报 `InvalidServiceException: /rosapi/...`                 | rosbridge 缺 rosapi 节点              | 用修好的封装脚本（launch 版自带 rosapi）                                                   |
| Foxglove 连上解析失败                                                   | Rosbridge 连接里 ROS 版本选错             | 显式选 **ROS 1**                                                                 |
| 规划器狂刷 a* error / Replan failed                                    | ① 真被围住 ② **并发探测伪故障**               | 停掉 `rostopic hz`/`echo` 后重跑再判断                                                |
| 机器人突然动                                                            | 裸 `/cmd_vel` 被发布                   | 确认只有 T7 那条 relay 在转发                                                          |
| `/Odometry` 位置出现天文数字（几十万米级）                               | **faster_lio 发散**：SLAM 运行中狗被剧烈搬动/雷达被遮挡 → 退化 | T3 重启 SLAM，随后 T5 也重启（清脏地图）；起 SLAM 后别搬动狗                            |
| 3D 视图里出现一条**很长的黄线**（从 camera_init 拉到别的帧）              | 那是 **轨迹**（`/odom_visualization/path`、`/path`），长度=位移；说明又漂了（如 z 为负、跑到地下） | 同上重启 SLAM+规划器；不想看就在 3D 面板取消这两个图层                                   |
| 规划器**连续几百次** `a star error` + `from GEN_NEW_TRAJ to GEN_NEW_TRAJ`，`cmd_vel` 全 0 | 里程计漂到了障碍区（狗静止但位姿在几米外）→ rebound 阶段的绕行 A* 无处可去 | 先看 `/Odometry` 位置；不合理就 `stop_all.sh` + `start_all.sh`（避坑第 20 章） |
| relay 开了、规划在发速度，**狗仍然不动**                                   | 机器人在**手柄模式**，或心跳断了它自己退回去了 | `bash scripts/auto_mode.sh auto` 常挂后台（避坑第 19 章） |
| `bash scripts/xxx.sh` 一个字都不输出、exit 1                            | 脚本在 `set -u` 下 source 了 ROS 的 setup.bash | 改成 `set +u` → source → `set -u`（避坑 19.5） |
| 规划成功了一次就不动了，日志停在 `EXEC_TRAJ`                                | 目标点 1 米左右时不会;若 `linear.x=0/angular.z=±1` 则是航向对准 | 前者等它跑完；后者详见避坑第 18 章 |
| 每次 `first_optimize_step_success=1` 但 `final_plan_success=0`，日志紧跟着 `Need to reallocate time` + `acceleration limit exceeded ... > 1.5` | 目标点太近（< 1.5 m），重分配时间后峰值加速度超 `max_acc + acc_tolerance = 1.5` | 改发 ≥ 1.5 m 的目标点；已进 EMERGENCY_STOP 就**重新发目标点**（不用重启，避坑第 21 章） |
| 日志停刷 `wait for goal.`                                              | FSM 已回 `WAIT_TARGET`（正常待命，或上次失败后自动复位） | 直接发新目标点即可 |
| 重启命令报"已在跑，跳过"但服务其实没起来                                 | 杀掉 roslaunch 后 master 里**节点名会残留几秒**，只按节点名判定会误判 | `start_all.sh` 已改为"进程 + 节点"双重判定                                               |

**判据（一眼区分"没数据"和"数据被 ROS2 收走"）**：

```bash
rostopic hz /rslidar_points    # 有 → 雷达 OK
rostopic hz /imu/data          # 无 → 本体链路断了
ros2 topic hz /imu/data        # 有 → 流量被 ROS2 那份收走, 坐实端口抢占
```
