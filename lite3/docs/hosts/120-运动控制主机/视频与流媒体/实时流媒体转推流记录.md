## 1. 目标与结果

将 120 本机已有的 RTSP 视频流转换为 RTMP/FLV 并推送到：

```text
输入：rtsp://127.0.0.1:8554/test
输出：rtmp://172.31.68.227:1936/live/lite3
```

**流名称（stream key）登记**

| 项目 | 值 |
| --- | --- |
| 流名称 / stream key | `lite3` |
| 完整推流地址 | `rtmp://172.31.68.227:1936/live/lite3` |
| RTMP 服务器 | `172.31.68.227:1936`（应用名 `live`） |
| 对应机型 | Lite3 机器狗（stream key 以机型命名） |
| 曾用值 | `robotdog`，2026-09-09 19:13 改为 `lite3`；2026-09-21 连单元 `Description` 也同步改为 Lite3，至此 `robotdog` 已不出现在任何生效配置中 |

> ⚠️ **不要只看文档判断当前推的是哪个流名**，以实际进程命令行或脚本内容为准：
> `ps -eo pid,cmd | grep '[g]st-launch-1.0.*rtmpsink'`

已部署独立的**系统级**转发服务（2026-10-17 前为用户级，见文首变更说明），数据链路如下：

```text
/dev/video0
  -> rtsp_stream.service（GStreamer + MediaMTX）
  -> rtsp://127.0.0.1:8554/test
  -> rtmp-forward.service（H.264 depay / parse / FLV mux）
  -> rtmp://172.31.68.227:1936/live/lite3
```

转发不重新打开 `/dev/video0`，也不重新编码视频；它仅从已存在的本机 RTSP 流读取 H.264、去 RTP 封装、解析后封装为 FLV 再推送。这样不会与原始采集进程争用摄像头设备。

## 2. 手工运行 `./mediamtx` 报端口占用的原因

- RTSP TCP `:8554`；
- RTP/RTCP UDP `:8000`、`:8001`；
- HLS TCP `:8888`；
- WebRTC TCP `:8889`；
- RTMP TCP `:1935`；
- SRT UDP `:8890`。

因此在 `/home/ysc/rtsp_stream` 再执行 `./mediamtx` 会创建第二个实例。第二个实例无法绑定已被现有实例占用的 UDP `:8000`，遂输出 `bind: address already in use` 并正常退出。该错误不代表原始推流失败。

不要在服务运行时手工启动第二份 MediaMTX。需要重启原视频服务时使用：


## 5. 更换 RTMP 推送地址

**应修改转发脚本的 `target_url` 后重启服务；不要直接运行管线尾部。**

当前运行中的 `rtmp-forward.service` 会持续执行 `/home/ysc/rtsp_stream/rtmp_forward.sh`，其默认目标由以下变量决定：

```bash
target_url="${RTMP_TARGET_URL:-rtmp://172.31.68.227:1936/live/lite3}"
```

脚本会自动把 `live=1` 附加到 `rtmpsink` 的 `location` 属性。因此更换地址时，`target_url` 只写 RTMP 基础 URL，**不要**把 `live=1` 写进变量值。例如，更换为新服务器和新 stream key 时：

```bash
# 编辑脚本，只修改这一行的默认地址
nano /home/ysc/rtsp_stream/rtmp_forward.sh

target_url="${RTMP_TARGET_URL:-rtmp://新服务器地址:端口/应用名/新流名}"

# 仅检查 shell 语法，不运行推流
bash -n /home/ysc/rtsp_stream/rtmp_forward.sh

# restart 会先停止旧 RTMP 会话，再按新地址启动；无需手工先 stop
sudo systemctl restart rtmp-forward.service
```

只改脚本时无需执行 `sudo systemctl daemon-reload`；该命令仅在修改 `rtmp-forward.service` 单元文件后才需要。

不应直接运行下列片段：

```bash
rtph264depay ! h264parse config-interval=-1 ! \
flvmux streamable=true ! \
rtmpsink location='rtmp://服务器/应用/流名 live=1'
```

原因如下：

1. 它缺少 `rtspsrc` 输入，单独执行不是完整的 GStreamer 管线；
2. 即使补全输入后手工运行，也会绕过 `rtmp-forward.service` 的重连和状态管理；
3. 旧服务仍在运行时会产生两个并行 RTMP 推送，旧目标不会自动停止。

更换后立即核验新目标：

```bash
systemctl show rtmp-forward.service -p ActiveState -p MainPID -p NRestarts
ss -tnp | grep '新服务器地址:端口'
curl -I http://127.0.0.1:8888/test/index.m3u8
```

`ActiveState=active`、`NRestarts=0`、新目标的 TCP `ESTAB` 会话以及本机 HLS 返回 200，分别证明服务、转发进程、网络连接和源流仍正常。最后仍须在新 RTMP 服务端确认 stream key 已入流。

## 7. 开机自启与常驻模式（linger）

> ⚠️ **本节（linger）自 2026-10-17 起不再适用于本转推服务。**
> 外推已迁移为**系统级**单元，开机自启由 `systemctl enable` 保证，**不依赖 linger、也不依赖登录会话**。
> 以下内容保留仅供历史对照（若将来还有其它用户级服务需要常驻，方法仍然适用）。

转发服务**曾**是用户级 systemd 单元。用户级单元默认只在用户**有登录会话**时才存在——
SSH 一断开，`user@<UID>.service` 被拆除，推流随之停止。
当时要让它在后台持续运行且开机自启，必须为该用户开启 **linger（常驻）**。

> 2026-09-21 之前 `Linger=no`，表现为：每次新 SSH 会话里服务的 `ActiveEnterTimestamp`
> 都是「刚启动」，推流无法持续。开启后该现象消失。

### 7.1 开关位置

| 项目 | 位置 |
| --- | --- |
| 落盘标志文件 | `/var/lib/systemd/linger/ysc`（root 创建，文件存在即表示已开启；**重启后仍然有效**） |
| 查询当前值 | `loginctl show-user ysc \| grep -i Linger` |
| 单元文件 | `/home/ysc/.config/systemd/user/rtmp-forward.service` |
| 开机自启链接 | 由 `systemctl --user enable` 写入，位于 `~/.config/systemd/user/default.target.wants/` |

### 7.2 启用方式

需 root 或具备 sudo 权限的账户执行：

```bash
# 1) 开启常驻：立即拉起 user@<UID>.service，且开机后无需登录即启动
sudo loginctl enable-linger ysc

# 2) 确认转发服务已设为开机自启
systemctl --user enable rtmp-forward.service

# 3) 立即启动（若尚未运行）
systemctl --user start rtmp-forward.service
```

### 7.3 生效范围

- **作用于**：`ysc` 的全部**用户级** systemd 单元，即 `~/.config/systemd/user/` 下、由 `systemctl --user` 管理的服务（本例为 `rtmp-forward.service`）。
- **不作用于**：系统级服务。源流采集 `rtsp_stream.service` 由 root 的 systemd 管理，本来就随系统启动，与 linger 无关。
- **持续性**：linger 标志写在 `/var/lib/systemd/linger/`，**重启后保持有效**；配合已 `enable` 的单元，即可实现开机自动推流。

### 7.4 验证常驻是否真的生效

开一个**新的** SSH 会话后查看：

```bash
systemctl --user show rtmp-forward.service -p ActiveState -p MainPID -p ActiveEnterTimestamp
```

判定标准：

- `ActiveEnterTimestamp` **不随新会话变化**（仍是之前那个时间）→ 常驻已生效；
- 若每次新会话都显示一个「刚刚」的时间戳 → 说明 linger 未开启，服务只是被本次登录带起来的。

### 7.5 关闭与回退方法

| 目的 | 命令 |
| --- | --- |
| 仅临时停推流（保留开机自启与常驻） | `systemctl --user stop rtmp-forward.service` |
| 取消开机自启并立即停止 | `systemctl --user disable --now rtmp-forward.service` |
| 关闭常驻（重启后不再自动拉起用户级服务） | `sudo loginctl disable-linger ysc`（即删除 `/var/lib/systemd/linger/ysc`） |
| 完全移除该转发服务 | 删除 `~/.config/systemd/user/rtmp-forward.service` 后执行 `systemctl --user daemon-reload`（脚本 `/home/ysc/rtsp_stream/rtmp_forward.sh` 需另行删除） |
| 改回流名 `robotdog` | 编辑脚本 `target_url` 为 `rtmp://172.31.68.227:1936/live/robotdog`，再 `systemctl --user restart rtmp-forward.service` |

> 回退提醒：关闭 linger 后，若此时没有 `ysc` 的登录会话，用户级服务会停止；
> 下次登录后才会再次启动。

## 8. 网络不可达时自动关闭推流（保护机制）

网络环境变更导致 `172.31.68.227:1936` 连不上时，不应让它无限重连刷日志。
2026-09-21 起，脚本内置了「连续失败即自停」逻辑。

### 8.1 判定方式

**每轮推流之前**，先用 `python3` 做一次到目标 `host:port` 的 TCP 连通性探测
（不依赖 GStreamer 的报错，因此目标彻底不可达时能立刻判定）。

- 探测成功 → 计数清零，正常启动 `gst-launch-1.0` 推流；
- 探测失败 → 连续失败计数 +1，记录一条日志，等待 `RETRY_SECONDS` 后重试；
- **连续失败达到 `MAX_CONNECT_FAILURES`（默认 3）→ 写出完整诊断日志，以退出码 `3` 退出。**

### 8.2 为什么退出码 3 就等于“关闭服务”

> ⚠️ **2026-10-17 起该 exit-3 豁免已删除。** 原配置会让"上游抖动 → 脚本 exit 3"之后
> systemd **不再重启 = 永久停推**，只能靠整机重启恢复（这正是本服务历史停机的主要原因）。
>
> 原配置（已废弃）：
> ```ini
> RestartPreventExitStatus=3   # 退出码 3 时不再重启 —— 这就是“自动关闭”
> SuccessExitStatus=3          # 视为正常停止，单元最终为 inactive（而非 failed）
> ```
>
> 现行配置：**`Restart=always` + `RestartSec=30`** —— 上游瞬断时 30s 退避自动重连自愈；
> 上游长时间不可达时也只每 30s 试一次，不会空转刷日志。

所以脚本退出后 `systemd` 会在 30s 后重新拉起、推流自愈，一般**不再需要人工 `start`**。

### 8.3 日志

- 位置：`/home/ysc/rtsp_stream/logs/rtmp_forward.log`（默认，可用 `RTMP_FORWARD_LOG` 修改）
- 每条均带 ISO8601 时间戳，同时写入日志文件与 systemd journal（`systemctl status` / `journalctl -u rtmp-forward.service` 可见）
- 触发自停时会额外写出一段诊断块，内容包括：时间、主机、用户、目标地址、源流地址、
  连续失败次数与阈值、最近一次转发进程退出码、`ip route get <目标>`、网卡地址、
  到目标的 TCP 会话、源流 HLS 自检结果。

### 8.4 可调参数

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `MAX_CONNECT_FAILURES` | `3` | 连续探测失败多少次后自动关闭 |
| `RETRY_SECONDS` | `5` | 每次失败后的等待秒数 |
| `PROBE_TIMEOUT` | `5` | 单次 TCP 探测的超时秒数（内含 socket 3s 超时） |
| `RTMP_FORWARD_LOG` | `/home/ysc/rtsp_stream/logs/rtmp_forward.log` | 日志文件路径 |

修改方式（推荐用 drop-in，避免被后续改动覆盖）：

```bash
sudo systemctl edit rtmp-forward.service
# 写入：
# [Service]
# Environment=MAX_CONNECT_FAILURES=5
sudo systemctl restart rtmp-forward.service
```

### 8.5 自停后如何恢复

1. 先看日志确认原因：`tail -50 /home/ysc/rtsp_stream/logs/rtmp_forward.log`
2. 确认网络恢复：`ip route get 172.31.68.227`、`ss -tnp | grep 172.31.68.227:1936`
3. 重新启动：`sudo systemctl start rtmp-forward.service`
   （现行配置为 `Restart=always`，多数情况 systemd 会在 30s 内自动拉起；此步仅用于立即恢复）

### 8.6 验证记录（2026-09-21 00:52）

用不可达地址 `192.0.2.1:1936`（RFC 5737 保留网段）做自测，阈值设为 2：

- 日志完整记录了路由（`via 192.168.0.1 dev wlan0 src 192.168.0.197`）、网卡、
  “无已建立连接”、源流 `HLS=200`；
- 用临时单元验证 systemd 行为：结果为 `ActiveState=inactive`、`NRestarts=0`、
  `Result=success` —— **确认没有被重启**，即自动关闭生效；

## 9. 安全注意事项

不要将带鉴权信息的 RTMP URL、访问令牌或密码直接提交到仓库或共享脚本。若目标地址日后带有密钥，应将其放入权限为 `0600` 的用户级环境文件，并通过 systemd `EnvironmentFile=` 引用；修改后重新启动 `rtmp-forward.service`。

开启 linger 意味着该用户的用户级服务会在无人登录时持续运行，应确保这些服务的日志与网络行为是可接受的，避免遗留无人看管的常驻进程。

## 10. 2026-10-17：迁移为系统级 systemd（与 M20 技术逻辑统一）

### 10.1 背景与目的

120 的外推原先由**用户级**单元托管，开机自启依赖 `loginctl enable-linger ysc`。
为与 M20 主机（AOS 196）的 `m20video.service` 统一技术逻辑，将其迁移为**系统级**单元：
自启不再依赖 linger，运维命令统一为 `systemctl`（无 `--user`、无需 `XDG_RUNTIME_DIR`）。

### 10.2 迁移顺序（★关键）

两套并存会**重复推流、撞流名 `live/lite3`**。因此顺序铁律是**先停用户级 → 再起系统级**：

```bash
# 1) 停用用户级（先停推，防双推）
export XDG_RUNTIME_DIR=/run/user/$(id -u)
systemctl --user stop    rtmp-forward.service
systemctl --user disable rtmp-forward.service
systemctl --user stop    rtmp-conn-guard-user.timer
systemctl --user disable rtmp-conn-guard-user.timer

# 2) 部署并启用系统级
sudo install -m 0644 rtmp-forward.system.service /etc/systemd/system/rtmp-forward.service
sudo systemctl daemon-reload
sudo systemctl enable --now rtmp-forward.service
sudo systemctl enable --now rtmp-conn-guard.timer
```

### 10.3 系统级单元要点

- `User=ysc`、`WorkingDirectory=/home/ysc/rtsp_stream`，ExecStart 仍为 `/home/ysc/rtsp_stream/rtmp_forward.sh`（**脚本与推流地址均未变**）；
- `Restart=always` + `RestartSec=30`（不再有 exit-3 豁免，见第 8.2 节）；
- `KillMode=mixed`、`TimeoutStopSec=25`、`OOMScoreAdjust=-300`（风格对齐 M20 `m20video.service`）；
- 日志走 journal（`SyslogIdentifier=rtmp-forward`），脚本自身仍写 `/home/ysc/rtsp_stream/logs/rtmp_forward.log`。

**看门狗必须显式传参**：

```ini
# /etc/systemd/system/rtmp-conn-guard.service
ExecStart=/usr/local/sbin/rtmp-conn-guard.sh rtmp-forward.service
```

`rtmp-conn-guard.sh` 的 `DEFAULT_SVC` 候选为 `m20video.service / rtsp_stream.service`，
120 上**没有 `m20video`** → 会自动**误选 `rtsp_stream`**（该服务不产生 `:1936` 连接）
→ 看门狗失效，且僵尸时会**重启错的（本地 RTSP）服务**。显式传参从根本上杜绝此问题；
脚本候选表也已补入 `rtmp-forward` 作双保险（`m20video, rtmp-forward, rtsp_stream`）。
