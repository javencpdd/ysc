# Lite3 分层避障架构设计与 3D 升级硬件评估

> 范围：参考 [SCAN-Planner](https://github.com/wuyi2121/SCAN-Planner)（Spatial Collision-Aware Local Planning for Route-Guided Long-Range Quadruped Navigation，arXiv:2606.19555）为 Lite3 规划模块设计"全局 2D + 局部 3D"分层避障架构；并评估全局地图由 2D 升级为 3D（体素/ESDF）的开销与硬件结论。
>
> 依据：`docs/operations/host-maintenance.md`、`docs/operations/indoor-patrol-fire-detection.md`、`docs/hosts/103-感知导航主机/`；SCAN-Planner 仓库 README 与论文（采集时间 2026-09-15）。
>
> 凡笔记未覆盖或需实机标定的量，标注 **[待确认]**；性能数字为**量级估算**，须实机实测校准。

## 1. SCAN-Planner 参考要点

### 1.1 它是什么

| 项 | 内容 |
| --- | --- |
| 定位 | **局部规划器**（local planner），为上层任务提供"稳健的底层规划基础"；不是完整导航栈 |
| 全称 | Spatial Collision-Aware Local Planning for Route-Guided Long-Range Quadruped Navigation |
| 平台 | 四足机器人，默认参数针对 Unitree Go2 |
| ROS | Ubuntu 20.04 + ROS Noetic（社区提供 `ros2-community` 分支） |
| 许可 | **Apache 2.0**（优于 AGPL 类，商业友好） |
| 基础 | 构建于 [EGO-Planner](https://github.com/ZJU-FAST-Lab/ego-planner)；地图表示受 [ROG-Map](https://github.com/hku-mars/ROG-Map) 启发；定位用 FAST-LIO2 |

### 1.2 三个可直接借鉴的设计

| 设计 | 内容 | 对本项目价值 |
| --- | --- | --- |
| **偏航感知双圆柱 footprint**（yaw-aware twin-cylinder） | 用两个圆柱模拟细长机身，做全身碰撞评估 | Lite3 同样是细长机身；比单球/单圆柱膨胀更贴合，窄通道通过性更好 |
| **膨胀 3D 占用地图 + 稀疏查询** | 不使用 ESDF；把占用地图按圆柱半径与垂直间隙膨胀，轨迹优化时做稀疏碰撞查询 | **关键**：3D 化不等于必须上 ESDF，绕开最大的算力开销来源 |
| **机器人中心滑动地图 + 边界回退**（robot-centric sliding map with boundary fallback） | 固定大小窗口以机器人为中心，环形缓冲零拷贝滑动；目标不可达时用单层虚拟自由体素越界搜索，取边界体素作为回退目标 | **内存有界**，适合大规模/长距离；内置死胡同恢复机制 |

### 1.3 论文报告的验证条件与结果

- **机载计算机：NVIDIA Jetson Orin NX**，感知、建图、规划、控制全部在其上实时运行。
- **传感器**：Unitree Go2（内置雷达更换为 **Livox Mid-360**），深度相机 **RealSense D435**。
  > 与本项目高度一致：103 侧已有 `start_livox.sh`（MID360）与 RealSense 启动脚本。
- 密集障碍对比（每场景 50 次试验）：

| 方法 | 成功率 SR↑ | 碰撞率 CR↓ | SPL↑ |
| --- | --- | --- | --- |
| EGO-Planner-2D | 0.96 | 0.04 | 0.88 |
| EGO-Planner-3D | 0.76 | 0.24 | 0.75 |
| CMU-Planner | 0.92 | 0.08 | 0.86 |
| ART-Planner | 0.44 | 0.56 | 0.31 |
| **SCAN-Planner** | **1.00** | **0.00** | **0.95** |

> 论文未提供模块级耗时表与地图分辨率/窗口尺寸的具体数值；**这些是本项目需自行标定或向作者确认的参数**。

## 2. 分层避障架构设计

### 2.1 总体分层

```text
┌─────────────── 全局层（Global / 2D）───────────────┐
│ 输入：2D 占用栅格 lite3.yaml/.pgm（pcd2grid, 0.05m）│
│ 定位：hdl_localization（NDT_OMP，PCD 点云地图）     │
│ 规划：Nav2（dr_nav2）→ 全局路径                     │
│ 输出：nav_msgs/Path，frame_id = "map"               │
│ 频率：低频，按需/周期重规划（1–5 Hz）                │
└──────────────────┬──────────────────────────────────┘
                   │ ① 全局路径裁剪 + 前瞻
                   │ ② TF: map → base_link
                   ▼
┌─────────── 接口层（Route Adapter）────────────┐
│ 沿全局路径取前瞻距离内的窗口                  │
│ 选取/插值局部目标（sub-goal）                 │
│ 输出 PoseStamped + 路径段（供局部层做引导）   │
└──────────────────┬──────────────────────────────┘
                   ▼
┌───────── 局部层（Local / 3D）—— SCAN 式 ─────────┐
│ 输入：MID360 点云 + RealSense 深度 + 里程计      │
│ 地图：robot-centric 3D 滑动占用地图 + 膨胀层     │
│ 规划：多项式初始化 → 双圆柱碰撞检测 →            │
│       （必要时）投影 A* 引导 → B 样条优化        │
│ 输出：geometry_msgs/Twist → /cmd_vel             │
│ 频率：高频，10–20 Hz                             │
└──────────────────┬──────────────────────────────┘
                   ▼
        VOA SafetyController（保留）→ /cmd_vel_corrected
                   ▼
        transfer/jetson2motion → UDP 43893 → 120 jy_exe
```

### 2.2 与现有模块的对应关系

| 层 | 现有实现 | 升级方向 |
| --- | --- | --- |
| 全局层 | Nav2 + `lite3.yaml`（已有） | 基本不动，仅输出路径给接口层 |
| **接口层** | **无，需新建** | `route_adapter`：路径裁剪、前瞻、sub-goal 选取、重规划仲裁 |
| 局部层 | VOA（2.5D 高度图 `6×4`，分辨率 `0.05`，只做安全限速） | 升级为 SCAN 式 3D 局部规划器；**VOA 保留为下游安全兜底** |

> 设计取舍：不废弃 VOA。它已验证、且是安全链路一环；局部 3D 规划器输出 `/cmd_vel`，VOA 继续在其后做地形/超声安全修正。两层职责不重叠。

### 2.3 数据接口与协作方式

#### ① 全局 → 局部：路径下发

| 项 | 建议 |
| --- | --- |
| 话题 | `/global_path`（`nav_msgs/Path`）由 Nav2 输出；`route_adapter` 订阅后发布 `/local_goal`（`geometry_msgs/PoseStamped`）与可选的 `/local_path_segment`（`nav_msgs/Path`） |
| 全局路径是否直接下发全部 | **否**。局部层只消费**前瞻窗口内**的路径段；全量路径交给局部层会造成目标在滑动地图之外、频繁触发边界回退 |
| 前瞻距离 `lookahead` | 建议 **3.0 m**，需小于局部滑动地图半径（例：窗口 40 m 时取 3–5 m 合理）；机器人速度越高取越大 **[待确认]** |
| sub-goal 选取规则 | 在路径上取距机器人 `lookahead` 处、且**位于当前局部地图内**的点；若被新障碍物遮挡，则取路径上最后一个在自由空间内的点 |
| 下发时机 | 周期（1–5 Hz）+ 事件（全局路径更新、局部重规划失败）双触发 |

#### ② 局部 → 全局：失败上报与重规划请求

| 上报 | 触发 | 全局层响应 |
| --- | --- | --- |
| `LOCAL_BLOCKED` | 局部规划连续失败超阈值 | 请求 Nav2 全局重规划 |
| `DEAD_END_RECOVERING` | 触发边界回退 | 暂停推进 sub-goal，等待恢复完成 |
| `GLOBAL_PATH_INFEASIBLE` | 全局路径段长期不可通行 | 请求全局重规划或跳过当前路径点 |

#### ③ 坐标系

| 坐标系 | 用途 | 备注 |
| --- | --- | --- |
| `map` | 全局路径、2D 栅格、路点 | 由 hdl_localization 提供 |
| `odom` | 里程计 | `leg_odom` / `leg_odom2` |
| `base_link` | 机器人本体 | 局部 3D 滑动地图以机器人为中心 |
| `rslidar` / `camera_link` | 传感器 | 需 TF 静态变换 |

**关键**：全局路径在 `map` 系，局部地图以 `base_link` 为中心。`route_adapter` 必须用 TF `map → base_link` 做变换后再交给局部层。**[待确认]** 实际 TF 树结构（建议 `ros2 run tf2_tools view_frames` 导出核对）。

#### ④ 数据格式

| 数据 | 类型 | 说明 |
| --- | --- | --- |
| 全局路径 | `nav_msgs/Path` | `frame_id="map"` |
| 局部目标 | `geometry_msgs/PoseStamped` | 建议统一到 `map` 系，由局部层自行转到局部系，避免歧义 |
| 点云 | `sensor_msgs/PointCloud2` | MID360 / RealSense；建议先降采样再进局部层 |
| 里程计 | `nav_msgs/Odometry` | 高频状态估计 |
| 局部轨迹输出 | `nav_msgs/Path` 或直接 `geometry_msgs/Twist` | 若保留 VOA，输出 `/cmd_vel` 即可 |
| 状态/事件 | 自定义 `LocalPlannerStatus` | 含 `blocked_count`、`fallback_active`、`replan_reason` |

### 2.4 局部规划失败与重规划触发条件

参考 SCAN-Planner 的两级机制，建议如下：

| 级别 | 触发条件 | 动作 |
| --- | --- | --- |
| **L1 轨迹重优化** | 双圆柱碰撞检查发现轨迹存在碰撞段 | 在入口/出口点间做投影 A* 搜索，构造反弹方向对，重新优化 B 样条。**不上报全局** |
| **L2 边界回退** | 反弹搜索时，原始 sub-goal 在滑动地图内不可达（典型：sub-goal 位于新观测障碍物之后，或超出地图边界） | 临时扩单层虚拟自由体素 → 允许 A* 越界 → 取离开处边界体素为回退目标 → 在真实地图内重规划。上报 `DEAD_END_RECOVERING` |
| **L3 全局重规划** | 连续 N 次（建议 **N=3**，或持续 **3 s**）无法生成可行轨迹 | `route_adapter` 请求 Nav2 重规划；回退策略：先尝试全局重规划，仍失败则跳过当前路径点并记录（复用巡检方案 4.3 的"有限重试 + 跳过"） |
| **L4 任务中断** | 连续多个路径点失败，或定位状态异常 | 按巡检方案 4.2 / 4.3 停止任务并告警 |

> **务必避免** ROS 1 `TaskTransfer` 式的无限重试；每一级都要有计数上限与超时。

## 3. 全局地图 2D → 3D 的开销评估

### 3.1 先明确：3D 化有两种，开销差一个量级

| 方案 | 说明 | 推荐度 |
| --- | --- | --- |
| **A. 局部 3D 滑动地图**（SCAN-Planner / ROG-Map 式） | 仅维护机器人周围的固定大小窗口，内存有界，**ESDF-free** | **推荐** |
| **B. 全局 3D 体素 + ESDF** | 整栋建筑维护体素地图与距离场 | **不推荐**（见下） |

### 3.2 内存开销（量级估算）

以室内多房间约 **40×40 m、层高 3 m** 为典型场景：

| 方案 | 参数 | 体素数 | 内存 |
| --- | --- | --- | --- |
| 现状 2D 栅格 | 40×40 m @ 0.05 m | 0.64 M cell | **≈ 1 MB** |
| A. 局部 3D 滑动窗口 | 40×40×8 m @ 0.10 m | 12.8 M voxel | 占用 13 MB + 膨胀层 13 MB ≈ **26 MB** |
| A. 局部 3D 滑动窗口（更细） | 40×40×8 m @ 0.05 m | 102 M voxel | 占用 102 MB + 膨胀 102 MB ≈ **204 MB** ⚠ |
| B. 全局 3D 体素（占用） | 40×40×3 m @ 0.10 m | 4.8 M voxel | **≈ 5 MB**（若用哈希/八叉树可更低） |
| B. 全局 3D + ESDF（float32） | 同上 | 4.8 M voxel | ≈ 19 MB（ESDF）+ 5 MB（占用）≈ **24 MB** |
| B. 更大场景 100×100×5 m @0.10m + ESDF | | 50 M voxel | 占用 50 MB + ESDF **200 MB** ⚠ |

**结论**：**内存不是主要瓶颈**——robot-centric 滑动窗口天然有界，全局 3D 若用哈希/八叉树也可控。真正的瓶颈在**算力与实时性**。

### 3.3 算力与实时性开销（量级估算，须实测）

| 环节 | 2D（现状） | 3D 局部滑动（方案 A） | 3D 全局 ESDF（方案 B） |
| --- | --- | --- | --- |
| 点云预处理 | 轻量 / 仅 VOA 用 | 降采样 + 坐标变换，**5–15 ms/帧** | 同左 |
| 地图更新（raycasting + 膨胀） | 2D costmap，1–5 ms | **10–30 ms/帧**（膨胀层随偏航更新时更贵） | 占用更新同左，**ESDF 传播额外 50–500 ms** ⚠ |
| 规划 | Nav2 A*/DWA，10–50 ms | B 样条优化 + 稀疏碰撞查询，**5–20 ms** | ESDF 梯度优化 10–30 ms（但被 ESDF 构建拖累） |
| 可持续频率 | 10–20 Hz | **10–20 Hz** | 通常 **< 5 Hz** ⚠ |
| 主要风险 | — | 点云频率 × 分辨率敏感 | ESDF 更新是系统级瓶颈 |

**关键判断**：ESDF 的构建/传播是 3D 化的最大陷阱。EGO-Planner 系列（含 SCAN-Planner）的核心贡献正是**绕开 ESDF**——用膨胀占用地图 + 稀疏碰撞查询替代距离场。因此：

> **若做 3D 升级，应选择方案 A，且明确不引入全局 ESDF。**

### 3.4 关键性能瓶颈（按严重性排序）

1. **点云处理频率与 raycasting**（最严重）
   - MID360 标称 20 万点/秒；若 10 Hz 输入则每帧约 2 万点，raycasting 遍历量 ∝ 点数 × 射线长度/体素尺寸。
   - 缓解：输入降到 **5–10 Hz**；体素分辨率 **0.10 m**（而非现状 0.05 m）；先做体素降采样再更新。
2. **膨胀层更新**（含偏航感知）
   - 机器人转向时膨胀层需重算，是 CPU 尖峰来源。
   - 缓解：限制膨胀更新频率（如 5 Hz）；缓存多档偏航的膨胀模板 **[待确认 SCAN-Planner 具体做法]**。
3. **规划耗时**
   - B 样条优化本身不贵；投影 A* **仅在碰撞时触发**，不应是稳态开销。若投影 A* 频繁触发，说明前瞻/sub-goal 选取不合理，需调参而非加算力。
4. **与烛火检测争抢 GPU**
   - 检测方案形态 A 占用 1–1.5 GB GPU 显存、每帧 30–60 ms。局部规划主要是 CPU/几何计算，**冲突有限**，但内存与 CPU 仍会争抢。

## 4. 硬件评估与结论

### 4.1 现有 103 主机算力推定

笔记实测：`board t186ref`、L4T **R35.4.1**、**6 个在线 ARMv8 核**、最大 **1907.2 MHz**、`lscpu` 报 NVIDIA vendor、内存 **6.7 GiB**。

| 候选 | CPU | AI 算力 | GPU | 内存 | 与实测吻合度 |
| --- | --- | --- | --- | --- | --- |
| **Jetson Xavier NX (8GB)** | 6× Carmel @1.9 GHz | **21 TOPS** | 384-core Volta | 8 GB | **高**：6 核 + 1.9 GHz + NVIDIA 自研核，且支持 L4T R35 |
| Jetson TX2 | 2×Denver2 + 4×A57 | 1.33 TFLOPS | 256-core Pascal | 8 GB | 中：6 核吻合，但**官方仅支持到 L4T R32**，与 R35 矛盾 |
| Orin NX 8GB | 6× A78AE | 117 TOPS | 1024-core Ampere | 8 GB | 低：应为 t234 |

> **推定：103 大概率是 Jetson Xavier NX（8 GB）**。但 `t186ref` 与 L4T R35 存在矛盾，**必须实机核验**：
> `cat /proc/device-tree/model`、`cat /etc/nv_tegra_release`、`sudo tegrastats`、`cat /sys/devices/gpu.0/*`

### 4.2 与 SCAN-Planner 验证平台的差距

| 维度 | 现有 103（推定 Xavier NX） | SCAN-Planner 平台（Orin NX 16GB） | 差距 |
| --- | --- | --- | --- |
| AI 算力 | 21 TOPS | 100–157 TOPS | **约 1/5** |
| CUDA 核心 | 384（Volta） | 1024（Ampere） | 约 1/2.7 |
| CPU | 6× Carmel @1.9 GHz | 8× A78AE @2.0 GHz | 约 1/2.5–1/3（A78 单核显著强于 Carmel） |
| 内存 | 8 GB（可用 6.7 GiB） | 16 GB | 1/2 |

**且 SCAN-Planner 平台上"感知、建图、规划、控制全部实时运行"是完整占用**——我们的 103 还要额外承担：hdl_localization（NDT）、Nav2、VOA、烛火检测（YOLOv8n TensorRT）、Transfer。

### 4.3 结论

| 结论 | 内容 |
| --- | --- |
| **方案 A（局部 3D 滑动地图，ESDF-free）在现有 103 上是否可行** | **有条件可行，但余量严重不足**。单独跑局部规划可以，叠加烛火检测 + 定位 + Nav2 后，CPU 与内存都会吃紧。必须先实测。 |
| **方案 B（全局 3D + ESDF）** | **明确不可行**。ESDF 更新 50–500 ms 会直接摧毁实时性，且内存可达数百 MB。 |
| **是否需要外接算力模块** | **需要**（若确定要走 3D 局部规划且保留机载检测）。 |
| **推荐型号** | **Jetson Orin NX 16GB**，而非 AGX Orin。理由见 4.4。 |
| **最省钱的替代路径** | 先把烛火检测从 103 卸载到 120（RK3588 NPU，形态 B），释放 103 的 GPU/CPU 给规划；若仍不够再上 Orin NX。 |

### 4.4 为什么推荐 Orin NX 而不是 AGX Orin

用户提到"外接 Jetson AGX Orin 一类的算力模块"。我的建议是 **Orin NX 16GB 更合适**：

| 维度 | Orin NX 16GB | AGX Orin 32/64GB |
| --- | --- | --- |
| AI 算力 | 100–157 TOPS | 200–275 TOPS |
| 尺寸 | **70 × 45 mm** | 100 × 87 mm |
| 功耗 | **10–25 W** | 15–60 W |
| 与现有 103 的机械/接口兼容 | **与 Xavier NX 同为 70×45 mm、接口兼容，很可能可直接换模块升级** | 尺寸与供电差异大，需重新设计载板与结构 |
| 散热/供电 | 四足机器人可接受 | 高功耗对电池与散热压力大 |
| 官方参考 | **SCAN-Planner 论文验证平台即 Orin NX**，风险最低 | 无直接参考 |
| 是否 overkill | 否 | **是**：局部规划以 CPU/几何计算为主，并非纯 AI 吞吐，275 TOPS 用不满 |

> **最优先的路径是"换模块"而非"外接"**：若 103 确为 Xavier NX 且载板兼容，直接更换为 Orin NX 16GB 是最省事、风险最低的升级（无需改结构、改供电、改连线）。**[待确认]** 载板型号与 Orin NX 兼容性。

### 4.5 分级实施建议

| 阶段 | 动作 | 目标 |
| --- | --- | --- |
| **P0（零成本）** | 实机核验 103 型号；跑通现有 Nav2 + VOA；记录 CPU/内存基线（含烛火检测） | 拿到真实余量数据 |
| **P1（低风险）** | 仅做**接口层** `route_adapter` + 保留 2.5D VOA，不引入 3D；验证全局→局部的数据链路与重规划仲裁 | 先验证协作机制，不碰算力 |
| **P2（中风险）** | 在 103 上接入 SCAN-Planner 类局部 3D 规划器，**先降配运行**（点云 5 Hz、体素 0.10 m、窗口缩小），并把烛火检测卸载到形态 B | 验证 3D 局部规划在现有硬件的可行性 |
| **P3（硬件）** | 若 P2 达不到 10 Hz，升级 Orin NX 16GB（优先换模块，其次外接） | 满足实时性 |

## 6. 一句话总结

**架构上采用"全局 2D 栅格（Nav2）+ 新建 route_adapter 接口层 + 局部 3D 机器人中心滑动占用地图（SCAN-Planner 式，双圆柱 footprint、ESDF-free、边界回退）"，VOA 保留为下游安全兜底；重规划分 L1 重优化 / L2 边界回退 / L3 全局重规划 / L4 任务中断四级并全部设上限。**

**硬件上：3D 化不要碰全局 ESDF（50–500 ms 更新是致命瓶颈）；局部 3D 滑动地图内存有界（约 26 MB @0.10 m）可行，但现有 103（推定 Xavier NX，21 TOPS）相对 SCAN-Planner 验证平台 Orin NX 差约 5 倍且还要承载检测/定位/Nav2，余量不足——推荐升级或外接 Orin NX 16GB（而非 AGX Orin，后者尺寸/功耗/overkill），并优先尝试"同尺寸换模块"；在此之前，先把烛火检测卸载到 120 的 RK3588 NPU 以释放 103 资源。**
