# 网络、多容器与硬件

## ROS 1 网络的关键事实

ROS Master 默认使用 11311 端口，但节点发现彼此后会建立点对点连接，并可能使用动态端口。因此：

```text
能访问 Master ≠ 能访问所有节点
```

只执行 `-p 11311:11311` 不能自动解决完整的多机 ROS 通信。

## 单容器

入门阶段最稳定：

```bash
export ROS_MASTER_URI=http://localhost:11311
unset ROS_IP
unset ROS_HOSTNAME
```

所有节点都在同一网络命名空间中，不需要声明外部地址。

## Compose 多容器

示例：

```yaml
services:
  master:
    image: osrf/ros:noetic-ros-core
    command: roscore
    environment:
      ROS_MASTER_URI: http://master:11311
      ROS_HOSTNAME: master

  workstation:
    image: ros1-noetic-dev
    depends_on:
      - master
    environment:
      ROS_MASTER_URI: http://master:11311
      ROS_HOSTNAME: workstation
      DISPLAY: host.docker.internal:0.0
      QT_X11_NO_MITSHM: "1"
    stdin_open: true
    tty: true
```

Compose 默认网络能解析服务名，因此各节点使用 `master`、`workstation` 等内部名称。若需要从 Windows 或局域网中的机器人直接连接这些节点，仍需重新设计可达地址和路由。

## `ROS_IP` 与 `ROS_HOSTNAME`

原则只有一个：节点声明的地址必须能被其他相关节点回连。

| 场景 | 建议 |
|---|---|
| 单容器 | 不设置 `ROS_IP`/`ROS_HOSTNAME`，使用 localhost |
| Compose 内部 | 使用 Docker 可解析的服务名 |
| 原生 LAN 多机 | 使用稳定、可路由的 LAN IP 或主机名 |
| Windows Docker + 真实机器人 | 优先评估 host networking、WSL mirrored 或原生 Linux |

不要在多机网络中把 `ROS_IP` 设置为 `127.0.0.1`；对方会把它解释为对方自己的 loopback。

## VPN 与防火墙

VPN、终端安全软件和 Windows 防火墙都可能影响 Docker backend、X11 和机器人 LAN。异常时检查：

```powershell
docker network ls
docker network inspect bridge
```

容器内：

```bash
ip -brief addr
ip route
cat /etc/resolv.conf
getent hosts host.docker.internal
```

排错时可以短暂做隔离测试，但不要把永久关闭防火墙作为解决方案。

## GPU：计算与图形是两条链路

容器能运行 `nvidia-smi` 或 CUDA 测试，只能说明计算设备可见；它不保证 VcXsrv 下的 RViz/Gazebo 已使用完整硬件图形加速。

分别检查：

```bash
nvidia-smi
glxinfo -B
```

第一个验证 CUDA/设备访问，第二个查看 X11/OpenGL 实际 renderer。不要把两者混为一谈。

## USB 设备

Windows → WSL → Docker 的典型路径是：

```text
Windows USB
  → usbipd-win
  → WSL2 中出现设备
  → Docker --device 映射
  → 容器内驱动访问
```

Windows PowerShell：

```powershell
usbipd list
usbipd bind --busid <BUSID>
usbipd attach --wsl --busid <BUSID>
```

如果尚未安装 `usbipd`：

```powershell
winget install --interactive --exact dorssel.usbipd-win
```

WSL 中先确认：

```bash
lsusb
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
```

只有 WSL 已看到设备，才继续将明确设备传入容器：

```powershell
docker run --device=/dev/ttyUSB0 ...
```

优先使用 `--device`，不要为了省事直接使用 `--privileged`。

## 串口权限

容器或 Linux 主机中执行：

```bash
ls -l /dev/ttyUSB0
id
getent group dialout
stat -c '%g' /dev/ttyUSB0
```

根据设备实际 GID 为容器进程增加补充组：

```text
--group-add <gid>
```

Compose 中可以使用：

```yaml
group_add:
  - "<gid>"
```

当项目开始持续使用 LiDAR、RealSense、CAN、串口 MCU 或多机 LAN 时，迁移到原生 Linux 往往比继续叠加透传层更可靠。
