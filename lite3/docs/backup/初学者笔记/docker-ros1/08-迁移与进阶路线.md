# 迁移与进阶路线

## 为什么要分阶段迁移

Windows Docker Desktop 很适合低风险地学习 Linux、Docker 和 ROS 1，但它叠加了 Windows、WSL2、容器、X Server、网络与设备透传。随着图形和硬件需求增长，这些边界会逐渐成为主要成本。

推荐演进路线：

```text
Windows Docker + VcXsrv
  → 完成 ROS Graph、catkin、TF/URDF 和基础 RViz
  → WSL2 + WSLg 或原生 Ubuntu
  → 完成 Gazebo、SLAM、Navigation 和传感器接入
  → Linux-native Docker + 受支持的 ROS 2
```

## 迁移判断表

| 需求 | 是否继续 Windows Docker | 建议 |
|---|---|---|
| turtlesim、node/topic/service | 是 | 保持当前环境 |
| Python/C++ ROS 节点、catkin | 是 | 源码挂载并用 Git 管理 |
| TF/URDF、偶尔 RViz | 是 | 继续使用并关注 GLX |
| 每天大量使用 RViz | 可以 | 开始评估 WSLg |
| 大型 PointCloud、复杂 Gazebo | 不优先 | WSLg 或原生 Linux |
| USB 串口 | 可做但层级较多 | 小规模实验可继续 |
| LiDAR、RealSense、CAN | 不建议长期使用当前架构 | 原生 Linux |
| 多机 ROS 与真实移动机器人 | 网络较复杂 | 原生 Ubuntu 优先 |
| 稳定实时性 | 不适合 | 原生 Linux 与专用实时方案 |
| 长期新项目 | 不建议继续 Noetic | 迁移到受支持的 ROS 2 |

## 迁移时保留什么

迁移不是重新开始。应保留：

- Git 中的 `src/` 源码；
- Dockerfile、Compose 和依赖清单；
- launch、URDF、RViz 配置与测试数据；
- 镜像 digest 或离线镜像备份；
- 已验证的 ROS topic、service 和 TF 接口约定；
- 排错日志与验收清单。

以下内容通常需要调整：

- `DISPLAY` 与图形转发方式；
- `ROS_IP`、`ROS_HOSTNAME` 和网络拓扑；
- USB/串口设备路径、udev 规则和组权限；
- 用户 UID/GID 与工作空间 ownership；
- GPU 驱动和容器 runtime 配置。

## ROS 1 到 ROS 2 的概念映射

| ROS 1 | ROS 2 学习重点 |
|---|---|
| roscore / Master | DDS 分布式发现，无单点 Master |
| catkin | ament / colcon |
| roslaunch XML | ROS 2 launch（常用 Python） |
| nodelet | components / composition |
| ROS 1 参数服务器 | 每个节点自己的参数 |
| TCPROS/UDPROS | DDS 与 QoS |
| rosbag | rosbag2 |
| `rostopic` / `rosnode` | `ros2 topic` / `ros2 node` |

迁移前应先掌握 ROS 1 的数据流和坐标系，而不是死记命令。概念理解越扎实，迁移越顺利。

## 最终目标

理想的长期工程形态通常是：

```text
原生 Ubuntu
├── 直接管理硬件
│   ├── /dev/ttyUSB*
│   ├── /dev/video*
│   ├── CAN
│   └── Ethernet
└── Linux-native Docker
    ├── 开发容器
    ├── 感知容器
    └── 算法/部署容器
```

因此，正确的方向不是“以后不用 Docker”，而是把 Docker 从 Windows 上的教学沙箱迁移为 Linux 上可复现、可部署的工程工具。
