# 环境选择与整体架构

## 目标

先理解每一层负责什么，再开始安装。发生故障时，只有分清层级，才能避免把显示问题误判为 ROS 网络问题。

## 推荐架构

```text
Windows 10/11
├── Docker Desktop
│   └── WSL2 backend
│       └── Ubuntu 20.04 + ROS Noetic 容器
└── VcXsrv（接收容器发出的 X11 绘图请求）
```

各层职责如下：

| 层级 | 主要职责 | 典型问题 |
|---|---|---|
| Windows | 桌面、显卡驱动、防火墙 | X Server 被拦截、端口不可达 |
| WSL2 / Docker Desktop | Linux VM、容器网络和文件共享 | Docker backend、NAT、VPN 冲突 |
| ROS 容器 | Ubuntu、ROS 包、节点与工作空间 | 软件依赖、环境未 source |
| VcXsrv | 显示 Linux X11 窗口 | `DISPLAY` 错误、GLX 不兼容 |
| ROS Graph | 节点发现和点对点通信 | `ROS_MASTER_URI`、地址不可回连 |

ROS 网络与 GUI 显示是两条独立链路：

```text
ROS 节点 ──TCPROS/XMLRPC── ROS 节点
GUI 程序 ──────X11─────── VcXsrv ── Windows 桌面
```

因此，`rosnode list` 正常不代表 RViz 一定能显示；`xeyes` 正常也不代表 ROS Master 已启动。

## 三种典型场景

### 单容器学习

所有节点都在同一个容器中，使用：

```bash
export ROS_MASTER_URI=http://localhost:11311
unset ROS_IP
unset ROS_HOSTNAME
```

这是最适合初学者的方式。它避开了 ROS 1 多节点动态端口跨 NAT 的复杂性。

### Compose 多容器

Master、开发节点和算法节点位于同一个 Docker network。使用 Compose 服务名作为 `ROS_HOSTNAME`，不需要把所有动态端口映射到 Windows。

### 真实机器人或局域网多机

节点必须向其他机器声明一个实际可回连的 LAN 地址。这时需要综合考虑 Docker host networking、WSL2 mirrored networking 或原生 Linux。不要只映射 11311 端口后就认为 ROS 1 网络已打通。

## 生命周期与使用边界

Ubuntu 20.04、ROS Noetic 和 Gazebo Classic 11 已属于遗留技术栈。它们仍适合：

- 学习 ROS 1 的通信模型、catkin、TF 和 URDF；
- 复现实验、课程或现有机器人的旧项目；
- 通过固定镜像保存依赖。

不适合直接承担：

- 暴露在公网的长期生产服务；
- 对安全更新有严格要求的新系统；
- 需要长期维护的新机器人项目。

## 环境选择建议

| 需求 | 推荐环境 |
|---|---|
| ROS 基础、turtlesim、rqt | Windows Docker + VcXsrv |
| TF、URDF、偶尔使用 RViz | Windows Docker 可继续使用 |
| 高频 RViz、复杂 Gazebo、大点云 | WSL2 + WSLg 或原生 Ubuntu |
| USB LiDAR、RealSense、CAN、多机 ROS | 原生 Ubuntu 优先 |
| 长期新项目 | 受支持的 Ubuntu + ROS 2 |
