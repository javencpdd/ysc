# 移植部署流程（换一台 M20）

> **两个直接回答**
>
> **① 不是"把这个文件夹复制到 M20"。** 要复制的是 `pack.sh` 打出来的**构建产物包**
> （约 600KB），不是仓库目录。直接 `scp -r` 整个文件夹会带上 `frontend/node_modules`
> （几百 MB）、`venv`（路径绑定，换机必坏），而且 `frontend/dist` 必须在 PC 上现构建。
>
> **② 路径有要求，而且比你想的更要紧** —— 安装路径**决定了服务以哪个用户运行**，
> 还决定 systemd 单元里所有绝对路径。见 §3。
>
> ⚠️ 本文是移植的**唯一权威文档**。`docs/deploy-to-second-host.md` 只是指向这里的桩，
> 别再往那边加内容（避免两份漂移）。
>
> 本文所有事实来自 2026-10-18 真机（196）实测与脚本源码核对。

---

## 1. 为什么不能直接复制文件夹

| 目录/文件 | 直接拷会怎样 |
|---|---|
| `frontend/node_modules/` | 几百 MB，且含平台相关二进制；**PC 侧构建，不进包** |
| `venv/` | 里面是绝对路径软链（`bin/python` → 具体 Python 路径），换机必坏；`install.sh` 会重建 |
| `frontend/dist/` | 必须**在 PC 上构建**：AOS 没装 Node，且时钟慢 846 天导致 npm 走 HTTPS 必失败 |
| `hls/` | 运行产物（20MB 滚动切片），拷过去纯属浪费 |
| `__pycache__/` | 版本相关字节码 |
| `.git/` | 体积大，且含历史口令（见 §9 注意事项） |

`pack.sh` 已经把这些剔干净了，**用它，别自己 `cp -r`**。

## 2. 包里到底有什么

```bash
bash deploy/pack.sh /tmp/m20console.tgz     # PC 侧执行
tar tzf /tmp/m20console.tgz | head          # 顶层是 m20pro_console/
```

| 收进包 | 说明 |
|---|---|
| `backend/` | 后端源码 |
| `deploy/` | 全部部署脚本（含 `install.sh` / `install_helpers.sh` / `_apply.sh` / helper 本体 / sudoers 模板） |
| `frontend/dist/` | **已构建**的前端产物 |
| `tools/` | 探针与逆向工具（`tools/capture/` 被剔除，体积大） |
| `note/` | 文档（含本文）——**AOS 上排障主要靠它** |
| `requirements.txt`、`config.example.toml` | 依赖与配置示例 |

| **不在包里** | 原因 |
|---|---|
| `frontend/src`、`node_modules` | 已构建，源码无需上机 |
| `docs/`、`README.md`、`tests/` | 开发侧资料，不参与运行；**这也是本文放在 `note/` 而不是 `docs/` 的原因**——`note/` 会随包上机 |

体积参考（真机实测）：**包 625KB → 安装后 46MB**（`venv` 23MB + `hls` 20MB 滚动窗口 + 代码约 1.7MB）。

## 3. 路径要求（重点）

### 3.1 硬性要求

| 要求 | 原因 | 违反的后果（**已实测**） |
|---|---|---|
| **绝对路径** | `install.sh` 参数直接写进 systemd 单元 | 相对路径 → 服务起不来 |
| **不含空格** | 单元里是 `WorkingDirectory=<路径>/backend`、`ExecStart=<路径>/venv/bin/python`，systemd 按空白拆词 | 实测生成 `ExecStart=/opt/my dir/monitor/venv/bin/python …` → systemd 拆成 `/opt/my` 与 `dir/monitor/…` 两个词 → **`status=203/EXEC`** |
| **不含 `#`** | `install.sh` 用 `sed -e "s#/home/djw/monitor#$INSTALL_DIR#g"`，`#` 是**分隔符** | 实测 `sed` 直接 **rc=1**（`unterminated s command`）→ 单元文件被写成空文件，`set -e` 让安装**中止在第 5 步** |
| **不含 `&`** | sed 替换串里 `&` 表示"整个匹配"，会被展开成旧路径 | 实测路径 `/opt/m20&monitor` 生成<br>`WorkingDirectory=/opt/m20/home/djw/monitormonitor/backend` → **路径错乱，服务找不到代码** |
| **可写、可 chown** | `install.sh` 会 `chown -R $RUN_USER` | 权限不足 → 装到一半失败 |
| **不要放 `/tmp`** | 多数系统重启清空 `/tmp`；AOS 上还会被各种清理脚本扫 | 重启后服务消失 |

> 三条破坏效果都是 2026-10-18 用本仓库的单元模板**实际跑 sed 验出来的**，不是推测。
> 一句话记住：**路径只用字母、数字、`-`、`_`、`/`**，别用空格和 `#&$` 这类字符。

**推荐命名**：全小写、无空格、无特殊字符，如 `/home/user/m20monitor`、`/opt/m20monitor`。

### 3.2 路径决定"服务以哪个用户运行"——最容易踩的一条

`install.sh` 里的推断逻辑（源码原文）：

```bash
OWNER_FROM_PATH="$(basename "$(dirname "$INSTALL_DIR")")"
if [[ "$INSTALL_DIR" == /home/* ]] && id -u "$OWNER_FROM_PATH" >/dev/null 2>&1; then
    RUN_USER="$OWNER_FROM_PATH"          # /home/djw/monitor → djw
else
    RUN_USER="${SUDO_USER:-$(id -un)}"   # 非 /home/* → 跑 sudo 的那个人
    warn "用户 $OWNER_FROM_PATH 不存在，服务将以 $RUN_USER 运行"
fi
```

翻译成人话（**右列是 2026-10-18 在 196 上实跑推断逻辑的结果**）：

| 安装路径 | 运行用户 | 196 实测 |
|---|---|---|
| `/home/djw/monitor`，且**系统里真有 `djw` 账户** | `djw` | 该账户不存在 → 实际得 `user` |
| `/home/djw/monitor`，但**没有 `djw` 账户** | **降级为跑 sudo 的人**，并打 warn | `user` ✅（这就是现状） |
| `/home/user/m20monitor`（`user` 存在） | `user` | `user` ✅ |
| `/opt/m20monitor`（不在 `/home/*`） | 跑 sudo 的人 | `user` ✅ |
| `/home/nobody999/monitor`（用户不存在） | 跑 sudo 的人 | `user`（并 warn） |

> 🚨 **`root` 风险**：以 `root` 身份**直接**执行（不经 `sudo`）时，`SUDO_USER` 为空
> → `id -un` = `root` → **服务以 root 运行**，整套控制闸的意义大打折扣。
> `install.sh` 只检查 `EUID=0`，拦不住这种情况。
> 装完务必核对：`systemctl show m20pro-console -p User --value`
>
> 196 的实际情况：**`djw` 账户不存在**，所以服务跑在 `user` 下（功能无差异）。
> 想改成 `djw` 就 `useradd` 后重跑 `install.sh`，或改单元 `User=` 再 `daemon-reload`。

### 3.3 换路径后要同步改什么

| 位置 | 是否自动 | 说明 |
|---|---|---|
| systemd 单元内所有绝对路径 | ✅ 自动 | `install.sh` 用 sed 全局替换 `/home/djw/monitor` → 你的路径 |
| `M20_VIDEO__HLS_DIR` | ✅ 自动 | 同上（它在单元里是字面量） |
| 静态资源目录 | ✅ 不需要改 | `main.py` 里是 `os.path.join(_BACKEND_DIR, …)`，随安装目录走 |
| `_apply.sh` 的目标目录 | ⚠️ 手动 | 用第 2 个参数：`_apply.sh <tgz> <安装目录>`，默认 `/home/djw/monitor` |
| `m20monitor` 的帮助文本 | ⚠️ **不会改**（仅显示） | 它打印"目录 /home/djw/monitor"，实际功能走 systemctl，**不影响运行**，属已知外观问题 |
| 部署文档里的示例命令 | ⚠️ 手动 | 本文与 `docs/deployment.md` 的示例都按 `/home/djw/monitor` 写 |

### 3.4 怎么选：三种可选形态

**一句话：选一个"专属的、空的、持久的、不含特殊字符"的目录；不要拿解包目录当安装目录。**

先跑体检，别猜：

```bash
bash tools/preflight_new_host.sh /home/user/m20monitor
# 它会逐条告诉你：绝对路径？有空格/#/&/$？在 /tmp 下？运行用户是谁？目录空不空？磁盘够不够？
# 末尾直接打印该执行的 install.sh 命令
```

| 候选形态 | 运行用户 | 评价 |
|---|---|---|
| `/home/<运行用户>/m20monitor` | **该用户**（唯一能主动指定运行用户的形态） | ✅ **首选**。语义清晰、家目录通常空间足、权限天然正确 |
| `/opt/m20monitor` | 跑 sudo 的那个人 | ✅ 可用。适合不想污染家目录；但**无法指定运行用户**，只能靠"谁 sudo 谁就是运行用户" |
| `/srv`、`/data` 等自定义挂载点 | 同上 | ✅ 可用（只要不落在临时文件系统上；注意重启后挂载是否还在） |
| `/tmp/...`、`/var/tmp/...`、`/run/...` | — | ❌ **禁止**。重启/TMPDIR 清理会把整个安装目录带走，服务直接消失 |
| `/home/<用户>`（**家目录本身**） | 父目录名 `home` 不是用户 → 降级 | ❌ **禁止**。会把 `backend/ note/ tools/ hls/` 铺在家目录根上，且 `rsync --delete` 会动到同名子目录 |
| 已装着别的东西的目录 | — | ❌ **禁止**。`install.sh` 对 `backend/`、`tools/`、`note/` 做 `rsync -a --delete`，会删掉目标子目录里"源里没有"的文件 |

#### 能不能把"解包后的目录自身"当安装目录？

技术上能跑通（`rsync -a --delete "$src/" "$dst/"` 在 `src == dst` 时是**无害 no-op**，实测 rc=0、文件完好），
但**不建议**，四个理由：

1. **解包位置通常是 `/tmp`** → 重启/aos 的清理脚本会连服务一起清掉；
2. **再解一次包就会混在一起**：新旧文件在同目录，`install.sh` 的 `--delete` 语义依赖"源是完整的包"，
   而你手上那个目录可能已经跑过一轮、被 venv 和 `hls/` 污染过；
3. **安装目录与"包"的生命周期被绑死**：想回滚到上一版就没有独立的中转副本了；
4. **没有"干净重装"这个动作**：`rm -rf 安装目录` 这种最干脆的恢复手段会连解包副本一起没了。

所以分两个目录：

```
/tmp/m20pro_console/            ← 解包目录（中转站，装完即可删；600KB）
/home/user/m20monitor/          ← 安装目录（持久，服务真正跑在这里）
```

> 💡 `install.sh` 用 `SRC_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"` 定位自己，
> **从哪个目录执行都可以**，不必 `cd` 进包。

#### 实测记录：非默认路径真的装通了吗？

**装通了。** 2026-10-18 在 196 上用 `install.sh /home/user/m20monitor` 实装了一遍，结果：

| 检查 | 结果 |
|---|---|
| 安装目录 | `/home/user/m20monitor`（36MB，含 venv 与 hls/） |
| 单元 `WorkingDirectory` / `ExecStart` | 全部指向新路径 ✅ |
| 单元 `User=` | `user`（按父目录名 `user` 推断，正确） |
| 服务 | `active` |
| `/health` | `{"ok":true,"connected":true,"data_source":"udp"}` |
| 前端 `/` 与 `/api/v1/state` | 均 200 |
| 依赖 helper 的功能（热点） | 正常返回 `CA9B_NO.1273_24G` |
| `hls/` 目录 | 在新路径下自动创建 |

验证完已还原到 `/home/djw/monitor`（单元 md5 与备份一致），测试目录已删除。
所以"路径可改"这条是**真机验证过**的，不是推演。

> ⚠️ 两个实操小摩擦（都踩过）：
> 1. **`/tmp/m20pro_console` 若是 sudo 解包的，普通用户 `rm -rf` 不掉**（owner=root）。
>    换包时用 `sudo rm -rf`，或解到新目录（如 `/tmp/pkgtest`）。
> 2. 安装会**覆盖同名的 systemd 单元**（`m20pro-console.service`），
>    即"新路径装上 = 控制台切到新路径"。装之前若不放心，先
>    `cp /etc/systemd/system/m20pro-console.service /tmp/unit.bak`，还原就是拷回来 + `daemon-reload` + `restart`。

## 4. 完整流程

### 4.0 先选模式：远程一键 vs 本地安装

两条路**最终跑的都是同一个 `install.sh`**（安装动作永远在 M20 上执行），
区别只是"谁驱动、要不要先手动登上去"。

| | **模式 A：远程一键** | **模式 B：本地安装** |
|---|---|---|
| 怎么操作 | PC 上一条命令，脚本自己 ssh/scp/调用/验收 | 手工把包送进去，登录后本地执行 |
| 命令 | `bash deploy/install_remote.sh user@IP [目录]` | `scp` + `ssh` + `install.sh`（三到四条） |
| 前置 | PC 能 ssh 到目标机；知道 sudo 口令 | 只要能把文件送到目标机（scp / U 盘 / 跳板机都行） |
| 顺带做的事 | **连通性检查 + `--check` 预演 + 远程预检 + 装完验收** | 预检要自己单独跑 |
| 适合 | 常规换机、批量部署、CI | 现场无网络通路、只能 U 盘带包；或想逐步看清每一步 |

**建议默认走模式 A**：它把"测通、预检、安装、验收"串成了一条命令，
每一步都会打印结论，出问题能直接定位到是哪一层。

### 4.1 模式 A：从外部主机一键远程安装

**目标一律写 `user@ip`，不要用主机别名。** 别名看不出"到底连的哪台"，
换机器还得先去改 `~/.ssh/config`；写 IP 则一眼可核对，报错时也好定位。

```bash
cd m20Pro/m20Pro_robot_monitor

# ① 先只测连通性（强烈建议；不装任何东西，随时可跑）
bash deploy/install_remote.sh --check user@192.168.0.196
```

`--check` 会分四层报结论，哪一层挂了就修哪层：

| 层 | 看什么 | 挂了怎么办 |
|---|---|---|
| ① SSH 可连接性 | 免密能否 BatchMode 直连 | 脚本会打印 `ping` / `nc -vz IP 22` / 手动 `ssh` 三条排查命令 |
| ② 远端身份与系统 | `hostname` / `id -un` / 内核 / uptime | 先确认 `user` 是不是对的用户名 |
| ③ sudo 可用性 | 用 `M20_SUDO_PASS` 试 `sudo id -un` | 口令不对（默认是**半角单引号** `'`）或用户不在 sudoers |
| ④ 关键前置速览 | python3 / systemd / `30000/udp` / `basic_server` 二进制 / 安装目录是否已存在 | 缺 python3 或 30000 没在听 → 这台可能不是 M20 Pro 或 basic_server 没起 |

```bash
# ② 真正安装（默认装到 /home/user/m20monitor）
bash deploy/install_remote.sh user@192.168.0.196
#    或指定路径
bash deploy/install_remote.sh user@192.168.0.196 /opt/m20monitor
```

它内部按 6 步走，每一步都有 `[n/6]` 输出：

| 步 | 做什么 |
|---|---|
| 0 | 连通性检查（同 `--check`） |
| 1 | 确认 `frontend/dist`，缺了尝试本地 `npm run build` |
| 2 | `pack.sh` 打成 600KB 的包 |
| 3 | 上传预检脚本 + 包到 `/tmp` |
| 4 | **远程预检**（`preflight_new_host.sh <安装路径>`）→ 不通过就**停手，不做任何更改** |
| 5 | 检查目标是否已装（已装则提示用 `_apply.sh`，除非 `--force`） |
| 6 | 解包到 `/tmp/m20stage.<pid>` → `sudo install.sh <安装路径>` → 打印健康检查 |

末尾会打印 `服务: active  运行用户: xxx`，并在运行用户是 `root` 时告警。

常用环境变量与选项：

```bash
M20_SUDO_PASS='你的口令' bash deploy/install_remote.sh user@192.168.0.196   # sudo 口令不是 '
M20_USER=ysc            bash deploy/install_remote.sh 192.168.0.50         # 只写 IP 时补的用户名
bash deploy/install_remote.sh user@192.168.0.196 --force                   # 已装也重装
bash deploy/install_remote.sh user@192.168.0.196 --skip-preflight          # 跳过预检（不建议）
```

> ⚠️ 参数只写 IP（不写 `user@`）时，脚本会**明确告警"已按 `user@IP` 处理"**并继续——
> 因为不告警直接用 SSH 默认用户，很容易装到意料之外的账户下（进而影响运行用户，见 §3.2）。

### 4.2 模式 B：先复制到 M20，再本地安装

适用于"PC 到 M20 没有 SSH 通路"（只能 U 盘/跳板机/别的机器中转）的情形。

```bash
# ── PC 侧：只想拿到一个可搬运的包 ──────────────────────
cd m20Pro/m20Pro_robot_monitor
cd frontend && npm run build && cd ..        # 必须在 PC 构建（AOS 没有 Node）
bash deploy/pack.sh /tmp/m20console.tgz      # 625KB
scp /tmp/m20console.tgz user@192.168.0.196:/tmp/     # 或拷到 U 盘

# ── M20 侧 ──────────────────────────────────────────────
ssh user@192.168.0.196

# ① 只读预检：环境 + 安装路径一起体检
scp 上来或从包里取 tools/preflight_new_host.sh
bash /tmp/preflight_new_host.sh /home/user/m20monitor

# ② 解包到临时中转站（**不要**把解包目录当安装目录，见 §3.4）
mkdir -p /tmp/pkg && tar xzf /tmp/m20console.tgz -C /tmp/pkg

# ③ 安装
sudo bash /tmp/pkg/m20pro_console/deploy/install.sh /home/user/m20monitor

# ④ 验收
python3 /home/user/m20monitor/tools/verify_deploy.py
rm -rf /tmp/pkg                                # 中转站用完即删
```

> 💡 **两个"路径"别混**：
> · **解包位置**（`/tmp/pkg`）**无所谓**，装完就可以删，只要磁盘够放 600KB；
> · **安装路径**（`install.sh` 的第 1 个参数）**才有要求**，它决定服务装在哪、以谁运行（§3）。
>
> `install.sh` 用 `SRC_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"` 定位自己，
> 所以从哪个目录执行都行，不必 `cd` 进包。

`install.sh` 现在跑 **8 步**：目录 → venv → 依赖（http 镜像）→ 权限 → systemd →
启动验证 → `m20monitor` → **受控提权 helper（`m20-ap-ctl` / `m20-video-ctl` + sudoers）**。

> **第 8 步是 2026-10-18 才补的。** 此前 `install.sh` 完全不碰 `/usr/local/sbin`，
> 换机后热点/推流面板会报「受控入口不存在或不可执行」，而**服务本身是正常的**，
> 极易误判。这是换机最容易漏的一步。

### 4.3 装到非默认路径

方式 A 直接传第二个参数；方式 B 把 `install.sh` 的参数换掉：

```bash
bash deploy/install_remote.sh user@192.168.0.196 /opt/m20monitor     # 模式 A
sudo bash /tmp/pkg/m20pro_console/deploy/install.sh /opt/m20monitor  # 模式 B
```

装完先核对运行用户（§3.2 的 root 风险）：

```bash
systemctl show m20pro-console -p User --value     # 应为普通用户，不是 root
systemctl show m20pro-console -p ExecStart --value | head -1
```

### 4.4 后续迭代（不重装）

首次装完之后，日常改动**不要重跑 `install.sh`**（它会重建 venv、重装依赖，慢）。
用 `_apply.sh` 只替换应用文件：

```bash
# PC
cd frontend && npm run build && cd ..
```

## 6. 回滚


> 反过来也别指望删目录能清掉 sudoers——它是系统文件。

## 7. 常见坑（按出现频率）

| 现象 | 原因 | 处理 |
|---|---|---|
| 「受控入口不存在或不可执行」 | 没跑 `install_helpers.sh`（换机第一坑） | `sudo bash <安装目录>/deploy/install_helpers.sh <运行用户>` |
| `sudo -n` 报 `a password is required` | sudoers 里的用户名 ≠ 运行用户 | 用实际用户重跑 `install_helpers.sh` |
| 服务 `status=203/EXEC` | 安装路径含空格 | 换无空格路径重装 |
| 单元文件内容损坏 / 路径被截断 | 安装路径含 `#` 或 `&` | 换路径重装 |
| 服务以 `root` 运行 | 用 root 直接 sudo，`SUDO_USER` 为空 | `useradd` 正常用户后重装，或改单元 `User=` |
| 重启后服务没了 | 装到了 `/tmp` 或未 `enable` | `systemctl enable m20pro-console`；换持久路径 |
| 相机页黑，`local.ready=no` | 厂商推流链没起 | `sudo m20-video-ctl start local`；看 `/var/log/m20-video-local.log` |
| 前端打不开 / 白屏 | 打包时 `frontend/dist` 不存在（pack.sh 会警告） | PC 上 `npm run build` 后重新打包 |
| `pack.sh` 返回非 0 但包是好的 | 末尾清理被拦截（已修：现以"包非空"为判据） | 更新到最新 `pack.sh` 即可 |
| 远程脚本连不上，但 `ssh 别名` 能连 | 用了主机别名，而脚本里要的是 `user@ip` | 统一写 `user@IP`（别名看不出连的是哪台，换机还得改 `~/.ssh/config`） |
| 装到了意料之外的账户下 | 参数只写了 IP，SSH 用了默认用户 | 脚本会告警"已按 `user@IP` 处理"；请显式写 `user@IP` 或用 `M20_USER=xxx` |
| 远程装完"运行用户"不对 | `user@ip` 的 `user` 与安装路径父目录名不匹配 | 见 §3.2；同时装 `/home/user/xxx` 与 `user@ip` 最一致 |
| `/tmp/m20pro_console` 删不掉（Permission denied） | 之前用 `sudo` 解包，目录归 root | `sudo rm -rf`，或解到带时间戳的新目录（`install_remote.sh` 已这样做） |

## 8. 多机并存的两个注意

1. **热点重名会连错机器**：两台若都叫 `CA9B_NO.1273_24G`，PC 的 WiFi 列表分不清。
   建议在新机器上改掉（面板「机器人设置 → WiFi 热点 → 新 SSID」，base 上限 12 字符）。
2. **控制台只管网所在那台**：`basic_server` 只监听本机 `127.0.0.1:30000`，
   两个控制台互不共享状态。要统一看多台得另做聚合层，不在本仓库范围。
