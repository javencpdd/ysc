## 2. 逆向方法（可复现）

### 2.1 前提

`basic_server` **符号未剥离**，这是整个方法成立的前提：

```
/opt/robot/share/basic_server/bin/basic_server      # md5 e578e07a2039a4180885c670687e70ea
```

### 2.2 注册结构

指令表在 C++ 里的形态是：

```cpp
std::unordered_map<int, std::unordered_map<int, std::function<void(rapidjson::Value&, ...)>>>
//                  ^ Type            ^ Command                ^ handler
```

AArch64 上的注册代码形如：

```asm
adrp  x2, <pool>          ; .text 常量池，首 8 字节 = handler 函数指针
add   x2, x2, #imm
mov   wN, #0x2            ; Type = 2
str   wN, [sp, #A]        ; 存进外层 map 的键槽
bl    unordered_map<int, unordered_map<int,function>>::operator[]
mov   wM, #0x15           ; Command = 21
str   wM, [sp, #B]        ; 存进内层 map 的键槽
bl    unordered_map<int, function>::operator[]
```

**锚点选内层 map 的 `operator[]` 调用**（外层调用之后还有别的代码，容易串）。

### 2.3 三步还原

```bash
# ① 车上取反汇编 + 符号表
objdump -d /opt/robot/share/basic_server/bin/basic_server > /tmp/bs.asm
nm      /opt/robot/share/basic_server/bin/basic_server > /tmp/syms.txt

# ② 还原 (Type, Command) → handler 地址
python3 tools/re_cmdtable.py /tmp/bs.asm > /tmp/tbl.txt        # 42 行

# ③ 地址 → handler 名
python3 tools/re_cmdname.py /tmp/tbl.txt /tmp/syms.txt > note/cmdtable-42.txt
```

### 2.4 ⚠️ 两个反汇编解析的坑（都真实踩过）

**坑 A：objdump 的助记符与操作数之间也是制表符。**

```
行格式：  "  addr:\t<机器码>\t<助记符>\t<操作数>\t// 注释"
```

只取 `parts[2]` 拿到的是**十六进制机器码**，不是助记符。必须
`"\t".join(parts[2:])`。症状是脚本输出 0 行——因为没有任何一行"像"指令。

**坑 B：用贪婪正则解 mangled 名会静默产出垃圾。**

`_ZN9CmdHandle15cmdHandle_SteerE<参数...>` 中 `15` 是 `cmdHandle_Steer` 的
**长度前缀**（Itanium ABI）。曾用 `([A-Za-z0-9_]+)E` 抓名字，参数串里全是
字母数字下划线（`rapidjson`/`GenericValue`/`MemoryPoolAllocator`/`basic_string`…），
贪婪匹配**一路吃到最后一个 `E`**，解出的"名字"是整整一串 mangled 参数——
而脚本毫无察觉、照样打印。**必须按长度前缀切片**（`tools/re_cmdname.py` 已修）。

## 3. 帧头 magic = 权限位

16 字节帧头第一个字段：

| magic | 使用者 | 权限 |
|---|---|---|
| `EB 91 EB 90` | 本控制台默认 | 常规 |
| `EB 90 EB 90` | 厂商 App | **DeviceControl 类** |

**只有 `1101/3`（分设备供电）认授权 magic。** 用 `EB91EB90` 下发会得到
`ErrorCode 57351 / "No operation permission"`。

两种 magic 对**心跳 / 运动 / 查询完全等价**，所以：

- 只在 `1101/3` 上按指令切换，**绝不全局替换**；
- 由 `patrol_codec.encode()` 自动处理，调用方无感；
- **接收侧两种都要认**——授权 magic 的应答也是 `EB90EB90` 回的，
  `decode_frame` 原本只认 `EB91EB90`，会漏掉这类响应。

## 4. 各指令实测结论

### 4.1 补光灯 `1101/2`（`LED`）

- 写 `{"Front":1,"Back":1}` → 车侧回 `{"ErrorCode":0}`。
- **但状态不在响应里。** 真正的状态在**设备帧 `1002/5`** 的
  `Items.Led.Fill.Front/Back`，下发后约 **1s** 翻转 → 这是四项设置里
  **唯一能闭环校验**的。
- ⚠️ **`Led.Fill`（补光灯）与 `DevEnable.LedHost/LedExt`（电源指示灯）不是一回事**，
  两者都叫 Led。后者走 `1101/3`。
- ⚠️ **整键下发**：只开前灯不带后灯当前值 = 把后灯关掉。

### 4.2 首启回零 `1101/10` + `1101/11`

- 成因：车侧 `basic_server.toml` 第 14 行 `autoResetJointsZero = true`。
- **写（1101/10）车侧不回帧**——实测发完 3s 无应答，但值确实改了。
  所以 `result=ok` 只表示"报文发出去了"，界面必须再发 `1101/11` 才敢点亮"已验证"。
- 报文记录里这条显示 `no_response`，**那是"不知道"，不是失败**，
  别让用户反复重试。
- 约束原文：`can not reset joints zero unless standing or lying down`。

### 4.3 休眠 `1101/6` + `1101/7`

`1101/7` 读回 `{"Sleep":0,"Auto":false,"Time":10}`：

| 字段 | 含义 |
|---|---|
| `Sleep` | 当前是否休眠（**整数**，非布尔） |
| `Auto` | 自动休眠开关 |
| `Time` | 分钟数 |

三种用法差别极大，别混：

| 用法 | 效果 | 需确认 |
|---|---|---|
| `sleep=true` | **整车休眠**：趴下并依次断 LED→风扇→视频→关节供电 | ✅ |
| `sleep=false` | 唤醒整车 | ❌ |
| `auto/minutes` | 只改自动休眠策略，**不会立刻睡着** | ❌ |

休眠会连带关传感器，运行日志实证顺序：
`LED_FILL` → `FAN_SPEED` → **`VIDEO_POWER`** → `JOINTS_POWER`。
所以「唤醒整车」在效果上就是恢复相机/雷达/灯/风扇供电。

### 4.4 心跳 `100/100`

- 5Hz，只决定"**机器人往谁推状态**"。
- 超时后 basic_server **清除客户端**，**不是运动保护**。
- 心跳与指令是**两个独立 UDP socket** → 停心跳不影响指令。
- 真机实证：全停 50s 后 `motion_state` 仍 17（RL 站立）。
- **结论：不要追求"断链自动趴下"**——站立中卸力就是摔倒。
  车侧真正的断链保护在 `rl_deploy` 的 DDS_CMD 看门狗（`Disable lynx`），
  效果是停运动而非趴下。

### 4.5 喇叭/音响：无硬件

用户问过"能不能外放声音"。取证：

| 检查 | 结果 |
|---|---|
| `aplay -l` | 空 |
| `/proc/asound/cards` | `--- no soundcards ---` |
| `/dev/snd` | 只有 `seq` / `timer`，**无 PCM 设备** |

**AOS 主机本身不带音频硬件，不是软件没接。** 所以不加，也不放一个按了没反应的按钮。

## 5. 车侧"静默"行为汇总（最危险的一类）

这些的共同特征：**不回错误码，但值确实变了或没变**。用户以为设了 60，车上跑的是 30。

| 行为 | 实测 | 控制台对策 |
|---|---|---|
| **休眠时长夹取** | `Time` 只认 5~30。12→生效、**60→30**、**3→5**，`Auto` 照常生效，**不回错误码**（二进制里有串 `Sleep time shoud between 5 and 30`，但响应帧里没有） | 后端 `robot_sleep` 先拒越界（`MINUTES_OUT_OF_RANGE`，一帧不出）。⚠️ 前端 `<input min max>` **不拦提交，不能依赖** |
| **回零写无应答** | 1101/10 发完 3s 无应答，值已改 | 写后必须 1101/11 回读；UI 标 verified/stale |
| **`SetXXX_POWER failed` 只是日志级别** | 日志这么打，功能照样生效 | 别当故障排查 |
| **`DevEnable.Lidar` 非布尔** | 2=运行中 / 1=启动中 / 0=关 | 判"关"只能 `==0`，`==1` 会把运行中的雷达误判成已关 |
| **`DevEnable.GPSMode` 是车侧生效值** | 下发 1~2s 后才收敛 | 切换后必须回读；直接切回 `0x11111` 可能不接受 → 增量法先 `0x00011` 再 `0x11111` |
| **`1101/10` 的 `no_response`** | 报文记录里显示为失败态 | 前端明写"那是不知道，不是失败" |

**判定实验的方法论**（休眠夹取这条）：一步只能看出"没变成 12"，两步才能区分
"夹取"与"丢弃"——先设合法基准值，再发越界值，看结果是边界值还是基准值。

## 6. WiFi：双接口·单射频

### 6.1 拓扑

M20 的无线是**一块射频两个接口**：

```
phy#0
 ├── wlan0  type AP       10.21.41.1/24   dnsmasq 发地址   ← 自身热点
 └── p2p0  type managed  192.168.0.196                        ← 上联外部 WiFi
```

**AP 信道被上联绑架**：配置里写 `band=bg`（2.4G），实际跟着上联跑
**channel 40（5200 MHz）**。

### 6.2 能力边界

| | 能不能改 | 依据 |
|---|---|---|
| SSID | ✅ | 只改信标内容，不动射频 |
| 密码 | ✅ | 同上 |
| 频段 | ❌ | 与上联抢射频 |
| 信道 | ❌ | 同上 |

**控制台只开放 SSID + 密码**，不是"提供了但提示别改"，而是根本不提供这两个字段。

实测 `nmcli con down/up myap24G` 期间 **`p2p0` 全程 `100 connected`、
`192.168.0.196` 未丢** → 连着外部 WiFi 时可以改自身热点。

### 6.3 厂商用明文文件管热点

| 文件 | 内容 | 截断 |
|---|---|---|
| `/var/opt/robot/conf/host_name` | 热点名 base | `head -c 12`，自动补 `_24G`/`_5G` |
| `/opt/robot/scripts/wifi/password` | 密码 | `head -c 16` |

生效靠 `/opt/robot/scripts/board_resources/wifi/ap_start.sh start 24G`
（先 `nmcli c delete myap…` 再 `nmcli c add` 重建）。
开机 `host_start.sh` 会 rerun 它 → **`nmcli con modify` 的改动重启必丢**。

### 6.4 `nmcli con modify` 为什么走不通（两条都实测失败）

1. 连接处于 **activated** 时改 SSID **不生效**，`con up` 也不会重新应用；
2. 先 `con down` 再改 → 撞上"AP 关停 → `wlan0` 消失 → 连接短暂不存在"的窗口，
   `nmcli con modify` 报 `unknown connection`（rc=10）。

另外 AP 激活后有 **4~8s 假死期**（NetworkManager 的 ip-check/secondaries
状态机），采一次状态就下结论会误判 → **必须轮询到 activated**。

## 7. 踩坑清单（按阶段）

### 7.1 逆向阶段

| # | 坑 | 症状 / 修法 |
|---|---|---|
| R1 | objdump 助记符与操作数间也是 Tab | 取 `parts[2]` 拿到机器码 → 脚本 0 行。改 `"\t".join(parts[2:])` |
| R2 | 贪婪正则解 mangled 名 | 解出一整串参数当"名字"，脚本毫无察觉。改按长度前缀切片 |
| R3 | 相对路径取二进制 | `pgrep` 拿到 `./basic_server`，`strings` 得 0 行。用绝对路径 |
| R4 | sudo 需要口令 | `strings`/`objdump` 都要 root。用 `printf "'\n" \| sudo -S …`（口令是半角单引号 `'`） |
| R5 | **heredoc 抢走 sudo 口令管道** | `sudo -S sh -c '…' <<EOF` → sudo 读到的是配置内容（"Sorry, try again"×3）。改**本地写文件 → scp → 单条 `sudo sh -c 'cp && …'`** |
| R6 | `/tmp` 旧文件占位 | `nm > /tmp/syms.txt` 报 Permission denied 但 `wc` 又有行数——是上一轮 root 建的文件没删掉。换个新路径 |

### 7.2 协议阶段

| # | 坑 | 症状 / 修法 |
|---|---|---|
| P1 | 授权 magic 的应答也是 `EB90EB90` | `decode_frame` 只认 `EB91EB90` → 漏响应。接收侧两种都认 |
| P2 | 应答发回**请求源端口** | `UdpControlSink` 原只发不收 → 加守护接收线程 |
| P3 | `no_response` 不代表车没执行 | 无 `ErrorCode` 字段的响应也算 `ok` |
| P4 | 20Hz 看门狗 tick 也会进记录 | 过滤掉，否则报文记录被刷爆 |

### 7.3 WiFi / 提权阶段

| # | 坑 | 症状 / 修法 |
|---|---|---|
| W1 | `uplink` 永远找不到 | 按 `802-11-wireless.mode == managed` 筛，但 **station 连接不写 mode 字段（空）** → 永远不匹配。改查**活跃连接表** `nmcli -t -f NAME,DEVICE con show --active` 并排除 AP |
| W2 | `GENERAL.STATE:` 前缀 | `state.startswith("100")` 判不出已连接。先剥前缀 |
| W3 | `set -u` 下 `local w1="" w2=""` 不初始化 | `[ -n "$AP_DEV" ] && w2=…` 条件不成立时不赋值 → 后面引用 `unbound variable`，真机直接崩 |
| W4 | SSID 白名单过严 | `[a-zA-Z0-9_-]` 把点号挡了，而原名 `CA9B_NO.1273_24G` **含点** → 连还原都做不到。改**只挡不可打印字符** |
| W5 | `con up` 后 AP 假死 | 短暂 `30 (disconnected)`，采一次就下结论会误判。轮询 30s |
| W6 | 密码走 argv | 任何本地用户 `ps` 一下就能看见。改走 **stdin**，sudoers 也因此不需要通配符 |
| W7 | **`sudo -n nmcli` 在自己的会话里失败** | sudoers 只放行 helper 本身。验证 nmcli 源必须带口令，否则会误判成"nmcli 读不到 PSK" |

### 7.4 前端 / 部署阶段

| # | 坑 | 症状 / 修法 |
|---|---|---|
