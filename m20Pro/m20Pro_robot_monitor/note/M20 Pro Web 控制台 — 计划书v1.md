## 0. 结论先行

1. **方案与架构已定稿**：**模块化单体**——单进程 FastAPI 驻 AOS 196，UDP 心跳 + ASDU 解析为主通道，ROS2 为可选增强通道（`DataSource` / `ControlSink` 双层抽象 + WS schema 契约冻结，三条迁移路径见 §18）。
2. **执行策略：先 mock 后真机**。M1 全程无需真机、零风险：MockSource 驱动全链路（心跳→解析→状态→WS 10Hz→前端→stale 降级）并冻结 schema 契约；M2 才上 196，只做"替换数据源 + 核对字段"这一件事。
3. **三个范围决策点已锁定**（§14.1，2026-10-14 用户确认无异议）：视频本期做但收缩为 HLS 单路先行；**控制通道本期集成、分层开放**（L0 只监 / L1 低危可控 / L2 黑名单，轴指令看门狗兜底）；MockSource 覆盖全部 5 类 ASDU 消息集 + 回放模式。
4. **协议真相已判明**（§10）：16 字节帧头 + JSON（PatrolDevice 信封），控制指令全集来自 docs/04 §1.2，参考 `m20-android-sdk`（Apache-2.0，只参考协议不复制代码）——**Q2「字节布局」风险关闭**；5 类状态消息的 Type/Command 与 Items 结构已按 docs/04 原文逐条核实（§10.4），残留仅为状态字段语义的真机核对。
5. **协议事实三处修正**（v1.2 起，依据 docs/04 原文）：① M20 Pro 为**轮足**，运控关节 **16 个**（4 腿 × HipX/HipY/Knee/Wheel），非 lite3 式 12 关节；② 步态切换字段名为 **`GaitParam`**，值域 0x1001/0x1003/0x3002/0x3003；③ MotionParam 只保留原文值 0/1/2/3/4/17（旧稿推测值已删）。

# 第一部分 总纲与约束

## 1. 背景、目标与非目标

### 1.1 背景
- M20 Pro 现场缺一个好用的本地 Web 监控界面：厂商 3000 端口控制台（`m20video`）已停用禁自启，手柄/APP 是另一套体系。
- Lite3 已有成熟方案 `lite3_robot_monitor`（FastAPI + Vue3 + WebSocket 10Hz + ECharts），**应当复用而非重造**。
- m20Pro 当前在 196（AOS）上**曾有过 3000 端口 Web 控制台**（`m20video` 服务，已禁用；`basic_server` 监听 30001/30002），说明厂商本就有前端范式可借鉴。
- 现有资料已厘清 m20Pro 的数据接口形态（§10/§11），具备动手条件。

### 1.2 目标（本期）
- 浏览器实时查看 M20 Pro 状态：**基础状态、运控状态（含关节 `MotorStatus`——16 个：4 腿 × HipX/HipY/Knee/Wheel，M20 Pro 为轮足）、设备状态（电池 `BatteryList` 多电池）、异常状态（`ErrorList`）**。
- **Web 控制**（分层开放，ADR-004）：**运动控制**（六轴轴指令 20Hz + 站立/趴下/软急停/步态/使用模式）、**休眠/唤醒（唤醒全车含传感器）**、照明灯、自主充电开始/退出；默认 L0 只监，L1 需显式开启 + 二次确认 + WS 租约；Charge=2 黑名单；轴指令看门狗零位兜底。
- 集成相机视频流（前/后，`video1`/`video2`）。

### 1.3 非目标（本期不做）
- 不重复造前端栈（直接复用 Vue3 组件，仅做字段对齐）。
- **不开放高危指令**（清除充电状态 Charge=2）、不做手柄硬件对接（ControllerSDK 是 Android 侧的事，Web 端用虚拟摇杆替代）。
- 不做导航任务编排、不做 AI 识别回环（可后续叠加，架构预留接口）。

## 2. 硬约束与质量属性优先级

### 2.1 硬约束（来自 2026-10-14 实测，不可假设）

| # | 约束 | 架构含义 |
|---|---|---|
| C1 | LAN 只能直连 AOS `192.168.0.196`；**监控协议与 MediaMTX 均监听在 AOS 本机**（`10.21.31.103`/`10.21.33.103` 皆 AOS 内网 IP，非 GOS；GOS 是 `10.21.31.104`） | 后端驻 196 后**同主机内网口直达**监控协议与视频源，无需跨主机；LAN 只暴露 Web/WS |
| C2 | 监控协议：机器人=服务端，UDP `10.21.31.103:30000` / TCP `:30001`；外部 ≥1Hz 发心跳后机器人**主动推送**（基础 2Hz / 运控 10Hz / 设备 2Hz / 异常 2Hz+变更额外）；**载荷为帧头+JSON（PatrolDevice 信封）**，见 §10 | 数据层是"**主动心跳 + 被动接收**"；解析 = 16 字节帧头 + `json.loads`，无二进制布局风险 |
| C3 | 视频：相机物理接在 **AOS**（前后 `SM_USB_107X`），MediaMTX 也在 **AOS 本机**运行 → RTSP `10.21.31.103:8554/video1\|video2`（`10.21.31.103` 即 AOS 内网 IP，**非 GOS**.104），196 上等价于 `127.0.0.1:8554` | 取流优先用 **196 本机 MediaMTX**（近零中继）；**视频源与监控协议同在 AOS**，进一步锁定部署主机 |
| C4 | 控制指令含危险项（清除充电状态=2，官方标注**危险**） | 控制通道默认关闭 + 安全闸 + 黑名单 |
| C5 | 端口已被占：`30001/30002`(basic_server)、`8554/1935/8888/8889`(MediaMTX)、`3000`(遗留 m20video)、`21/22/9393` | 控制台端口必须避开，建议 `8080`/`8081` |
| C6 | 196 时钟慢 ~846 天（**TLS 必失败**）、WiFi 间歇丢包、`/`（overlayroot）仅 14G 可用 | 不依赖 HTTPS；应用装 `/home/djw/monitor`（用户指定，与 `/` 同分区）；心跳带重试；时钟修复后再议 TLS |
| C7 | ~~ASDU 报文逐字节布局未精读~~ **已关闭**：协议 = 16 字节帧头 + JSON（§10），无二进制布局谜团 | ACL（防腐层）从"struct 拆字节"降为"帧头校验 + JSON 字段映射"；残留仅为**字段语义真机核对**，ACL 的隔离价值不变 |

### 2.2 质量属性优先级
**可靠性 > 可维护性 > 可观测性 > 性能**。
理由：这是运维/调试工具——"状态停更但界面不报"比"帧率低 5Hz"危险得多。宁可少做一个图表，不可让用户看到假数据。

## 3. 领域分析（Bounded Contexts）

划分六个上下文，彼此用明确边界隔开：

```
 ┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
 │  数据接入 Ingestion │ → │   状态 State      │ → │  实时推送 Realtime │
 │  心跳发送          │   │  唯一权威状态      │   │  WS fan-out 10Hz  │
 │  UDP 收包          │   │  + 新鲜度(stale)   │   │                   │
 │  帧头+JSON 解码    │   │                   │   │                   │
 └───────────────────┘   └───────────────────┘   └───────────────────┘
 ┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
 │  视频 Video        │   │  控制 Control      │   │  展示 Presentation │
 │  MediaMTX 代理     │   │  分层开放          │   │  Vue3 + ECharts   │
 │  RTSP → HLS        │   │  L0只监/L1低危/    │   │  + 运动面板        │
 │                   │   │  L2黑名单+看门狗   │   │                   │
 └───────────────────┘   └───────────────────┘   └───────────────────┘
```

**Context Mapping（最重要的一条边界）**：Ingestion → State 之间必须放**防腐层（Anti-Corruption Layer, ACL）**。ASDU 解析器负责把协议报文翻译成领域状态对象；**协议怎么变，都关在解析器里**，不污染 State、不污染前端。这是整个设计里唯一不可妥协的边界。

# 第二部分 架构设计

## 4. 架构选型：三个方案与决策

### 4.1 方案 A：模块化单体（复用 lite3 骨架）
单进程 FastAPI：ingestion 线程 + state + ws hub + 视频代理 + 前端静态资源，模块间以清晰接口相连，**不拆进程**。

| 获得 | 放弃 |
|---|---|
| 最小部署面（一个 systemd unit，一次 `systemctl restart`） | ingestion 与 API 同生共死（需靠线程隔离 + 看门狗 + `/ready` 缓解） |
| 复用度最高，与 lite3 同构，团队学习成本近零 | 无法独立扩展视频/数据两条通路 |
| 调试简单（一个 journald 日志流） | 单进程内存上限即整机上限 |

### 4.2 方案 B：ROS2 中心化
后端订阅 ROS2 话题（传感器/运动/速度/自主充电），前端经 rosbridge 或自研 WS 网关展示。

| 获得 | 放弃 |
|---|---|
| 数据语义最丰富（话题类型自带 schema），与厂商生态一致 | 必须在 196 装配 ROS2 + DDS 环境，依赖链重 |
| 控制走 topic 最自然 | ROS2 话题清单**未实测**（Q4）；DDS 发现/QoS 排障成本高 |
| 后续可无缝接导航任务监控 | 发现不稳定时"整链黑屏"；与 lite3 前端复用度低 |

**适用时机**：后续要做导航任务监控、rviz 级可视化时再引入——届时只是新增一个数据源实现（见 ADR-001 与 §18）。

### 4.3 方案 C：微服务化（ingestion / video / api / frontend 各自成服务）

| 获得 | 放弃 |
|---|---|
| 各通路独立扩缩、故障隔离彻底 | 4 进程/端口的运维成本 |
| — | 进程间通信（谁持有 state 权威？） |
| — | 在 RK3588 单机上跑微服务是典型的 architecture astronautics |

### 4.4 决策：**选 A**；B 作为后续增强通道**预留接口**；C **明确拒绝**
理由：团队 1–2 人、单机部署、架构已被参照项目钉死、当前最大风险是"协议没吃透"而非"吞吐不够"。A 的取舍（同生共死）用"线程隔离 + 心跳看门狗 + `/ready` 探针 + systemd Restart"缓解，可接受。
**保留可逆性**：把数据源抽象为 `DataSource` 接口（lite3 已有 `data_source.py` 雏形），未来接 ROS2 只是新增一个实现类，上层零改动——这是让 B 随时可来的关键，且成本几乎为零。

## 5. 总体架构

### 5.1 部署拓扑

```
浏览器(LAN)
   │  HTTP + WebSocket
   ▼
[m20pro-console 后端]  ← 跑在 AOS 192.168.0.196
   │  ├─ 心跳发送器 ≥1Hz ──► AOS 本体 10.21.31.103:30000 (UDP, 同主机内网口)
   │  ├─ UDP 接收 ◄──────── 机器人 ASDU 状态推送(回同一 socket)
   │  ├─ 帧头+JSON 解析 → StateStore
   │  ├─ 控制出口(同一 socket) ──► 轴指令20Hz / 站立 / 步态 / 照明 / 休眠唤醒 / 充电
   │  ├─ MediaMTX RTSP 代理 ──► 127.0.0.1:8554/video1|video2 (196 本机 MediaMTX)
   │  └─ (可选) ROS2 订阅 ← 196 本机 ROS2 话题
   ▼
WebSocket 10Hz 推送 + 视频流 → Vue3 前端
```

**为何后端跑在 196**：监控协议与 MediaMTX **均监听在 AOS 本机**（`10.21.31.103` 系 AOS 内网 IP，196 即 AOS 的 LAN 侧）→ 后端驻 196 后同主机内网口/回环直达，LAN 只暴露 Web/WS。这也契合"开发都在 AOS"的现场约定。

**数据层选型**：**主通道 = UDP 心跳 + ASDU 解析**（不需要 ROS2 环境，最稳，复用 lite3 套接字骨架）；ROS2 话题作为**可选增强**，复用参照项目 `ros_*` 模块思路（ADR-001）。

### 5.4 关键接口（契约先行）

| 接口 | 签名 / 语义 | 备注 |
|---|---|---|
| `DataSource` | `start() / stop() / on_frame(cb)` | 三种实现可互换，上层不感知来源 |
| `StateStore.update(topic, payload, ts)` | **仅 ingestion 可写**；读侧只读快照 | 写入口唯一，杜绝并发写乱 |
| `StateStore.snapshot()` | → dict，含 per-topic `ts` 与 `stale` 标志 | 前端永远不猜数据新鲜度 |
| `WsHub.broadcast(snapshot)` | 每 100ms 一次，JSON | 与 lite3 前端 `api/index.js` 兼容 |
| `ControlGateway.execute(cmd, params)` | L0 → `403 CONTROL_DISABLED`；L1 需租约+前置校验；L2 任何配置拒绝 | 黑名单指令（Charge=2）任何配置下都拒绝 |
| `POST /api/v1/control/motion` | 运动状态转换/步态/模式/照明/休眠/充电（L1 白名单） | 入参白名单校验，审计日志 |
| `POST /api/v1/control/axis` | 轴指令（X/Y/Z/Roll/Pitch/Yaw ∈ [-1,1]；**服务端安全上限 ±0.40**） | 20Hz 由看门狗循环发送；单发=一次性指令 |
| `POST /api/v1/control/estop` | 软急停（MotionParam=2） | **无需 enable 也可用**（安全手段优先于开关） |
| `GET /api/v1/schema` | WS 快照 JSON schema（带 `version` 字段） | **前后端契约，版本化冻结**——后端换数据源时前端零改动（§18 路径 3 的保险） |

### 5.5 模块职责与失败行为

| 模块 | 职责 | 失败行为 |
|---|---|---|
| HeartbeatSender | ≥1Hz 向 AOS:30000 发心跳 | 发送异常 → 重试 + 计数；连续失败 → `/ready` degraded |
| UdpReceiver | 本地端口收 ASDU 推送 | socket 异常 → 重建；收包速率掉零 → 触发 stale |
| AsduParser (ACL) | 协议 → 领域模型 | 解析失败 → 死信计数 + warn 日志，**不抛出到 ingestion 之外** |
| StateStore | 权威状态 + 新鲜度 | 超阈未更新 → 标记 stale（不删旧值，只标脏） |
| WsHub | 快照 fan-out | 客户端断连自动清理；服务端 ping 30s |
| VideoProxy | RTSP→HLS | 上游断 → HLS 列表保留最后片段 + 前端提示"视频中断" |
| ControlGateway | 指令安全闸（分层/租约/黑名单/前置校验/审计） | 默认 L0 disabled；租约随 WS 断开失效（**前端每 2s 自动续约**，2026-10-15 修复：此前 UI 侧无续约调用方，开启 5s 后指令全被租约闸拒发）；**急停永不受开关限制** |

## 6. 关键流

### 6.1 状态上报链路（正常路径）
`HeartbeatSender(≥1Hz)` → AOS:30000 → 机器人开始推送 → `UdpReceiver` 收到 ASDU → `AsduParser` 解码（帧头+JSON） → `StateStore.update(ts=now)` → `WsHub` 每 100ms 取快照广播 → 前端 `useRobotState` 渲染。
**时延预算**：网络 + 解析 < 10ms；WS 广播周期 100ms → 端到端 < 200ms，对 10Hz 遥测充分。

### 6.2 降级路径（重点：不许假数据）
- 心跳发送失败 / 超过 `stale_threshold`（默认 500ms，可配）无推送 → StateStore 标 stale → 前端**顶部红色横幅"数据已停更 mm:ss"** + 各面板置灰。**绝不把旧数据当新数据展示。**
- 解析失败率 > 阈值 → `/ready` 返回 degraded + warn 日志，不静默。
- 后端崩溃 → systemd `Restart=on-failure` 自动拉起；前端 WS 断线自动重连。
- 目标：**MTTR < 1 分钟（自动恢复）**。

### 6.3 视频链路

**2026-10-16 起（ADR-011）：浏览器直连 MediaMTX，不经后端中转**
| 档位 | 地址 | 延迟 | 说明 |
|---|---|---|---|
| 主链路 | `http://<host>:8889/<path>/whep`（WHEP/WebRTC） | ~0.3s | 原生 `RTCPeerConnection`，媒体走 ICE/UDP `:8189` |
| 兜底 | `http://<host>:8888/<path>/index.m3u8`（MediaMTX 自带 HLS） | ~2–3s | hls.js；`hlsAllowOrigin: '*'` |
| 第三层 | `/hls/live.m3u8`（后端 ffmpeg 中继） | ~2–3s | ADR-003 的产物，仅保留兜底 |

原始实现（ADR-003）：`VideoProxy` 从 **196 本机 MediaMTX** `127.0.0.1:8554/video1|video2` 拉流 → 切 HLS → 前端 `VideoPanel`（hls.js）播放。

> **端口取舍（2026-10-15 实现定稿）**：HLS 产物**挂载在主应用 `/hls` 路径下**（单端口 8080），
> 而非原规划的独立 `:8081` —— 少一个进程/端口，与前端静态托管保持"单端口"一致。
> `video.hls_port` 保留为可选项（未来需独立端口时启用）。

#### 6.3.1 ⚠️ 前置：相机需先唤醒（2026-10-15 实测，运维必知）
机器人**休眠时相机不通电**：实测休眠态下 `/dev/video*` 不存在、`lsusb` 无 `0bda:3035`、
MediaMTX 无 `video1/video2` 路径（ffmpeg 取流返回 404）。
- 唤醒指令：`1101/6` + `Items={"Sleep": false}`（即 §10.3.2 的"退出休眠/唤醒全车含传感器"）；
- 验证：唤醒后 `Sleep` 由 `1` → `0`，`/dev/video0~3` 出现，两颗 `SM_USB_107X (0bda:3035)` 挂载，
  `video1/video2` 均有流（`h264 High 800×600 30fps`）。
- **Auto 自动休眠当前为 `true` + `Time=5` 分钟**：控制台持续发心跳应可抑制自动休眠（待观察）；
  若发现相机周期性掉线，优先查是否被自动休眠。

#### 6.3.2 实测参数（2026-10-15）
| 项 | 实测值 |
|---|---|
| 编码 | **必须用 `-c:v copy` 不转码** —— 196 的 ffmpeg 4.2.7 **无 rkmpp 硬编**（只有 libx264 软编） |
| 首切片耗时 | **1 s**（验收标准 ≤3s ✅），加了 `-fflags nobuffer -flags low_delay -probesize 32 -analyzeduration 0` |
| 片段 | 1s/片 ~250KB，`hls_list_size=3` + `delete_segments` → 目录有界 ~1.1MB |
| 传输 | `-rtsp_transport tcp`（WiFi/内网丢包环境比 UDP 稳） |
**取舍（2026-10-15 原判 → 2026-10-16 修订）**：原判"选 HLS 而非 WebRTC，延迟 1–3s 对**监控**可接受，WebRTC 留作后续升级"。2026-10-16 因**"前后双路同看"**诉求复核，确认三件此前未核实的事实：① MediaMTX 实为 **v1.4.2**，`webrtc: yes` + `:8889` + ICE UDP `:8189` + **`webrtcAllowOrigin: '*'`** 全就绪（CORS 预检实测 204）；② 其自带 HLS `:8888` **双路均 200**（video1/video2 实测 ffmpeg 各抓帧 40KB / 37KB 出图）；③ 单路 ffmpeg 中继**结构上无法同时输出两路**（切换要重启 ffmpeg）——这是"双路同看"的硬约束。故按 **ADR-011** 升级为 WebRTC 主 + HLS 兜底。
**不变的是**：**遥控低延迟诉求应通过带安全闸的控制通道满足，而不是靠压视频延迟**——这是两条不同的路，不要混。本次改的是**监控体验**，控制安全仍只依赖 ADR-004 的四道闸与"看门狗只停不趴"。

### 6.4 控制链路（分层开放，ADR-004）
```
[浏览器 MotionPanel] --WS/REST--> ControlGateway（安全闸）
                                      │ 分层校验（L0/L1/L2）+ 前置条件 + 值域钳制
                                      ▼
                              patrol_codec 编码（帧头+JSON）
                                      │ 同一 UDP socket
                                      ▼
                              AOS 10.21.31.103:30000
```
- **L0 只监（默认）**：任何控制请求返回 `403 CONTROL_DISABLED`——**急停除外**（安全手段优先于开关）。
- **L1 低危可控（需显式开启）**：站立/趴下/软急停/步态/使用模式/照明/休眠唤醒/充电开始-退出。开启条件：配置显式 `enable` + 前端二次确认 + **心跳租约**（WS 断开即失效）。
- **L2 高危黑名单（永不开放）**：`Charge=2`（清除充电状态，官方标注危险）。
- **轴指令看门狗**（**只停不趴**，2026-10-15 二次事故修正）：20Hz 循环发送中，① **松杆 / feed 停更 250ms / WS 断开 / 服务停机** → 一律 **零位一帧 + 停发**（不软急停——车侧 rl_deploy 150ms 速度看门狗自动清零，车体平滑停住）；此后保持"停"等待恢复，新 feed 即续发；② **绝不自动软急停** —— 软急停只能由人显式触发（两次真机事故均为"自动软急停"所致：运动中被打急停栽倒 / 站立中被打急停卸力软塌，机制已整体切除）；③ 安全零位帧豁免四道闸（`send_safety_zero`）。**绝不让机器人带着最后一条指令无限运动**——这是控制通道最重要的单点设计。
- **运动前置校验**：轴指令下发前校验 `MotionState ∈ {站立(1), RL控制(17)}` 且 `ControlUsageMode=0`（常规模式，docs/04 §1.2.5 原文约束），否则拒绝并提示先站立/切模式。
- 指令经 `patrol_codec` 编码后走**同一 UDP socket**（与心跳/接收复用）发往 `10.21.31.103:30000`。

## 7. 架构决策记录（ADR）

> ADR 记录 **WHY**，不只是 WHAT。原 PLAN 旧稿的 D1–D5 关键技术决策已分别并入 ADR-001~004 与 §6.1（推送频率），不再单列。

### ADR-001 数据通道：UDP 心跳 + ASDU 解析，而非 ROS2 订阅
- **Context**：需要读取全部状态；UDP 心跳与 ROS2 订阅两条路都可行。
- **Decision**：默认 UDP 心跳通道；ROS2 作为 `DataSource` 的另一个实现**预留接口**，不上主链路。
- **Consequences**：获得零 ROS2 依赖、最稳、与 lite3 同构；放弃话题级 schema 与语义丰富度；协议字段语义未吃透前解析器可能反复改——**用 ACL 隔离该代价**。

### ADR-002 部署位置：后端驻 AOS 196
- **Consequences**：内网直达监控协议与 MediaMTX，LAN 只暴露 Web/WS；放弃"部署在开发机"（够不到内网）。代价：须绕开 196 的时钟/TLS/丢包问题（C6）。

### ADR-003 视频经后端代理（RTSP→HLS），浏览器不直连
> ⚠️ **2026-10-16 修订：主链路已被 ADR-011 取代**（改为浏览器直连 MediaMTX 的 WebRTC/WHEP）。
> 本 ADR 的 ffmpeg 中继**保留为第三层兜底**（代码 / 单测 / API 均未删除），但不再是默认链路。
- **Consequences**：规避浏览器不支持 RTSP 与跨网直连；放弃"零中转"的极低延迟（监控场景可接受）。代理消耗 CPU（RK3588 可用 `/dev/mpp_service` 硬解）。

### ADR-004 控制通道分层开放：L0 只监 / L1 低危可控 / L2 高危黑名单
- **Context**：初版设计"本期零真实指令，只留闸门接口"。用户 2026-10-14 要求**本期集成控制指令**（Web 控制运动 + 唤醒传感器），参考 `m20-android-sdk`；协议真相判明后（帧头+JSON，§10）实现成本大幅下降。安全红线（C4：Charge=2 官方标注危险）不变。
- **Decision**：控制通道本期实现，按危险度分层：
  - **L0 只监（默认）**：任何控制请求 `403 CONTROL_DISABLED`——**软急停除外**（安全手段优先于开关）；
  - **L1 低危可控**（需配置 `enable` + 前端二次确认 + WS 心跳租约）：站立/趴下/软急停/步态切换/使用模式/照明灯/休眠唤醒/充电开始-退出；
  - **L2 高危黑名单（永不开放）**：`Charge=2`（清除充电状态）。
- **Consequences（获得）**：Web 端可遥控运动（轴指令 20Hz）+ 一键急停 + 休眠/唤醒；打开"上装设备/机械臂"等未来集成的协议底座（PatrolDevice 自定义消息）。
- **Consequences（代价与缓解）**：机器人可被 Web 端驱动 → 运动风险 → 用四道闸缓解：① 分层开关 + 租约；② **轴指令看门狗（只停不趴）**（松杆/停更/断连 → 零位停发等待恢复；**绝不自动软急停**——两次事故复盘后整体切除，§6.4）；③ 运动前置校验（MotionState ∈ {站立, RL控制} + 常规模式）+ 服务端值域钳制（安全上限 ±0.40）；④ 全量审计日志（谁/何时/发了什么）。
- **为何不是"全开"或"全关"**：全开违背 C4 安全红线；全关不满足用户本期需求。分层让"监控用户"和"操作员"两种角色各得所需，且黑名单指令在任何配置下都到不了机器人。

### ADR-005 实时通道选 WebSocket 而非 SSE
- **Context**：监控是 server→client；未来控制需 client→server。
- **Decision**：WS（复用 lite3 前端 composables/api；控制指令可走同一连接或 REST）。
- **Consequences**：获得双向能力与前端复用；放弃 SSE 的简洁自动重连——需自实现 ping/pong 与重连（成熟模式，成本可控）。

### ADR-006 状态权威唯一 + 新鲜度语义
- **Decision**：StateStore 是唯一权威，ingestion 独占写；快照带 per-topic `ts`；超时即 stale。
- **Consequences**：前端永远不猜数据新鲜度；放弃"各 topic 独立订阅推送"的带宽优化（单客户端 10Hz 快照仅数 KB/s，无需优化）。

### ADR-007 无数据库：内存状态 + 有界原始报文环形缓冲
- **Context**：监控工具，状态即问即答，无历史查询需求。
- **Decision**：不引入 DB；保留最近 N 帧原始 ASDU（有界，默认 1000 帧）供调试（对齐 lite3 `RawPacket`/`PacketMonitor`）。
- **Consequences**：重启即失历史（可接受）；放弃事件历史查询——若后续要"异常事件时间线"再加 SQLite（见 §18 演进）。

### ADR-008 配置集中 + 启动校验（fail fast）
- **Decision**：目标 IP/端口/心跳频率/阈值全部走 `config.py`（env 可覆盖），启动时校验必填项与端口冲突。
- **Consequences**：换主机只改一处；放弃"改了就跑"的随意性——**配置错误要在启动时炸出来，而不是运行时静默失败**。

### ADR-009 后端语言与框架：Python 3 + FastAPI（而非 Go / Node / Rust）
- **Context**：需选定后端语言；候选 Python(FastAPI) / Go / Node(TS) / Rust。
- **Decision**：**Python 3.10+ + FastAPI + uvicorn**，venv 隔离。
- **Consequences（获得）**：
  1. lite3 后端代码（`parser.py` / `state_manager.py` / WS / `main.py`）可**复制改造**，工期从周降到天；
  2. 团队是 ROS/Python 原生，零学习成本；
  3. ADR-001 预留的 `Ros2TopicSource` 用 `rclpy` 零摩擦接入；
  4. `pydantic-settings` 直接兑现 ADR-008 的 fail-fast；
  5. 196 已具备 `python3` / `ffmpeg` / `cv2`（2026-10-14 实测），无需另装运行时。
- **Consequences（放弃）**：
  1. Go 的单静态二进制部署便利——用 venv + systemd 弥补，RK3588 上差异可忽略；
  2. Go 的 goroutine 并发模型——asyncio + 单 ingestion 线程已够；视频转码是**独立 ffmpeg 进程，不吃 GIL**，故 GIL 在本项目不是瓶颈；
  3. 前后端同语言的类型共享——以 OpenAPI / 共享 JSON 契约替代。
- **为何不选**：
  - **Go**：lite3 后端**一行都不能留**（全量重写），且 `rclpy` 不可用会关死 ROS2 增强门；收益（静态二进制）在 venv 方案前不明显。
  - **Node**：196 运行时未验证；二进制解析与数据校验生态弱于 Python 的 `struct` + pydantic；团队不熟。
  - **Rust**：10Hz 遥测属过度工程，编译期与学习成本不成比例。

#### ADR-009 补充：换其他语言的损益账（2026-10-14，用户追问"换语言会不会有增强"）

**先算工作量画像——本控制台是低速率遥测面板，不是高并发服务**：

| 负载 | 量级 | 语言敏感度 |
|---|---|---|
| ASDU ingestion | 2+10+2Hz ≈ **14 帧/秒**，每帧数十至数百字节，解析**微秒级/帧** | 任何语言均 <0.1% 单核 |
| WS 扇出 | 10Hz 快照 × LAN 内 1–5 个浏览器，数 KB/s | 可忽略 |
| 视频转码 | **独立 ffmpeg 子进程**（C 实现，不吃 GIL） | 与语言无关 |
| 心跳发送 | 1Hz，一个 socket | 可忽略 |

**语言不在瓶颈上**。真正的约束是 Q2（ASDU 字段语义待真机核对）、C6（196 时钟/丢包）、联调迭代速度——三者均与语言无关。且 AOS 普通进程虽只剩 3 个小核（isolcpus 隔离了大核），本控制台预算也仅 ~1% 单核，余量充足。

**换语言的净损益**：

| 候选 | 增强 | 代价 | 净判断 |
|---|---|---|---|
| Go | 单静态二进制；goroutine（本负载用不上） | lite3 后端 **100% 重写**（T1.3–T1.7 全废）；**无 `rclpy` 等价物 → 关死 §18 路径 1 的 ROS2 零摩擦接入**；venv 已弥补部署差异 | **负** |
| Node(TS) | 前后端同语言 | 196 运行时未验证；二进制解析/数据校验生态弱于 `struct`+pydantic；后端全重写 | **负** |
| Rust | 理论最快 | 10Hz 遥测属过度工程；编译期+学习成本；后端全重写；同样无 rclpy | **负** |
| C++ | 与机器人本体同栈 | Web 开发生态最差；全重写；无净收益 | **负** |

**何时重议语言（触发条件，出现任一才重开此决策）**：
1. **实测**控制台在 196 上持续占用 >20% CPU，或 WS 并发客户端 >50——按实测数据说话，不按想象；
2. 范围升级为**多机器人汇聚网关**（N 台 × 高速率扇入——那更是 172.31.68.227 汇聚点的活，不是本控制台）；
3. 团队更替为 Go/Rust 原生团队；
4. 196 上 `python3` 被厂商裁剪不可用。

**架构已留的口子**：`DataSource` / `ControlSink` / WS schema 契约三层抽象意味着——即使将来真需换语言，替换单位是**模块或旁路进程**（如解析热循环用 Rust 写 PyO3 扩展，或按 §18 路径 2 拆独立进程），**不是整个后端**；前端因 schema 冻结而零改动。

### ADR-010 控制出口对称抽象：`ControlSink`
- **Context**：数据入口已抽象为 `DataSource`；若控制出口写死 UDP socket，未来接 ROS2 控制回路（`cmd_vel` → topic）必须重构。
- **Decision**：控制出口同样抽象为 `ControlSink` 接口，本期实现 `UdpControlSink`（复用同一 UDP socket，真实出口），**预留 `Ros2ControlSink`**。
- **Consequences**：与 `DataSource` 严格对称，"数据来源 / 控制出口"两个维度均可替换；代价是本期多一层薄抽象（一个接口 + 一个实现，约 20 行）。`UdpControlSink` 不再是 no-op，但 `ControlSink` 接口签名不变——**上层（网关/看门狗/前端）对"出口是 UDP 还是 ROS2"零感知**。

### ADR-011 视频改为**浏览器直连 MediaMTX**：WebRTC(WHEP) 主 + HLS 兜底（2026-10-16，**取代 ADR-003 的主链路**）
- **Context**：用户提出"相机画面能不能前后都抓取 + 采用 WebRTC"（2026-10-16）。复核 196 现状后发现三个此前未核实的事实：① MediaMTX 实为 **v1.4.2**（非早期版本），`webrtc: yes` / `webrtcAddress: :8889` / **ICE UDP `:8189`** / **`webrtcAllowOrigin: '*'`** 全部就绪，CORS 预检实测 `204` + `Access-Control-Allow-Origin: *`；② 其自带 HLS（`:8888`）**双路均可用**（video1/video2 各 200，ffmpeg 抓帧各 40KB / 37KB 均出图，H.264 800×600）；③ ADR-003 的"单路 ffmpeg 中继"**结构上无法同时输出两路**（切换需重启 ffmpeg），是"双路同看"的硬约束。
- **Decision**：视频主链路改为**浏览器直连 MediaMTX，不再经后端中转**：
  - **主链路 WHEP/WebRTC** `http://<host>:8889/<path>/whep` —— 原生 `RTCPeerConnection`（无新增 npm 依赖），`POST application/sdp` 换 answer，媒体走 ICE/UDP，延迟约 0.3s；
  - **兜底 MediaMTX HLS** `http://<host>:8888/<path>/index.m3u8` —— hls.js，约 2–3s；
  - **第三层** 后端 `VideoProxy`（ffmpeg → `/hls/live.m3u8`）**保留但不再是主链路**（代码 / 单测 / API 全保留，零破坏）；
  - **主机名由前端按 `location.hostname` 拼**，后端 API 只给端口与 path —— 写死 `127.0.0.1` 会让浏览器连自己（页面在本机看似正常、上机即黑屏），写死 `192.168.0.196` 换网段即失效；
  - **前后双路同看**（video1 前 / video2 后 各一个 `<video>`，布局可切"并排 / 仅前 / 仅后"）；每路独立降级：WebRTC 重试耗尽 → 该路转 HLS，互不影响。
- **Consequences（获得）**：延迟 1–3s → ~0.3s；**前后双路同时看**（旧架构做不到）；后端省掉一路 ffmpeg（CPU 更宽裕）；链路少一跳（少一个故障点）；两路独立降级。
- **Consequences（代价与缓解）**：① 依赖浏览器到 196 的 **UDP `:8189` 可达**（同 WiFi 网段成立；跨网段/NAT 会失败）→ 自动降级 HLS；② 页面为 http（非 https）——WHEP **拉流**不需要 `getUserMedia`，`RTCPeerConnection` 在非安全上下文仍可用；③ MediaMTX 的 8889/8888 由厂商 `start.service` 拉起（非本工程引入的新依赖，但属外部前置）。
- **边界不变（重要）**：本决策改的是**监控体验**（低延迟 + 双路），**不是**把遥控安全寄托在视频延迟上——ADR-004 的四道闸与"看门狗只停不趴"仍是控制安全的唯一依据，两条路不混。

### ADR-012 定时移动**计时在后端** + 轴指令双通道可选（steer 2/21 / real 2/25）（2026-10-16）
- **Context**：用户两条诉求 —— ① "在速度控制中选择左右移动，一点反应都没有"；② "加一个选方向 + 速度 + 移动多少秒的功能"。① 的已有取证：车侧 `cmd_vel_limit.yml` 中 `vy_limit=0.40` 与 `vx_limit` **相同**（排除"横移对输入值要求更高"）；审计证明 `y=-0.4` 多帧 `result=ok`（指令确实发出）；取样时 `motion_state=4`（趴下，轴指令本就不生效）。**2026-10-16 新取证**：basic_server 内三条话题 —— `2/21 cmdHandle_Steer → /STEER + /HANDLE_STEER`、`2/25 cmdHandle_RealSteer → /REAL_STEER`（字段同构）；`rl_deploy` 二进制中 `/STEER` 与 `/REAL_STEER` 字符串均在，其 steer 处理链产出 `current_cmd_velx / current_cmd_vely / current_cmd_velyaw`（**RL 侧具备横向速度通道**）。但"2/21 的命令最终落在哪条订阅队列"**无法只靠字符串定论**（drdds 模板同时含 Pub/Sub 两类符号）→ 需要"同一轴值换通道"的对照实验。
- **Decision**：
  - **定时移动放后端**（`AxisWatchdog.feed_timed`）：`POST /api/v1/control/axis/timed {x..yaw, duration_s∈[0.5,30], channel}`。计时走内部 deadline、**不依赖前端定时器**（浏览器 `setInterval` 会被节流——切后台/省电；靠前端计时停不住车）；到点走与松手完全相同的路径（零位一帧 + 停发，**绝不软急停**）；`feed()/pause()/stop()` 均中止它（人随时可抢回控制权）；API 入口先走 `ControlGateway.precheck`（只过闸不发送）——未开启 / 无租约 / 未站立**即时拒发**（被拒入审计），不让用户看着倒计时空转。
  - **轴指令通道可选**：`channel: "steer"`（2/21，默认，**行为与旧版完全一致**）/ `"real"`（2/25）。编码 `patrol_codec.axis`(21) / `axis_real`(25)；COMMANDS 注册 `axis_real`（`motion: True`，同走前置校验）；钳制闸覆盖两条通道；**零位帧跟随当前通道**（`send_safety_zero(command=…)`），保证正在控制的那条订阅队列立刻看到零位。
- **Consequences（获得）**：① 定时移动天生"断网也按时停"；② "同一轴值换通道"变成**一键可做的对照实验**（配合面板「实际 左右 Y」读数），把"左右平移无反应"从猜测变成可判定的实验；③ `precheck` 让"点了没反应"类问题有即时的被拒原因（审计可查）。
- **Consequences（代价与缓解）**：多一个通道选择项 = 少量认知负担（默认 steer，仅排查时切换）；30s 上限防"长按无人看管"（API 层 422 + 看门狗内部 30s 钳制，双保险）。
- **边界不变**：通道选择**不改变任何安全语义**——两条通道过同一套四道闸（前置 + 钳制 + 审计）；"只停不趴"仍是看门狗唯一兜底策略。
- **2026-10-16 晚：对照实验已执行、结论见 ADR-013** —— 通道假设**被推翻**（两通道在基础步态下行为完全一致）；"左右平移无反应"的真因是**步态**。`channel` 选择**保留作排查工具**，默认仍是 steer。

### ADR-013 横移能力由**步态**决定：后端 `warning` 字段 + 前端实时警示（2026-10-16，**推翻 ADR-012 的通道假设**）
- **Context**：ADR-012 的"同一轴值换通道"对照实验已由真机执行（`tools/probe_motion.py`，5Hz 同时采 `motion` + `basic` + `watchdog` 三联数据，以审计的"步态切换"记录为锚对齐时间轴，1290 有效样本 / 280s）。实测：
  - 0x1001 空闲底噪：`vy ≈ +0.057 m/s`（稳定常量、非抖动），`vx ≈ +0.065`，`height = 0.574`；
  - 0x1001 + real(2/25) 右移 0.4×5s：`|vy|max = 0.0543` —— **在底噪内 ⇒ 不动**；零位帧正常发出、审计全 `ok`（排除"没发出去"）；
  - 0x1001 + steer(2/21) 右移 0.4×5s：`|vy|max = 0.0503` —— **同样不动** ⇒ **通道假设不成立**；
  - 切 **0x3002 平地（敏捷）** 后右移 0.3×2.9s：`|vy|max = 0.1011`（≈2× 底噪）+ **`height` 0.574 → 0.461**（机身下沉）⇒ **动了**（用户目视确认）；
  - 同步态前进 0.2×2s：`|vx|max = 0.3098`（阳性对照成立，说明指令链本身健康）。
  - 用户视角佐证：基础步态下"姿态有细微变化但没移动，5s 结束后姿态恢复"——正是"Y 只原地调姿态"的现象学描述。
- **Decision**：**把结论产品化，但不做拦截**（保留用户自行验证与标定的余地）：
  - **后端**：`POST /api/v1/control/axis/timed` 响应新增可选 `warning` 字段 —— 当 `|y| ≥ 0.01` 且当前步态属标准系时返回提示文本（0x1001 = 实测不支持横移；0x1003 = 同系未实测；敏捷系或 `basic` 未上报 = 空串，不误报）。
  - **前端**：两处**实时预判**（读 `basic.gait`，比等服务端返回更早）—— ① 摇杆区：模式为「前后 + 左右平移」且步态属标准系 → 黄框警示；② 定时移动区：方向选「左移 / 右移」且步态属标准系 → 黄框警示（后端 `warning` 作为 `basic` 数据滞后时的兜底）。文案统一指向**「平地（敏捷）0x3002」**这一可用解。
- **Consequences（获得）**：① "左右平移没反应"从"看不出来的玄学"变成**界面上就有解释**，用户不必再看 `linear_y` 读数猜；② 结论可复现（探针工具 + 审计锚点已入库）；③ 未改动任何控制语义，标准系步态下"原地调姿态"能力（对正机身等用途）仍可正常使用。
- **Consequences（代价与缓解）**：① 敏捷步态 0x3002 会让**站高从 0.574 降到 ~0.46（机身降约 11cm）**——属该步态正常行为，已在文档与面板提示中写明；② 若后续固件改了步态语义，需同步更新 `_lateral_gait_warning` 与前端 `lateralHint` 两处文案（**已用同一个 `patrol_codec.GAIT_*` 常量族 + 单测守护，避免各写各的**）。
- **边界不变**：警示**只提示、不拦截**（与 ADR-004 的"安全闸"分层明确区分：闸是硬的，提示是软的）；横移的**真机标定**（如 Y 起动阈值）仍属待办。
- **另记（未处理）**：`_clamp_params` 六轴统一钳 ±0.40，而车侧 `vyaw_limit = 1.2` → **转向只用到官方量程 1/3**；放宽涉及转向失控风险，待真机标定后另行评估。

### ADR-014 单页改**三标签页**（监控 / 相机 / 运动控制）+ 切标签即松手（2026-10-16）
- **Context**：用户诉求"监控各个传感器状态的界面、相机画面界面和运动控制界面能不能分成三个可切换的标签页，参考 lite3 上的 monitor 程序"。原单页纵向堆叠（RobotStatus → JointPanel → MotionPanel → VideoPanel）的问题：① 视频在最后一屏，看相机要滚很久；② 写方向控件与只读遥测混在同一视口，误触面大；③ 单屏信息密度过高。
- **Decision**（对齐 lite3 monitor 的两条取舍 + 一条 M20 特有的加固）：
  - **三标签分层**：`传感器监控`（RobotStatus + JointPanel，只读遥测）/ `相机画面`（VideoPanel，只读视频）/ `运动控制`（MotionPanel，写方向）。写方向放最后、标签用**警示色激活态 + 红点**、页内顶部常驻警示条（与 lite3 的 `console` 标签同款语义）。
  - **一律 `v-show` 不用 `v-if`**：切换只改可见性、**不卸载组件**。理由是实测出来的——`VideoPanel.onUnmounted` 会 `stopStream` 拆掉全部取流（WHEP/HLS 重连要 0.3~2s，且 MediaMTX 侧会话churn）；`MotionPanel` 卸载会让定时倒计时轮询断更。代价：隐藏的视频流仍在解码（可接受，换回瞬时无缝）。
  - **刻意不记忆上次标签**（无 localStorage）：每次加载都回到只读的「传感器监控」——防止重新打开页面直接落在写方向页上误触指令（lite3 同款取舍，写方向场景下这条更重要）。
  - **★切标签即松手（M20 特有加固）**：`MotionPanel` 新增 `active` prop + `watch`：`active` 变 false 且摇杆激活中 → 立即 `releaseJoy()`（零位停发）。**根因**：`onJoyDown` 用了 `setPointerCapture`，多指触屏下"一指按住摇杆、一指点标签"会让**捕获中的 pointermove 继续喂看门狗**——车会在用户看不见的标签后面继续走。此前只有"页面切后台"（`visibilitychange`）一条松手路径，覆盖不到标签切换。
- **Consequences（获得）**：① 视频与遥测一屏可达，不再滚页；② 写方向入口收窄到单一标签 + 警示色 + 常驻警示条，误触面显著下降；③ 切换零成本（连接/倒计时都不重建）。
- **Consequences（代价与缓解）**：① 三个面板常驻内存与连接（视频双路持续解码）——单机单用户场景可接受，若后续要多用户并发再考虑按需挂载；② 摇杆松手依赖 `active` prop 传递——若未来加第四个标签或改布局，**必须同步传 `:active`**（已在 prop 注释与警示条文案中写明）。
- **定时移动的跨标签语义（明确取舍）**：定时移动由**后端**执行，切标签**不中断**（否则"切到相机标签边看边动"这个自然工作流被破坏）；配套**跨标签可见性**——顶部琥珀色"定时移动进行中：剩余 Xs / 共 Ys"横幅 + 「运动控制」标签上的红色倒计时角标，确保任何标签下都知道"车还在动"。中止需回运动控制标签（横幅已说明）。
- **边界不变**：不新增任何控制通道、不改任何安全语义（四道闸 / 只停不趴 / 软急停仅由人触发全部照旧）；标签切换本身**不是**安全边界，安全边界仍是 ADR-004 的闸 + 看门狗。

### ADR-015 心跳（遥测）可主动让渡 + "系统关停不会让车趴下"实证（2026-10-16）
- **Context**：用户问"能不能主动发送和停止心跳，当系统关闭后，m20 会不会应该没有心跳信息自动趴下"。这触及失控保护（dead-man switch）语义，必须先取证再决定要不要做、怎么做。
- **取证（2026-10-16，basic_server / rl_deploy 二进制 + 协议文档 + 真机实验）**：
  1. **心跳只是"注册推送对象"**：docs/04 §1.2.1 原文"机器人会向**持续发送心跳指令的 IP 和端口**上报实时状态信息和异常状态信息"；basic_server 二进制含 `Heartbeat new client connected, peer=[%s:%d]` / `Heartbeat timeout! Cleared %zu client(s).` —— 心跳超时的动作是**清除客户端**（停止向我们推送），**不是**运动保护。
  2. **心跳与指令是两个独立 UDP socket**：`UdpHeartbeatSource._sock`（发心跳 + 收状态推送）与 `UdpControlSink._sock`（发指令）各自独立 → 停心跳**不影响**指令链路可达性。
  3. **车侧真正的断链保护在 rl_deploy 的 DDS_CMD 看门狗**：二进制字符串 `DDS_CMD topic data update timeout %f. Disable lynx`（另有 `GetStatus` 分支）；状态机符号 `StandUpState / LieDownState / JointDampingState / StartDampingState / ChargeLiedownState`。车侧另有 150ms steer 看门狗（无新数据即清零速度字段，见 T2.7 §7）。
  4. **★真机实证（决定性）**：`systemctl stop m20pro-console` 停 **50s**（心跳与指令全部中断）后重启 → `motion_state` 前后均为 **17（RL 站立）**、`height` 0.494 不变、`linear_x/y` 仅空闲底噪。旁证：控制台重启后 `sent_packets=0`（零指令）持续数分钟，车同样稳定站立。
  - **结论：机器人不会因为"没心跳 / 系统关闭"而趴下。** 且**不应追求"断链自动趴下"**——2026-10-15 两次事故已证明站立中被卸力软塌（`JointDampingState`）就是摔倒；正确语义是"断链 → 停 + 保持站立"（看门狗 v3「只停不趴」）。
- **Decision**：
  - **提供主动让渡能力**：`UdpHeartbeatSource.pause()/resume()`（停发但不拆 socket/线程，恢复瞬时）+ `POST /api/v1/link/heartbeat {paused, confirmed}` + `GET` 同径查状态。暂停是**危险方向**需二次确认；恢复视野是安全动作不设卡。
  - **★不蒙眼开车（新增第五道闸）**：`ControlGateway._check_telemetry` —— 遥测暂停时拒绝一切驱动类指令（`TELEMETRY_PAUSED`，409），豁免 `heartbeat`（否则"停了想恢复"被自己的闸锁死）与 `soft_estop`（安全手段优先）。暂停 API 内部还会**先自动零位停发**正在进行的控制（摇杆 / 定时移动）。
  - **降级语义分色**：复用 `ServiceSnapshot.degraded / degraded_reason`（**未动冻结契约**）承载 `heartbeat_paused`；前端据此把"主动暂停"（琥珀横幅 + 恢复按钮）与"链路故障"（红色横幅）区分——`connected=False` 的提示语义是"快检查"，而这里是"别把没数据误解成车没事"。
- **Consequences（获得）**：① "控制台挂了车会怎样"从推测变成**可一键复现的实验**（暂停心跳 ≈ 让渡遥测，全停服务 ≈ 系统关闭，两者都已实证车保持站立）；② 多端竞争时可主动让出推送（机器人只推给持续心跳的一方）；③ 遥测暂停不会顺带把指令链路一起断，避免"以为断了其实没断"的错觉。
- **Consequences（代价与缓解）**：① 停心跳即失明，故加了二次确认 + 自动停控制 + 驱动闸三重保护；② `degraded_reason` 是前后端字符串约定（与既有 `CONTROL_DISABLED` 等 reason 码同模式），已用单测钉住常量 `main.DEGRADED_HEARTBEAT_PAUSED`。
- **边界不变**：不新增任何运动能力、不改四道闸既有语义（新闸只做"减法"：多一种拒绝场景）；软急停永远可达；"只停不趴"仍是唯一兜底策略。

### ADR-016 开启开机自启（2026-10-17）：以实测性能为依据 + 开机顺序加固（**取代 2026-10-16"关闭自启"的临时决定**）
- **Context**：用户问"这个 monitor 程序对 AOS 主机性能占用怎么样，如果不高的话，还是开启开机自启动"。此前（2026-10-16）自启被关闭是出于"占用未知"的谨慎；而实测发现 AOS 每次重启后控制台都停在 `inactive (dead)`，需要人工拉起——**这本身就是可用性缺陷**（机器人重启后监控盲区）。所以本条 ADR 的前提是"先测量，再决定"，而不是先入为主地开或关。
- **★实测数据（2026-10-17，AOS 独占测量）**：

  | 指标 | 控制台 `m20pro-console` | 对照（同主机同时段） |
  | --- | --- | --- |
  | 常驻内存 RSS | **≈ 49 MB** | — |
  | 线程数 | **4** | — |
  | CPU 空载 | **1.71 %** | `rl_deploy` 12.7 %、`systemd-journald` 11.2 %、`yesense_node` 8.5 %、`basic_server` 3.7 %、`hsLidar` 2.6 % |
  | CPU：1 客户端 10 Hz | 6.22 % | — |
  | CPU：2 个远程客户端 10 Hz | 4.33 % | — |
  | CPU：3 并发客户端 | 15.13 % | — |
  | 生命周期均值 %CPU | 6.7 | — |
  | CPU 亲和 | **0-3** | `rl_deploy` **4-5**（内核 `isolcpus=0,4,5,6,7`）→ **零重叠** |

  - **口径**：CPU 为 8 核总量口径（`nproc --all = 8`，可用 `nproc = 4`）。加压场景的 HTTP 客户端**从 PC 侧发起**，否则客户端自身 CPU 会被算进目标进程（测量中踩过这个坑，修正后 6.22 % → 干净的 4.33 %）。
  - **★决定性论据是 CPU 亲和**：控制台 `Cpus_allowed_list = 0-3`，运控 `rl_deploy` 钉在 `4-5` —— **两者核集合不相交**，即使控制台满载也不可能饿死运控。内存 49 MB 对 16 GB 机型可忽略。
- **Decision**：
  1. **开启自启**：`systemctl enable m20pro-console`（`WantedBy=multi-user.target`，已确认生成 `multi-user.target.wants` 符号链接）。`deploy/install.sh` 第 140 行本就带 `systemctl enable`，故重新部署后仍保持自启。
  2. **开机顺序加固**：单元新增 `After=start.service`，**只排序、不加 `Requires`/`Wants`**。厂商 `start.service`（Type=forking, enabled）负责拉起 `basic_server`（UDP 30000 状态源）与 `mediamtx`（RTSP 8554 相机源）；让它先跑可消除开机瞬间"链路断开 / 相机离线"的假警报。**若厂商服务起不来，控制台照常启动**——只监不控的服务如实显示"链路断开"才是正确行为，绝不能因依赖失败而拖死开机。
  3. **不改重启策略**：沿用 `Restart=on-failure` + `RestartSec=3`。实测 `stop → start` 冷启动 6s 内 `active`、遥测恢复（`connected=true`、报文 580/580 零解析错误）。
- **Consequences（获得）**：① 机器人/196 重启后监控自动恢复，消除人工拉起前的盲区；② 开机顺序避免假警报，减少"重启后看到红条以为坏了"的误判；③ 性能从"担心"变成"有数"，后续新增功能有基线可对比。
- **Consequences（代价与缓解）**：① 控制台会在机器人开机后自动开始发心跳（抢推送对象）——与 ADR-015 的让渡能力并存，需要独占推送时可一键暂停；② 自启后若后端启动失败会按 `on-failure` 反复重启，已用 `systemd-analyze verify` 确认单元无循环依赖。
- **遗留观察（与自启无关，2026-10-17 发现）**：本次核查发现 `/dev/video*` **全部不存在**，`dmesg` 显示 `usb 7-1: USB disconnect`（开机后 667s，设备 `SM_USB_107X`）——即**双目相机在物理层掉线**，`mediamtx` 没有任何已发布路径（`/video1`、`/video2` HLS 均 404），厂商 `push_video.sh` 自掉线起一直在空转重试。这是硬件/接线问题，不是本控制台的缺陷，需人工检查相机 USB 连接与供电。

### ADR-017 回零与"唤醒"语义取证：状态照实呈现，不臆造指令（2026-10-17）
- **Context**：用户三问 —— ① 开机第一次站立是不是都要先回零、能不能识别到并同步到运动控制页；② 「唤醒」按钮是不是在唤醒传感器，能否按相机 / GPS / 雷达拆到各自标签页；③ 有没有主动关闭传感器的功能。这三个问题都触及**协议边界**（哪些能力真实存在），必须先取证再决定，否则会把"以为有"做成"假按钮"。
- **★取证（196 二进制 + 配置 + 运行日志 + 真机抓包）**：
  1. **回零真实存在且默认自动开启**：`/opt/robot/share/basic_server/conf/basic_server.toml` 第 14 行 `autoResetJointsZero = true` —— 这就是"开机后第一次站立会先回零"的直接成因。
  2. **回零状态本来就上报了**：真机 `BasicStatus` 实测含 `ResetJointsZero` 与 `StatusCode`（此前解析器未映射，属遗漏而非新增能力）。运控 `rl_deploy` 含 `qw_m20::ZeroCalibrationState` 状态机与 `state=SetZero` 日志串。
  3. **回零有前置约束**：basic_server 原文 `can not reset joints zero unless standing or lying down`——只有站立或趴下态可回零。
  4. **"唤醒"不是传感器级**：docs/04 §1.2 请求指令全集只有 11 条，与传感相关的仅 `1101/6` 休眠模式设置（`Sleep`/`Auto`/`Time`），**没有任何按相机 / 雷达 / GPS 分别开关的指令**。
  5. **但休眠确实会连带关传感器**：`Basic_server` 运行日志实证，进入休眠依次 `SetLED_FILL` → `SetFAN_SPEED` → **`SetVIDEO_POWER`** → `SetJOINTS_POWER` —— 所以"唤醒退出休眠"**在效果上**就是恢复相机 / 雷达 / 灯 / 风扇供电。厂商 change_log v1.2.70 亦记「相机使能仅保存用户手动操作的配置，休眠自动关闭后直接重启」。
  6. **分设备供电状态是有的**：`DeviceStatus.DevEnable` 真机实测 `{"FanSpeed":100,"LoadPower":1,"LedHost":1,"LedExt":1,"FP":1,"Lidar":{"Front":0,"Back":0},"GPS":1,"GPSMode":69905,"Video":{"Front":1,"Back":1}}`。basic_server 内部按 `VIDEO_POWER`/`LIDAR_POWER`/`JOINTS_POWER`/`LED_FILL`/`FAN_SPEED` 分通道控制（见其日志），但**UDP 侧未公开单设备开关的 Type/Command**（其 `cmdHandle_DeviceCtrl`/`ResetJointsZero` 等 handler 存在，编号未知）。
- **Decision**：
  1. **回零：只呈现、不臆造值域**。`ResetJointsZero` 值域**未见任何官方文档**，故仅标注实测的 `0=无需回零`，其余透传数值 + "回零中/待回零(N)"；运动控制页新增「关节回零」指示，并在 `motion_state=3`（开机阻尼）时常驻提示"点站立后运控会先回零再起立"。
  2. **唤醒入口按用户要求分区，但语义统一标注为整车**：相机画面页放「唤醒整车（恢复相机供电）」并就地显示相机前后供电；运动控制页保留「唤醒整车」+ 雷达前后供电；GPS 页待建，字段已备（`gps_enable`/`gps_mode`）。**按钮文案一律带"整车"二字**，避免再次被理解成单设备唤醒。
  3. ~~**不做"主动关闭传感器"按钮**：协议无此能力，做了就是假按钮。~~ **⚠️ 已被 ADR-018 推翻**（2026-10-17 抓包破解 `1101/3`）—— 当时结论过于保守，能力确实存在、只是编号未公开。保留本条仅为记录判断演变过程。
  4. **不盲扫指令编号**：basic_server 有多条未公开且含动作的 handler（含 `cmdHandle_Reboot`），在车处于站立态时盲试 `1101/x` 有触发急停/重启的风险。后续若需单设备控制，改用**零风险取证**：让用户在厂商 App 上操作一次，同时 `tcpdump` 抓 30000 端口报文取真实编号。**该取证路径已在 ADR-018 走通并拿到编号。**
- **Consequences（获得）**：① "首次站立为什么慢"由推测变成界面上可看的回零状态；② 相机黑屏时可在相机页就地唤醒，不必切页；③ 雷达 `Front/Back = 0/0` 这类"设备其实没供电"的事实首次可见（此前完全不可见）。
- **Consequences（代价）**：① 分设备开关只能"看"不能"点"，与用户预期有落差——已在界面文案中写明原因；② `device` topic 上报频率低于 `basic`，新增字段可能有百毫秒级延迟（实测 age 188ms，可接受）。
- **边界不变**：未新增任何下发指令、未改控制闸与看门狗语义；软急停永远可达。

### ADR-018 分设备供电开关 `1101/3`：抓包破解 + 第五道闸（2026-10-17，**修正 ADR-017 决策 3**）
- **Context**：ADR-017 决策 3 判断"协议无单设备开关能力"，因此只做状态呈现、不做按钮。用户 2026-10-17 追问「不能单独的开启或关闭相机、gps或激光雷达吗」，并配合在厂商 App 上实际操作开关、同步抓包 —— 这一轮取证**推翻了 ADR-017 的前提**：能力确实存在，只是编号未公开。
- **★取证（tcpdump 抓 30000 + 对照车侧日志 + 自己回放）**：
  1. **抓包窗口**：`/tmp/m20cap.pcap`（5.6MB，02:21:25~02:23:38）。源地址两类：厂商 App `10.21.33.11:40778`（665 包）与本机回环 `127.0.0.1`（控制台心跳）。**99 字节的全是心跳**，过滤后只剩 5 条指令包。
  2. **指令族确认**：`1101 / 3`，`Items` 的**键名**决定目标设备。抓到的 5 条与车侧 `[CmdHandle]` 日志逐条对齐：
     - `{"GPSMode":69905}` → `设置GPS模式为:0x11111`
     - `{"Lidar":{"Front":0,"Back":0}}` → `设置雷达开关 front:0 back:0`（用户关雷达，实证）
  3. **★破解关键：帧头 magic 是权限位**。同样 Items 我们自己下发却回 `ErrorCode 57351 / "No operation permission"`。对比 App 与我们自己的 16 字节帧头，唯一差异是 magic：App = `EB 90 EB 90`，我们 = `EB 91 EB 90`。**换 magic 后立刻 `ErrorCode 0` 并真正执行**（车侧日志同步出现 `设置广角相机开关 front:1 back:1`）。
  4. **magic 作用域实测**：`1101/7` 休眠查询、`1101/2` 照明灯、`100/100` 心跳在两种 magic 下**都正常**（`1002/1` 则都回 `Unsupported protocol type`）⇒ 该 magic 只对 DeviceControl 类指令构成门槛，**是超集而非另一套协议**。
  5. **键名逐个回放实证**（只下发"当前已有值"，幂等零风险），车侧日志确认：`Video`→广角相机开关、`Lidar`→雷达开关、`GPS`→GPS开关、`LedHost`→主机电源指示灯、`LedExt`→外部负载电源指示灯、`FanSpeed`→风扇转速、`LoadPower`→外部负载开关、`FP`→对频模块开关。
  6. **★上报值域不是布尔**：开启雷达后 `DevEnable.Lidar` 变 `2` 而非 `1`（车侧日志 `mLIDAR_POWER_.front 2` = 运行中；1 = 已供电/启动中；0 = 关）。⇒ 判定"是否关闭"只能用 `== 0`。
  7. **UDS CLI 不通往这条路**：`/tmp/basic_server.cmd.socket` 需 root，且其子命令只有 `example/cmd/led/motion/dds`（`cmd` 仅 `getinfo`），**没有设备电源开关**。
- **Decision**：
  1. **`1101/3` 进指令表**，键名走**白名单**（`DEVICE_SWITCH_SPEC`，9 键）—— 这条指令能物理断电任何设备，键名猜错等于盲目操作硬件，绝不透传任意 Items。`pair` 类型必须显式给 `Front` 与 `Back`，**绝不默认 0**（那等于悄悄断电）。
  2. **magic 按指令切换、绝不全局替换**：`patrol_codec.encode()` 见 `COMMANDS[name]["authorized"]` 才用 `HEAD_TAG_AUTHORIZED`。心跳/运动链路已验证过，不动它 = 零回归。单测守护"其余指令一律 `EB 91 EB 90`"。
  3. **新增第五道闸 `_check_device_switch`**：
     - 关闭必须二次确认（`CONFIRM_REQUIRED`，409）—— 断电不可逆；
     - **站立/RL 态禁关雷达**（`PRECONDITION_FAILED`）—— 雷达是运控平衡参考输入。厂商 App 不拦，我们拦：真机连摔过两次，这类风险不该交给"手快点错"。开启随时允许；
     - 键名/值域非法 → `BAD_PARAMS`（400）且**一帧不发**。
  4. **按钮按用户要求分区**：相机画面页（前/后相机）、GPS 定位页（GPS）、运动控制页（前/后雷达 + 其他设备：指示灯×2 / 外部负载 / 对频 / 风扇）。
  5. **GPSMode 不进 UI**：语义未公开（真机值 0x11111），只留后端/取证用。
- **Consequences（获得）**：① 用户三个问题全部闭环，且是**真能力不是假按钮**；② 拿到一条此前完全未公开的指令族（含 magic 权限位这一协议事实）；③ 分设备开关与既有四道闸同构，审计/租约/L1 全部自动生效。
- **Consequences（代价）**：① 依赖厂商 App 的客户端标识，若厂商改 magic 需重新取证（已在代码注释与 README 留痕取证路径）；② 多一个需要维护的白名单表；③ 风扇只做 0/100 两档（转速语义无文档，不做连续滑杆）。
- **边界不变**：未放宽任何既有闸；软急停永远可达；轴指令通道与看门狗语义零改动。
- **验证**：本地 **132 项**单测全绿（新增 `test_device_switch.py` 15 例）；196 真机两轮端到端 —— 进程内（真实 `UdpControlSink`）与 **HTTP API**（复现前端行为，含 L1 + 续约）全部通过，结束时现场恢复原状（GPS=1 / Lidar=0/0 / Video=1/1）。

### ADR-019 指令报文记录：留下原始字节帧 + 机器人响应六态（2026-10-17）
- **Context**：用户诉求「控制台应该可以像 lite3 控制台那样，保存发出的控制指令的报文，并给出是否成功响应的标记」。此前的审计只记**语义参数**（`{"x":0.4}`）与闸结果，有两个盲区：① 协议复盘时看不到线上真正的字节（帧头 magic 问题就是靠对比字节才发现的）；② 指令发出去之后**机器人到底回没回、回了什么**完全不可见 —— 出了问题只能猜。
- **Decision**：
  1. **单开 `control/command_log.py`**，不塞进 `_audit`。审计是**操作视角**（含被闸拒的、没有报文），报文记录是**报文视角**（线上真实跑过的字节 + 应答）；粒度不同，硬合一起两边都说不清。两个端点都保留。
  2. **留完整字节帧 hex**（含 16 字节帧头，可原样反解）+ `Type/Command` + **协议字段** `Items`（大写 `X/Y/Z/...`，线上真身；前端小写参数在审计里）。报文视角必须以线上为准。
  3. **响应六态**：`ok`（ErrorCode==0）/ `error`（!=0，附 ErrorMessage）/ `no_response`（超时）/ `send_failed`（socket 都没出去）/ `rejected`（被闸拦，`frame_hex=null`）/ `pending`。**无 ErrorCode 字段的响应也算 `ok`** —— 休眠查询回 `{"Sleep":0,"Auto":false,"Time":10}` 就属于这种，"有数据回来"本身即说明指令被接受。
  4. **匹配策略**：按 `(Type, Command)` + FIFO 取最早未匹配。局限（同键多条在途只回一条会记错位）可接受：控制台不对同一指令并发下发，轴指令由看门狗串行化。
  5. **超时用惰性判定**（读出口扫一遍），不起后台定时器 —— 报文记录的消费频率（WS 10Hz / 轮询 1.5s）远高于用户需要看到结果的频率。
  6. **20Hz 看门狗 tick 不进记录**（走自己的发送循环，不经 `execute()`），否则一秒 20 条、200 条环形 10 秒滚掉。但**安全零位帧 / 软急停 / 停用补零**一律留证 —— 事故复盘时"停机前最后发了什么"是关键证据。
  7. **界面放全局底部可折叠面板**（`PacketLogPanel.vue`）而非某个标签页：相机页 / GPS 页 / 运动控制页发的指令都要能就地看到响应，切页才能看等于看不到。默认收起只占一行，展开才按 1.5s 轮询。
- **★踩坑（本轮最大收获，已加回归测试）**：第一版做完所有指令都标 `no_response`。根因：**basic_server 把指令应答发回「请求的源端口」**（实测同 socket 发 `1101/7` 即同 socket 收到响应），而 `UdpControlSink` **只发不收** —— 应答全堵在 socket 缓冲区。修法：给出口加守护接收线程（范式同 `UdpHeartbeatSource._rx_loop`），收到转交 `CommandLog` 关联。指令链路与遥测链路仍是两个独立 socket，互不影响。回归测试 `test_udp_sink_receives_command_response` 用一对真实 UDP socket 锁住这条性质。
- **Consequences（获得）**：① 协议复盘有了字节级证据（此前只能靠语义参数推断）；② "发了没回"从不可见变成一等公民，且**明确区分"没回"与"失败"**；③ 与四道闸/审计天然同构，`rejected` 也能在报文面板看到（否则"点了没反应"会被误认为面板坏了）。
- **Consequences（代价）**：① 多一个接收线程（daemon，`close()` 即停，已测）；② FIFO 匹配有上述局限；③ 报文带 hex，200 条的内存占用略高于审计（可接受）。
- **边界不变**：未新增任何下发指令、未放宽任何闸；看门狗"只停不趴"语义零改动。
- **验证**：本地 **155 项**全绿（新增 `test_command_log.py` 23 例）；196 真机验证 —— `usage_mode`(1101/5) 1.2ms、`sleep_query`(1101/7) 2.1ms 均标 `ok` 并带回完整响应体；`device_switch` 未确认关闭标 `rejected` 且无报文；未知指令标 `BAD_PARAMS`。

### ADR-020 前端 ref 解包缺陷修复 + GPSMode 语义化（2026-10-17）
- **Context**：用户两条反馈 —— ①「设备的供电开启和关闭的按钮我按不了」；②「gps切换模式别用code代号表示，用其真实含义表示（GPS\BDS\Galileo）」。
- **① 按钮按不了 —— 真 bug，根因是 Vue 3 的 ref 解包规则**：
  - `useDeviceSwitch()` 返回的是**普通对象**（属性是 ref）。Vue 3 模板**只对顶层 setup 绑定做 ref 解包**，所以模板里写 `dev.busy` 拿到的是 **Ref 对象本身**（恒真）→ `:disabled="!!dev.busy"` **永真** → 三个页面的设备开关按钮全部永久禁用。与 L1、租约都无关（实测 L1 已开、租约有效，照旧按不了）。
  - 修法：**在组件里解构到顶层**（`const { busy: devBusy, ... } = useDeviceSwitch(props)`），模板用 `devBusy`。三个面板（VideoPanel / GpsPanel / MotionPanel）同步修。
  - 教训：这类"看起来是权限问题、其实是渲染层"的缺陷，光看后端状态永远查不出来 —— **必须核对模板绑定语义**。
- **② GPSMode 语义化 + 可切换**：
  - `DevEnable.GPSMode`（真机 69905 = `0x11111`）不是黑盒代号，是 **GNSS 系统掩码**。位定义**不是猜的**：来自车侧 GNSS 驱动配置 `/opt/robot/share/node_driver/config/gps.yaml` 的 `sysMask` 注释原文 —— `bit0 GPS L1CA / bit4 BDS B1I / bit8 GLONASS L1 / bit12 Galileo E1 / bit16 QZSS`，默认 `0x11111` = 全系统（GN 模式）。
  - 协议常量放 `asdu_parser`（协议真相单一来源，且不能倒置 `control → ingestion` 的依赖方向）；前端可选清单从 `/api/v1/schema` 的 `gps_modes` 取，**不在 JS 里硬编码掩码**（那份迟早与 `gps.yaml` 漂移）。
  - 呈现：只显示星座真名（`全系统（GN 模式）` / `仅 GPS` / `仅 北斗（BDS）` / `GPS + BDS` / `全部关闭（无定位）`），原始掩码作副标注。含未知位时**显式标注**（`（含未知位 0x20000）`），不假装看懂。
  - GPS 页加切换器（走 `1101/3` 的 `GPSMode` 键，无需二次确认 —— 它不是"断供电"；掩码 0 例外，那确实是全关）。
- **★衍生发现一：`DevEnable.GPSMode` 是"车侧实际生效值"，不是"我们下发的值"**。basic_server 收到 `gps_node` 上报后才更新；下发瞬间短暂显示期望值，约 1–2s 后被真实值覆盖。→ **切换后必须回读校验**，GPS 页在 4s 后回读，值没变就明确提示「⚠ 已下发但车侧未生效」。绝不假装成功。
- **★衍生发现二：直接切回「全系统」`0x11111` 车侧不接受**（回 `ErrorCode: 0` 但模块不应用，实测连试两次失败）；**增量法**先切 `0x00011`（GPS+BDS）再切 `0x11111` 则成功。判别手段：`gps_node` 日志的 `系统模式: XX` 是从 NMEA 语句前缀反推的观测量（`GP`/`GB`/`GA`），多系统模式下前缀**跳变**、单系统模式**固定**。
- **Consequences（获得）**：① 设备开关按钮真正可用（此前完全是死的）；② GPS 模式从"看不懂的 69905"变成"哪些星座在定位"，且能切；③ 建立了"切换类操作必须回读校验"的范式。
- **Consequences（代价）**：切换器件多一个 4s 延迟的校验定时器（仅 GPS 页，切走即随组件销毁）。
- **边界不变**：未新增指令族（复用 `1101/3`）；未放宽任何闸；`GPSMode` 不在运动锁定列表内（GPS 不参与平衡，运动中切换最多影响定位精度）。
- **验证**：本地 **164 项**全绿；真机 —— 「仅 GPS」「仅北斗」切换经 `gps_node` 日志确认真实生效；现场已恢复「全系统」`0x11111`。

### ADR-021 「状态+动作分离」开关 + 关闭判定必须对比当前状态（2026-10-17）
- **Context**：用户反馈「其他设备这边怎么只有关闭没有开启呀」（附截图，一排按钮全写着「关闭」）。
- **问题一：表述缺陷（不是功能缺失）** —— 旧按钮文字写的是"**点了会做什么**"：设备当前开着，标签就显示「关闭」。但界面上**没有任何当前状态的指示**，一排「关闭」看上去就像"只能关不能开"。
  - **Decision**：把**状态与动作分开** —— 新增 `DeviceToggle.vue`，每台设备摆出「开 / 关」两个选项，**高亮的是当前状态**，点另一个即切换（与 GPS 页的卫星系统模式选择器同一范式，全站一致）。当前态按钮不再可点（避免无意义重复指令）；`value=null`（未收到上报）时两个都不高亮且禁用，**绝不猜**。三处面板（相机页 / GPS 页 / 运动控制页）统一替换。
  - 取值语义沿用既有铁律：**非 0 即"开"**（雷达上报 2=运行中也是开），`== 1` 会把运行中的雷达误判成关闭。
- **问题二（顺带挖出的真 bug）：`togglePair` 语义反转** —— 我把调用方改成传"**目标值**"（状态+动作分离后必然如此），但函数内部还是老的"**取反**"语义 → **点「开」实际发「关」**。
  - **Decision**：函数与参数一起改名 `togglePair → setPair`、`toggleFlag → setFlag`，参数 `wantOn` 明确为"目标状态"，并在注释里写明这次的误用史 —— **命名要让人在读代码时就能看出语义，而不是靠记忆**。
- **问题三（最隐蔽，也是"点开启没反应"的真因）：`_check_device_switch` 的"是否关闭"判定只看目标值**。
  - `1101/3` 的 Items 是**整键覆写**：开前相机必然带 `{"Video":{"Front":1,"Back":0}}`，那个 `Back:0` 只是"保持后相机原本就关着"。
  - 旧实现见到 0 就判"关闭" → 要求二次确认；而前端点「开」**不会弹确认框**（它认为不是关闭）→ 指令被拒，用户看到 `CONFIRM_REQUIRED`，表现为**"点开启毫无反应"**（报文记录实证：`03:55:48 device_switch rejected items={"items":{"Video":{"Front":1,"Back":0}}}`）。
  - **Decision**：`device_switch_turns_off(items, current)` 增加 `current`（当前 `DevEnable`）参数，**逐路比较"开→关"才算关闭**；`ControlGateway` 新增 `device_provider`（返回原始 `DevEnable`，与 Items 同构，不能扁平化 —— 判定要逐路比较）；**取不到当前状态时回退保守判定**（有 0 就要确认），宁严勿松。运动锁同样改为"只拦关闭**正在运行**的雷达"。
- **问题四（竞态，已验证并修复）**：连点两路时，第二次会用到**尚未回读**的另一路旧值（2Hz 上报），把刚打开的那路又写回 0。**服务端安全闸正确拦住了"关"的方向**（不会造成危险），但操作失败。修法：`useDeviceSwitch` 记录**最近成功下发的 Items**（6s TTL），`setPair` 的"另一路"优先取该缓存。实测从"两次且第二次被拒"变成**一次到位 `{Front:1,Back:1}`**。
- **Consequences（获得）**：① 开关语义一眼可读（状态高亮 + 双向选项），不会再被误解成"只能关"；② 修掉三类真实缺陷（语义反转 / 判定误伤 / 竞态）；③ 建立"判定要基于当前状态、不能只看目标值"的范式。
- **边界不变**：安全闸一条没放宽 —— 真关（开着 → 0）仍必须二次确认，运动态禁关运行中的雷达仍然生效，回归测试逐条锁住。
- **验证**：本地 **169 项**全绿（新增 5 例覆盖关闭判定）；**真机 + 真实浏览器点击验证**（Playwright）—— 点「开」正确发出 `{"Video":{"Front":1,"Back":0}}` 并被车侧接受，UI 与车侧状态同步更新为 `前相机=开`；现场已恢复 `Video=1/1`。
- **工程教训**：这一轮用户两次反馈（"按钮按不了"、"只有关闭没有开启"）**根因都不在后端**，光查状态与接口永远查不出来。**必须真的把界面打开看一眼** —— 本轮起，涉及界面改动的验收一律带一次真实浏览器渲染核对。

### ADR-022 推流服务受控启停（2026-10-17）
- **Context**：用户要求「在相机画面界面，把 m20video 对应的那个推流服务接进去，可以开启或关闭」。
- **先分清楚两条链**（这一步不做就会做错）：
  - `local` **本地推流** = 厂商 `mediamtx` + `push_video.sh` → **控制台画面靠它**；
  - `relay` **外推中继** = `m20video.service`（rtmp_1012）→ 转发到远端 `172.31.68.227:1936`，**关掉控制台画面照旧**。
  - 用户点名的是 `relay`，但在**相机画面页**只做 relay 会让人困惑（"我关了推流，画面怎么还在"）→ **两条都做，界面分开标注**。
- **Decision（权限：收一个受控入口，而不是给控制台 root）**：
  - 两条链都以 root 运行，控制台跑在 `user`。新增 `/usr/local/sbin/m20-video-ctl`（源码 `deploy/m20-video-ctl`），只接受 `status|start|stop|restart` × `local|relay` 八种组合，**参数严格白名单**；sudoers **逐条列出、不用通配符**（`deploy/sudoers-m20-video-ctl`）—— 不给 root，也不放开 systemctl 全权。
  - 后端 `sudo -n` 调用（**非交互**：没配好 sudoers 要立刻失败，而不是挂着等口令），未授权时回**可操作的**错误（直接告诉用户装哪个文件）。后端与 helper **两侧都校验**目标/动作白名单。
- **Decision（状态语义：判"有没有真的在出流"，不判进程数）**：本地推流有个经典坏法 —— **进程活着但不出流**（gst 存活、`mpph264enc` 内部报 NULL、HLS 404）。故状态以 **HLS 能否 200** 为准（`local.ready`），并把"有进程、没流"单列 `local.stuck` → 界面「进程在但没出流（需重启推流）」。**首次上线就靠这条抓到了现存故障**：`processes=5 / gst=0 / HLS 404/404`。
- **Decision（不用厂商 `start_server.sh`）**：它会 `sudo ./mediamtx &` **再起一个 mediamtx**（8554/8888 已被占用）→ 端口冲突；且会「等 PTP 同步最多 60s」再**前台运行**推流脚本 → 挂住控制台 HTTP 线程。改用：`mediamtx` 仅在缺失时补启 + 后台直接跑 `push_video.sh`（它自身就是带自愈的 supervisor：每路独立监控、指数退避重连、trap 清理）。
- **Decision（不受控制闸约束）**：这不是机器人指令，是 AOS 本机服务。且"画面黑了想重启推流"很可能正好发生在 L0（控制未开）时 —— 把恢复手段锁在 L1 后面是错的。`stop` 仍需二次确认（画面会消失）。
- **★踩坑一（命名禁忌）**：厂商 `stop.sh` 执行 `pkill -f v4l2` / `pkill -f push_video` —— 任何调用链的**命令行里出现这些字样就会把自己杀掉**。故入口参数用 `local` / `relay`，绝不写完整进程名。
- **★踩坑二（真 bug，已加回归测试）**：动作只返回**被操作那条链**的状态 → 上层把缺失的另一条显示成「未运行」（凭空断言）。修法：helper 动作后一律输出**两条链的完整状态**；后端对**整个缺失的分组**改说「状态未知」，绝不编造。
- **★踩坑三**：脚本文件 CRLF 会让远端 `bash -n` 报 `syntax error near '{'`（2026-10-17 连踩两次，Python 在 Windows 下写文本会转 CRLF）。已把 `deploy/m20-video-ctl` 写进 `.gitattributes`（`eol=lf`），部署前也做一次二进制转换兜底。
- **Consequences（获得）**：① 相机页能直接重启推流，"黑屏"第一反应有了落点；② 状态判据是"真的在出流"，不再被"进程在跑"骗；③ 建立可复用的**受控提权入口**范式（sudoers 白名单 + 参数白名单 + 非交互）。
- **Consequences（代价）**：多一个系统级文件与 sudoers 条目（已给卸载方式），需随部署流程一起维护。
- **遗留（**需用户参与**）**：诊断中发现**相机 USB 设备根本没枚举**（`/dev/video*` 不存在、`lsusb` 无 `SM_USB_107X`、dmesg 只有 `USB disconnect` 无重连）。车侧 `DevEnable.Video=1/1` 且日志里 `restartVideoServer 脚本执行成功`（04:04 与 04:23 各一次），但硬件没回来；厂商 `usb_ctl.sh`（GPIO 125）enable/断电重上也无效。**判断为硬件/接线层面问题，需目视检查相机与 USB 线**，不是软件能修的。这也是本页画面为空的**真正原因**（不是推流服务挂）。
- **验证**：本地 **182 项**全绿（新增 `test_video_service.py` 13 例）；真机 + 真实浏览器点击 `restart relay` —— `m20video.service` 的 `ActiveEnterTimestamp` 随之更新，状态回「运行中（目标可达）」；`stop` 不带确认被 `CONFIRM_REQUIRED` 拦下；非法 target/action 被 `BAD_TARGET`/`BAD_ACTION` 拦下且未执行任何命令。

### ADR-023 逆向整张指令表 + 前后补光灯 `1101/2`（2026-10-18）
- **Context**：用户问「M20 有喇叭/音响能外放声音吗？App 上还有前后照明灯、首启回零开关、自动休眠时间、WiFi 热点设置，能加进 monitor 吗」。厂商 `docs/04` 只有 11 条请求指令，远不够；此前已用抓包破解 `1101/3`，说明**二进制里有更多指令**。
- **Decision（先把表逆向全，再挑功能）**：`nm`（符号未剥离）+ `objdump -d` 反汇编
  `/opt/robot/share/basic_server/bin/basic_server`。注册结构是
  `unordered_map<int, unordered_map<int, std::function<void(rapidjson::Value&)>>>`；
  以**内层 map 的 `operator[]` 调用为锚点**向前找最近两个不同栈槽的 `str`（`Type`/`Command`），
  再用 `nm` 把 handler 地址映射回 `cmdHandle_*` 函数名，共还原 **42 条**。
  工具沉淀在 `tools/re_cmdtable.py` / `tools/re_cmdname.py` / `tools/probe_cmd.py`。
  📄 **完整指令表（含 30 条未实现指令的清单）、各指令实测结论、25 条踩坑已独立成文：
  [`逆向与真机取证笔记.md`](逆向与真机取证笔记.md)，原始数据 `cmdtable-42.txt`。**
  该笔记回答"车侧实际是什么"，与计划书（"为什么这么设计"）分工。
- **★逆向本身踩的两个坑**（详见取证笔记 §2.4）：① objdump 行
  `addr:\t<hex>\t<insn>\t<ops>` 中**助记符与操作数间也是 Tab**，只取一个字段拿到的是
  机器码 → 脚本静默输出 0 行；② 用 `([A-Za-z0-9_]+)E` 解 mangaled 名会**贪婪吃到最后一个
  `E`**，把整串参数当"名字"解出来而脚本毫无察觉 → 必须按 Itanium ABI 的**长度前缀**切片。
  两条都已加回归测试（`tests/test_re_tools.py`）。
- **喇叭结论（如实告知，不造假）**：`aplay -l` 空、`/proc/asound/cards` = `no soundcards`、
  `/dev/snd` 只有 `seq`/`timer`、**无 PCM 设备** → AOS 主机不带音频硬件，**不是软件没接**。
  故不加该功能，也不在界面上放一个按了没反应的按钮。
- **Decision（补光灯取 `1101/2`）**：写 `{"Front":1,"Back":1}` 车侧回 `{"ErrorCode":0}`；
  但**状态不在响应里** —— 真正的状态在设备帧 `1002/5` 的 `Items.Led.Fill.Front/Back`，
  下发后约 1s 翻转。故界面做成「下发 → 等 2.5s → 读设备帧比对」，是四项里**唯一能闭环校验**的。
- **★踩坑一（命名极易混）**：`Led.Fill`（补光灯）与 `DevEnable.LedHost/LedExt`（**电源指示灯**，
  走 `1101/3`）都叫 Led，但是两个东西。控制台在两处都加了"不是一回事"的说明。
- **★踩坑二（整键覆写）**：`1101/2` 是整键下发 —— 只开前灯不带后灯当前值，等于把后灯关掉。
  后端 `light()` 固定带两路；前端回填另一路时也要取**当前设备帧值**。
- **Consequences（获得）**：① 指令表从"猜"变成"查"，后续加功能先查表再探针；
  ② 补光灯可控且**状态可见**，用户能确认真的生效了。
- **验证**：真机下发 `Front:0/Back:0` → 设备帧 `Led.Fill` 翻成 0/0；再下发 1/1 → 翻回 1/1。
  新增 `tests/test_robot_config.py`（含 `1101/2` 编码断言）。

### ADR-024 首启回零开关 `1101/10+11`（2026-10-18）
- **Context**：App 上有「首次启动前是否回零」开关，用户要能看能改。成因见 ADR-017
  （车侧 `basic_server.toml` 的 `autoResetJointsZero`）。
- **Decision（写必须靠读回校验）**：`1101/10` 写 `{"Enable":bool}`、`1101/11` 读回
  `{"Enable":bool}`。**真机实测：写指令车侧不回帧**（发完 3s 无应答，但值确实改了）。
  所以 `result=ok` 只表示"报文发出去了"，界面**必须**再发 `1101/11` 才敢点亮"已验证"。
- **Decision（查询缓存 + `age_s`）**：`CommandLog` 新增 `QUERY_KEYS={(1101,7),(1101,11)}`，
  响应到达时**先于**在途匹配入缓存，并暴露 `age_s`。前端据此区分三种状态：
  **没问过**（`known=false`，显示"未知"）/ **问过没答**（`known=false` 但已发过）/
  **已答但过期**（`age_s>30` 标 stale）。绝不把"未知"显示成"关闭" —— 那是凭空断言。
- **Decision（按方向确认）**：**关闭**回零（下次开机不标定直接站立，关节位置未经确认）需
  `confirmed=true`；开启不需要。见 ADR-025 同一范式。
- **★踩坑**：报文记录里这条会显示 `no_response`，**那是"不知道"不是失败** ——
  若把它当失败去"重试"，用户会疯狂点击而毫无必要。界面在回零区直接写明了这一点。
- **Consequences（获得）**：开机行为从"只能看 toml"变成界面上可查可改，且改了有回读证据。
- **Consequences（代价）**：每次读回都要多发一个 UDP 查询（界面 6s 轮询只走 GET，
   **不重复发 UDP**，只在挂载和写入后各问一次）。
- **验证**：真机 `enable=false`（带确认）→ 回读 `{"Enable":false}`；再 `enable=true`
  → 回读 `{"Enable":true}`。未带确认被 `CONFIRM_REQUIRED` 拦下且**一帧未发**。

### ADR-025 休眠设置 `1101/6+7`：车侧静默夹取（2026-10-18）
- **Context**：用户要「自动休眠的时间」。`1101/6` 写休眠（ADR-018-1 已知是**整车**休眠：
  依次关 LED→FAN→VIDEO_POWER→JOINTS_POWER 并趴下），`1101/7` 读配置。
- **Decision（三种用法分开，别混）**：`sleep=true` = **立即整车休眠**（需确认）；
  `sleep=false` = **唤醒整车**；`auto/minutes` = **只改自动休眠策略，不会立刻睡着**。
  三者在界面上是三个独立控件，文案分别写明后果。
- **★核心发现（静默夹取）**：`1101/7` 读回 `{"Sleep":0,"Auto":false,"Time":10}`。
  `Time` 的合法区间车侧只认 **5~30**。**实测判定**：12→生效、60→**30**、3→**5**，
  且**不回错误码**（二进制里确实有串 `Sleep time shoud between 5 and 30`，但响应帧里没有它），
  `Auto` 照常生效。判定实验：先设 12（合法基准），再发 60 → 变 30（夹到上界），
  再发 3 → 变 5（夹到下界）—— 一步只能看出"没变成 12"，两步才能区分"夹取"与"丢弃"。
- **Decision（后端先拒，不给车侧夹取的机会）**：用户填 60 被静默降成 30 是最难排查的
  一类问题（界面显示"改成功"，车上跑的是另一个值）。故 `robot_sleep` 在
  **服务端**校验 `5<=minutes<=30`，越界返回 `MINUTES_OUT_OF_RANGE` 且**一帧不出**。
  前端输入框的 `min/max` 只是辅助 —— **HTML 校验不拦提交，不能依赖**。
- **Consequences（获得）**：休眠时长成为"所见即所设"，不再有静默失真。
- **Consequences（代价）**：若厂商后续放开区间（比如支持到 60），需同步改后端常量。
- **验证**：越界 5 例（60/31/4/0/-5）全部 `MINUTES_OUT_OF_RANGE` 且 `sink.sent == []`；
  边界 5/10/30 放行且 `Items.Time` 正确；`sleep=true` 未确认被拦且零报文；
  真机读回 `{Sleep:0,Auto:false,Time:10}` 与后端缓存一致。
  ⚠️ **未执行**「立即休眠」的真机验证（会让趴下的车切断关节/视频供电）——
  其报文路径与「唤醒整车」同源，且确认闸已单独验证。

### ADR-026 WiFi 热点：双接口·单射频（2026-10-18）
- **Context**：用户问「M20 有两个网卡，一个开自身热点、一个连外部 WiFi；连着外部 WiFi 时
  能不能改自身热点的信息」。同时要求把「WiFi 热点设置」加进控制台。
- **Decision（先搞清拓扑再动手）**：M20 无线是**一块射频两个接口** —— `phy#0` 上同时有
  `wlan0`（type AP，`10.21.41.1/24`，dnsmasq）和 `p2p0`（type managed，上联外部 WiFi，
  `192.168.0.196`）。**AP 信道被上联绑架**：配置写 `band=bg`（2.4G），实际跟着上联跑
  channel 40（5200 MHz）。
- **结论**：实测 `nmcli con down/up myap24G` 期间 **`p2p0` 全程 `100 connected`、
  `192.168.0.196` 未丢** → **连着外部 WiFi 时可以改 SSID/密码**。
  但**频段/信道改不了也不该开放**：与上联抢射频的后果是 AP 起不来，或直接把上行
  （我们的 SSH 通路）带下去。故控制台**只开放 SSID + 密码**。
- **Decision（走厂商明文文件，不走 `nmcli con modify`）**：厂商用明文文件管热点 ——
  名 `/var/opt/robot/conf/host_name`（`head -c 12`，自动补 `_24G`/`_5G`）、
  密码 `/opt/robot/scripts/wifi/password`（`head -c 16`）；生效靠
  `ap_start.sh start 24G`（先 `nmcli c delete` 再 `add` 重建）。
  开机 `host_start.sh` 会 rerun 它 → **`nmcli con modify` 的改动重启必丢**。
- **★踩坑一（`nmcli con modify` 两条路都走不通）**：① AP 处于 activated 时改 SSID
  **不生效**，`con up` 也不重新应用；② 先 `con down` 再改，会撞上"AP 关停 → `wlan0`
  消失 → 连接短暂不存在"，`nmcli con modify` 报 `unknown connection`（rc=10）。
  另：AP 激活后有 **4~8s 假死期**（NetworkManager 的 ip-check/secondaries 状态机），
  采一次状态就下结论会误判 —— **必须轮询到 activated**。
- **Decision（受控提权，仿 ADR-022 范式）**：`/usr/local/sbin/m20-ap-ctl`
  （root:root 0755）+ sudoers **零通配符**，只放行 `status` 与 `set --confirmed`。
  新值走 **stdin**（`ssid=…\npassword=…`）而非 argv —— 密码不进 `ps` 输出，
  sudoers 也就不需要通配符。流程：值域校验 → 写两文件 → `ap_start.sh start 24G` →
  轮询 AP activated(30s) → **复查上联(20s)**，掉了就回滚文件 + 重建 AP + 抢救上联 →
  用 `iw dev wlan0 info` 校验实际 SSID 是否等于 `base_24G`，不等也回滚。
- **★踩坑二（SSID 白名单过严）**：最初用 `[a-zA-Z0-9_-]` 过滤 SSID，而车上原名是
  `CA9B_NO.1273_24G`（**含点**）→ 连还原都做不到。改为**只挡不可打印字符**
  （Python 侧 `_SSID_PRINTABLE`）。另外**厂商会截断**：SSID base 只取前 12 字符、
  密码只取前 16，后端按 1~32 / 8~63 校验后，helper 再按厂商口径收窄。
- **★踩坑三（`uplink` 永远找不到）**：按 `802-11-wireless.mode == managed` 筛上联连接，
  但 station 连接**一般不写 mode 字段**（空），永远不匹配。改为只查**活跃连接表**
  `nmcli -t -f NAME,DEVICE con show --active` 并排除 AP 的 con/dev。
  另外 `GENERAL.STATE:` 前缀要剥掉，否则 `state.startswith("100")` 判不出已连接。
- **Consequences（获得）**：热点名/密码可在控制台改，**上行断裂一定回滚**，
  且已连设备掉线前有明确警告。
- **Consequences（代价）**：多一个系统级文件 + sudoers 条目；SSID base 上限 12 字符
  是厂商限制，不是我们的选择。
- **验证**：真机经 HTTP API 改 SSID 为 `YSCTEST_24G` → `applied`、`iw` 校验实际 SSID 一致、
  上联全程 `100 connected`；随后**精确还原** `CA9B_NO.1273_24G` / 原密码，
  车侧两文件逐字节核对一致。未确认 / SSID 41 字符 / 密码 3 位分别被
  `CONFIRM_REQUIRED` / `BAD_SSID_LENGTH` / `BAD_PASSWORD_LENGTH` 拦下且未改动。

### ADR-027 拉流开关（省 196 上行）+ ffmpeg 重启退避修正（2026-10-18）
- **Context**：用户问「能不能主动关闭相机画面的拉流过程，避免增加 M20 的网卡负担」。
- **先量，再动手**（真机，单浏览器两路）：

  | 状态 | `p2p0` tx |
  |---|---|
  | 相机页在拉流 | **694 KB/s** |
  | 点「暂停拉流」 | **423 KB/s** |
  | 恢复 | 746 KB/s |

  即**两路拉流约 270 KB/s（≈2.2 Mbps）上行**。M20 的出口 `p2p0` 是 WiFi
  （Tenda 5G，信号常年在 -53~-66dBm 抖动）→ 这个量级值得管。
- **根因不是"忘了做开关"，是架构上停流的位置错了**：`App.vue` 用 `v-show`
  切标签（**不卸载组件**），而停流写在 `VideoPanel.onUnmounted` 里 →
  **控制台一开着，两路视频就一直在拉，不管你停在哪个标签页**。
  原注释还把这写成"可接受的副作用（切回瞬时无缝）"——代价当时没量过。
- **Decision（三个"想不想拉"取与，而不是只加一个按钮）**：
  `flowWanted = props.active && pulled && !document.hidden`

  | 来源 | 场景 |
  |---|---|
  | `props.active`（App.vue 传 `tab === 'video'`） | 切到别的标签页 → 停 |
  | `document.hidden`（Page Visibility API） | 切到别的浏览器标签/最小化 → 停 |
  | `pulled`（手动） | 想在相机页但不想占带宽 → 停 |

  只做手动开关不够：**用户会忘**。只做自动也不够：想盯着画面又嫌带宽时没辙。
- **Decision（停流必须"真拆"）**：WHEP `DELETE <resourceUrl>` + `pc.close()`，
  HLS `hls.destroy()`，再把 `<video>.srcObject` 置空。
  不是"隐藏但还在解码"——那只是自欺。恢复时重建（多等 0.3~2s）。
  **推流服务（`local` 链）不受影响**，别把"本页不拉"误解成"把推流关了"。
- **Decision（暂停时要说清原因）**：黄条显示"已切到其他标签页…"/"已手动暂停拉流…"，
  否则用户看到黑屏会以为相机坏了。
- **★顺带发现并修掉的真 bug（ffmpeg 重启无退避）**：本地推流挂掉时，
  后端 ffmpeg 代理每 2s 重启一次，**永远不停**（真机实测连刷到第 14 次）。
  根因是 `backoff = 2.0` 写在 `Popen` **成功之后** —— 但**"起来"不等于"出流"**：
  源站没推流时 ffmpeg 起来就 `DESCRIBE failed: 404` 退出，退避永远长不起来。
  修法：进程存活不足 `STABLE_SECONDS=10s` 就翻倍，真活住了才重置。
  真机实测退避序列 `2→4→8→16→30→30`（封顶），同窗口内重启次数从十几次降到 6 次。
- **Consequences（获得）**：① 不在相机页时不占上行；② 挂在相机页但不想看时可手动停；
  ③ 上游断流时后端不再每 2s 白起一次 ffmpeg（每次都要重建 RTSP 连接）。
- **Consequences（代价）**：切回相机页要重连（0.3~2s），不再"瞬时无缝"——
  带宽与无缝二者不可兼得，选了带宽。
- **验证**：真机浏览器对四种场景逐一断言 `<video>.srcObject` 与黄条文案——
  切标签（有流→空→有流）/ 手动暂停恢复 / 模拟 `document.hidden` 切换，全部正确；
  带宽 694→423→746 KB/s 闭环。新增 4 项退避单测，总 **221 → 225 项**全绿。

## 9. 安全设计（不可妥协）

1. **分层开放（ADR-004）**：L0 只监默认（不发送任何控制/运动指令）→ L1 低危需配置 enable + 前端二次确认 + WS 心跳租约（断开即失效）→ L2 黑名单。
2. **危险指令硬禁用**：清除充电状态（Charge=2）**任何配置下不可调用**（无"除非"）。
3. **轴指令四道闸**：看门狗只停不趴（松杆/停更/断连 → 零位停发等待恢复；绝不自动软急停）+ 运动前置校验（MotionState∈{站立,RL控制} + 常规模式）+ 服务端值域钳制（**安全上限 ±0.40**，2026-10-15 实测）+ 全量审计日志（结构化 JSON：操作者/时间/指令/参数/结果）。
4. **软急停优先**：急停按钮不受控制开关限制——安全手段永远可达。
5. **不依赖 HTTPS**（C6 时钟问题）；监听限内网可达；CORS 显式来源（不用 `*`）。
6. **输入校验**：任何来自 client 的参数都当不可信——控制指令参数白名单校验（浏览器不是可信边界）。
7. **脱敏合规**：遵循仓库约定——真实口令/密钥不入库，只提交 `*.example`；不提交第三方二进制。
8. **端口不冲突**：不与 `basic_server`(30001/30002)、遗留 `m20video`(3000) 争抢。

## 10. 协议实现参考（M20 Pro 本体监控/控制协议）

> 本部分是控制台的**实现直接依据**，合并两个来源：
> ① `../../docs/04-软件开发指南V1.3.0-钉钉全文.txt`（协议语义：指令全集 + 字段含义）
> ② GitHub `DeepRoboticsLab/m20-android-sdk`（RobotProtocol / RobotConnectUDP：传输帧格式 + 连接参数，Apache-2.0）
>
> **结论先行：整套协议 = 16 字节二进制帧头 + UTF-8 JSON 信封（`PatrolDevice`）**。
> 早期判断"ASDU 逐字节布局未吃透"（Q2）系误判——ASDU 指应用层消息信封，载荷是 JSON，无二进制字段布局谜团。

### 10.1 传输层（帧格式来自 m20-android-sdk `RobotProtocol.Head`）

| 项 | 值 |
|---|---|
| 传输 | UDP（docs/04 另给 TCP `:30001` 备选，本期不走） |
| 端口 | `30000` |
| 目标 IP | `10.21.31.103`（docs/04 §1.1.2）或 `10.21.33.103`（SDK 默认）——**二者均为 AOS 本体内网 IP**（196 即 AOS 的 LAN 侧，属同主机内网口，非 GOS）；最终以 196 上机 `ss -lunp` 确认监听地址（Q1 收敛） |
| 帧头 | 16 字节：`EB 91 EB 90`(4) + `dataSize` LE16(2，帧体长度) + `messageID` LE16(2，线程安全自增) + `protocolType`(1，`0x01`=JSON) + `RESERVE`(7×`0x00`) |
| 帧体 | UTF-8 JSON，见 §10.2 |

帧头小端序。`parseUdpFrame` 校验 `HEAD_TAG` 与长度，不匹配丢弃。

**地址真相**：`10.21.31.103`/`10.21.33.103` 均为 AOS 本体内网 IP（非 GOS；GOS 是 `10.21.31.104`）。后端驻 196（=AOS LAN 侧）后**同主机内网口直达**，无需跨主机。

### 10.2 应用层信封（PatrolDevice）

```json
{
  "PatrolDevice": {
    "Type": 100,
    "Command": 100,
    "Time": "2026-10-14 14:00:00",
    "Items": {}
  }
}
```

- `Type`（消息大类）+ `Command`（命令码）组合唯一标识一条消息（SDK `CommandType(type, command)`，`toString()` 为 `"type-command"`）。
- `Time`：`yyyy-MM-dd HH:mm:ss` 本地时间串。**注意 196 时钟慢 ~846 天（C6），该字段不可信**——一律透传，新鲜度判断只用本机单调时钟（§6.2 stale 语义不变）。
- `Items`：参数/字段体，随消息类型变化（确切结构见 §10.3/§10.4）。
- 推荐 JSON 格式（docs/04：JSON 下 ASDU 处理性能更快且数据结构更全面）。

### 10.3 指令全集

#### 10.3.1 心跳与连接

| Type | Command | 功能 | Items | 频率 |
|---|---|---|---|---|
| 100 | 100 | 心跳 | `{}` | docs ≥1Hz；SDK 默认 200ms(5Hz) |

- **机器人只向持续发送心跳的 IP:端口主动推送状态**——不发心跳就没有任何推送（这是与 lite3 裸 UDP 推送的本质区别）。
- **同一 socket 收发**：机器人把状态推回心跳发送方的 IP:端口，因此发送心跳的 socket 即接收 socket（Q3 由此收敛，无需独立 bind）。
- 连接语义（SDK）：收到心跳才判定连接成功；`connectSuccessTimeOut`（默认 3000ms）内无任何数据 → 标记断开，但**不关 socket**，消息照常发送，恢复后自动重连。
- **★2026-10-16 实测修正两点**：
  1. **"同一 socket"只对数据链路成立，指令链路是另一个 socket**：本控制台 `UdpHeartbeatSource._sock`（心跳+收状态）与 `UdpControlSink._sock`（发指令）各自独立 → 停心跳**不影响**指令可达。这是"遥测让渡"功能（ADR-015）敢做的前提。
  2. **心跳超时不会让车趴下**：basic_server 二进制 `Heartbeat timeout! Cleared %zu client(s).` —— 超时动作是清除客户端（停止推送）；真机实证 `systemctl stop` 全停 50s 后车仍保持 `motion_state=17`（RL 站立）。车侧断链保护在 rl_deploy 的 DDS_CMD 看门狗（`Disable lynx`），效果是停运动而非趴下。

#### 10.3.2 控制指令（docs/04 §1.2 全集）

| Type | Command | 功能 | Items 关键字段 | 危险级 |
|---|---|---|---|---|
| 1101 | 5 | 使用模式切换 | `Mode`: 0=常规(手动) 1=导航 2=辅助 | 低 |
| 2 | 22 | 运动状态转换 | `MotionParam`: 0=空闲 1=站立 2=关节阻尼(软急停) 3=开机阻尼 4=趴下 17=RL控制（**以此表为准**，旧稿推测值 -2/-1/5 不见于 docs/04，勿用） | 低（软急停是安全手段） |

### 10.5 控制安全序列（实现约束，与服务端闸门一一对应）

1. **轴指令双重前置条件**（docs/04 §1.2.5 原文"仅支持在常规模式下执行" + §1.2.3 状态机）：`ControlUsageMode=0`（常规）**且** `MotionState∈{站立(1), RL控制(17)}`。步态切换会自动切到对应运动模式（标准/敏捷），无需手动先切模式。服务端下发轴指令前校验这两项。
2. **软急停**：`MotionParam=2`（关节阻尼）= 停止所有运动，Web 端必备急停按钮（比"断网"可靠——断网只停发送，不停机器人）。
3. **持续指令看门狗（只停不趴，2026-10-15 二次事故修正）**：轴指令 20Hz 循环中，**松杆 / 停更 250ms / 断连 / 停机 → 零位一帧 + 停发**，之后保持停等待恢复；**绝不自动软急停**（两次真机事故均为自动软急停所致：运动中被打急停栽倒、站立中被打急停卸力软塌——机制整体切除，软急停只由人触发）。**绝不让机器人带着最后一条指令无限运动。**
4. **值域钳制**：服务端对 [-1,1] 截断——浏览器不是可信边界。
5. **黑名单**：`Charge=2` 任何配置下拒绝（ADR-004）。

### 10.6 与 lite3 协议的区别（改造点）

| lite3 | m20Pro |
|---|---|
| 裸 UDP 推送，无需请求 | **心跳驱动**：不发心跳就收不到任何推送 |
| 二进制 `0x0901/0x0902/0x0903` + `struct` 解析 | **帧头 + JSON**：`struct` 只解 16 字节帧头，帧体 `json.loads` |
| 对端 IP 直推 | 机器人=服务端(:30000)，外部=客户端；推送回到心跳发送方 socket |
| 12 关节（3 自由度×4 腿） | **16 关节（4 自由度×4 腿，轮足含轮毂）** |

> **✅ 已选定方案一并已执行完毕**（2026-10-14）：
> - `chronyc makestep` 返回 `200 OK` **但 `date` 未变**（chrony 源全部 `^?` 不可用、Update interval 0.0）→ 追加 `sudo date -s @<本地 epoch>` 直接校时成功，`date` 已回到 `2026-10-14`。
> - chrony 配置 `makestep 1 -1` 已就位（固化）。
> - **经验**：`makestep` 不生效时用 `date -s` 兜底，不要卡在 chrony 上。
> - 后续 M2/部署时若发现时钟又漂移，先查 chronyd 是否具备 `CAP_SYS_TIME`。

**上机装依赖的第二、三个坑（2026-10-14 实测）**：

#### ⚠️ 时钟问题修订（2026-10-15 二次实测，方案一未持久）

按方案一校时后**时钟又被拉回 2024-06-20**（约 20 秒内），排查结论：
- chrony 的 **8 个参考源本身全部返回 `-20306h`（慢 846 天）**，且 Reach=377（源可达）——即上游 NTP 给出的就是错时间；
- `makestep 1 -1` 允许**反向**步进，反而让 chrony 把手动校时又拉了回去；
- 停掉 `chronyd`（`systemd-timesyncd`/`ntp` 本就未运行）后**仍**被拉回 → 存在未识别的第三方对时来源（待查，可能是机器人内部对时服务）；
- `hwclock -r` 显示 RTC 比系统时间快 846 天（硬件时钟本身偏移）。

**结论与对策**：
1. **控制台不受影响** —— 新鲜度一律用 `time.monotonic()`（ADR-006），`PatrolDevice.Time` 只作展示不做判定。**这次实测反过来验证了该决策的正确性。**
2. **装依赖改用 HTTP 镜像 + `--trusted-host`，绕开 TLS/时钟依赖**（实测 `http://mirrors.aliyun.com/pypi/simple/` 返回 200，清华 http 返回 403）：
   ```
   pip install -r requirements.txt -i http://mirrors.aliyun.com/pypi/simple/ \
       --trusted-host mirrors.aliyun.com
   ```
3. 现场排障注意：**196 上日志/文件时间戳仍显示 2024**，不要据此判断事件先后。

**其余已知坑**：① 脚本换行符必须 LF（`.gitattributes` 已固化，Windows 检出仍可能带 CRLF，部署前 `sed -i 's/\r$//'`）；② 196 WiFi 间歇丢包 → `scp`/`rsync` 需带重试；③ 只传 `frontend/dist`，不传 `node_modules`（`pack.sh` 已如此处理）。

## 18. 演进策略（ROS2 兼容与迁移路径）

### 18.0 核心论据：部署形态与数据来源正交
模块化单体是**部署形态**（一个进程、一个 systemd 单元、一台主机 196），ROS2 中心化是**数据来源与总线语义**（谁产生状态、谁编排控制）。二者被三层抽象隔开，互不绑架：

1. **数据入口抽象 `DataSource`**（§5.4）：`M20UdpHeartbeatSource`（当前实现）与 `Ros2TopicSource`（未来）实现同一接口 `start() / stop() / on_frame(cb)`，上层 `StateStore` 只见规范化后的 `RobotSnapshot`，**不知道也不关心帧来自 UDP 还是 DDS topic**。
2. **控制出口抽象 `ControlSink`**（ADR-010，对称设计）：`UdpControlSink`（当前）与 `Ros2ControlSink`（未来）实现同一接口 `send(cmd) / result()`，上层控制服务只见 `ControlCommand` 领域对象，不知道出口是 ASDU 报文还是 ROS2 topic/service。
3. **前后端契约冻结 `GET /api/v1/schema`**（§5.4）：WS 快照 JSON 的 schema 由后端显式发布并做契约测试，**前端只依赖 schema 不依赖数据来源**。来源换了，schema 不变，前端零改动。

> 一句话：**换数据来源不动上层，换后端不动前端。** 这就是"后期兼容"的全部机制，从 v1 起就埋好，不需要推倒重来。

### 18.1 三条迁移路径（按侵入性递增）

**路径 1｜`Ros2TopicSource` 接入（推荐首选，零架构改动）**
- 在 `sources/` 下新增 `Ros2TopicSource`，实现 `DataSource` 接口；ROS2 依赖**运行时按需导入**（`rclpy` 缺失时优雅降级为"仅 UDP 源"）。
- 两个 source **可同时运行**：UDP 心跳源 + ROS2 订阅源并存，`StateStore` 按"字段级新鲜度"仲裁（ROS2 帧带 `frame.stamp`，UDP 帧带 `recv_monotonic`，各自 staleness 独立判定）。此模式可长期共存——比如运控关节走 ROS2（10Hz+）、设备电池走 UDP ASDU（协议里没有对应 topic 时）。
- 工作量：新增 1 个源适配器 + 字段仲裁规则，**不动**状态层、WS 层、控制层、前端。

**路径 2｜独立 ros_bridge 进程接入（隔离演进，适合 ROS2 生态爆炸期）**
- 若 ROS2 侧要挂的东西越来越多（多机器人、Nav2、SLAM、RViz 工具链），把 ROS2 相关代码拆为**独立进程** `m20pro-ros-bridge`（复用 lite3 的 `ros_bridge_node` 思路），它订阅 ROS2 后**以与 ASDU 推送相同的 WS/REST 契约**向主进程回传，或主进程反向订阅它。
- 好处：`rclpy` 的崩溃/资源占用不波及主控制台进程；ROS2 环境变量、DDS 发现、domain id 全部关在子进程里。
- 代价：多一个 systemd 单元、跨进程序列化开销（本地回环可忽略）。

**路径 3｜彻底 ROS2 中心化（换后端不换前端）**
- 终局形态：本体监控协议退居"ROS2 不可用时的降级通道"，主数据面换成 ROS2 topic（运动状态）/service（控制）。
- **前端零改动**——因为 §5.4 的 WS 快照 schema 从 v1 就冻结并由 `GET /api/v1/schema` 契约测试守护；换掉的是 FastAPI 后端（可整体换成 ROS2 `rclpy` + FastAPI 混合，或纯 `rosbridge_suite` + 前端 WebSocket）。
- 触发条件（三者其一）：① 官方本体监控协议弃用；② 需要消费第三方 ROS2 生态（Nav2 规划结果、语义地图）；③ 多机器人编排要求 DDS 原生发现机制。

### 18.2 迁移代价对比

| 路径 | 架构改动 | 代码改动 | 停机 | 可回退性 |
|---|---|---|---|---|
| 1 `Ros2TopicSource` | 无 | 新增源适配器 | 零（滚动重启） | 删文件即回退 |
| 2 独立 bridge 进程 | 中（+1 单元） | 拆进程 + 适配契约 | 零 | 停单元即回退 |
| 3 ROS2 中心化 | 大（换后端） | 前端 0 行、后端重写 | 计划窗口 | 保留 UDP 源即降级回退 |

### 18.3 里程碑之外的后续可选（每项都只是新增实现或新模块，不动主干）
1. `Ros2TopicSource` → 导航任务监控；
2. SQLite 异常事件时间线（补 ADR-007 放弃的能力）；
3. WebRTC 低延迟通道；
4. AI 识别叠加（外部 AI 服务调研已有结论，采样器可复用）；
5. 控制通道逐步开放——**每一步都必须过一次安全闸评审**。
