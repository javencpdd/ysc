### 标定结论

- **线性关系：`vel_x ≈ 1.34 × 控制值`**（近似过原点），可作限速映射依据。
- 安全阈值：**默认 0.25（≈0.32 m/s）｜上限 0.40（≈0.54 m/s）｜≥0.70 禁用**。
- 已固化：服务端轴值域钳制 `±0.40`（`config.py` / `control_gateway.py` / `config.example.toml`）；前端"速度上限"输入框（0.05~0.40，默认 0.25，localStorage 持久化；摇杆满舵 = 所填数值）。

## 4. 修正记录（首测暴露的两个真实缺陷 + 后续改造）

1. **"松手即软急停 → 车趴下"缺陷（已修）**：`AxisWatchdog.pause()` 原硬编码 `_trip()`（零位 + 软急停）。修复：新增 `trip` 参数与 `_soft_pause()`；`/control/axis/stop` 改传 `trip=False`（松手 = 零位停发，车侧 150ms 看门狗自然清零，不软急停）；**异常路径（WS 断开 / 页面隐藏 / feed 超时）仍默认 `trip=True`** 兜底。
2. **租约无自动续约缺陷（已修）**：前端 `useRobotState.js` 的 `renewLease()` 从未被调用，而 `lease_seconds=5s` → 开启控制 5 秒后所有指令被租约闸拒发（`rejected` 计数的隐藏增长源）。修复：前端每 2s 自动续约（仅 `control.enabled` 时）；196 实测 3 轮续约后 `lease_remaining` 恒 ≈5s。
3. **虚拟摇杆改造（深夜上线，参考 lite3 ControlPanel.vue）**：替换六宫格方向按钮。与 lite3 的关键差异 —— m20 看门狗要求 ≤250ms 持续 feed：拖动期间以 60ms（≈16Hz）定时器持续 `POST /control/axis {continuous:true}`（即使指针不动也必须续发）；**松手时先等在途最后一发落地再调 `axis/stop`**，避免残余 feed 在暂停后重新激活看门狗。
4. rl_deploy 日志交叉验证：测试时段（车时间 01:33~01:34）运控侧零错误零切换；01:35:15 `Recv [MotionState]: 4` = 用户测试后正常趴下（17→4）。`01:24:29 VelControl TOML 保存` = `autoResetJointsZero=true`（自动重置关节零位），**与速度无关**。

## 5. 新系统事实（影响后续设计）

- **`LocationStatus`（ASDU 1002/7 的 `pos_x/pos_y/pos_z`）不跟随短距离运动**：用户确认三轮测试"车是自由行走的"（累计约 2m），但 pos 坐标纹丝不动（`(-1.199, 0.546, 1.166)` 跨多次测试同值）。
  **结论：室内短距场景不能用 pos 坐标做位移校验 / 巡逻反馈**（待研究；可能因 LIO 未收敛或该坐标是重定位锚点）。

## 7. 事故复盘："一按前进就失控、摔倒或趴下"（2026-10-15 深夜）

**现象**：用户反馈按"前进"后车体失控、栽倒。车侧日志实锤复原了完整机制。

**取证**（basic_server / rl_deploy，车侧时间）：

- `01:49:18 Recv [MotionState]: 2` → `motion state: 17 -> 2`；4 秒后 `[SAFE_CTRL] 姿态异常: roll=-3.9 pitch=-20.3 yaw=-96.4`（**车体栽倒**）→ 车自动尝试"摔倒爬起"（`启动摔倒爬起`，步态 0xf003）→ `01:49:28.470` 又收到 `17 -> 2`（**再次软急停**，爬起被打断）→ `01:49:35 [VelControl] 摔倒爬起失败，触发软急停`。
- `01:51:36` 用户重新站立（`Recv [MotionState]: 1`）成功（步态 0x1001）；**17 秒后 `01:51:53.914 Recv [MotionState]: 2`** —— 用户按"前进"→ 车瞬间被软急停 → 趴下。
- 全天 `Recv [MotionState]` 历史呈 `1（站立）/ 2（软急停）` 交替（00:23–00:39 达 7 次以上）——即用户早前"反复站起和趴下"的实锤序列。
- **`Recv [MotionState]: 2` 就是我们 `soft_estop()` 的编码**（`patrol_codec`: `motion_state(2)` → `{"type":2,"command":22,"items":{"MotionParam":2}}`）→ **所有软急停均来自控制台**。另有一个 `10.21.33.11` 心跳客户端（仅订阅状态推送、从未发过指令）已排查排除。

**机制（旧版代码）**：

1. 前端 `press('前进')` 只发**一次** `continuous=true`（不持续 feed）→ 服务端看门狗 250ms 后 `feed_timeout` → `_trip()` = 零位 + **软急停**；
2. 松手 `axis/stop` → `pause()`（旧签名 trip=True）→ **又是软急停**；
3. ⇒ **无论按多久、怎么松，旧版每次"前进"操作都必然产生软急停**；车若在运动中 → 突然被打断 → 失稳栽倒（姿态异常 pitch −20.3° 实锤）。

**修复（2026-10-15 深夜，已部署并验证）**：

- **分级兜底**（`AxisWatchdog`）：
  - feed 停更 250ms → **零位一帧 + 停发**（不软急停），等待恢复；
  - 停更 / 断连持续 **10s**（`stale_estop_ms`）无恢复 → 升级零位 + 软急停（车已停稳，趴下无运动学风险）；
  - 异常断开（WS 断 / 页面隐藏）宽限期内**租约恢复即取消升级**（刷新页面不误伤）；
  - 用户松手（`trip=False`）→ 零位停发，无升级。
- **安全零位帧豁免四道闸**（`ControlGateway.send_safety_zero()`）：排查中发现次生缺陷——零位兜底此前会被租约闸拦截（审计 `axis -> rejected`），租约一过期兜底形同虚设。
- 前端摇杆加固：最多 3 发在途（网络慢时多发抗抖动）+ 8% 中心死区 + 首次使用警示文案。
- 验证：单测 **70 项全绿**；196 真机行为验证（车待机、全程不动车）：`feed → 停更 1.2s → stale=True 且 trip_count=0 → 恢复 feed → stale=False → 松手 → paused` 全链路符合设计。

## 8. 事故复盘（二）："突然又倒了" —— 延迟升级误伤 + y/yaw 死区观察（2026-10-15 凌晨 03:55 真实时间）

> ⚠️ §7 的"分级兜底（10s 升级软急停）"已被本节 v3 修订**取代**：自动软急停机制整体切除。
> 两次事故同源——**任何"自动软急停"都会把机器人放倒**。

**现象**：用户测试"左右平移 / 转向"时车体突然倒下，怀疑与 y/yaw 指令有关。

**取证**（控制台审计 500 条 + basic_server / rl_deploy 交叉验证；196 系统时间）：

- 用户完整操作序列（审计）：`02:12:20–47` 左右平移 y：0.02→0.06→0.12→0.20→0.30→±0.40（-0.40 保持 5s）；`02:12:49–55` 转向 yaw：±0.03→±0.40（+0.40 保持 3.5s）；`02:12:56–58` 前后 x：0→0.40 冲刺 + 反向 -0.40；`02:13:00.6` 短推（终点 yaw=0.20，x=-0.02）后 **02:13:01.47 客户端彻底静默 10 秒**——连 2s/次的租约续约都中断（页面冻结或链路断流；整场操作还有 3 次 0.5~1s 级瞬断，Q7 WiFi 抖动同源）。
- `02:13:11.500` 看门狗 `feed_stale_escalated` **自动软急停**（距静默起点 10.03s = `stale_estop_ms`）。
- 车侧：`02:13:11.501` `收到关节阻尼指令 → rl_control → joint_damping`（快照 300s）；**全天零姿态异常、零摔倒记录** → 车不是走摔的，是**站立中被卸力软塌**（用户视角 = "倒了"）。
- 结论：**与左右平移/旋转指令无关**——是"断流 10s 自动软急停"在无恢复场景下的误伤。estop 锁存后，用户后续所有操作被闸拦（`CONTROL_DISABLED`）。
- 车侧其余记录：`02:13:15.50 motion 2 -> 0`（软急停自动回 idle）；此后全天无任何 MotionState 指令。

**y/yaw "小值不动" 观察**：审计显示用户对平移/转向从小指令（0.02~0.06 级）逐级上探。判定为**车侧策略起动阈值**（RL 策略对平移/转向普遍存在最小速度阈值，前后方向阈值较低）+ y/yaw 未经实车标定——**非面板故障**；具体阈值待受控标定（方案：仿 x 的阶梯测试，从 0.10 起逐级上探，读 `linear_y` / `omega_z` 反馈）。

**修复（v3"只停不趴"——自动软急停整体切除，已部署验证）**：

- `AxisWatchdog`：删除 `stale_estop_ms` / 延迟升级链 / `_trip()` / `trip_count`；**任何中断（停更 / 松手 / 断连 / 停机）一律"零位一帧 + 停发等待恢复"**；软急停只能由人显式触发（面板按钮 / HTTP）。`pause()` 同时作废当前 feed——`resume()` 后必须等**新** feed 才发送（不会用旧轴值恢复驱动）。
- 依据：车侧 rl_deploy 自带 **150ms steer 看门狗**（无新数据即清零速度字段）——链路断了车**本来就会停**；控制台任何"自动放倒"只会制造事故（两次事故同源，车侧日志均为实锤）。
- 前端加固：`visibilitychange` 页面切后台**自动松手**（防"按住摇杆切走 → 浏览器节流定时器 → feed 断流"）；每次按下摇杆**先补一次续约**（防"从后台回来首推被租约闸拒"）；摇杆警示文案更新（平移/转向起动阈值说明）。
- 验证：单测 **69 项全绿**（含 10s / 60s / 10min 超长"不软急停"断言）；196 部署 + 真机行为验证通过；审计确认测试窗口内**零 soft_estop 下发**。

**给用户的操作提醒**：

- 本次"倒"非运动学事故；建议目视检查车体（关节/机身/外壳）后重新站立。
- y/yaw 未经实车标定：从小幅慢试做起；急停随时可用。断流/松手/切后台现在只会"停"，不会"趴"。

## 9. 横移无反应排查（2026-10-16）+ 定时移动 / 双通道工具落地

**用户报**："用 0.4 的速度左右平移，m20 好像还是动不了" → 追问"在速度控制中选择左右移动，却一点反应都没有"。

**已排除项**（逐条取证，按时间序）：

1. **不是"横移对输入值要求更高"**：车侧 `/opt/robot/share/rl_deploy/conf/cmd_vel_limit.yml` 实测原文 `vx_limit: 0.40 / vy_limit: 0.40 / vyaw_limit: 1.2 / vx_yawlimit: 0.50` —— `vy_limit` 与 `vx_limit` **完全相同**；conf 目录仅 3 个文件，无横向专用阈值配置。
2. **不是"服务端拒发"**：控制台审计显示 `y=-0.4` 连续多帧 `result=ok`（帧确实发出且过闸）。
3. **取样时`motion_state=4`（趴下）**：趴下态轴指令本就不生效（前置校验之外的"静默忽略"）——至少能解释部分观察。
4. **量纲不一致（另记）**：服务端六轴统一钳 ±0.40，而车侧 `vyaw_limit=1.2` → **转向只用到官方量程 1/3**（待办：yaw 单独放宽，涉及转向失控风险，需真机标定后另行评估）。

**新取证（2026-10-16，basic_server / rl_deploy 二进制字符串）**：

- basic_server 内三条话题：`/STEER`、`/HANDLE_STEER`（由 **2/21** `cmdHandle_Steer` 发布）与 `/REAL_STEER`（由 **2/25** `cmdHandle_RealSteer` 发布）；两路指令字段完全同构（X/Y/Z/Roll/Pitch/Yaw）。
- `rl_deploy` 二进制中 `/STEER` 与 `/REAL_STEER` 字符串**均在**；steer 处理链符号 `DDSSteerDataHandler / HandlerSteer / ChannelSteer / ch_steer_`，产出 `current_cmd_velx / current_cmd_vely / current_cmd_velyaw` —— **RL 侧具备横向速度（vely）通道**。
- 局限：drdds 生成代码同时含 Pub/Sub 两类符号，"2/21 的命令最终落在 rl_deploy 的哪条订阅队列"**无法只靠字符串定论**。rl_deploy 今日日志无 steer 记录（不打印流量），文本配置中无通道绑定。
- 另值：当前车侧运行态实测 `motion_state=17`（RL 控制）、`gait=0x1001`（基础标准）、`control_usage_mode=0`（常规）。

**工具落地（2026-10-16 更新，部署 196 完成）**：

- **定时移动** `POST /api/v1/control/axis/timed {x..yaw, duration_s 0.5~30, channel}` —— 后端计时，到点自动零位停发（与松手同路径）；中止走 `axis/stop`；入口 `precheck` 即时拒发（未开启/未站立）。
- **轴指令双通道** `channel: steer(2/21 默认) / real(2/25)` —— `/axis` 与 `/axis/timed` 均支持；零位帧跟随当前通道；两条通道同套闸（前置 + ±0.40 钳制 + 审计）。
- 前端面板「定时移动」区：方向（前进/后退/左移/右移/左转/右转）+ 速度 + 秒数 + 通道 + 开始/中止 + 倒计时。

**对照实验（2026-10-16 已执行，真机闭环）**：

协议（探针 `tools/probe_motion.py`，5Hz 同时采 `topics.motion` + `topics.basic` + `watchdog` 三联数据；以"步态切到 12290"的审计记录为锚对齐时间轴；共 1290 有效样本 / 280s）：

1. 基础步态（0x1001）空闲基线 —— 测底噪；
2. 基础步态 + `axis_real`（2/25）右移 0.4 × 5s；
3. 基础步态 + `axis`（2/21）右移 0.4 × 5s；
4. 切 0x3002 平地（敏捷）+ 右移 0.3 × 2.9s；
5. 切 0x3002 + 前进 0.2 × 2s（阳性对照）。

| 0x1001 空闲（底噪） | **0.057**（均值，稳定常量非抖动） | 0.065 | 0.574 | 基线 |
| 0x1001 + real 右移 0.4 | **0.0543** | — | 0.574 | **在底噪内 ⇒ 不动** |
| 0x1001 + steer 右移 0.4 | **0.0503** | — | 0.574 | **在底噪内 ⇒ 不动** |
| 0x3002 + 右移 0.3 | **0.1011**（≈2× 底噪） | — | **0.574 → 0.461**（机身下沉） | **动了**（用户目视确认） |
| 0x3002 + 前进 0.2 | — | 0.3098 | — | 阳性对照成立 |

另有佐证：两条通道测试期间 `watchdog` 的零位帧均正常发出、审计全 `ok`，排除"链路没发出去"。

**★ 最终结论（推翻通道假设）**：

- **横移能力由「步态」决定，与指令通道无关**。0x1001 基础（标准）步态下 Y 指令**只原地调整姿态、不产生位移**（用户描述"姿态有细微变化但没移动，5s 后恢复"正是此现象）；切 0x3002 平地（敏捷）后横移立即生效。
- 2/21（steer）与 2/25（real）两条通道在基础步态下**行为完全一致**（0.0543 vs 0.0503，均 ≤ 底噪）—— 原"主通道没被车侧消费"的假设**不成立**；通道选择作为排查工具保留，默认仍为 steer（最小惊讶）。
- 与计划书 §10.3「移动步态仅 X/Y/Yaw 生效」的暗示一致：**Y 生效与否取决于当前步态族**。
- **副作用须知**：切 0x3002 敏捷步态时站高会从 0.574 降到 ~0.46（**机身降低约 11cm**），属该步态正常行为，非故障。

## 10. 心跳让渡 + "系统关停后车会不会趴下"实证（2026-10-16）

**用户问**："能不能主动发送和停止心跳，当系统关闭后，m20 会不会应该没有心跳信息自动趴下。"

### 取证（二进制 + 文档 + 真机）

- **心跳只是"注册推送对象"**：docs/04 §1.2.1 原文"机器人会向**持续发送心跳指令的 IP 和端口**上报实时状态信息和异常状态信息"；`basic_server` 二进制含 `Heartbeat new client connected, peer=[%s:%d]` / `Heartbeat timeout! Cleared %zu client(s).` → 心跳超时的动作是**清除客户端**（停止推送），不是运动保护。
- **心跳与指令是两个独立 UDP socket**：`UdpHeartbeatSource._sock`（发心跳 + 收状态推送）vs `UdpControlSink._sock`（发指令）→ 停心跳**不影响**指令链路。（计划书 §10.3.1 原"同一 socket 收发"只对数据链路成立，已修订。）
- **车侧真正的断链保护在 rl_deploy 的 DDS_CMD 看门狗**：`DDS_CMD topic data update timeout %f. Disable lynx`（另有 `GetStatus` 分支）；状态机符号 `StandUpState / LieDownState / JointDampingState / StartDampingState / ChargeLiedownState`。车侧另有 150ms steer 看门狗（无新数据即清零速度字段，见 §7）。
- `hanging_detection.yml`（`enabled: true`）是**倾倒检测**（BasicFlat/NaviFlat 步态下的吊挂识别），与心跳无关，勿混淆。
- `conf/cmd_vel_limit.yml` 与 `config/cmd_vel_limit.yml` md5 相同（`b8f70056…`），无第二份速度配置。

### ★真机实证（决定性，2026-10-16）

| 步骤 | 观测 |
|---|---|
| 基线 | `motion_state=17`（RL 站立）、`gait=0x3002` |
| `systemctl stop m20pro-console` | `is-active: inactive`，静默 **50s**（远超 basic_server 心跳超时） |
| `systemctl start` + 8s | `is-active: active`，遥测恢复 |
| **恢复后** | **`motion_state=17`（仍站立）**、`height=0.494`（不变）、`linear_x/y = -0.0354 / -0.0017`（仅空闲底噪）、`connected=true` |

旁证：控制台重启后 `sent_packets=0`（**零指令**）持续数分钟，车同样稳定保持 `motion_state=17`。

**⇒ 结论：系统关闭 / 停心跳都不会让车趴下。且不应追求"断链自动趴下"**——两次自动软急停事故已证明站立中被卸力软塌（`JointDampingState`）就是摔倒；正确语义是"断链 → 停 + 保持站立"（看门狗 v3）。

### 功能落地：心跳让渡 + 遥测闸（ADR-015）

- `UdpHeartbeatSource.pause()/resume()`：停发但不拆 socket/线程（恢复瞬时）；`stats()` 增 `paused/paused_seconds/pausable`。
- `POST /api/v1/link/heartbeat {paused, confirmed}`（+ `GET` 查状态）：**暂停需二次确认、恢复不需**（恢复视野是安全动作）；暂停前服务端**先零位停发正在进行的控制**。
- **新第五道闸** `ControlGateway._check_telemetry`：遥测暂停 → 拒绝一切驱动类指令（`TELEMETRY_PAUSED`，409），豁免 `heartbeat`（否则"停了想恢复"被自己锁死）与 `soft_estop`。
- 降级语义复用 `ServiceSnapshot.degraded/degraded_reason`（**未动冻结契约**），原因码 `heartbeat_paused`；前端琥珀横幅（+恢复按钮）与红色"数据停更"分色。
- 测试：新增 `test_data_source.py`（4 例，**真 localhost UDP socket**）+ `test_heartbeat_api.py`（7 例）+ 网关 +5 例 → **109 项全绿**。
- **196 端到端验证**：未确认暂停 → `CONFIRM_REQUIRED`；开启 L1 后暂停中发轴指令 → `TELEMETRY_PAUSED` 409 且**一帧不发**；恢复后同一条指令放行；全程 `motion_state=17` 不变；结束时控制已归位（`enabled=false`）。
