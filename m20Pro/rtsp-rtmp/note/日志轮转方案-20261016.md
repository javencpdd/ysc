# 推流日志轮转方案（文件大小上限 + 轮换存储）

> 实施日期：2026-10-16
> 目标主机：M20 Pro AOS 196（`192.168.0.196`，账号 `user`）
> 需求来源：用户要求"在现有日志记录功能中增加文件大小上限与轮换存储机制"，并明确
> "也就是固定日志空间的最大值，然后进行轮换存储机制"。

---

## 1. 需求拆解

| 需求 | 落地方式 |
|---|---|
| 单文件达到上限（如 10MB）自动切分，新建/清空后继续写入 | `M20LOG_MAX_BYTES`（默认 10485760） |
| 保留最近 N 个历史文件（如 5 个），超出删除最旧的 | `M20LOG_KEEP`（默认 5） |
| **固定日志空间最大值**（总占用有硬上限） | `M20LOG_TOTAL_MAX_BYTES`（默认 0 = 由前两项隐含：`10MB×(5+1)=60MB`） |
| 轮转文件带序号或时间戳命名 | `M20LOG_NAME_FMT`：`seq`（`forward-f.1.log`）或 `ts`（`forward-f-20261016-030900.log`） |
| 切换过程不丢日志、不中断写入 | `copytruncate` + **追赶式复制**；并发抢锁**非阻塞** |
| 多进程 / 多线程安全 | `flock` 互斥（无 flock 时回退 `mkdir` 原子锁）+ 双检 + `O_APPEND` 原子追加 |
| 日志目录、文件名格式可配置 | `M20LOG_DIR`、`M20LOG_NAME_FMT`、`M20LOG_TS_FMT` |
| 保持现有日志调用方式不变 | `log "xxx"` 调用点**一行都没改**，只替换 `log()`/`rotate_log()` 内部实现 |

## 2. 改造前的现状与缺陷

原 `rtmp_forward.sh`（L67-83）只有这段：

```bash
rotate_log() {
    [ -f "$LOG_FILE" ] || return 0
    size=$(stat -c %s "$LOG_FILE" 2>/dev/null || echo 0)
    if [ "$size" -ge "${LOG_MAX_BYTES:-5242880}" ]; then
        mv -f "$LOG_FILE" "$LOG_FILE.1" 2>/dev/null
    fi
}
rotate_log            # ← 只在脚本启动时调用一次
```

| 缺陷 | 后果 |
|---|---|
| `rotate_log` **只在启动时调用一次**，运行期永不检查 | 日志无限增长 → 实测堆积到 **475MB** |
| 只保留 `.1` 一份，`mv -f` 直接覆盖 | 历史只留一代 |
| 命名无序号/时间戳 | 无法区分新旧 |
| **用 `mv`** | gst 启动时 `>>"$LOG_FILE"` 打开并**长期持有 fd**；`mv` 后 fd 仍指向旧 inode → 日志继续写进 `.1`，新 `.log` 永远是空的，且 `.1` 无限增长 |
| 无任何锁 | 两路并发可能同时轮转 |

## 3. 关键设计决策：为什么必须 `copytruncate`

`rtmp_forward.sh` L331/333 启动管道的方式：

```bash
taskset -c "$CPUSET" "${PIPE[@]}" >>"$LOG_FILE" 2>&1 &
```

gst-launch 在**启动时打开一次 fd 并长期持有**。实测对照（真机 196）：

| 模式 | 结果（400 行写入 + 期间轮转 2 次） |
|---|---|
| `mv` | `app.log` **消失**，19200 字节**全部写进** `app.1.log`，且 `.1` 会无限增长 ❌ |
| `copytruncate` | 当前文件 1776 字节、末行为 `gstline 0400`（最新行仍在当前文件）；`.1` 保存了旧内容 ✅ |

生产链路上的最终证据（对正在推流的 `forward-f.log` 实做一次轮转）：

```
轮转前: inode 651947, 265418 字节, 2394 行
轮转后: forward-f.1.log = 265418 字节（diff 完全一致，零丢失）
        forward-f.log   = 0 字节, inode 仍是 651947 ← truncate 语义，未换文件
gst 进程 3027 的 fd: 1 -> /home/user/rtmp_1012/logs/forward-f.log  (2 同)
```

因为只截断、不改名，gst 的 fd 路径**始终有效**，写入零中断。

### 3.1 追赶式复制：解决"复制→截断"窗口丢日志

朴素 copytruncate（`cat` 后 `truncate`）会丢掉复制期间新增的字节。8 进程并发压测下：

| 实现 | 期望 1200 行 → 实际 |
|---|---|
| `cat` + `truncate`，`flock -w 2`（阻塞） | **328 行**（丢 73%） |
| **追赶式复制 + `flock -n`（非阻塞）** | **1200 行，零丢失、零损坏** |

两项改进：
1. **追赶式复制**：记录上轮复制偏移，把 `[偏移, 末尾]` 追加到临时文件；若文件仍在增长则再来一轮（默认最多 `M20LOG_CATCHUP_ROUNDS=4` 轮）。丢失仅剩"最后一轮读取到 truncate 之间"的极小窗口。
2. **抢锁非阻塞**：`M20LOG_LOCK_WAIT=0`。原设 2 秒反而有害 —— 竞争进程被阻塞，醒来时正好撞上 truncate，白白多丢一轮。拿不到锁说明别的进程正在轮转，交给它即可。

## 4. 配置项说明（默认值）

配置位置：`/home/user/rtmp_1012/config.env`（末尾"日志轮转配置"段）

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `M20LOG_MAX_BYTES` | `10485760`（10MB） | **单文件大小上限**。达到即切分，随后继续写入 |
| `M20LOG_KEEP` | `5` | **保留最近几份历史**（不含当前正在写的）。超出的从最旧删起 |
| `M20LOG_TOTAL_MAX_BYTES` | `0` | **总占用硬上限**（当前 + 全部历史）。`0`=不额外限制，隐含上限 `MAX_BYTES×(KEEP+1)`=`10MB×6=60MB`。设为具体值（如 `52428800`）即绝对固定占用。注意会为当前文件预留一个满文件空间，故实际稳定在 `≤ 该值` |
| `M20LOG_DIR` | 空 | 历史文件存放目录。留空 = 与日志文件同目录 |
| `M20LOG_NAME_FMT` | `seq` | 轮转文件命名：`seq` → `forward-f.1.log`；`ts` → `forward-f-20261016-030900.log`；也可写模板，占位符 `{base}` `{ext}` `{n}` `{ts}` |
| `M20LOG_MODE` | `copytruncate` | 轮转方式。**本项目必须用 `copytruncate`**（gst 持有 fd）。`mv` 仅适用于"每次 open 追加"的写入方 |
| `M20LOG_TS_FMT` | `%Y%m%d-%H%M%S` | `{ts}` 的时间格式 |
| `M20LOG_CHECK_BYTES` | `4096` | 写入方累积写入多少字节做一次检查（主触发条件，确定性，不依赖时钟）。副作用：单文件最多超出上限约此值 |
| `M20LOG_MIN_CHECK_INTERVAL` | `1` | 低频日志的最小检查间隔（秒），保证迟早被检查到。`0`=每次都检查 |
| `M20LOG_CATCHUP_ROUNDS` | `4` | copytruncate 追赶复制轮数 |
| `M20LOG_LOCK_WAIT` | `0` | 抢锁等待秒数。`0`=非阻塞（推荐） |
| `M20LOG_SCAN_DIR` | `/home/user/rtmp_1012/logs` | 巡检脚本扫描目录 |
| `M20LOG_SCAN_GLOB` | `*.log` | 巡检匹配模式 |

> **兼容性**：旧的 `LOG_MAX_BYTES`（原 5242880）仍然有效，优先级低于 `M20LOG_MAX_BYTES`；
> 若未设 `M20LOG_MAX_BYTES` 则回退到 `LOG_MAX_BYTES`。

> **总空间上限怎么算**：单路日志稳定占用 ≤ `M20LOG_TOTAL_MAX_BYTES`（若为 0，则 ≤ `MAX_BYTES×(KEEP+1)`）。
> 当前有两路（`forward-f`、`forward-b`），故总占用约为该值的 **2 倍**。
> 例如想固定"推流日志最多占 100MB"，可设 `M20LOG_TOTAL_MAX_BYTES=52428800`（50MB × 2 路）。

## 5. 部署清单

### 5.1 主机 196 上的文件

| 路径 | 作用 |
|---|---|
| `/home/user/rtmp_1012/lib/m20-log.sh` | 轮转库本体（可 source，也可独立执行） |
| `/usr/local/sbin/m20-log-rotate.sh` | 巡检脚本（扫描日志目录并轮转） |
| `/etc/systemd/system/m20-log-rotate.service` | `Type=oneshot` |
| `/etc/systemd/system/m20-log-rotate.timer` | `OnBootSec=2min`、`OnUnitActiveSec=60s` |
| `/home/user/rtmp_1012/config.env` | 新增轮转配置段（备份 `config.env.bak-logcfg-20261016`） |
| `/home/user/rtmp_1012/rtmp_forward.sh` | `log()`/`rotate_log()` 内部改为调用库（备份 `rtmp_forward.sh.bak-logrotate-20261016-034406`） |

### 5.2 为什么需要独立的巡检定时器

`gst-launch` 由内核直接 `>>` 追加日志，**不经过 shell 的 `log()` 函数**，所以"写入方自己检查大小"这条路径完全盖不住它。GStreamer 异常时会疯狂刷 WARNING/ERROR（实测 `mpph264enc` 报错可达 ~60 条/秒），日志增长极快。因此必须有一个独立的、固定周期巡检的轮转者 —— 这就是 `m20-log-rotate.timer`。

两道防线：
1. **写入方触发**：`log()` → `m20log_emit` → 每累积 4KB 检查一次（覆盖脚本自身的日志）
2. **定时器兜底**：每 60 秒扫描目录（覆盖 gst 直写的那部分）

### 5.3 改造后的 `log()`（调用方式不变）

```bash
log() {
    local line
    line="$(date '+%Y-%m-%d %H:%M:%S') [forward-$STREAM] $*"
    if command -v m20log_emit >/dev/null 2>&1; then
        m20log_emit "$LOG_FILE" "$line"      # ← 内部自动按需轮转
    else
        printf '%s\n' "$line" >>"$LOG_FILE" 2>/dev/null   # 库缺失时兜底
    fi
    [ "${CONSOLE_LOG:-0}" = "1" ] && printf '%s\n' "$line"
    return 0
}
```

原有 `log "xxx"` 调用点（启动横幅、看门狗告警、退出清理等 15 处）**全部保持原样**。

## 7. 运维手册

```bash
# 查看当前配置
grep '^M20LOG' /home/user/rtmp_1012/config.env

# 手动跑一次巡检（dry-run 只看不动）
sudo /usr/local/sbin/m20-log-rotate.sh --dry-run
sudo /usr/local/sbin/m20-log-rotate.sh

# 强制轮转某个日志（不看大小）
sudo /usr/local/sbin/m20-log-rotate.sh --help
M20LOG_VERBOSE=1 /home/user/rtmp_1012/lib/m20-log.sh --rotate /home/user/rtmp_1012/logs/forward-f.log force

# 库自检（造 400 行小文件验证轮转）
/home/user/rtmp_1012/lib/m20-log.sh --self-test

# 查看轮转日志
sudo journalctl -u m20-log-rotate.service --since '1 hour ago'

# 临时用更小的上限验证（不改配置）
sudo env M20LOG_MAX_BYTES=100000 M20LOG_VERBOSE=1 /usr/local/sbin/m20-log-rotate.sh
```

### 7.1 常见调整

| 想要 | 怎么改 `config.env` |
|---|---|
| 保留更多历史 | 调大 `M20LOG_KEEP` |
| 固定总占用为 X MB | `M20LOG_TOTAL_MAX_BYTES=$((X*1048576))`（两路各一份） |
| 改用时间戳命名 | `M20LOG_NAME_FMT=ts` |
| 单文件上限改小 | `M20LOG_MAX_BYTES=5242880`（5MB） |

改完 `config.env` 无需重启服务，巡检定时器下一次触发即生效；`rtmp_forward.sh` 的写入方检查需重启 `m20video` 才读取新值。

### 7.2 回滚

```bash
# 1) 停用定时器
sudo systemctl disable --now m20-log-rotate.timer
sudo rm -f /etc/systemd/system/m20-log-rotate.{service,timer}
sudo rm -f /usr/local/sbin/m20-log-rotate.sh
sudo systemctl daemon-reload

# 2) 还原脚本与配置
sudo cp /home/user/rtmp_1012/rtmp_forward.sh.bak-logrotate-20261016-034406 \
        /home/user/rtmp_1012/rtmp_forward.sh
cp /home/user/rtmp_1012/config.env.bak-logcfg-20261016 /home/user/rtmp_1012/config.env

# 3) 重启中继
sudo systemctl restart m20video
```

> 注：`lib/m20-log.sh` 保留无害（无人调用即不生效），也可一并删除。

## 8. 已知边界

1. **单文件最多超出上限约 `M20LOG_CHECK_BYTES`（默认 4KB）** —— 因为检查是按累积字节触发的。要把上限卡得更死可调小该值（代价是检查更频繁）。
2. **`M20LOG_TOTAL_MAX_BYTES` 是"软硬"上限** —— 会为当前正在写的文件预留一个满文件空间，故稳态 `≤ 该值`；但若单文件上限本身大于该值，则以单文件为准。
3. **`copytruncate` 无法做到绝对零丢失** —— 追赶式复制把窗口压到毫秒级，但理论上仍有极小窗口。若某写入方是"每次 open 追加"（不用长持 fd），可对该文件单独用 `M20LOG_MODE=mv` 实现严格零丢失。
4. **命名不匹配的历史文件不会被自动清理** —— 例如遗留的 `forward-f.log.1`（旧命名，475MB）与新规则 `forward-f.1.log` 不同，保留策略不会删除它，需手工清理。
5. 修改 `config.env` 后，**已在运行的 `rtmp_forward.sh` 进程**不会重新读取（shell 已载入内存），需重启 `m20video` 生效；但巡检定时器每次都重新读配置，不受此限。
