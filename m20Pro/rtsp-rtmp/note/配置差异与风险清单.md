# 配置差异与风险清单（RTSP / RTMP）

## 1. 三套互不相同的 RTSP 目标地址 ⚠️ 最高优先级

代码里同时存在三个不同的推流目的地，改需求时极易改错文件：

| 出处 | 目标地址 | 是否生效 | 说明 |
|---|---|---|---|
| `push_video.sh` → `build_pipeline()` | `rtsp://127.0.0.1:8554/video1` `/video2` | ✅ **当前生效** | 本机自环，mediamtx 中转 |
| `start_push_video.sh` + `SM_USB_107X_*.json` | `rtsp://192.168.0.198:8554/video1` | ❌ 无人调用 | 同网段的 **.198** 主机 |
| `org/push_video.sh` (旧版 fallback) | `rtsp://10.21.31.155:8554/video1` `/video2` | ❌ 已废弃 | 早期调试地址 |

**影响**：当前 Camera 图像只推到本地 mediamtx，只有能连到 196 的客户端才能拉。若下游算法期望在 .198 上收流，会拿不到画面；反之若把 in-车 Pipeline 改成 .198，又可能因为网络抖动引入延迟与丢帧。

**建议**：把DEST 抽象成单一变量（如 `/opt/robot/scripts/board_resources/rtsp_service/rtsp_target.conf`），三处统一读取。

另外注意 `SM_USB_107X_{0,1}.json` 都是 `.../video1`，`{2,3}.json` 对应 `/video2`；而 `rtsp_url` 字段和 `pipeline_template` 字符串里的地址是**重复写的两份**，改一处忘一处是必然的。

## 2. SM_USB_107X 编码器参数分歧 ⚠️

同一款摄像头，两套定义完全不同：

```
push_video.sh  (生效):  mpph265enc gop=2 header-mode=each-idr
SM_USB_107X_*.json:     mpph265enc rc-mode=1 bps=1800000 bps-max=2000000 qp-min=12 qp-max=45
 org 旧版 fallback:     mpph265enc rc-mode=0 bps=1800000 bps-max=2000000 qp-min=12 qp-max=45
```

三个问题：
1. **生效版本完全没有码率控制参数**（无 `rc-mode` / `bps`）。`rc-mode` 不设等于用 mpph265enc 默认值，码率不可控，弱网下可能爆带宽。
2. **rc-mode 语义在两套配置里不一致**：JSON 用 `1`（CBR），旧 fallback 用 `0`（VBR），同素材同场景给出两种码率曲线。
3. **分辨率冲突**：生效版 SM_USB_107X → **800×600**；JSON 里写 **1280×720**。摄像头本身若原生输出 720p，降采样到 800×600 会损失视野面积/NDVI 精度，需确认是有意为之。

另外 `gop=2` 相当激进（每 2 帧一个 IDR），配合 `header-mode=each-idr` 会让每个 IDR 都带 VPS/SPS/PPS，**码率开销明显上升**，换来的是拉流端极快起播。若场景是干净链路，考虑放宽到 `gop=15~30`。

**建议**：明确 SM_USB_107X 的目标,opencv 链路和 gst 链路二选一走，或让 push_video.sh 直接读取 JSON 的 `encoding` 字段保持单一数据源。

## 3. RTMP 完全未被使用（事实确认）

grep 全量代码：
- 没有任何 `rtmp://` 推流地址
- 没有任何拉流端 / 播放器 / FFmpeg 引用 RTMP
- `push_video` 二进制不链接 librtmp

唯一的 RTMP 痕迹是 `mediamtx.yml` 的 `rtmp: yes`。端口 1935 实测 OPEN，但闲置。

> 如果原本打算用 RTMP 做远程图传，**目前这条链是断的** —— 没人往 mediamtx 推 RTMP，外部 RTMP 拉流会直接失败（RTSP 推上去的流 mediamtx 会转封装成 RTMP 输出，所以外部 RTMP 客户端其实能拉到 `rtmp://192.168.0.196:1935/video1`，这条路是通的，只是没人用）。

## 4. 潜在 Bug

### 4.1 指数退避整数溢出（latent）

`push_video.sh:493`
```bash
local delay=$((RETRY_BASE_DELAY * (2 ** (retry_count - 1))))
if [ "$delay" -gt "$RETRY_MAX_DELAY" ]; then delay=$RETRY_MAX_DELAY; fi
sleep "$delay"
```
本地复现实测：

| retry_count | 计算出的 delay |
|---|---|
| 30 | 1073741824 |
| 62 | 4611686018427387904 |
| **63** | **-9223372036854775808**（溢出） |
| 64+ | 0 |

第 63 次连续重试时 `delay` 变负，`-9223... > 30` 判定为假 → **不会被 clamp 到 30** → 执行 `sleep -9223372036854775808` → sleep 报错立即返回 → **退化为忙循环**，CPU 打满 + 日志刷屏。

因为 `MAX_RETRY=0`（无限重试），只要摄像头持续闪断（每次都撑不过 5 次健康检查就断开），理论上能累计到 63 次触发。

**修复**：
```bash
local delay=$RETRY_MAX_DELAY
if [ "$retry_count" -lt 6 ]; then
    delay=$((RETRY_BASE_DELAY * (2 ** (retry_count - 1))))
fi
```

### 4.2 `start_push_video.sh` 进程增殖（当前未启用，但代码还在）

```bash
while true; do
    if [ -e "/dev/video$video_device" ]; then
        taskset -c $core ./push_video "$config_file"
        ./restart.sh          # ← restart.sh 内部会 pkill -f push_video 然后重启 start_server.sh
    fi
    sleep 3
done
```
`restart.sh` 里 `pkill -f push_video` 会杀掉**自己所属的整棵脚本树**（包括正在执行这个 while 循环的父 shell 被 SIGTERM 后，又因果lap... 而 router），再拉起全新的 `start_server.sh` → 新 `push_video.sh`。旧 shell 若未被杀净则带着自己的 while 继续跑 → 进程数翻倍。

这与观察到的历史混乱一致。当前 `start_server.sh` 直接调 `push_video.sh`（新版已不含 restart.sh 调用），所以**暂不会触发**，但文件未删，一旦有人改回调用 start_push_video.sh 就会复现。

### 4.3 `stop.sh` 的退出码判断失效

```bash
pkill -f v4l2
pkill -f push_video
if [ $? -eq 0 ]; then ...   # 只看第二个 pkill，且 pkill 无匹配时返回 1 ≠ 失败
```
语义错误：无匹配进程也会打印"所有进程已成功关闭"。另外 `stop.sh` **不杀 mediamtx**，多次执行会产生多个 mediamtx 实例争抢 8554。

### 4.4 `restart.sh` 会连带重启 mediamtx

`restart.sh` → `start_server.sh` → `sudo ./mediamtx &`。若反复调用 restart.sh，**可能起多个 mediamtx**（旧的没被杀），后续启动的会因端口占用失败。
建议 restart.sh 明确 `pkill -f mediamtx` 后再起。

## 5. 安全 / 运维短板

| 项 | 现状 | 建议 |
|---|---|---|
| **RTSP 鉴权** | `authMethods: [basic]`，但 `authInternalUsers` 为空 → **等于无鉴权**，任何人可推/拉任意路径 | 加 `authInternalUsers` 或 ip whitelist |
| **paths 通配** | `paths:` 只有空的 `all_others:` → 任意路径名都可被发布 | 显式定义 `video1:` `video2:`，其他路径拒绝 |
| **API 关闭** | `api: no` | 调试期改成 `yes`，用 `curl 127.0.0.1:9997/v3/paths/list` 查在线流，比 ps/netstat 高效得多 |
| **Metrics 关闭** | `metrics: no` | 打开后可接 Prometheus 观测码率/连接数 |
| **无 systemd 托管** | 仅由 `start.sh` 后台 `&` 拉起 | mediamtx 或 start_server.sh 崩溃后**不会自动恢复**；建议加 systemd unit + `Restart=always` |
| **日志** | `LOG_TO_FILE=0` → 只打 stderr，`LOG_FILE` 形同虚设 | 改成 1 并加 logrotate；现在 `push_video.log` 的定位代码写了但没启用 |
| **usb_ctl.sh 未接入** | GPIO 125 硬复位摄像头的能力被注释 | 多次重连失败后可自动调用 `usb_ctl.sh disable && sleep 2 && enable` 做硬复位 |

## 6. 修改优先级建议

| 优先级 | 事项 |
|---|---|
| P0 | 统一 RTSP 目标地址为单一配置项（避免改错文件） |
| P0 | 给 SM_USB_107X profile 补 `rc-mode` / `bps` 码率参数 |
| P1 | 修 4.1 指数退避溢出（改 1 行） |
| P1 | 打开 `api: yes` + 显式定义 `paths: video1/video2` |
| P1 | 加 RTSP 鉴权或网络隔离 |
| P2 | restart.sh 增加 `pkill -f mediamtx`；stop.sh 修正退出码判断 |
| P2 | 删除或重写 `start_push_video.sh`（避免 4.2 复活） |
| P2 | 加 systemd unit + `Restart=always`；启用文件日志 |
| P3 | 评估 800×600 vs 1280×720、gop=2 是否为预期；不需要就删掉未使用的 RTMP/HLS/WebRTC/SRT 开关 |
