> 评估日期：2026-10-14（02:20–03:20 完成**上机实测复核**）
> 评估对象：196 主机（`aos`，RK3588 级 8 核）「USB 双相机 → MediaMTX 本机自环 → rtmp_1012 中继 → SRS（172.31.68.227:1936）」全链路
> 评估基准：全量代码审查（本地镜像）+ 2026-10-12 上机实测数据 + **2026-10-14 全链路端到端实测**
> ✅ **主机已在线，第 5 节"待复核"项已全部实测**（详见 §7）。第 6.3 节原「主机当前离线」判断已更正为**本机网络路径问题**。
>
> **实测总览（一句话）**：链路**零丢帧、零花屏、时间戳健康、CPU/内存充裕、上行 0% 丢包**；稳态附加时延仅 **≈80 ms**。真正的问题不在推流本身，而在**周边环境**——主机时钟差了 **846 天**、`tk-mtx.service` 已空转重启 **1935 次**、上游相机服务无守护、WiFi 信号 **-65 dBm 无余量**。

## 1. 链路全貌

```
SM_USB_107X ×2 (MJPEG 800×600@30)
   │ v4l2src → jpegdec(软解) → videoconvert(I420) → mpph264enc(硬编 2Mbps CBR) → h264parse
   ▼ rtspclientsink (loopback, latency=10)
MediaMTX v1.4.2 (8554/1935/8888/8889)   ← 无 systemd 守护、无认证
   ▼ rtspsrc (TCP interleaved, latency=100)
rtmp_1012 中继 (m20video.service, 绑核 0-3)
   ▼ rtph264depay → h264parse(config-interval=-1) → flvmux(streamable) → rtmpsink(live=1)
SRS 172.31.68.227:1936/live/m20pro-{f,b}   ← 单目标，无备用
```

## 2. 分环节评估

### 2.1 拉流环节

**现状**：相机侧 MJPEG 采集后软解 JPEG、转 I420、MPP 硬编 H.264，经 loopback 推入本机 MediaMTX；中继以 `rtspsrc protocols=tcp latency=100` 拉回。

| # | 发现 | 风险/瓶颈 | 建议 | 预期收益 | 优先级 |
|---|---|---|---|---|---|
| R1 | `jpegdec` 为软件 JPEG 解码 | 相机侧 CPU 15.8% 单核/路中含此项；若相机支持 YUYV/H.264 直出可省 | `v4l2-ctl --list-formats-ext` 核实 SM_USB_107X 支持的格式（**需上机复核**），优先则改 caps | 每路省约 0.05–0.1 核 | P2 |
| R2 | MediaMTX 无守护、无认证、`overridePublisher: yes` | ① 它崩溃则源与观众全断，无人重启；② 同网段任意主机可读流、可踢掉相机 publisher 抢推 | paths 段为 `video1/video2` 增加 `publishUser/publishPass` + `overridePublisher: no`；相机侧与中继侧 RTSP URL 带认证 | 消除抢推与盗看风险 | P1 |
| R3 | `rtspsrc latency=100ms`、无 `drop-on-latency` | 无——这是实测验证过的正确配置（加了会 CRITICAL 雪崩，96 万条/2 分钟） | **保持不变**，勿被"低延迟优化"误导 | — | 保持 |
| R4 | loopback 双跳（相机→mediamtx→中继） | 延迟成本 <20ms，换来做种解耦（摄像头重连不影响拉流地址）价值更高 | 不建议改 | — | 保持 |

### 2.2 解码 / 转码环节

**现状**：`SOURCE_CODEC=h264` 纯 remux，零转码。这是 2026-10-12 完成的关键改造，实测 CPU 197.6% → 13.9%（单核），降 14.2 倍。

| # | 发现 | 风险/瓶颈 | 建议 | 预期收益 | 优先级 |
|---|---|---|---|---|---|
| R5 | **两侧配置无联动**：相机侧 H.264 补丁位于打包文件（boardresources），OTA/重装会被还原；还原后源变 H.265，中继仍按 h264 走 `rtph264depay` | **单点故障**：解包器持续报错、管道起不来，重试循环空转刷屏，不自愈 | ① 短期：`m20video doctor` 增加源编码一致性检查（DESCRIBE 探测 `a=rtpmap`）；② 中期：中继启动前探测源编码，不符则自动切换 `SOURCE_CODEC` 并重启 | 消除「OTA 后推流静默死亡」路径 | **P0** |
| R6 | h265 回退模式（转码）约 1.98 核/两路 | 可接受但应视为临时态；`videoconvert` NV12→I420 占 95%/路，系统无 RGA 转换元素 | 保持相机侧 H.264，不回退；若必须回退，接受 2 核开销 | — | P2 |
| R7 | `mpph264enc` 喂 NV12 花屏（绿紫条纹，行步长错配） | 后人若"优化"掉 I420 强制即复现花屏 | `config.env`/`push_video.sh` 已有大字警告与 `video/x-raw,format=I420` 强制，**保留勿动** | — | 保持 |

### 2.3 封装环节

**现状**：`h264parse config-interval=-1 → flvmux streamable=true → rtmpsink live=1`。配置正确。

| # | 发现 | 风险/瓶颈 | 建议 | 预期收益 | 优先级 |

| R9 | 无音频轨道 | 若业务无音频需求则无影响 | 确认即可，无需动作 | — | 保持 |
| — | `config-interval=-1` | 无——保证每个 IDR 前带 SPS/PPS，防中段接入花屏 | **保持** | — | 保持 |

### 2.4 网络传输环节（最大风险区）

**现状**：196 经 WiFi 接入，RTMP over TCP 到 172.31.68.227:1936；两路 2Mbps CBR ≈ 4Mbps 持续上行。

| # | 发现 | 风险/瓶颈 | 建议 | 预期收益 | 优先级 |
|---|---|---|---|---|---|
| R10 | **WiFi 链路质量无监测、无自适应**：196 经 WiFi 接入且实测间歇丢包；4Mbps 持续上行在机器人移动/远离 AP 时触发 TCP 重传 → 延迟抖动、卡顿、周期性断流 | RTMP 无速率自适应机制，唯一兜底是看门狗（`STALL_SENDQ=1MB`）重启管道，恢复期 5–30s 观众看到冻结画面 | ① 部署条件允许则改**有线**（背部网口），一劳永逸；② 必须 WiFi 则：确认 5G AP/信号强度/固定信道，按第 6 节场测；③ **降码率**（见 R14）直接减小上行压力；④ 看门狗阈值保留 | 卡顿/断流频次预计下降 50%+（有线场景基本消除） | **P0** |
| R11 | 目标单点 + 退出码 3 未接 `RestartPreventExitStatus` | 目标长期不可达时：探测 3×5s 失败 → 退出码 3 → systemd `Restart=always` 每 ~25s 空转重启一轮，日志空转（有 5MB 轮转兜底，不致命） | 加 drop-in：`RestartPreventExitStatus=3`，复现 120 主机「网络长期不可用则停推等网络」语义 | 消除空转；网络恢复后 `m20video up` 即恢复 | P1 |
| R12 | 端到端延迟预算约 0.5–2s（**估算**：采集~33ms + 硬编~20ms + mediamtx 一跳~10ms + rtspsrc 缓冲≤100ms + 播放器缓冲 0.3–1.5s 占大头） | RTMP 固有上限；若遥控要求 <500ms 则不满足 | 按需启用 mediamtx WebRTC（8889 已开）作为第二低延迟分发通道，遥控端用 WebRTC、监看端用 RTMP | 遥控路径 <500ms | P2 |
| R13 | **无掉线告警** | 推流中断只能靠观众发现；主机当前离线即无人推流，也无任何通知 | 目标端 SRS 侧对 `m20pro-f/b` 配置掉线探测/hook（或 196 上 cron 心跳 curl 目标端），掉线 >30s 通知运维 | MTTR 从"小时级人工发现"降到分钟级 | P1 |

## 7. 上机实测复核（2026-10-14 02:20–03:20，196 主机在线）

> 方法说明：所有测量在 196 主机上就地执行（避免把 WiFi 段的不确定性混进来）。涉及"时延"的测量采用**内容哈希对齐法**：同时开两个读取端，A 读本机 MediaMTX 的 `rtsp://127.0.0.1:8554/video1`（近似"零中继"基线），B 读远端 SRS 的 `rtmp://172.31.68.227:1936/live/m20pro-f`（完整链路）；两路输出无损灰度 PNG，用 **MD5 逐帧配对**，再比对同一帧的**文件落盘墙钟**。这规避了 RTMP 时间戳跨进程不可比的问题。

### 7.1 交付质量：零丢帧、零花屏、时间戳健康

| 项 | 实测结果 | 结论 |
|---|---|---|
| **逐帧一致性**（40 s 并发抓帧） | A（本地 RTSP）**1173 帧** / B（远端 RTMP）**1173 帧**，**逐帧 MD5 完全一致（0 处差异）** | ✅ 中继**零丢帧、零损坏**，remux 路径无损 |
| **稳态帧率** | 两路均为 **3340 ms / 100 帧 = 30.0 fps**（t+3s 后进入稳态，A/B 完全同步） | ✅ 与编码 30 fps 一致 |
| 目标流元数据 | `h264 (High) / yuv420p(progressive) / 800×600 / 30 fps` | ✅ 与设计一致 |
| **花屏** | 前后视各抓 3 帧 PNG 人眼检查（见 `note/evidence-20261014/`） | ✅ **无绿紫条纹、无错位、无宏块**（I420 强制修复持续有效） |
| **PTS/DTS 单调性** | 源 RTSP 与出流 RTMP 均 **0% 非递增、0% 相等、0% 倒退**（各 246/232 帧采样） | ✅ 健康 |
| 帧间隔步进 | 源 90000 Hz 下 2881–2885 与 3234–3241 tick 交替 = **32.0 ms / 36.0 ms 混杂，均值 33.37 ms (29.97 fps)** | ⚠️ **±6% 抖动**（R26），来自相机侧，非中继 |

> **更正**：日志/命令输出中出现的 `Application provided invalid, non monotonically increasing dts to muxer` **不是链路缺陷**——对照实验显示，同一 RTMP 输入用 `-r 30`、`-vsync 0` 或默认参数输出到 `null` 均为 **0 条告警**，而 RTSP 输入默认输出有 16 条/12s；ffprobe 逐帧核对源与出流 DTS **完全单调**。该告警源于 ffmpeg **输出端 image2/null 的时基换算**，属测量工具假阳性。

### 7.2 延迟：稳态附加 ≈80 ms，观众端首帧 5.7 s 可优化到 1.7 s

**（1）链路稳态附加时延 ≈ 80 ms**

| 采样点 | 帧序号 | A（本地 RTSP）落盘 | B（远端 RTMP）落盘 | 同帧到达差 |
|---|---|---|---|---|
| 加入初期 | #1 | 00:51:46.242 | 00:51:50.125 | **+3.883 s** |
| 加入初期 | #2 | 00:51:46.252 | 00:51:50.135 | +3.883 s |
| 稳定末期 | #1171 | 00:52:24.616 | 00:52:24.699 | **+0.083 s** |
| 稳定末期 | #1173 | 00:52:24.622 | 00:52:24.699 | **+0.077 s** |

- 初期的 3.883 s **不是链路时延**，而是 B 端 ffmpeg 的输入探测缓冲：B 在第 1–100 帧只用 **657 ms**（152 fps）就把积压吐完，第 101–201 帧用 1580 ms，随后与 A 完全同速 → **积压被高速排空后收敛**。
- 收敛后同帧到达差 **0.077–0.083 s**，即**整条中继链路的稳态附加时延 ≈ 80 ms**，量级与 `rtspsrc latency=100`（100 ms 抖动缓冲）严格吻合。基线 A（本机 MediaMTX 直读）在 12 s 内正点送达 336 帧、lead 仅 0.42 s，说明本机段本身几乎零缓冲。
- **可优化项（R28）**：`latency=100` 占绝对大头，链路质量实测良好（见 7.3）时可试 `latency=50`，省 50–70 ms。**务必保持 `drop-on-latency` 关闭**（R3 的雪崩教训）。

> ⚠️ **方法学校准与结论修正（2026-10-14 03:25，重要）**
>
> 上述「≈80 ms」是**单点采样**，后续用**三路并发读数**做了校准才发现问题：
>
> | 测量 | 配置 | 结果 |
> |---|---|---|
> | 点采样（末帧） | latency=100 | 0.077 s |
> | 200 帧均值 | latency=50 | 0.104 s |
> | 1305 帧均值 | latency=50 | **0.322 s** |
> | **方法噪声底**（A2−A，两路同读本机 RTSP） | — | **0.018 s** |
>
> 噪声底仅 18 ms，但三次真实测量散布 77–322 ms → **该差值被读取端（ffmpeg）自身的探测/缓冲状态主导**，不能作为链路稳态时延的精确值。已修正结论：
>
> - **RTMP 中继链路的稳态附加时延量级为 0.1–0.3 s**（上界含读取端残余缓冲），**不能精确到十毫秒级**。
> - 因此 **R28（latency 100→50）预期省下的 50–70 ms 落在这套方法的噪声带内，"已实施但收益不可测"**。该改动本身无害（TCP interleaved + 实测 0% 丢包 + 变更后零丢帧、零新增告警），保留即可；若日后日志出现 `rtspsrc` 读失败，把 `LATENCY` 调回 100。
> - **要拿到可信的绝对时延**，需换方法：① 相机侧放时钟/秒表入画，与回拉抓帧比对（最可靠）；② 在 SRS 侧对同一帧的收包时间打点；③ 在 196 上用 tcpdump 同时抓 loopback 的 RTSP 与 WAN 的 RTMP，按 H.264 访问单元载荷匹配（可精确分离中继自身耗时）。

### 7.13 事故复盘：「服务已启动但服务器看不到流」（2026-10-15，R19 的实锤）

**现象**：196 上 `m20video up` 提示「m20video 已启动」，但 SRS 后台无流。

**结论：中继无锅，是上游相机没有发布到 MediaMTX。** 中继的行为完全正确——它按 `CHECK_SOURCE=true` 探测源流 HLS，拿到 **404** 后**拒绝启动 `rtmp-gst`** 并在重试循环里等待（`forward-f.log` 的 attempt 编号已累计到 205+）。「已启动」只代表监督进程起来了。

**根因（假死管道）**：相机 `gst-launch` 进程存活、持有 `/dev/video0|video2` 与 `/dev/mpp_service`，但 `mpph264enc` **每帧报错、从不向 `rtspclientsink` 交付数据** → sink 从未 ANNOUNCE → MediaMTX 报 `no one is publishing to path 'video1'`。

**决定性证据**：
| 观测 | 结果 | 含义 |
|---|---|---|
| `tcpdump -i lo 'tcp port 8554'` | 8 s 内 **1 个包、0 载荷** | 相机一个字节都没往 8554 发 |
| socket 状态 | `Send-Q=0`、`cwnd=10` | 连接建立但空闲 |
| `strace -p <相机pid> -e trace=sendto -yy` | 362 次 `sendto`/6 s，**全部写 `/dev/log`** | CPU 全烧在刷日志 |
| 日志内容 | `<11> mpp[pid]: mpp_frame: mpp_frame_deinit invalid NULL pointer input`，开机以来 **9516 条**（≈60 条/s） | 硬编每帧走错误路径 |

**恢复手法（已实测）**：`sudo bash /opt/robot/scripts/board_resources/rtsp_service/stop.sh` → 重启 `push_video.sh`。恢复后 `video1/video2` HLS 双双 **200**，**中继自动接管**（源探测成功后自行起 `rtmp-gst`），目标流 `m20pro-f/b` 回拉成功（h264/800×600/30fps）。
⚠️ `stop.sh` 的 `pkill -f v4l2/push_video` **必须 root 执行**；以 `user` 跑会报 `Operation not permitted` 并**静默失败**（本次踩到）。且排查时避免让**自己的命令行**含 `v4l2`/`push_video` 字样，否则可能被 `pkill -f` 连坐。

**两条被推翻的假设（留作教训）**：
1. **时钟不是原因**。用户质疑正确：2026-10-14 实测时时钟同样错 846 天，推流完好（1173 帧逐帧 MD5 一致）。时钟是**独立的另一个问题**（见 §7.14）。
2. **`CmaFree: 0 kB` 不是原因**。曾怀疑 256 MB CMA 耗尽导致硬编无法分配缓冲；**决定性反证**：用 root 杀掉两个编码器后 `CmaFree` 仍为 **0** → 这是 RK3588 的正常状态（CMA 页被页分配器当**可迁移页**占用，驱动申请时按需回收），**不可作为判据**。

**这一事故把 R19 从"理论风险"变成"已实际造成中断"**，并暴露了 R19 的**精确形态**：`push_video.sh` 的监控只判「**进程是否活着**」，不判「**是否真的在发布**」——所以管道卡死在"活着但不出数据"时它不会救。
🔧 **建议的 R19 修复**：给 `push_video.sh` 的监控循环加**存活判据**——`/dev/videoN` 被 gst 持有、但 `http://127.0.0.1:8888/videoN/index.m3u8` 连续 N 次非 200 → 杀掉该路管道并重启。
🔧 **另一个易用性缺陷**：`m20video up` 应改为**校验"源健康 + 目标可推"后才报成功**，现在报「已启动」但实际未推流，误导性很强。

**干扰源排查（用户提出：会不会是 AOS 的 m20monitor / GOS 的 aiDetect 影响）——逐条取证，结论：不是。**

| 嫌疑 | 证据 | 结论 |
|---|---|---|
| `m20-ai-detect`（GOS 104） | `is-active` = **inactive**（根本没跑）；到 AOS `10.21.31.103:8554` 的 RTSP 连接 **0** | **完全排除**（且它在另一台机器，物理上无法争用 AOS 的 MPP 硬编） |
| `m20pro-console`（AOS，m20monitor） | 视频代理源码 `backend/video/video_proxy.py` 明确用 **`-c:v copy`（纯转封装、不解码）** → **不打开 `/dev/mpp_service`**；作为**读者**也无法把发布者踢下线 | 排除争用与抢推 |

**顺带取到的开机时序与健康证据（更有价值）**：
- 时序（uptime 基准）：`mediamtx` **+13.1 s**（很早，竞态窗口其实不大）；原始相机管道约 **+60~90 s**——因为 `start_server.sh` 内置的**时间同步门禁**（`is_time_synced()` 检查 `date +%Y >= PTP_MIN_YEAR(2025)`）在年份为 2024 时判定失败，**等满 `PTP_SYNC_TIMEOUT=60s` 超时才继续**。该门禁本就是为时钟问题加的。

### 7.14 独立问题：系统时钟在 ±846 天之间来回跳（2026-10-15 查明，未修复）

**成因（本平台已知 ADR-004 的升级版）**：`ptp_manage.service` 运行 `ptp4l -f /var/run/ptp/ptp4l_eth0.conf -i eth0 -m -q -s` 与 **`phc2sys -s eth0 -w -z /var/run/ptp/ptp4l_eth0 -S 10.0 -m -q -l 6`**。`-s eth0` 表示 phc2sys 把**系统时钟**同步到 eth0 的 PTP 时钟；车队主时钟（机器人控制器）报 **2024-06-21**。chrony（NTP 源正确 = 2026-10-15）反复步进回去，形成**拉锯**。

### 7.16 残余缺口补齐：假死管道自愈守护（2026-10-16 落地）

**缺口**：能「自启」，但不能「自愈」。`start.service` 是 `Restart=no`；`push_video.sh::_is_stream_alive()` 只看**进程在不在**（`kill -0` + cmdline 含 `gst-launch`），不看**是否真的在发布** → §7.13 那种僵尸管道一旦发生无人救援。

**动手前先把「杀了能不能重生」这条安全网钉死**（否则守护会把活流变成死流）：

| 核实项 | 结论 |
|---|---|
| `push_video.sh` 外层结构 | `while true` → 等设备 → 起管道 → 内层 `while _is_stream_alive` → 退出后 `_kill_gst` + 退避 → **回到外层重建** ✅ |
| `MAX_RETRY` | **= 0（无限重试）** → 不会因反复触发而永久停推 ✅ |
| `STABLE_THRESHOLD` × `HEALTH_CHECK_INTERVAL` | 5 × 3 s = 稳定 15 s 后 `retry_count` 清零 → 计数不累积 ✅ |
| `RETRY_BASE_DELAY` / `RETRY_MAX_DELAY` | 2 s / 30 s 指数退避 → 单次恢复窗口约 **5~10 s** ✅ |

**落地物（不修改任何厂商文件）**

| 文件 | 说明 |
|---|---|
| `/usr/local/sbin/camera-liveness-guard.sh` | 守护本体；`--dry-run` 只报告不动作 |
| `/etc/systemd/system/cam-guard.service` | `Type=oneshot`，`After=network.target start.service` |
| `/etc/systemd/system/cam-guard.timer` | `OnBootSec=3min`、`OnUnitActiveSec=60s`、`AccuracySec=5s` |
| 状态 / 日志 | `/var/lib/cam-guard/<path>.fails`、`/var/log/cam-guard.log` |

**判定逻辑（保守，防误杀）**：① mediamtx 必须在 `:8554` 监听（否则源全断是中继侧问题，杀相机无意义）→ ② 管道已过 `GRACE_SEC=90` 宽限期 → ③ 该管道 cmdline 解析出的发布路径，其 HLS **连续 `FAIL_THRESHOLD=3` 次非 200** → 才 `TERM`（5 s 不退则 `KILL`）。杀掉后由 `push_video.sh` 自行重建。

**验证记录**

1. `--dry-run` 实跑：两路 HLS 均 200，计数清零，**无任何动作**。
2. `systemctl enable --now cam-guard.timer` → `enabled / active`，首次触发 +57 s、之后每 60 s。
3. 真实模式执行 2 次均 `Succeeded`、`ExecMainStatus=0`，两路仍 `200`。
4. **检测链路验证（不伤真机）**：把探测目标指向死端口 `HLS_BASE=http://127.0.0.1:9999`、`STATE_DIR` 指向临时目录后跑 dry-run → 正确解析 `pid=2069 path=video1`、`pid=2072 path=video2`、`运行 6523s`、`HLS=000`，走到「本应杀掉」分支 ✅；真实计数文件确认未被污染（仍为 0）。

**回滚**：`sudo systemctl disable --now cam-guard.timer && sudo rm -f /etc/systemd/system/cam-guard.{service,timer} /usr/local/sbin/camera-liveness-guard.sh && sudo systemctl daemon-reload`

**已知边界**：本守护只负责「杀掉假死管道」，**不负责**在 `push_video.sh` 整体挂掉时重新拉起它（一路 `gst-launch` 都没有时只写 WARN 日志）——那属 R19 上游守护范畴。若相机存在持续性硬件故障，守护会每 3 分钟造成一次约 10 s 的重建窗口（比永久僵尸不再出流要好，但需知道这个行为）。

### 7.17 双链路故障诊断 + 连接健康看门狗（2026-10-16 04:00–05:00，落地）

> 用户诉求："lite3 和 m20 的 rtmp 推流是不是都停了"。**诊断结论：M20 真停、Lite3 假死（僵尸连接）。** 本轮把两机的自愈能力补成"两层"。

**诊断过程与两处认知纠正**

1. **拓扑纠正（用户提醒）**：Lite3 推流**不在 103**，而在 **120**（`rtsp_stream.service`，`enabled`+`active`）。103 是 Jetson 感知导航主机，**无中继、无推流**。此前误看 103 得出"Lite3 没在跑"是错的。
2. **"假死"不是"停"**：Lite3 进程存活但 TCP 卡死——`ss -tni` 显示 `cwnd:1`、`Send-Q` 冻结（实测 3.5MB）、`retrans` 累加。因为进程没退出，**exit-3 重启逻辑根本不触发**。判定标准 = `cwnd`/`retrans` 异常，不是只看 Send-Q 或端口在不在。
3. **MASQUERADE 假设被证伪**：用户怀疑 120 "忘记" `sudo iptables -t nat -A POSTROUTING -s 192.168.1.0/24 -o wlan0 -j MASQUERADE`。实测规则**存在且命中**（`pkts=202`）；而 120 自身的 RTMP 源地址是 `192.168.0.197`，走的不是 `192.168.1.0/24` 这条规则 → 与推流失败无关。

**根因（两机同构）**：都经 **WiFi 上行到 Tenda**，链路间歇丢包 → 上游 `172.31.68.227:1936` 反复 TCP 卡死/探测失败。

- M20 中继在"**连接前**探测失败"时以 **exit 3** 退出；但旧 drop-in `RestartPreventExitStatus=3` **反而不让 systemd 重启** → 永久躺平。实证（`forward-b.log`）：`看门狗: 目标发送队列积压 1411205B (1/2)` → `收到退出信号，正在关闭推流...已停止`，`active-exited` code 3。
- 04:41 复发：手动重启后约 **6 分钟**再次掉线（WiFi 抖动持续）。

**两层次自愈（双机均落地：196 的 `m20video` / 120 的 `rtsp_stream`）**

| 层 | 修复 | 解决的盲点 |
|---|---|---|
| (a) drop-in | `/etc/systemd/system/{m20video,rtsp_stream}.service.d/restart-prevent.conf` 去掉 `RestartPreventExitStatus=3`（及 `SuccessExitStatus=3`），改为 **`RestartSec=30`** | **exit-3 瞬时失败** → 30s 退避自动重启；上游真宕机时也只每 30s 重试一次，不空转忙等 |
| (b) 看门狗 | 新增 `rtmp-conn-guard`（见下） | **僵尸连接**：进程存活但 TCP 卡死，不触发 exit 3，原逻辑完全看不见 |

**落地物（看门狗，双机一致；补丁源在 `patch/`）**

| 文件 | 说明 |
|---|---|
| `/usr/local/sbin/rtmp-conn-guard.sh` | 看门狗本体；自动识别本机中继（`m20video` 优先，其次 `rtsp_stream`）；读 `ss -tni` 判僵尸；`--` 后两参数可覆盖 `SERVICE` / `UPSTREAM` |
| `/etc/systemd/system/rtmp-conn-guard.service` | `Type=oneshot`，`ExecStart=/usr/local/sbin/rtmp-conn-guard.sh` |
| `/etc/systemd/system/rtmp-conn-guard.timer` | `OnBootSec=60s`、`OnUnitActiveSec=30s`、`AccuracySec=5s`、`WantedBy=timers.target` |

**判定逻辑**：服务 `active` 时读 `:1936` 的 ESTAB，满足**任一**且**连续 `BAD_LIMIT=3` 次采样（≈90s）** → `systemctl restart` + 进入 `COOLDOWN=300s` 冷却（避免抖动期空转）：

- `cwnd <= CWND_ZOMBIE(3)` **且** `Send-Q > SENDQ_MIN(64KB)`（窗口塌缩 + 数据积压）
- `retrans >= RETRANS_MAX(20)`（持续重传失败）
- 服务 active 但已**无任何**到上游的 ESTAB（链路彻底丢失）

> 参数均可环境变量覆盖（`CWND_ZOMBIE` / `SENDQ_MIN` / `RETRANS_MAX` / `BAD_LIMIT` / `COOLDOWN`）；状态文件在 `/var/lib/rtmp-conn-guard/`，日志在 `/var/log/rtmp-conn-guard.log`（前缀 `[conn-guard]`）。

**部署与验证**：双机 `systemctl enable --now rtmp-conn-guard.timer` → `enabled/active`。实测当前链路降级时段正确报 `suspicious ... bad 1/3 → 2/3`，**不误杀**（连续计数、非一击即杀，抖动期不会空转重启）。

**残余根因（软件救不了）**：WiFi 链路丢包是**硬件/部署层**问题。看门狗能在链路恢复后清掉僵尸，但链路差时重启也只是新建一条立即再卡死的连接。根治仍回到 **R10 / R32**：能上有线则有线，否则增强信号（当前 M20 -68 dBm 偏弱）。

**回滚**

```bash

sudo systemctl disable --now rtmp-conn-guard.timer
sudo rm -f /etc/systemd/system/rtmp-conn-guard.{service,timer} /usr/local/sbin/rtmp-conn-guard.sh
sudo systemctl daemon-reload

# drop-in（恢复"上游长期不可用则停推"语义）

```
