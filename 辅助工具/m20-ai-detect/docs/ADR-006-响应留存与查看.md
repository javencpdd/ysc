# ADR-006：响应留存与查看（SAVE_MODE / saved/ / 响应查看器）

- 状态：已采纳（2026-10-15）
- 相关：ADR-001（部署位）、ADR-004（时钟偏移）、ADR-005（可视化控制台）

## 背景

0.3.x 的行为面：每帧的 AI 响应看完即丢——JSONL 只留归一化字段（`n_items/items/alert`），
`result_image`（base64，占响应体积 ~94%）默认丢弃，旧开关 `M20AI_SAVE_RESULT_IMAGE=true`
仅在命中告警时落一张图到 `alerts/`，**原始响应本身从不落盘**。

使用者提出两个连带需求：

1. **看到响应**：控制台上要能看"接口实际返回了什么"，解析后显示检出了什么 / 是否检出；
2. **条件留存**：响应满足某种条件时，同时保存**处理后的图**和**处理后的响应**。

控制台（ADR-005）已具备单帧检测与配置编辑能力，是本需求自然的落点；但"看历史帧的响应"
需要数据支撑——不留存就没有回放，仅靠重新检测又受 raw/ 环形缓冲（200 MB，约几小时）限制。

## 决策

### 1. 一个四值旋钮 `M20AI_SAVE_MODE`，默认 `off`

| 值 | 触发条件 | 磁盘量级（1 fps） |
|---|---|---|
| `off`（默认） | — | 0（行为与 0.3.x 完全一致） |
| `alert` | 命中告警规则（`ALERT_LABELS` + `ALERT_SCORE`） | 通常 KB 级/天 |
| `any` | 检出任意目标（`n_items > 0`） | ≈ 20 MB/天（视检出率） |
| `all` | 每帧 | ≈ 100 MB/天 |

- **条件即配额**：`saved/` 不设自动清理——选什么条件，就等于选了什么磁盘增速；
  需要更细的控制（按标签分条件、saved/ 也做环形配额）是后续演进，触发判断已收敛在
  `Sampler._should_save()` 单点，加值只动 config + 这一处。
- **兼容**：未显式设 `SAVE_MODE` 时，旧开关 `SAVE_RESULT_IMAGE=true` 映射为 `alert`；
  显式设了以 `SAVE_MODE` 为准。旧目录 `alerts/` 废弃（新逻辑统一走 `saved/`），
  因线上该目录实际为空（`result_image_saved` 全程 false），无迁移成本。

### 2. 成对留存：`saved/<cam>/<帧名>.jpg` + 同名 `.json`

- `.jpg`：AI 返回的标注结果图（base64 解码后直接落盘，~120 KB）；
- `.json`：**原始响应剥掉 `result_image` 大字段**，替换为两个备注——
  `_result_image`（指向同名 jpg 的相对路径）与 `_result_image_bytes`（原字段长度），
  文件 ~2 KB，可直接阅读/diff；
- JSONL 记录同步写 `result_image_saved/saved_image/resp_path`（`v=2` 兼容加字段）；
- 单侧失败只记日志不抛：留存是增强，不该打断采集主循环。

**为什么不原样保留 base64**：每个 json 会涨到 ~500 KB，`all` 模式一天就是 40+ GB，
且 JSON 里嵌 data URL 对阅读和 diff 都不友好。图另存 + JSON 留引用保留了全部信息。

### 3. 响应查看器：已留存直读 + 未留存可重新检测

控制台 `GET /api/response?frame=&cam=&redetect=1`：

1. `saved/<cam>/<stem>.json` 存在 → 直读（`source=saved`），图从 `_result_image` 引用取；
2. 不存在且 `redetect=1` → 读 `raw/<cam>/<frame>` 原帧，**实时重调一次 AI 服务**
   （`source=redetect`，约 0.25 s，一次真实公网 API 调用，页面上有明确标注）；
3. 都没有 → 404 + 可操作提示（原帧可能已被环形缓冲覆盖）。

「最近检测」卡从"展示日志行"改为"展示今日 JSONL 尾部真实记录"（时间/检出概要/告警徽标/
已留存徽标），点任一帧出详情面板：帧信息 + 解析摘要 + 原始响应 JSON + 结果图 + 重新检测按钮。
单帧检测卡同时恒返 `raw_response` 并可勾选"保存这一帧"（落 `saved/console/`，同格式）。

## 后果

- **默认零行为变化**：`SAVE_MODE=off` 时采集/存储/磁盘与 0.3.x 一致，升级无感；
- 采集主循环仅在条件命中时多做两次写盘（jpg + json），不碰网络路径；
- 控制台 API 从 7 个路线增至 9 个（新增 `/api/recent`、`/api/response`），
  `POST /api/detect` 增加 `save=1`；前端"最近检测"语义变更（日志行 → 真实记录）；
- `saved/` 无自动清理，`all` 模式需使用者自行关注磁盘（页面留存策略卡有量级提示）；
- "重新检测"是**实时调用**，结果与历史帧当时的响应不保证一致（模型/参数可能已变），
  页面上以 `source` 字段区分两种来源。

## 复审条件

- `saved/` 出现无人清理的 GB 级堆积 → 补环形配额或按天数清理（复用 `prune_results` 模式）；
- 四值条件不够用（如"person 才存、chair 不存"）→ 细化触发条件，收敛在 `_should_save()`；
- raw/ 环形缓冲覆盖导致历史帧无法重查的投诉变多 → 评估默认 `SAVE_MODE=any`。
