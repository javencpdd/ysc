# ADR-002: 运行时与依赖策略 —— 零第三方依赖

- 日期：2026-10-15
- 状态：已接受
- 影响面：`pyproject.toml`（`dependencies = []`）、`tests/`（unittest 而非 pytest）、`Makefile`（无 venv 目标）、`deploy/bootstrap.sh`（只查 ffmpeg/python3）

## 背景

采样器需要：HTTP multipart 上传、JSONL 落盘、ffmpeg 子进程管理、JSON 解析、重试与环形缓冲。按常规做法会引入 `requests` + `pytest`，在 GOS（Ubuntu 20.04、离线 apt 源状态未知）上需要 venv/pip，多出：

- 一个可能失效的虚拟环境；
- pip 装包时的公网依赖（GOS 出公网本身就依赖 AOS NAT，是待验证前提）；
- 版本漂移（`requests` 版本差异导致 multipart 边界行为变化）。

## 决策

**只使用 Python 标准库，`dependencies = []` 刻意留空。**

| 需求 | 常规做法 | 本工程做法 | 代码位置 |
|---|---|---|---|
| multipart 上传 | `requests` | 手工构造 boundary + body | `detect.py: encode_multipart()` |
| 测试 | `pytest` | `unittest`（`discover`） | `tests/` |
| HTTP 客户端 | `requests`/`httpx` | `urllib.request` | `detect.py: Detector` |
| 进程管理 | `psutil` | `subprocess` + 文件 mtime 判活 | `capture.py`, `cli.py` |
| 配置 | `pydantic`/`dynaconf` | `dataclass` + `os.environ` | `config.py` |

代价：`encode_multipart` 约 40 行手写代码（已由 `test_detect.py` 覆盖结构与边界行为）；无 fixture 语法糖，测试略冗长。

## 依据

- 部署目标机 Python 3.8（Ubuntu 20.04 自带），`dataclasses`/`typing`/`unittest` 均可用；`pyproject.toml` 声明 `requires-python >= 3.8`。
- 集成测试 `test_integration.py` 用标准库 `ThreadingHTTPServer` 起假 AI 服务，验证了真实 HTTP + multipart + JSONL 全链路，41 项测试连续多轮全绿，证明标准库路径可用。
- GOS 的 pip/apt 公网可达性未验证（依赖 AOS NAT），任何第三方依赖都是未验证前提上的额外风险。

## 后果

### 正面

- 部署 = `rsync` + `python3 -m m20_ai_detect run`，无构建、无 venv、无 lockfile。
- 主机上 `python3` 升级不影响本工程（只用 3.6+ 稳定 API）。
- 开发机（Windows）与目标机（Linux）跑同一套测试，行为一致。

### 负面 / 代价

- 手写 multipart 是"重新发明轮子"，未来若要支持大文件分片/断点续传，建议届时引入成熟库并修订本 ADR。
- 无 pytest 的参数化与插件生态，测试代码量略大。

### 触发复审的条件

1. 需求超出标准库舒适区（如异步并发抽帧 `asyncio`+`aiohttp`、gRPC 推流）。
2. GOS 确认可稳定访问 PyPI 或已建内网 apt/pip 镜像。
3. 团队引入统一的第三方依赖基线（如公司内网 wheelhouse）。
