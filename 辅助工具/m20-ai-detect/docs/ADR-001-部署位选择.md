# ADR-001: 部署位选择 —— GOS（10.21.31.104）/home/djw

- 日期：2026-10-15
- 状态：已接受
- 影响面：`deploy/m20-ai-detect.service`、`deploy/m20-ai-detect.env.example`、`Makefile`（HOST/REMOTE_DIR 默认值）、`src/m20_ai_detect/config.py` 默认值

## 背景

M20 Pro 视频流 + 外部 AI 识别（`http://jsxy.aihyzh.com:30881`）的采样与落库程序需要一个运行位置。候选：

| 方案 | 位置 | 可达相机流 | 可出公网 | 对机器人影响 |
|---|---|---|---|---|
| E | AOS 196 | 本机 127.0.0.1 | 是 | 与运控/感知/视频抢 3 个小核（load 已 0.88） |
| N | NOS 106 | 内网 RTSP | 经 AOS NAT | 感知负载低（0.12），但属感知主机 |
| **F** | **GOS 104** | **内网 RTSP** | **经 AOS NAT** | **负载 0.21、可用内存 13.9G、厂商定位即"开发+对外服务"** |
| S | SRS 汇聚点 172.31.68.227 | 本机 SRS 已在收三路 | 是 | 需申请账号（未获批；**2026-10-15 降级为远期备选，见文末修订记录**） |
| G | 运维笔记本 | 经局域网 | 是 | 一次性验证可行，长期不可靠 |

约束条件：

1. **抽帧必须常驻**：ffmpeg 冷启动抓 1 帧实测 1.6–2.0 s（RTSP 握手），不能每次检测起一次进程。
2. **AI 服务拉不到内网流**：只能由内网侧主动上行帧，采样器必须在能访问 `10.21.31.x` 与公网的位置。
3. **不得干扰在跑业务**：AOS 同时运行 `rl_deploy`/`basic_server`/`hsLidar`/`rslidar`/`lio_ddsnode`/`height_map_nav`/`yesense_node`，且普通进程被 `isolcpus` 压到 3 个小核。
4. 代码与部署位解耦（只改 `M20AI_SRC_*` 环境变量），换位不需要改代码。

## 决策

- **部署在 GOS 10.21.31.104 的 `/home/djw/m20-ai-detect`，以 systemd 用户态服务 `m20-ai-detect.service` 常驻。**
- 账户事实（2026-10-15 上机核实）：**GOS 无 `djw` 系统账户**（`id djw` → no such user），唯一可用登录账户是 `user`（uid 1003，属 sudo 组）；`/home/djw` 是 root 所有的目录，已设 ACL `user:user:rwx`（含 default ACL，新文件自动继承）。故 unit 以 `User=user` 运行，工作空间路径维持用户决策的 `/home/djw` 不变。
- `CPUAffinity=0-3`：GOS `isolcpus=4,5,6,7` 把 4 个 A76 大核隔离给厂商关键任务，普通进程本就只能用 4 个 A55 小核，显式绑定避免调度器意外试探大核引发争抢。
- 存储落在 GOS 本地（`spool/raw/results/alerts`），机器人侧零写入。

## 依据

- 2026-10-14 实测：GOS 上 `curl rtsp://10.21.31.103:8554/video1` 返回 200，内网 ping 0.46 ms、0 丢包；NOS 实测同样可达（同网段）。
- 2026-10-14 晚已打通 AOS NAT（`POSTROUTING -s 10.21.31.0/24 -o p2p0 -j MASQUERADE` + FORWARD 放行，`netfilter-persistent` 持久化）。**2026-10-15 门禁实测推翻"已具备出公网条件"的假设**：GOS 默认网关 10.21.31.99 ARP 无应答（二层即死），且 AOS FORWARD 未放行 `eth2→p2p0` 的 NEW 连接，GOS 实际零出口。修复方案与命令见 **ADR-003**。
- 2026-10-14 负载实测：GOS load 0.21 / 可用内存 13.9G；AOS load 0.88。
- 厂商三主机分工口径：GOS = "开发 + 对外服务"，与"拉公网 AI 服务 + 落库"的用途一致。

## 后果

### 正面

- 机器人三主机算力零占用；GOS 挂了不影响机器人任何功能（`Wants=network-online.target`，不依赖机器人服务）。
- 与视频源（AOS MediaMTX）内网直达，延迟与带宽都不是瓶颈（2 Mbps 流只抽 1 fps）。
- 开发、测试、生产同机同目录，`install.sh` 一条命令闭环。

### 负面 / 代价

- **依赖 AOS NAT/FORWARD 规则持续有效**：AOS 重刷/重置 iptables 后 GOS 失去公网出口，AI 调用全失败。缓解：`doctor` 的 `ai_health` 项会 FAIL；持久化已做（`/etc/iptables/rules.v4`）。另需 GOS 默认路由经 AOS（见 ADR-003）。
- **依赖 AOS MediaMTX 持续推流**：相机服务重启期间无帧，采样器写 `source_down` 心跳而非崩溃。
- **`/home/djw` 是 root 所有目录**（非任何用户家目录）：靠 ACL 授权 `user` 读写。若厂商重建该目录丢掉 ACL，或清理 `/home/djw`，工作空间需迁到 `/home/user/m20-ai-detect`（改 env + unit 的 `ReadWritePaths` 两处）。
- eMMC 128G 与系统共用分区，`raw/` 环形缓冲 200 MB 上限 + 结果图默认丢弃，长期需盯 `stats`。

### 触发复审的条件

1. GOS 被厂商征用或 `/home/djw` 被清理 → 改投 NOS 106 或 227。
2. SRS 汇聚点（172.31.68.227）账号获批**且**满足下文"方案 S 重启评估条件"→ 才评估迁往方案 S；单纯账号获批不构成迁移理由。
3. AI 服务增加鉴权或迁到内网 → 采样器可能反向部署到 AOS 内网侧。
4. GOS 负载长期 > 1.0 或磁盘余量 < 5 GB。

## 决策修订记录

### 2026-10-15：方案 S（227 汇聚点）降级为远期备选

ADR-001 初版把"账号获批后评估迁 227"列为复审条件。方案落地后重新评估（用户质疑"为什么不直接本地推流并获取接口响应"），结论：**对"AI 检测"这个目标，227 没有增量价值，降级为远期备选**。依据：

1. **AI 服务拉不到内网流**是硬约束——检测必须跑在"内网 RTSP + 公网 AI"双通位置。GOS 双通已实测（200/52ms）；227 在 172.31.x 网段，能否出公网到 AI 服务未验证，账号也未申请。
2. **227 的流是中继转码后的 rtmp（2014kbps）**，相对 AOS 原始 RTSP（800×600 H.264）多一跳有损转码，时延与画质双输。
3. **227 的价值在"汇聚"不在"检测"**：它服务多机器人视频对账、跨网观看、统一存储，与单机抽帧检测是两个目标；让检测绕道 227 是用检测的可靠性换一个自己不需要的能力。
4. **数据主权**：JSONL 落 GOS 本地自主可控；迁 227 意味着检测数据落第三方节点。

**重启评估方案 S 的触发条件（满足其一即建 ADR 评估）**：

- 多机器人统一检测：一个采样器同时看 m20pro + lite3 三路以上，集中算力摊薄成本；
- 跨源对账：检测结果需与汇聚视频逐帧对齐取证；
- 异地灾备：GOS 故障时需要第二检测位接力；
- 外部消费：非机器人内网的系统要直接消费检测结果。
