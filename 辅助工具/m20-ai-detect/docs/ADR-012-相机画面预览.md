# ADR-012: 相机画面预览（控制台「相机画面」卡）

- 日期：2026-10-16
- 状态：已实施，真机验证通过（2026-10-16）
- 关联：ADR-005（控制台）、ADR-006（响应留存）、ADR-008（时间轴）、ADR-009（只读浏览）、ADR-011（关注目标与数据清空）

## 背景

用户在看控制台「采集开关 / 最近检测」区域时提出：

> "这个部分能不能加一个目前的开放的相机画面信息（rtsp 流？）"

即：不离开控制台就能看到**相机现在拍到的画面**——看"检出 7 个目标"时画面里到底是什么、AI 是不是在看它该看的东西。

两个约束决定了不能简单"嵌个 RTSP 播放器"：

1. **浏览器不能直接播放 RTSP**（原生只支持 HLS；Windows 浏览器连 HLS 也不原生支持，引 hls.js 会打破控制台"零依赖单页"的现状）；
2. **视频流在 AOS 196、控制台在 GOS 104**——跨主机嵌流会把 5050 页面的可用性绑定到另一台机器（浏览器到 196 的连通性、WebRTC/HLS 依赖），且与"检测器实际看到的画面"未必同源。

因此选择**服务端单帧快照**：控制台后端直接给"当前画面"一张 JPEG，前端当作图片刷新——最贴近"我就想看一眼"的需求，且完全复用现有链路。

## 决策

### 1. `GET /api/snapshot?cam=<name>`：单帧快照，三级来源

| 优先级 | 来源 | 条件 | 特征 |
|---|---|---|---|
| 1 | `ring` | `raw/<cam>/` 有不超过 `max(5s, 4/fps)` 的帧 | **采样器运行中即此处**：零额外开销，且正是**检测器刚处理过的画面** |
| 2 | `live` | 环形帧过期/缺失 | `ffmpeg` 单次抓帧（同一路 RTSP）：**采集未运行也能看实时** |
| 3 | `stale` | 抓帧失败 | 兜底返回环形缓冲最近一帧，`age_s` 如实标注，UI 显示"已定格 N 前" |

- 返回 JSON：`{ok, cam, src, source, age_s, frame, image(base64 JPEG)}`；
- 错误分流：配置类问题（未知相机/未启用相机）→ **400**（附 `bad_request`），抓帧失败 → **502**；
  本模块不向上抛异常——**一张图抓不到不允许影响控制台其它功能**。

### 2. 抓拍命令行：与常驻抽帧共用协议参数，但"抓完即退"

- `capture.build_snapshot_cmd()` 与常驻抽帧共用 `_input_args()`（RTSP 强制 TCP / RTMP 声明 flv / mjpeg 声明封装）与 `FORBIDDEN_TOKENS` 安全自检；
- 不落盘：`-frames:v 1 -q:v <jpeg_q> -f image2pipe -vcodec mjpeg pipe:1`；
- 单次 RTSP 握手实测 1.6~2.0 s（2026-10-14 AOS），故：**8 s 抓帧超时 + 短缓存**（成功 1.5 s、失败 3 s），模块级锁串行化，防多客户端连击拉起一堆 ffmpeg。

### 3. 前端「相机画面」卡：3 秒自动刷新、页签隐藏暂停

- 位置：首行「采集开关 | 最近检测」之后的全宽卡（与检测监控同一屏区）；
- 徽章四态：`实时`（ring）/ `即时抓帧`（live）/ `已定格`（stale，附 age）/ `抓帧失败`（err）；
- 多相机出现下拉切换（列表取自 `/api/config` 的启用相机）；`SNAP_BUSY` 防重入；
- `document.hidden` 时暂停自动刷新（不浪费带宽），手动按钮始终可用。

## 修过的一个坑（真机验证时发现）

抓帧缓存的时间戳第一版记在**抓帧开始前**——而单次 RTSP 握手本身要 ~4 s，等于每次请求都白扣 4 s 的 TTL：
真机连续两次 `_cached_grab` 实测第二次仍耗时 5.3 s（又抓了一遍）。改为**抓帧完成时刻**计时后，
第二次 0.0000 s 命中（同帧 64537 字节）。已用可注入时钟的单测固化该语义。

## 验证（GOS 104 真机，2026-10-16）

——采集正处于运行中（用户在用），全程未触碰采样器。

- **ring（采集运行中）**：`GET /api/snapshot?cam=front` → `ok=true, source=ring, age_s=1.5`，

## 修订记录 2026-10-17：`stale` 态升级为「⚠ 视频源不可达」醒目提醒（v0.7.1）

**起因（真实事故）**：2026-10-17 00:23 整机重启后，USB 相机约 00:34 从总线掉线
（`ls /dev/video*` 为空、push_video 日志"等待USB设备上线"、mediamtx 空转导致 video1/video2
无发布者、RTSP DESCRIBE 404）。快照按设计兜底返回 20 小时前的旧帧，但 UI 只标了琥珀色小字
"已定格"——**用户把定格旧帧误读为"画面卡住"**，且第一反应是怀疑控制台本身。

**修订**（仅前端 `index.html`，接口契约不变）：`source=stale`（RTSP 抓帧失败、只拿到旧帧）
与"无任何帧"两种失败，统一呈现为**红色徽标「⚠ 视频源不可达」**：

- 旧帧**置暗 40%** 显示——明确"这不是实时画面"，杜绝误读；
- 提示语按采集开关状态分流：采集运行中 → "采集运行中但取不到新帧"；未运行 → "采集未运行，且 RTSP 源也无响应"；
- 列出 RTSP 源地址与帧龄，给出最可能的原因（AOS 相机未上线 / USB 掉线 / 视频服务未起），
  并注明"恢复后自动回到实时"；
- 卡片提示文案同步说明该告警语义。

**配套运维结论**：USB 设备从总线消失后远程无法恢复，需现场重新插拔 / 检查供电；
push_video.sh 的 `while true` 会持续等待 USB 上线，**相机重新枚举后视频链自动自愈**，
无需手动重启任何服务。

## 修订记录 2026-10-18（v0.8.7）：相机画面改为「带宽友好」的拉流节奏

**问题（用户提出）**：相机画面卡自动刷新时会不会给车端（M20 网卡）添负担？能不能主动关掉。

**事实澄清（两种来源成本完全不同）**：
- `ring`（采集运行中）：读 GOS 本地 `raw/` 最新帧 → **零额外带宽**，3s 无负担；
- `live`（采集未运行）：`/api/snapshot` 每次都要 GOS 侧 **ffmpeg 起停 + 一整条 RTSP 会话**
  从 AOS MediaMTX 拉流（车端编码、网络、会话建立都要成本）→ 固定 3s 等于
  在车和 GOS 之间**挂了一条持续的额外流**；
- 视频源不可达时更糟：每次抓帧要烧满 8s 超时，旧代码仍按 3s 节奏重试，
  ffmpeg 几乎不间断空转。

**改造（纯前端，接口契约不变）**：
1. **按来源自适应节奏**：ring → 3s；live → **10s**；
2. **失败退避**：连续 3 次拿不到实时帧（stale 或 grab_failed）→ 暂停自动拉流，
   改为**每 60s 单次探测**；源恢复后自动回到原节奏（`snapMark()` 成功后清零计数）；
3. **一键停止拉流**：新增「停止拉流」按钮（`stopSnap()`：取消自动刷新 + 停定时器），
   之后只有「立即刷新」能按需取单帧；徽标变「已暂停」；
4. **折叠 / 切后台标签页 = 完全不发请求**（原有行为保留，`snapAutoDue()` 收口判断；
   折叠/展开时同步起停定时器）；
5. **成本透明**：卡内说明文案写明两种来源的代价；`snap-src` 悬停显示当前来源
   的成本说明（ring=不占车端带宽 / live=每次额外 RTSP 会话）。

**验证**：单测 249 → **255 项**（新增 `TestSnapThrottle` 6 项：移除固定 3s、
自适应常量、折叠/后台停发、停止按钮与重排钩子、失败退避与恢复、新 i18n 键被引用）；
`node --check` 通过；浏览器实测见部署记录。

## 修订记录 2026-10-18（v0.8.8）：相机多选 + 刷新频率可调

**需求（用户提出）**：① 刷新频率能不能自己调；② 相机能不能选前 / 后 / 都选 / 都不选。

**实现（仍为纯前端，`/api/snapshot?cam=` 契约不变）**：

1. **相机多选**：原单 `<select>` 改为 chips（`front` / `back` 各一枚，可任意组合，含全不选）。
   - 每台一个 `<figure><img><figcaption>`，按选中集合动态渲染；切结构才重建 DOM（避免闪烁）；
   - 选择存 `localStorage["m20ai-snap-cams"]`（与语言无关），**全不选 = 完全不拉流**，
     状态行提示「未选择相机 —— 不拉流」；
   - 每台独立 in-flight 标记 `SNAP_BUSY[cam]`：一台卡住不拖累另一台。
2. **刷新频率下拉**：`自适应（实时帧 3s / 即时抓帧 10s）` / `1s` / `2s` / `3s` / `5s` /
   `10s` / `30s` / `60s` / `关闭（仅手动刷新）`，存 `localStorage["m20ai-snap-every"]`。
   - 自适应模式下保留失败退避（连续 3 次全灭 → 60s 探测）；
   - 用户显式频率优先于自适应；选 `关闭` 等价于点「停止拉流」（后者就是把下拉设为 0）。
3. **成本可见**：note 写明 ring 零带宽 / live 每路每次一条 RTSP 会话；
   当 live + 间隔 < 10s 时状态行追加提醒「x 路 ×Ns 会重建 x 条会话，建议 ≥10s 或先开启采集」。
4. **按路状态**：每路各自标注 `实时帧 · Ns前` / `即时抓帧` / `旧帧 · Ns前（源不可达）` /
   `取帧失败`；汇总徽标：全通→实时/即时、部分不可达→红「部分相机不可达」、全灭→红「视频源不可达」。

**关键实现坑（真机上抓到）**：初始化调用 `snapEveryInit()/initFolds()/applyI18n()` 原本放在脚本
中部，而 `SNAP_SEL` 等 `var` 赋值在新代码块之后 —— `applyI18n → setFold → snapSchedule`
读到 `undefined.length` 抛错，**整页 JS 停摆**（表现为相机 chips 空、配置不加载）。
修法：把 bootstrap（`snapEveryInit() → initFolds() → applyI18n()`）**统一挪到脚本末尾**
（所有 var 赋值之后）。这类"函数提升但变量不提升"的坑，以后新增模块初始化一律放末尾。

**浏览器验证（playwright，v0.8.8，两路相机均在线）**：
| 场景 | 结果 |
|---|---|
| 默认 | chips `front✓ back✓`，两个画面框 |
| 取消 front | 只剩 `snapfig-back` |
| 全部取消 | 状态「未选择相机 —— 不拉流」，**12s 请求 0 次** |
| 只选 back + 3s | 12s 内 4 次，**只请求 back** |
| 全选 + 10s | 22s 内 front 2 次 / back 2 次（每轮两路各一次） |
| 选「关闭」 | 8s 请求 0 次；点「立即刷新」→ 2 次（两路各一） |
| 刷新页面 | 选择与频率记忆保持 |

单测 255 → **257 项全绿**（`TestSnapThrottle` 重写为 9 项，覆盖多选、频率、停发路径、逐路抓取、退避与恢复、i18n 键）。

## 修订记录 2026-10-18（v0.8.10）：修「多相机不同时刷新」

**现象（用户报告）**：设 1s 刷新、前后都选，两路画面明显不是同时更新。

**三个根因，逐个实测定位**：

1. **服务端一把全局锁把整个抓帧过程包住** —— `_cached_grab` 里 `with _lock: ... grabber(...)`，
   于是 front 抓 2s、back 再排 2s，两路串行、相差约 2s。
   改为**按相机分锁**（`_grab_locks[cam]`）：同一路仍串行（防连击），不同路可并行。
   实测（线程内直调 `snapshot_frame`）：back 1.98s / front 3.33s 同时起跑，总耗时 3.33s
   = 取两者最大值 → 并行生效。
2. **单路完成就立刻上屏** → 快的先跳、慢的后跳。改为**轮次栅栏 + 整轮统一渲染**：
   `snapLoad()` 开一轮，各路结果先存 `SNAP_PENDING`，全部到齐才一次性 `renderSnapOne()`
   上屏（徽标也只在整轮结束时汇总）。
3. **展示用 `ts` 取错口径**：原来取"响应打包时刻"，缓存命中时也会变，看起来像"一直在换图/
   不同步"。改为**图像真实时刻**：`ring/stale` 用帧文件 mtime，`live` 用抓帧完成时刻（存进缓存）。

**附带修掉的两个隐患**：
- `snapLoadOne` 里某路 busy 时直接 `return` 而不报到 → 整轮永远等不齐（只有 20s 保险兜底，
  期间不刷新）。现在 busy 跳过也计为"本轮完成"。
- `CACHE_TTL` 1.5s → **0.6s**：1s 轮询会有一半轮次吃到 1.5s 前的旧图（看着像"没刷新"）。

**验证（playwright，1s，两路都选，live 模式）**：
| 指标 | 修复前 | 修复后 |
|---|---|---|
| 两路取帧时刻差 | 2.2 ~ 3.2 s | **0.4 ~ 1.8 s** |
| 两路 caption 时间戳 | 差 3 秒 | **差 ≤1 秒**（如 04:12:05 / 04:12:06） |
| 每轮请求 | 一路连续两次、另一路缺席 | **两路成对出现** |
| 画面更新时机 | 谁先回来谁先跳 | **整轮同时上屏** |

**残留偏差是物理限制**（已在界面 note 说明）：`live` 每路要独立等 RTSP 握手 + 关键帧
（1~3s 不等），两路图像本身不可能严格同刻；**采集运行中走 `ring`（读本地帧）时两路才是同刻的**，
这也是"要对比前后画面"时的推荐用法。

单测 257 → **261 项**（新增按相机分锁、缓存带 wall 时刻、整轮统一上屏、busy 不悬挂 4 项）。

## 修订记录 2026-10-18（v0.8.11 / v0.8.12）：修「画面永久定格」+ 抓帧提速 + spool 防爆

**用户报告**：设 1s 刷新，但相机画面停在 04:16:57，而「最近检测」已到 04:19:29（差 2.5 分钟）；
且"不管采集开没开 1s 都没效果"。

### 根因一（致命，我的 bug）：切走标签页后定时器链断开，画面永久冻结

v0.8.7 把固定 `setInterval` 改成递归 `setTimeout` 以支持动态间隔，但 `snapSchedule()` 里：

```js
if (!snapAutoDue() || !d){ snapIdle(); return; }   // ← 直接 return，链断了
```

`snapAutoDue()` 在「页面隐藏 / 卡片折叠 / 未选相机 / 频率=关闭」时为假 → **整个定时器链终止**。
折叠和改频率有 hook 能重新唤醒，但**切走标签页再切回来没有**——于是画面停在切走那一刻，
只有手动点「立即刷新」或改频率才会动一帧。

**修复**：
1. 递归回调用 `try { snapLoad() } catch(e) {} finally { snapSchedule(); }` —— 任何异常都不许断链；
2. 注册 `visibilitychange` / `focus` / `pageshow` 三个唤醒钩子；
3. `snapLoad` 包一层 try/catch，异常时重置 `SNAP_ROUND_ACTIVE` 防止栅栏卡死。

**实测**（playwright 双 tab）：切走 7s → 切回 9s 内**发出 6 次请求**（修复前恒为 0）。

### 根因二：单帧抓取本身 2.7~6.6 秒，1s 设置被物理耗时卡住

直接实测 `ffmpeg -frames:v 1`：front **4170/5109/6621 ms**、back 2771/2785/3001 ms
（默认会先做流探测 + 缓冲一段再出帧）。加
`-fflags nobuffer -flags low_delay -probesize 32768 -analyzeduration 0` 后：
front **1903/1551/2606 ms**、back 1268/1819/1724 ms，两路并行总耗时 **2053 ms**。

→ 已写入 `build_snapshot_cmd()`（仅对 RTSP 源）。**即使优化后，live 的物理下限仍是 ~1.5-2.5s/轮**，
1s 只有在 `ring`（采集运行时读本地帧，实测 **62 ms**）才可能达到。

### 根因三（现场故障，非本工程）：AI 推理服务不可用

当时 `POST /v1/detect` 即使跳过 DNS 直连 IP 也 **20s 超时**（首页 GET 却 200），
采样器连续 `detect FAIL ... timeout / Errno -3 Temporary failure in name resolution`，
退避到 30s → **spool 积压 385 帧、raw/ 停更 3.5 分钟**（画面龄 208~220s）→
`_ring_latest` 判"不新鲜"（>5s）→ 预览只能走 live → 更慢。

顺带发现：**raw 文件的 mtime 保留了原始帧时间**（`copy2`），所以积压期用 mtime 判新鲜度会
