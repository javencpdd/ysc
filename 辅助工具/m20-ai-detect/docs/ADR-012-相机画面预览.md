# ADR-012: 相机画面预览（控制台「相机画面」卡）

- 日期：2026-10-16
- 状态：已实施，真机验证通过（2026-10-16）
- 关联：ADR-005（控制台）、ADR-006（响应留存）、ADR-008（时间轴）、ADR-009（只读浏览）、ADR-011（关注目标与数据清空）

## 背景

用户在看控制台「采集开关 / 最近检测」区域时提出：

> "这个部分能不能加一个目前的开放的相机画面信息（rtsp 流？）"

即：不离开控制台就能看到**相机现在拍到的画面**——看"检出 7 个目标"时画面里到底是什么、AI 是不是在看它该看的东西。

两个约束决定了不能简单"嵌个 RTSP 播放器"：

1. **浏览器不能直接播放 RTSP**（原生只支持 HLS；Windows 浏览器连 HLS 也不原生支持，引 hls.js 会打破控制台"零依赖单页"的现状）；
2. **视频流在 AOS 196、控制台在 GOS 104**——跨主机嵌流会把 5050 页面的可用性绑定到另一台机器（浏览器到 196 的连通性、WebRTC/HLS 依赖），且与"检测器实际看到的画面"未必同源。

因此选择**服务端单帧快照**：控制台后端直接给"当前画面"一张 JPEG，前端当作图片刷新——最贴近"我就想看一眼"的需求，且完全复用现有链路。

## 决策

### 1. `GET /api/snapshot?cam=<name>`：单帧快照，三级来源

| 优先级 | 来源 | 条件 | 特征 |
|---|---|---|---|
| 1 | `ring` | `raw/<cam>/` 有不超过 `max(5s, 4/fps)` 的帧 | **采样器运行中即此处**：零额外开销，且正是**检测器刚处理过的画面** |
| 2 | `live` | 环形帧过期/缺失 | `ffmpeg` 单次抓帧（同一路 RTSP）：**采集未运行也能看实时** |
| 3 | `stale` | 抓帧失败 | 兜底返回环形缓冲最近一帧，`age_s` 如实标注，UI 显示"已定格 N 前" |

- 返回 JSON：`{ok, cam, src, source, age_s, frame, image(base64 JPEG)}`；
- 错误分流：配置类问题（未知相机/未启用相机）→ **400**（附 `bad_request`），抓帧失败 → **502**；
  本模块不向上抛异常——**一张图抓不到不允许影响控制台其它功能**。

### 2. 抓拍命令行：与常驻抽帧共用协议参数，但"抓完即退"

- `capture.build_snapshot_cmd()` 与常驻抽帧共用 `_input_args()`（RTSP 强制 TCP / RTMP 声明 flv / mjpeg 声明封装）与 `FORBIDDEN_TOKENS` 安全自检；
- 不落盘：`-frames:v 1 -q:v <jpeg_q> -f image2pipe -vcodec mjpeg pipe:1`；
- 单次 RTSP 握手实测 1.6~2.0 s（2026-10-14 AOS），故：**8 s 抓帧超时 + 短缓存**（成功 1.5 s、失败 3 s），模块级锁串行化，防多客户端连击拉起一堆 ffmpeg。

### 3. 前端「相机画面」卡：3 秒自动刷新、页签隐藏暂停

- 位置：首行「采集开关 | 最近检测」之后的全宽卡（与检测监控同一屏区）；
- 徽章四态：`实时`（ring）/ `即时抓帧`（live）/ `已定格`（stale，附 age）/ `抓帧失败`（err）；
- 多相机出现下拉切换（列表取自 `/api/config` 的启用相机）；`SNAP_BUSY` 防重入；
- `document.hidden` 时暂停自动刷新（不浪费带宽），手动按钮始终可用。

- `src/m20_ai_detect/snapshot.py`（新模块）：`snapshot_frame()`（来源优先级；`grabber`/`now` 可注入便于测试）、`_ring_latest()`、`_cached_grab()`、`_grab_jpeg()`、`_fresh_window()`。
- `webconsole/server.py`：新增 `GET /api/snapshot` 路由与 `_get_snapshot()`（400/502 分流）。
- `webconsole/static/index.html`：卡片 + `snapLoad / snapFillCams / snapTag` + 3 s 定时器 + refreshAll 集成。
- 测试：`tests/test_snapshot.py`（12 项：命令构建 3 + 来源优先级/缓存/兜底/参数校验/新鲜窗口/缓存时间戳 9）；`test_webconsole.py` HTTP +2（ring 分支、未知相机 400）。全量 **209 → 223 项**。

## 修过的一个坑（真机验证时发现）

抓帧缓存的时间戳第一版记在**抓帧开始前**——而单次 RTSP 握手本身要 ~4 s，等于每次请求都白扣 4 s 的 TTL：
真机连续两次 `_cached_grab` 实测第二次仍耗时 5.3 s（又抓了一遍）。改为**抓帧完成时刻**计时后，
第二次 0.0000 s 命中（同帧 64537 字节）。已用可注入时钟的单测固化该语义。

## 验证（GOS 104 真机，2026-10-16）

**部署**：`NO_RESTART=1 ./deploy/install.sh` 同步（远端 import 自检 `v0.7.0`）后**只** `console-restart`
——采集正处于运行中（用户在用），全程未触碰采样器。

- **ring（采集运行中）**：`GET /api/snapshot?cam=front` → `ok=true, source=ring, age_s=1.5`，
  帧 `front_20261016_043436.jpg`（65170 字节，魔数 `ffd8`…`ffd9`，合法 JPEG）；
- **live（采集未运行时的路径）**：主机上直接对真实 RTSP 源跑 `_grab_jpeg` →
  成功 3.77~3.84 s / ~64.5 KB（采集运行中无法停采集验证，用直调等价覆盖）；
- **缓存**：`_cached_grab` 连调两次 → 第一次 3.77 s（真实抓帧）/ 第二次 **0.0000 s**（命中同帧）；
- **界面**：`GET /` 已含「相机画面」卡与 `snap-img / snap-cam / snap-auto / snapLoad` 元素；
- **待办**：用户浏览器实测确认画面渲染（本环境无法自动验证渲染）。

## 修订记录 2026-10-17：`stale` 态升级为「⚠ 视频源不可达」醒目提醒（v0.7.1）

**起因（真实事故）**：2026-10-17 00:23 整机重启后，USB 相机约 00:34 从总线掉线
（`ls /dev/video*` 为空、push_video 日志"等待USB设备上线"、mediamtx 空转导致 video1/video2
无发布者、RTSP DESCRIBE 404）。快照按设计兜底返回 20 小时前的旧帧，但 UI 只标了琥珀色小字
"已定格"——**用户把定格旧帧误读为"画面卡住"**，且第一反应是怀疑控制台本身。

**修订**（仅前端 `index.html`，接口契约不变）：`source=stale`（RTSP 抓帧失败、只拿到旧帧）
与"无任何帧"两种失败，统一呈现为**红色徽标「⚠ 视频源不可达」**：

- 旧帧**置暗 40%** 显示——明确"这不是实时画面"，杜绝误读；
- 提示语按采集开关状态分流：采集运行中 → "采集运行中但取不到新帧"；未运行 → "采集未运行，且 RTSP 源也无响应"；
- 列出 RTSP 源地址与帧龄，给出最可能的原因（AOS 相机未上线 / USB 掉线 / 视频服务未起），
  并注明"恢复后自动回到实时"；
- 卡片提示文案同步说明该告警语义。

**配套运维结论**：USB 设备从总线消失后远程无法恢复，需现场重新插拔 / 检查供电；
push_video.sh 的 `while true` 会持续等待 USB 上线，**相机重新枚举后视频链自动自愈**，
无需手动重启任何服务。
