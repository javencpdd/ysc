# ADR-011: 「关注目标」留存过滤可视化与数据清空

- 日期：2026-10-16
- 状态：已实施，真机验证通过（2026-10-16）
- 关联：ADR-006（响应留存）、ADR-008（时间轴与留存清理）、ADR-010（启动行为）、ADR-005（控制台）

## 背景

用户在使用中提出两个问题：

1. **"我能不能选择检测到了什么目标才保存图片"**。内核逻辑其实早已存在：`SAVE_MODE=alert` 时，
   只有"命中 `ALERT_LABELS` 且 score ≥ `ALERT_SCORE`"的帧才会留存（ADR-006）。但两个问题让这个能力"看不见"：
   - 配置入口藏在「告警规则」卡里，名字和"保存图片"没关系，不读文档无法发现两者是同一件事；
   - 用户不知道模型当前能检出哪些标签（当天实测分布 chair 8242 / person 488 / tv 25 / boat 4），填什么全靠猜。
2. **"顺便帮我把目前的保存日志和图片清空"**。此前清空能力只有 `aiDetect reset`（清 spool 积压帧），
   而用户要重置的是 saved/（224 对图片≈23M）、results/（检测记录≈9M）、raw/（原始帧缓存≈209M）。

## 决策

### 1. 「关注目标」成为一等概念——一个清单承担两个语义

不新增配置别名，把 `M20AI_ALERT_LABELS` / `M20AI_ALERT_SCORE` 统一表述为**关注目标**：
命中清单（且分值 ≥ 阈值）的帧 **①** 计入"告警次数"；**②** `SAVE_MODE=alert` 时保存图片。
一句话回答用户："想只保存检测到人的图片 → 关注目标填 `person`、留存条件选 `alert`。"

- 网页「告警规则」卡改建为**「关注目标」卡**：
  - 输入框 + 阈值滑杆（沿用 env 配置，不新增键）；
  - **今日检出标签 chips**（新 API）：按今日 JSONL 聚合各 label 计数（降序 top 20），
    点击即加入/移出清单——解决"不知道能填什么"；
  - 文案写明"清单为空 = 不保存任何图片（alert 模式）"；
  - 保存 → 写 env → 采集运行中自动重启生效（见决策 3）。
- `GET /api/retention` 增加 `alert_labels` / `alert_score` / `label_stats`
  （`label_stats` 只读今日 JSONL 尾部 4MB、60s 缓存；清空 results/ 后主动失效）。
- `POST /api/retention` 增加 `alert_labels` / `alert_score` 字段：
  - 标签只允许 `[A-Za-z0-9_.-]{1,40}`，单次 ≤ 32 个，重复自动去重（保持顺序），空串 = 清空清单；
  - 分数走 `validate_env` 全量校验（0–1），坏值 400 不落盘。

### 2. 数据清空：`purge` = 停采集（仅当运行中）→ 清所选 → 恢复采集原状态

- `Store.purge(kinds)`：**一次性整体删除**（区别于 `clean_saved` / `enforce_ring` 的渐进策略）：
  - `saved`（`*.jpg` + `*.json`，含 `console/` 等子目录）、`raw`（`*.jpg`）、
    `results`（**只删 `*.jsonl`**，其它文件不碰）、`spool`（`*.jpg`）；
  - 返回每类 `(文件数, 字节数)`，单文件失败只记日志不中断。
- `_purge_with_restart`（控制台 server）：
  - 采集**原本在运行** → stop → 清 → start（恢复原状态）；
  - **原本未运行 → 绝不动服务**（ADR-010：采集开关归用户掌握；旧 `spool_clear` 无条件"停→清→启"的行为一并修正）；
  - 状态无法确认（无 systemctl / 命令超时）→ 不碰服务直接清——各写入点均为短 open/write/close
    或整文件写入，与运行中采集的竞争窗口最坏损失极少量新记录；
  - 停采集失败即中止（**未清任何数据**）；清空抛错且采集被停过 → 尝试恢复启动；全程 logger 留痕。
- API：`POST /api/retention` 增加 `purge: ["saved","results","raw","spool"]`（非空数组、值域校验，重复去重）；
  `spool_clear: true` 保留为兼容别名（等价 `purge:["spool"]`）。
- 网页留存卡「清空积压帧」块升级为**「清理数据」块**：四类勾选框 + 当前占用显示（复用 /api/status 磁盘统计）
  + 动态确认文案（列出所选类别与不可恢复警告）。

### 3. 顺带修正：配置保存的"自动重启"不再拉起停着的采集

`POST /api/config` 的 `restart`（默认 on）旧行为是无条件 `svc-restart`——**会把用户停掉的采集启动**，
与 ADR-010 矛盾。修正为：

- 采集运行中 → restart，改动即时生效；
- 采集未运行 → **不启动**，提示"下次开启采集时生效"；
- 状态未知 → 提示手动重启。

按钮文案相应改为「保存并应用」。`POST /api/retention` 新增 `restart_collect: true`
（仅当采集运行中才重启；与 purge 同时提交时以 purge 的重启为准，避免双重启）。

  `_get_retention` / `_post_retention` / `_post_config` 扩展；删除 `clear_spool_with_restart`（被 `_purge_with_restart` 取代）。
- `webconsole/sysactions.py`：`service_is_active(runner) -> True/False/None`

- `src/m20_ai_detect/store.py`：`PURGE_KINDS` + `Store.purge()`。
- `webconsole/static/index.html`：关注目标卡（chips）、清理数据块、save-mode 文案；
  JS `fmtMB` / `renderLabelStats` / `toggleLabel` / `purgeSelected`。
- 测试：`test_store.py::TestPurge`（5 项）、`test_webconsole.py::TestPurgeWithRestart`（7 项）、
  关注目标 HTTP（8 项）、`service_is_active`（3 项）、"配置不拉起停采集"（1 项）；全量 209 项全绿。

## 修过的一个坑

`_label_stats` 尾读实现第一版：`seek(0, SEEK_END)` 测长后，**未截断时忘记 `seek(0)` 就 `read()`**，
于是永远读到空 bytes（Windows/Linux 一致），chips 恒显示"暂无记录"。单元测试抓出，改为 `else: fh.seek(0)`。

## 验证（GOS 104 真机，2026-10-16）

**部署**（`NO_RESTART=1 ./deploy/install.sh`，凡涉及采集一律不自动拉起）：
远端 import 自检 `sampler v0.6.0 / console v0.6.0`；`aiDetect` 重装后 md5 与本地一致；
helper / sudoers / unit 三者 md5 与本地一致（无需重装）；`console-restart` 后 `/api/status`
`version=0.6.0`，采集保持 `inactive`。

**API 与配置**：
- `GET /api/retention` 返回 `alert_labels` / `alert_score` / `label_stats`
  （实测今日分布 chairs 8410 / person 488 / tv 27 / boat 4，降序正确）。
- `POST {"alert_labels":["person"]}` → env 第 40 行 `M20AI_ALERT_LABELS=person`，
  回读 `alert_labels=['person']`、`save_mode=alert`、`alert_score=0.6`；提示"重启采集后生效"（采集未运行）。

**数据清空**（清空前的基线：saved 448 文件≈21.4MB / results 3 文件≈9.0MB / raw 3168 帧≈199.9MB）：
- `POST {"purge":["saved","results","raw"]}` → 返回逐类文件数与字节数，附
  "采集未运行，未做启停"；落盘复查三目录 **0/0/0**；`label_stats=[]`（缓存失效生效）；
  `frames_today=0 / alerts_today=0`；磁盘释放约 250MB。

**决策 3（不拉起停着的采集）**：`POST /api/config` 回写同值时提示
"已写入 env；采集未运行（不自动拉起），改动将在下次开启采集时生效"，采集保持 `inactive`。

**过滤链路端到端实测**：
- 负对照：`collect on` 运行 80s → 91 帧、538 个检出（chair 458 / tv 79 / laptop 1）、
  **0 条 `alert:true`、saved/ 0 文件**——无关注目标出现时什么都不存；
- 正测试：临时 `alert_labels=["chair"]` + `restart_collect:true` → 提示"已重启采集，env 级改动即时生效"；
  35s 后 **23 条 `alert:true` ↔ 23 个保存文件一一对应**（meta `_alert=true`）——命中即标记即保存；
- 收尾：恢复 `alert_labels=["person"]`、`collect off` 回到原关闭状态、测试残留二次 purged
  （saved 70 文件 + results 1 文件 + raw 158 帧），最终 saved/raw/results 归零。
  验证窗口内场景无 person，正路径以 chair 作代理目标走同一代码路径；person 帧自动保存由单测与既往生产记录背书。

**界面与命令**：控制台 `/` 已含「关注目标」「清理数据」及四个勾选框、
`label-stats` chips 容器；`aiDetect help` 的 `reset` 文案已更新为"停采集仅当运行中，清完恢复原状态"。
