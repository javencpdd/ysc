# ADR-016: 通用视频源抽象与设备适配（多机型 / 自动发现）

- 日期：2026-10-19
- 状态：已接受（2026-10-19 实施：T1–T7 完成——`Source` 模型、N 路配置、scheme 适配器、逐路退避、控制台源管理、三级发现器、profile/模板化；命名层见 ADR-017）
- 影响面：`src/m20_ai_detect/{config,capture,snapshot,sampler,store}.py`、`webconsole/{server.py,static/index.html,i18n.py}`、`deploy/{profiles,*.env.example,preflight.sh}`、README / USAGE / ADR-012
- 关联：ADR-017（身份与命名，承接本 ADR §背景表格里的"命名 ❌ 全绑 M20"一行）

## 背景

本系统最初只为 M20 Pro 的「前后两路 AOS RTSP」设计，现在要回答三个新问题：

1. **能否用于 Lite3？** Lite3 是单相机，而且 103 主机已有自己的 RTMP 发布链路（`appsrc → nvv4l2h264enc → rtmpsink`），源形态与 M20 完全不同。
2. **能否用于其它设备？** IPC（ONVIF）、USB 相机（`/dev/video*`）、甚至回放文件都可能要接。
3. **能否不让用户手填 URL？** 希望「扫描一下就知道有哪些流」，同时保留手工配置入口。

**现状盘点（grep 实测，2026-10-19）**：

| 层 | 是否已通用 | 证据 |
|---|---|---|
| 内核数据模型 | ✅ 已是 N 路 | `Config.cameras: List[Camera]`（config.py:100） |
| 采样器 / 快照 / 存储 / API | ✅ 全是 list-driven | `for cam in cfg.cameras` 出现在 cli/sampler/snapshot/server 共 8 处 |
| **配置入口** | ❌ 写死两路 | config.py:255-263 只有 `ENABLE_F/SRC_F/ENABLE_B/SRC_B` 两组槽位 |
| **UI 入口** | ❌ 写死两个复选框 | `index.html:1112` `el("en-f")/el("en-b")` |
| **命名** | ❌ 全绑 M20 | 包名 `m20_ai_detect`、env 前缀 `M20AI_`、unit `m20-ai-detect.service`、helper 路径 |

即：**这不是重写，是拆两个"假两路"的入口**——工程量被高估的风险远大于被低估。

### 硬约束（决定了设计边界）

- **`src` 串禁词**：`config.py:21` `FORBIDDEN_TOKENS = ("push_video","v4l2","gst-launch")`，含禁词的源地址在 `validate()` 阶段直接被拒（上游 `restart.sh` 会 `pkill -f` 这些词误杀）。→ **本地 USB 相机的 `-f v4l2` 绝不能出现在 env 里**，必须靠 URI scheme 在代码内部展开。
- **M20 的 MediaMTX 管理 API（9997）未开**（部署记录 2026-10-17）→ 拿不到路径列表，"标准接口发现"在 M20 上不可用，必须留降级路径。
- **unit 里 4 处写死 base 目录**（`WorkingDirectory`/`EnvironmentFile`/`PYTHONPATH`/`ReadWritePaths`）→ 改 base 就要改 unit，改名挂牌成本高。
- **采集(fps)与预览解耦**（ADR-012）→ 每路源的fps/延迟不同，健康检查要逐路独立，不能被一路坏源拖垮整轮。

## 决策

> **把「视频源」提升为一等公民：`Source` 抽象 + `type://` URI + 三级发现器 + profile 文件。**
> 包名 / env 前缀 / service 名**本期不改**，靠 `profile` + 展示名区分机型；改名留到真正要规模化多机型时一次性做（见 §6 复审条件）。

### 1. 数据模型：`Source` 取代隐式两路

```python
@dataclass
class Source:
    name: str            # 逻辑名，落盘目录/JSONL.cam 字段用它（已如此）
    uri: str             # device:///dev/video0 | rtsp://h/p | rtmp://... | file://... | onvif://ip
    type: str = ""       # 由 uri scheme 推导，**不由用户填**
    transport: str = "auto"   # rtsp 的 tcp/udp/auto
    enabled: bool = True
    fps_override: float | None = None   # 逐路 fps（默认继承全局 M20AI_FPS）
    ffmpeg_extra: tuple[str, ...] = ()  # 逐路附加参数（旋转/裁剪/分辨率）
    note: str = ""
```

`type` 由 scheme 推导表：

| scheme | 含义 | 展开出的 ffmpeg 读源 |
|---|---|---|
| `rtsp://` | RTSP（默认 UDP，失败回落 TCP） | 现有逻辑，加 `-rtsp_transport` |
| `rtsp+tcp://` | 强制 TCP（弱网/NAT 后必用） | `-rtsp_transport tcp` |
| `rtmp://` | RTMP 拉流（**Lite3 103 就是这条**） | `ffmpeg -i rtmp://...` |
| `http(s)://` | MJPEG / HLS / 图片快照 | 视 content-type，走 `mjpeg` 或 `image2` |
| `device://` | **本地 V4L2**（`device:///dev/video0`） | 内部拼 `-f v4l2 -i /dev/video0` |
| `file://` | 视频文件 / 图片序列（回放调试） | `-i /path.mp4` 或 `-loop 1` |
| `onvif://` | ONVIF IPC，运行时再解析真 RTSP URL | WS-Discovery → GetStreamUri |
| `ros://` | ROS2 图像话题（P2 可选，需本机 ROS 环境） | 需 rosbridge/SDK，本期不实现 |

> `device://` 存在的唯一理由就是绕过 `FORBIDDEN_TOKENS` 校验：env 里写 `device:///dev/video0`（不含 `v4l2` 字样），由 `capture.build_snapshot_cmd()` 在构建命令行时才展开 `-f v4l2`。（注：展开后命令行含 `v4l2`，仍有被 `pkill -f` 误杀的风险——`ros://` 与 `device://` **只在非 M20 平台的 profile 里启用**，见 §5。）

### 2. 配置语法：单行 `SOURCES`，向后兼容旧两槽

```bash
# 新语法（推荐）：分号分隔，name=uri
M20AI_SOURCES='front=rtsp://10.21.31.103:8554/video1;back=rtsp://10.21.31.103:8554/video2'
M20AI_SOURCES='cam0=device:///dev/video0'          # Lite3 / USB
M20AI_SOURCES='gate=rtmp://192.168.2.1:1935/live/0' # Lite3 RTMP 链路
```

- **分隔符选 `;` 不用 `,`**：URL与 `ffmpeg_extra` 里可能含逗号/等号，分号冲突概率最低。
- **兼容规则**：`SOURCES` 存在且非空 → 用新语法；否则回落到旧 `ENABLE_F/ENABLE_B/SRC_F/SRC_B` 自动合成，并在 `aiDetect doctor` 打印 deprecation 提示（不阻断）。旧 env 文件无需改动即可继续跑。
- UI 保存时**整份覆写**该行（幂等，不拆分、不做增量 diff），配合 §7 的源列表表格。

### 3. 三级发现器：`GET/POST /api/sources/discover`

RTSP 协议本身**没有目录列表**（不像 HTTP），所以发现只能分层：

| 级别 | 手段 | 适用 | 本系统落地 |
|---|---|---|---|
| **L1 标准接口** | ONVIF WS-Discovery（UDP 3702）→ GetProfiles → GetStreamUri；MediaMTX REST `/v3/paths/list`（:9997）；go2rtc `/api/streams` | IPC、自建流媒体 | **M20 上 9997 未开 → 自动降级** |
| **L2 本机推断** | 读本机 `mediamtx.yml` 的 `paths:` 段；枚举 `/dev/video*`（用 `v4l2-ctl --list-devices`，注意该命令名含禁词，仅**读设备**不入库）；扫 `ss -ltn` 上的 554/8554/1935 端口 | 站内/本机自身有流服务 | M20 属于此类（可从 `rtsp_service` 配置推断 video1/video2） |
| **L3 候选穷举** | 给定 `host[:port]` × 候选路径表，并发 `ffprobe`（`-nostdin`，3s 超时），成功的再 `ffmpeg` 抓 1 帧确认**能出图** | 兜底，**M20 的主力** | 已有 `preflight.sh` 的 probe 逻辑可复用 |

候选路径表（按命中率排序，可在 profile 里覆盖）：
`video1..video8, cam1..cam4, live/main, live/sub, stream0..stream2, ch1..ch4, profile1/profile2, 0/1/101/102, m20/front, m20/back`

每条结果带判定：`ok` / `auth_required`（401/RTSP 401）/ `timeout` / `refused` / `no_frame`（能连但抓不到帧）。

**安全护栏（必须）**：

- **禁止无边界扫描**：默认只探「本机 + profile 声明的 host」，L1 的 WS-Discovery 限制在本机接口所在网段，绝不扫整个路由域。理由：① 会被网络管理当扫描器；② `-nostdin` 之外，大规模并发 ffmpeg 会把 RK3588 打满。
- 并发上限 ≤ 8、单路超时 3s、总预算 ≤ 20s；超时即返回已发现部分。
- 发现的候选**不自动启用**，一律进 UI 让用户勾选后才写 env。

### 4. profile：机型 = 一组默认值，不是一份分支代码

```
deploy/profiles/
  m20pro-dual.env   # SOURCES=front=rtsp://10.21.31.103:8554/video1;back=.../video2
  lite3-single.env  # SOURCES=cam0=device:///dev/video0（或 rtmp://192.168.2.1:1935/live/0）
  ipc-generic.env   # 空 SOURCES，启用 ONVIF 发现
  local-usb.env     # 启用 device://，允许 v4l2 展开（**明确标注：不可用于 M20 的 restart.sh 环境**）
```

```bash
M20AI_PROFILE=m20pro-dual          # 只是默认值来源
M20AI_PLATFORM_NAME="M20 Pro · 双目"  # 纯展示，进控制台顶栏
```

**原则：profile 永远只是默认值；任何显式配置（含 `SOURCES`）优先。** profile 不存在也不该报错，退化为空。

### 5. 采集与预览的逐路隔离

- `sampler`：`for cam in sources` 已经天然支持；新增**逐路故障退避**——某路连续 N 次失败后，把它的探测周期拉长（指数退避 + 抖动），避免"一路坏了把整轮 fps 拖死"。
- `snapshot`：现已有 per-camera lock（`_grab_locks`），逐路并行抓帧不受影响；新增 `source="unreachable"` 时与既有 `stale` 分支合并。
- `store`：`saved/<name>/`、JSONL 的 `cam` 字段沿用 `name`，**不因 N 路变化。**

### 6. 命名：本期不动，但要留退路

保留 `m20_ai_detect` / `M20AI_` / `m20-ai-detect.service` 不变。理由：

- unit 有 4 处硬路径 + helper/sudoers/回滚话术都引用它，改名要连带改 `install.sh`、`install-local.sh`、`preflight.sh`、`bootstrap.sh`、全部文档与已部署的 104；
- 收益只是"在 Lite3 上看到 m20- 前缀不别扭"，属于观感而非功能。

**代价与对冲**：Lite3 上服务名仍是 `m20-ai-detect`。若不可接受，走一次性 `deploy/migrate-rename.sh`（引进新名 `ai-detect-agent`，unit 由脚本按实际 BASE 渲染生成从而消除硬编码，旧 env 键双认一个版本）。

### 7. UI 改造点（已实施）

| 位置 | 落地形态 |
|---|---|
| 设置 → 原「相机与采集」卡 → 更名「**视频源与采集**」 | 两个复选框换成**源列表表格**：名称 / 类型 tag（scheme 推导）/ 地址（+逐路 fps 标注）/ 状态 tag / 停用·启用 / 删除；手动添加一行（名称 + `类型://地址` + 可选帧率）；停用源**留在列表里**以便重新启用（`enabled=false` 不删行） |
| 同卡片 | 「**扫描**」按钮 → `POST /api/sources/discover`（`scope:"local"`，前端钳制 3s/20s）→ 结果区列出候选与六种判定（ok/auth_required/timeout/refused/no_frame/unresolved），**勾选后才写 env** |
| 同卡片 | 全局抽帧帧率沿用 `/api/config`（`M20AI_FPS`），与源列表同卡，保存后按 ADR-010 同样的重启语义生效 |
| 新增接口 | `GET /api/sources`（列表 + `allow_local_device` 闸门 + 原始 env 行）；`POST /api/sources`（action: **add/update/remove/enable/disable** 五动作，先 `parse_sources` → 列表运算 → `dump_sources` 整份序列化 → 合并整份校验 → 写 env → 采集在跑才重启）；`POST /api/sources/discover`（scope 白名单 `local|auto|host:<ip>[:port]` + 参数钳制） |
| i18n | 新增 `src.*` 键组（server 侧错误文案，zh/en）+ `cam.*` 前端键组；单测守护两侧键集合一致、无死键 |

> 与初版的差异：**未做「最近一帧 / 抓取耗时」两列**（预览卡已有帧龄与来源标注，避免重复）；**地址未脱敏**（env 里本来就是明文 RTSP 地址，控制台需登录态，参考 ADR-009 的既有取舍）。

## 依据

1. `src/m20_ai_detect/config.py:255-263` 只有两槽位；其余消费点均为 `for cam in cfg.cameras`（cli:204、sampler:93/100、snapshot:92/95、server:862/881），改入口即可 N 路。（代码实测，2026-10-19）
2. `config.py:21` `FORBIDDEN_TOKENS` 含 `v4l2`/`push_video`/`gst-launch` → 本地设备必须用 `device://` scheme 间接表达。（代码实测）
3. M20 MediaMTX API(:9997) 未开 → L1 发现在该机上不可用，L3 穷举是主力。（部署记录 2026-10-17；与本次 grep 的 `preflight.sh` 探测实现一致）
4. Lite3 103 已有 RTMP 发布链路（`appsrc → nvv4l2h264enc → flvmux → rtmpsink`），→ Lite3 profile 走 `rtmp://` 而非 RTSP。（`.workbuddy/skills/jetson-video-publish/SKILL.md`）
5. RTSP 无标准化目录列举能力（`DESCRIBE` 需先知道 path），故发现只能是"标准接口 + 本机推断 + 候选穷举"三层。（协议事实）

## 后果

### 正面

- 一套代码覆盖 M20 双目 / Lite3 单目 / IPC / USB / 文件回放，新增机型 = 加一个 profile 文件，不改 Python。
- 用户不必知道 `video1` 这种内部路径，扫描一下就有；老用户手写 URL 的入口完整保留。
- 内核零改动（`cameras` 已是 list），回归风险集中在 config 与 UI 两处，可用现有 268 个测试兜底。
- 逐路退避让"一路源挂了不影响其它路"，直接解决 ADR-012 里观察到的"环帧/卡帧"连带问题。

### 负面 / 代价

- **env 语法分裂**：新旧两套并存一个版本周期，文档与 chatbot 都要讲清楚优先级；`SOURCES` 单行一旦长起来可读性差（>4 路时应引入 `sources.d/*.env` 或 JSON）。
- **发现器有副作用风险**：并发 ffprobe 会占 CPU（RK3588 上尤其明显）、可能触发对端限流；必须限并发/限时间/限范围。
- **`device://` 的 pkill 雷区**：展开后的命令行含 `v4l2`，在跑厂商 `restart.sh` 的平台上仍可能被误杀——只能靠 profile 显式声明"本平台允许"，无法从代码侧彻底消除。
- **`type` 推导靠 scheme**：用户写 `rtsp://` 但服务端其实是 MJPEG over HTTP 之类，需要 `-f` 覆盖，`ffmpeg_extra` 成为逃生口，等于half-承认"穷举也没那么聪明"。

### 触发复审的条件

出现以下任一情况应重新评估（含 §6 的改名——**已于 2026-10-19 由 ADR-017 落地**：`app_id` 派生全部对外名字，`migrate-rename.sh` 执行改名）：

1. **要在 3 台以上不同机型部署** → 执行 `migrate-rename.sh --to <新身份> --apply --switch`（ADR-017）。
2. **单机 >4 路源** → 单行 env 不可读，改 `sources.d/` 目录或多行块语法。
3. **发现对下挂 USB hub 的即插即用要求**（相机热插拔要自动接管）→ 引入 udev 监听，而非轮询发现；这也意味着要正视 `device://` 命令行被 pkill 的风险。
4. **需要 ROS2 话题作为源**（Lite3 Foxglove 链路）→ `ros://` adapter 会引入 rclpy 依赖，与"纯 ffmpeg + 零重依赖"（ADR-002）冲突，需单独论证。
