# ADR-010: 配置项单位语义与启动行为调整（控制台常驻、采集默认关闭）

- 日期：2026-10-16
- 状态：已实施
- 关联：ADR-005（控制台）、ADR-007（aiDetect，本次修订）、ADR-008（留存清理）

## 背景

上线后发现两类问题，都由用户提出：

1. **单位语义不清**：留存策略卡里既有体积框又有时间框，用户不知道"填 20 还是 20M"、"填 7 是全 7 秒还是 7 天"。
   更危险的是 systemd 的默认语义：`journalctl --vacuum-size` 与 `SystemMaxUse` **必须带体积后缀**，而
   `--vacuum-time` 与 `MaxRetentionSec` 的**裸数字是秒** —— 用户填 `7` 想表达 7 天，实际会变成 7 秒，
   日志被瞬间清空且没有任何提示。
2. **启动行为与直觉不符**：`aiDetect up` 只起采样器，而用户要访问的网页是另一个服务 `m20-ai-console`，
   于是出现"我启动了怎么还是打不开"（浏览器 `ERR_CONNECTION_REFUSED`）。用户要求：
   **启动时只启动控制台；采集默认关闭，由控制台开关控制，且不再需要 `--all` 参数。**

## 决策

### 1. 每个字段都有明确的默认单位，裸数字按默认单位解释

| 字段 | 语义 | 默认单位 | 合法写法 | 默认值 / 范围 |
|---|---|---|---|---|
| `M20AI_RING_MAX_MB` | raw/ 环形缓冲上限 | **MB** | `200` / `200M` / `1G` / `512K`（K/M/G/T） | 200，≥10 |
| `M20AI_SAVED_MAX_MB` | saved/ 图片总量上限 | **MB** | 同上 | 500，0 = 不按体积清理 |
| `M20AI_SAVED_KEEP_DAYS` | saved/ 保留时长 | **天** | `7` / `7d` / `24h` / `30m` / `2w`（s/m/h/d/w） | 0 = 不按年龄清理 |
| `M20AI_RESULTS_KEEP_DAYS` | results/ 保留时长 | **天** | 同上 | 0 = 永不删 |
| journal 立即清理 size | vacuum 空间 | **MB** | 同上 | 无默认（必填其一） |
| journal 立即清理 time | vacuum 时长 | **天** | 同上 | 同上 |
| `SystemMaxUse` | journald 空间上限 | **MB** | 同上 | 留空 = 不限 |
| `MaxRetentionSec` | journald 保留时长 | **天** | 同上 | 留空 = 不限 |
| logrotate `rotate` | 轮转份数 | **份（整数）** | `7` —— **无单位后缀** | 7，1–365 |

单位不区分大小写（`7d` = `7D`，`1g` = `1G`）。

### 2. 解析在两层都做，systemd 参数在**调用前**归一化

- **采样器侧**（`config.py`）：新增 `parse_size_mb()` / `parse_days()`，
  四个 env 字段改用它 —— 即使有人手工把 `1G` 写进 env 文件，采样器也能正确解析。
  env 里**保留用户原始写法**（写 `1G` 就存 `1G`），可读性更好。
- **控制台侧**（`sysactions.py`）：`_norm_size()` / `_norm_time()` 在调 systemd **之前**归一化，
  关键是**把裸数字补成默认单位**：
  - `size` 裸数字 → `20M`（systemd 的 size 不接受裸数字）
  - `time` 裸数字 → `7d`（**systemd 裸数字是秒，必须重解释，否则 7 → 7 秒**）
- 归一化只作用于"即将交给 root helper / systemd 的那一份参数"，落 systemd 的值永远带单位，语义无歧义。

### 3. 非法输入必须给出可操作报错

错误消息统一包含三要素：**哪个字段** + **原始输入** + **合法写法示例**。

```
M20AI_RING_MAX_MB='1x' 的单位 'x' 无法识别。合法单位：k/m/g/t（或裸数字）；裸数字按 MB 解释
size 单位无法识别：'20X'（合法：K/M/G/T；裸数字按 MB）
rotate 必须是 1-365 的整数（份数，无单位；每份=一天的日志文件）
```

控制台保存配置时即拦截（`validate_env` → `Config.from_env` 抛错 → HTTP 400），坏值不落盘。

### 4. 启动行为：`up` = 控制台；采集由开关控制，默认关闭

**服务分工**：控制台（`m20-ai-console`，5050）是常驻入口；采样器（`m20-ai-detect`）是"采集"，默认不起。

| 命令 | 作用 |
|---|---|
| `aiDetect up` / `down` / `restart` | **只作用于控制台**（网页入口） |
| `aiDetect collect on` / `off` / `status` / `restart` | **采集开关**（采样器启停），默认 `off` |
| `aiDetect enable` / `disable` | **只作用于控制台**的开机自启；采集不设开机自启（保持默认关） |
| `aiDetect reset` | 清空积压帧（内部临时停/起采样器），语义不变 |
| ~~`--all`~~ | **移除**：不再有"一起操作"的选项 |

- 网页「采集开关」卡：`开启采集` / `停止采集` / `重启采集` 三个按钮 + 状态徽章（运行中 / 已关闭（默认）），
  顶部状态胶囊也改为显示采集状态（"采集运行中 / 采集已关闭"）。
- 停止采集**不影响历史数据**：时间轴、最近检测、文件浏览、日志照常可用（它们读的是磁盘数据）。
- 关掉采集后控制台仍需要能访问，因此**控制台仍是独立的可常驻服务**，由 `aiDetect up` 单独负责。

## 依据

- 用户原话："启动服务时只启动控制台，不自动启动采样器。采样器的开启与关闭应由控制台提供的命令或开关控制，
  默认状态为关闭，且状态可随时切换并展示……（就不需要加-all参数了）"
- 实际事故：用户 `aiDetect up` 后访问 5050 报 `ERR_CONNECTION_REFUSED` —— 采样器 active、控制台 inactive。
  实测确认 5050 无监听。
- 单测 **184 项全绿**（新增 `TestUnitsInConfig` 11 项、`TestJournalUnitNormalization` 10 项、
  `TestRetentionUnitRoundTrip` 3 项），覆盖：裸数字 = 默认单位、大小写、小数、K/G/T/w/h、
  负值拒绝、非法单位报错文案、`7 → 7d`（而非 7 秒）、控制台 POST 落盘后采样器仍能解析。

## 后果

### 正面

- 用户不必记忆"哪个框要带单位"：带不带都行，裸数字 = 该字段的自然单位。
- 消除 systemd 裸数字时长的静默事故（`7` 不再等于 7 秒）。
- 启动/采集职责分明：开网页不会意外开始采集，停采集也不影响查历史。

### 负面 / 代价

- **`aiDetect` 语义变更，破坏旧习惯**：从前 `aiDetect up` 是起采样器、`restart` 是重启采样器；
  现在这两个命令指向控制台，起/重启采样器要用 `collect on` / `collect restart`。
  已在使用说明、usage、`status` 输出里多处提示，并明确 `--all` 已被移除（传参会直接报错，不会静默忽略）。
- `reset` 仍会临时起采样器（其语义就是"清空后以实时为准"），与"默认关闭"不冲突但需知晓。

### 触发复审的条件

- 若将来需要"采集开机自启"（现场无人值守场景），需重新设计默认值与该开关的持久化方式；
- 若引入更多带单位的字段（如带宽、并发数），应复用 `parse_number_with_unit()` 而不是各写一套。
