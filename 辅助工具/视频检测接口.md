# 「AI 识别服务」接口能力与适用场景分析


## 一、这是什么服务

FastAPI（uvicorn）部署的**视觉能力中台**，Swagger UI 文档，OpenAPI 3.1，共 **122 个路径 / 123 个操作**（GET 61、POST 61、DELETE 1），**无任何认证机制**（规范中无 securitySchemes）。核心设计是「**一帧进、一帧出**」：把 33 项图像/视频识别能力各封装成独立 HTTP 接口，每次请求同时返回**结构化结果 + base64 结果图**。

## 二、四层接口架构

| 层 | 接口 | 数量 | 能力 | 典型场景 |
|---|---|---|---|---|
| ① 元数据/运维 | health、capabilities、samples、camera×4、streams×2 | 9 | 服务自检、能力发现、摄像头与推流运维 | 部署探活、监控告警、前端动态生成参数控件 |
| ② 能力推理 | `POST /api/v1/tasks/{capability_id}` | 33 | 上传图片/视频，返回结构化结果+结果图 | 单帧离线分析、接入业务系统 |
| ③ 实时推流 | `GET /api/v1/stream/{id}`、`/snapshot`、`POST /push` | 27×3 | MJPEG 边推理边推流；抓拍一帧；回传客户端帧 | 演示大屏、定时抓图、机器人相机接入 |
| ④ 会话管理 | `GET/DELETE /api/v1/streams` | 2 | 查看/停止推流会话，释放摄像头 | 多用户推流排障、异常会话回收 |

## 三、基础设施接口（9 个）逐个说明

| 接口 | 能力 | 适用场景 |
|---|---|---|
| `GET /api/v1/health` | 状态、版本、默认推理设备、可用 provider、已加载模型、就绪/缺失能力数 | 上线前自检、监控探活；`missing_models` 可判断权重是否补齐 |
| `GET /api/v1/capabilities` | 33 项能力的 id/参数/默认值/样例/是否支持推流 | 客户端动态发现能力；文档站前端的参数控件即由它生成 |
| `GET /api/v1/tasks/{id}/samples/{name}` | 取内置样例图/视频 | 无自有素材时快速试调、演示、回归测试 |
| `GET /api/v1/camera/sources` | 服务端配置的摄像头源列表 | 部署验收时确认采集源 |
| `GET /api/v1/camera/probe` | 探测某源当前能否读到画面（失败返回 503 + 原因） | 排查推流无画面问题 |
| `POST /api/v1/camera/reset` | 清除摄像头打开失败的冷却记录 | 占用摄像头的程序退出后立即重试，不等冷却 |
| `GET /api/v1/cameras` | 哪路摄像头被哪个采集线程持有、几路会话在用 | 多用户同时推流时的设备占用排查 |
| `GET /api/v1/streams` | 当前活跃推流会话 | 运维监控 |
| `DELETE /api/v1/streams` | 按 `capability_id`/`source` 过滤停止推流并释放摄像头 | 会话回收、异常清理 |

## 五、推流三件套的关键设计（选型时最容易踩坑的点）

| 形态 | 画面来源 | 接口 | 场景 |
|---|---|---|---|
| 服务端推流 | **服务端机器**的摄像头 `0`、`/dev/video0`、RTSP、HTTP 流、`ros://<话题>` | `GET /stream/{id}?source=&fps=3` | 大屏演示；**机器人 ROS 相机话题可直接接入**（对 Lite3 等 ROS 平台是现成通道） |
| 定时抓拍 | 同上，取一帧处理后返回 JPEG | `GET /stream/{id}/snapshot` | 定时抓图存档、低帧率巡检 |
| 客户端回传 | **访问者自己的**摄像头帧（canvas.toBlob 上传） | `POST /stream/{id}/push` | 浏览器端演示，不占用服务端设备，多人互不干扰 |

注意：27 个「一帧进一帧出」的能力才有推流；opencv-11/12 算法有状态、opencv-13~16 无逐帧输入，故无 stream/snapshot。同一路流只跑一个推理线程、多观看者共享，`fps` 默认 3 且推理跟不上时自动降速。

## 六、实测验证（2026-10-13 16:04 GMT+8）

- `GET /api/v1/health` → `status:ok`，33/33 能力就绪，11 个模型已加载，`default_device:cpu`，providers 仅 `AzureExecutionProvider`+`CPUExecutionProvider`（**该实例无 CUDA，请求 cuda 会如实回退 CPU**）。
- `POST /api/v1/tasks/ai-04-yolov8-object-detection`（内置样例 bus.jpg）→ HTTP 200，0.36s，服务端耗时 96ms；返回 `results.type=detection`，5 个框（bus 0.847、person 0.88/0.87/0.87…），`result_image` 为 base64 JPEG data URL（响应体约 216KB）。与文档契约完全一致。

## 七、局限与注意事项

1. **无鉴权**：规范中无任何安全方案，公网可直接调用——生产使用必须自行加网关/鉴权。
2. **结果图随 base64 返回**：单次响应体积大（本次 216KB），批量调用时建议评估是否需要关闭或改走对象存储。
3. **视频类任务为同步阻塞**（最多 600 帧、秒级），高并发需在客户端排队。
4. 摄像头源均在**服务端**，所有用户看到同一路画面；用访问者摄像头必须走 `/push`。
5. 摄像头打开失败有冷却期（避免 OpenCV 原生异常杀进程），释放占用后需调 `/camera/reset`。
6. 摄像头不可用返回 `503 camera_unavailable`，缺 PyTorch 返回 `500 missing_dependency`，均有机器可读错误码。
